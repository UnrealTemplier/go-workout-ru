# Timeouts обязательны: тайм-ауты шагов и глобальный тайм-аут Саги

## Условие

93. **Timeouts обязательны.**: Каждый шаг Saga должен иметь timeout. Overall Saga должна иметь timeout. Без timeouts Saga может висеть вечно.

### Исходная формулировка

**Timeouts обязательны.**: Каждый шаг Saga должен иметь timeout. Overall Saga должна иметь timeout. Без timeouts Saga может висеть вечно.

## Теория

В распределенных системах любая сетевая операция без явного тайм-аута рано или поздно зависнет из-за молчаливого обрыва TCP-соединения (Half-Open Socket), потери SYN/ACK пакетов или перегрузки удаленного ядра. Сага без тайм-аутов оставляет заблокированными складские остатки, кредитные лимиты и горутины оркестратора навсегда. Архитектура саги требует двухуровневого тайм-аут менеджмента:
1) Step Timeout (тайм-аут шага, например, 3–5 секунд на RPC-вызов) — предотвращает зависание отдельной сетевой операции;
2) Overall Saga Timeout (глобальный дедлайн саги, например, 60 секунд на весь сценарий) — гарантирует, что суммарное время выполнения с учетом всех ретраев не превысит бизнес-SLA. При истечении глобального тайм-аута сага принудительно переводится в откат.

## Решение по шагам

1. Создайте родительский контекст с глобальным дедлайном `context.WithTimeout(parent, 2*time.Second)`.
2. Для каждого шага порождайте дочерний контекст с локальным тайм-аутом `context.WithTimeout(sagaCtx, 500*time.Millisecond)`.
3. Обработайте ошибку `context.DeadlineExceeded` на уровне шага.
4. В случае глобального тайм-аута прервите пайплайн и запустите компенсации с отдельным свежим контекстом.
5. Продемонстрируйте работу механизма при зависании одного из сервисов.

## Код решения

**`saga_timeouts.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type StepExecutor func(ctx context.Context) error

func ExecuteWithStepTimeout(parentCtx context.Context, stepName string, stepTimeout time.Duration, fn StepExecutor) error {
	stepCtx, cancel := context.WithTimeout(parentCtx, stepTimeout)
	defer cancel()

	done := make(chan error, 1)
	go func() {
		done <- fn(stepCtx)
	}()

	select {
	case <-parentCtx.Done():
		return fmt.Errorf("global saga timeout exceeded during '%s': %w", stepName, parentCtx.Err())
	case <-stepCtx.Done():
		return fmt.Errorf("step '%s' timeout exceeded (%v): %w", stepName, stepTimeout, stepCtx.Err())
	case err := <-done:
		return err
	}
}

func main() {
	// Глобальный тайм-аут всей саги: 1.5 секунды
	globalCtx, globalCancel := context.WithTimeout(context.Background(), 1500*time.Millisecond)
	defer globalCancel()

	fmt.Println("[Saga] Initiating multi-step flow with strict timeouts...")

	// Шаг 1: Быстрый шаг (успех)
	err1 := ExecuteWithStepTimeout(globalCtx, "FastPayment", 500*time.Millisecond, func(ctx context.Context) error {
		time.Sleep(100 * time.Millisecond)
		fmt.Println(" -> FastPayment completed in 100ms")
		return nil
	})
	if err1 != nil {
		fmt.Printf("Step 1 failed: %v\n", err1)
		return
	}

	// Шаг 2: Зависший удаленный сервис (эмуляция 3 секунд ожидания при локальном лимите 600ms)
	err2 := ExecuteWithStepTimeout(globalCtx, "HangingWarehouse", 600*time.Millisecond, func(ctx context.Context) error {
		select {
		case <-time.After(3 * time.Second):
			return nil
		case <-ctx.Done():
			return ctx.Err()
		}
	})

	if err2 != nil {
		fmt.Printf("[Saga ABORTED] %v\n", err2)
		if errors.Is(err2, context.DeadlineExceeded) {
			fmt.Println("[Saga RECOVERY] Deadline exceeded: Triggering compensations with fresh detached context...")
			// Для отката используется отдельный контекст, не зависящий от globalCtx
			rollbackCtx, cancelRollback := context.WithTimeout(context.Background(), 2*time.Second)
			defer cancelRollback()
			fmt.Printf("[Saga ROLLBACK] Refund executed in %v\n", rollbackCtx.Err())
		}
	}
}
```

ℹ️ Многоуровневый тайм-аут менеджмент саги с корректным отсечением зависших шагов

 -> FastPayment completed in 100ms
[Saga ABORTED] step 'HangingWarehouse' timeout exceeded (600ms): context deadline exceeded

## Под капотом

Использование `context.WithTimeout` опирается на внутренний таймер `time.Timer` рантайма Go, связанный с каналом `Done()`. При наступлении дедлайна горутина таймера переводит контекст в состояние `canceled` и пробуждает селекты. При этом горутина шага должна проверять `ctx.Done()`, иначе она продолжит крутиться в фоне, вызывая утечку памяти (Goroutine Leak).

## Подводные камни

1. Передача протухшего контекста в компенсацию: если вызвать `Compensate(globalCtx)` после истечения глобального тайм-аута, вызов немедленно вернет `context deadline exceeded` без отправки сетевого запроса. Для компенсации обязателен `context.WithoutCancel(parent)` с новым таймаутом.
2. Слишком короткий Step Timeout: установка тайм-аута меньше p99 сетевого RTT приведет к ложным отказам.

## На собеседовании

Вопрос: Как правильно выбирать величину тайм-аута для каждого шага саги?
Ответ: Тайм-аут шага должен рассчитываться по формуле: `Timeout = p99_latency + (retries * backoff) + network_jitter`. Сумма тайм-аутов всех последовательных шагов должна быть строго меньше глобального SLA клиентского запроса, оставляя запас времени (Headroom 20–30%) на гарантированное выполнение компенсирующих транзакций.
