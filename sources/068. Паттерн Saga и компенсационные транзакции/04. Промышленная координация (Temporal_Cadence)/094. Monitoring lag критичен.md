# Monitoring lag критичен: мониторинг Outbox Lag, Inbox Lag и метрики согласованности

## Условие

94. **Monitoring lag критичен.**: Мониторьте outbox lag (unprocessed events), inbox lag (unprocessed messages), saga completion time. Lag = inconsistency.

### Исходная формулировка

**Monitoring lag критичен.**: Мониторьте outbox lag (unprocessed events), inbox lag (unprocessed messages), saga completion time. Lag = inconsistency.

## Теория

В архитектуре на базе Outbox/Inbox и Саги системная рассинхронизация (Inconsistency Window) прямо пропорциональна лагу очередей. Если Outbox Poller отстает от скорости записи на 5000 сообщений, это значит, что 5000 заказов уже созданы в БД сервиса Заказов, но Склад и Оплата еще даже не начали их обработку! Для надежного контроля над системой вводятся ключевые метрики Prometheus:
1) `outbox_unprocessed_records_gauge` — количество строк в `outbox_events` со статусом `processed = false`;
2) `inbox_consumer_lag_gauge` — разница между максимальным оффсетом Kafka и последним закоммиченным оффсетом консьюмера;
3) `saga_duration_seconds_histogram` — гистограмма времени от создания до завершения/отката саги;
4) `saga_compensation_rate` — доля саг, завершившихся откатом (превышение порога 2% сигнализирует о P1-инциденте).

## Решение по шагам

1. Создайте структуру экспортера метрик `SagaMetrics`.
2. Реализуйте сбор метрик Outbox Lag и Inbox Lag.
3. Смоделируйте увеличение нагрузки (Spike) и рост лага.
4. Реализуйте функцию проверки пороговых значений (Alert Evaluator).
5. Продемонстрируйте срабатывание алерта `HighOutboxLagAlert` в консоли.

## Код решения

**`saga_lag_monitoring.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type SagaMetricsCollector struct {
	mu              sync.Mutex
	outboxLag       int64
	inboxLag        int64
	totalSagas      int64
	compensatedSaga int64
}

func (m *SagaMetricsCollector) RecordOutboxQueueSize(size int64) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.outboxLag = size
}

func (m *SagaMetricsCollector) RecordInboxLag(lag int64) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.inboxLag = lag
}

func (m *SagaMetricsCollector) RecordSagaCompleted(wasCompensated bool) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.totalSagas++
	if wasCompensated {
		m.compensatedSaga++
	}
}

func (m *SagaMetricsCollector) EvaluateAlerts() {
	m.mu.Lock()
	defer m.mu.Unlock()

	fmt.Printf("\n--- Prometheus Metrics Scrape (%s) ---\n", time.Now().Format("15:04:05"))
	fmt.Printf("outbox_unprocessed_records: %d\n", m.outboxLag)
	fmt.Printf("inbox_consumer_lag: %d\n", m.inboxLag)

	compRate := 0.0
	if m.totalSagas > 0 {
		compRate = (float64(m.compensatedSaga) / float64(m.totalSagas)) * 100
	}
	fmt.Printf("saga_compensation_rate: %.2f%%\n", compRate)

	// Правила алертинга (Alerting Rules)
	if m.outboxLag > 1000 {
		fmt.Printf("[CRITICAL ALERT] HighOutboxLag: %d unprocessed messages! Debezium/Poller is failing!\n", m.outboxLag)
	}
	if compRate > 5.0 {
		fmt.Printf("[WARNING ALERT] HighCompensationRate: %.2f%% sagas failing and rolling back!\n", compRate)
	}
}

func main() {
	metrics := &SagaMetricsCollector{}

	// Нормальная работа системы
	metrics.RecordOutboxQueueSize(42)
	metrics.RecordInboxLag(15)
	for i := 0; i < 98; i++ {
		metrics.RecordSagaCompleted(false)
	}
	metrics.RecordSagaCompleted(true) // 1 откат из 99
	metrics.EvaluateAlerts()

	// Нагрузочный пик / Сбой коннектора (лаг растет)
	fmt.Println("\n>>> Outbox Poller crashed! Messages accumulating in DB... <<<")
	metrics.RecordOutboxQueueSize(2450)
	metrics.RecordInboxLag(120)
	for i := 0; i < 10; i++ {
		metrics.RecordSagaCompleted(true) // Пошли откаты
	}
	metrics.EvaluateAlerts()
}
```

## Под капотом

Для мониторинга Outbox в PostgreSQL выполняется быстрый периодический запрос:
`SELECT count(*) FROM outbox_events WHERE processed = false;`
Чтобы этот запрос не вызывал Seq Scan при миллионах строк, создается частичный индекс:
`CREATE INDEX idx_outbox_unprocessed ON outbox_events(created_at) WHERE processed = false;`
Благодаря частичному индексу размер индекса равен только числу необработанных строк (быстро и легко).

## Подводные камни

1. Запрос `SELECT COUNT(*)` без частичного индекса: на нагруженной БД такой подсчет лага каждые 15 секунд вызовет просадку IOPS и деградацию всей системы.
2. Оповещения только по среднему лагу (Mean): средний лаг может быть низким, в то время как отдельные 'ядовитые' саги зависают на часы. Необходим мониторинг возраста старейшего сообщения (`max(now() - created_at)`).

## На собеседовании

Вопрос: Что опаснее для HighLoad-платформы: растущий Outbox Lag или растущий Inbox Lag?
Ответ: Оба критичны, но растущий Outbox Lag опаснее: он означает, что доменные события вообще не выходят за пределы локальной БД микросервиса, и вся downstream-система 'слепа'. Растущий Inbox Lag указывает на то, что сообщения уже в брокере, но воркеры консьюмера не справляются с потоком (требуется горизонтальное автоскейлирование HPA по метрике KEDA).
