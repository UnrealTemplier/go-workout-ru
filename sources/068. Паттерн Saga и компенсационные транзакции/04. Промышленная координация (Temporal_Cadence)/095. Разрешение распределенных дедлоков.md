# Разрешение распределенных дедлоков: Sweeper зависших саг и таймаут-компенсация

## Условие

95. **Разрешение распределенных дедлоков**: В Хореографии Заказ А ждет денег от пользователя, а Заказ Б ждет освобождения склада. Напиши планировщик, который проходится по 'зависшим' (PENDING) сагам старше 10 минут, принудительно инициирует событие `TimeoutFailed` и запускает процесс компенсации.

### Исходная формулировка

**Разрешение распределенных дедлоков**: В Хореографии Заказ А ждет денег от пользователя, а Заказ Б ждет освобождения склада. Напиши планировщик, который проходится по "зависшим" (PENDING) сагам старше 10 минут, принудительно инициирует событие `TimeoutFailed` и запускает процесс компенсации.

## Теория

В распределенной событийно-ориентированной системе может возникнуть взаимная циклическая блокировка ресурсов (Distributed Deadlock): Заказ 1 заблокировал остатки товара и ждет оплаты, а Заказ 2 оплатил, но ждет освобождения того же товара. Без централизованного детектора дедлоков оба заказа останутся в состоянии `PENDING` навсегда. Паттерн Deadlock Sweeper (Watchdog / Garbage Collector саг) решает эту проблему: фоновый демон периодически сканирует хранилище саг, находит зависшие процессы с `status = 'PENDING' AND updated_at < NOW() - INTERVAL '10 minutes'`, переводит их в статус `TIMED_OUT` и публикует в шину событие `SagaTimeoutFailedEvent`, инициирующее каскадное освобождение ресурсов.

## Решение по шагам

1. Создайте структуру `StuckSaga` с временем последнего обновления.
2. Реализуйте хранилище с методом поиска зависших саг старше порогового интервала.
3. Реализуйте планировщик `SagaSweeperWorker`.
4. Для каждой найденной зависшей саги переведите статус в `TIMED_OUT` и отправьте событие компенсации.
5. Продемонстрируйте принудительное завершение зависшей саги в `main`.

## Код решения

**`deadlock_sweeper.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type SagaItem struct {
	ID        string
	Status    string
	UpdatedAt time.Time
}

type SweeperStore struct {
	mu    sync.Mutex
	sagas map[string]*SagaItem
}

func NewSweeperStore() *SweeperStore {
	return &SweeperStore{sagas: make(map[string]*SagaItem)}
}

func (s *SweeperStore) FindStuckSagas(threshold time.Duration) []*SagaItem {
	s.mu.Lock()
	defer s.mu.Unlock()

	cutoff := time.Now().Add(-threshold)
	var stuck []*SagaItem

	for _, saga := range s.sagas {
		if saga.Status == "PENDING" && saga.UpdatedAt.Before(cutoff) {
			stuck = append(stuck, saga)
		}
	}
	return stuck
}

func (s *SweeperStore) MarkTimedOut(sagaID string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if item, ok := s.sagas[sagaID]; ok {
		item.Status = "TIMED_OUT"
		item.UpdatedAt = time.Now()
	}
}

type DeadlockSweeper struct {
	store   *SweeperStore
	timeout time.Duration
}

func (d *DeadlockSweeper) RunSweepCycle(ctx context.Context) int {
	stuckList := d.store.FindStuckSagas(d.timeout)
	fmt.Printf("[Sweeper] Scanning for stuck sagas (> %v)... Found: %d\n", d.timeout, len(stuckList))

	for _, saga := range stuckList {
		fmt.Printf("[Sweeper RECOVERY] Saga %s is DEADLOCKED/STUCK (last updated %s). Forcing Timeout Compensation!\n",
			saga.ID, saga.UpdatedAt.Format("15:04:05"))

		// 1. Атомарно переводим статус в базе
		d.store.MarkTimedOut(saga.ID)

		// 2. Публикуем событие отката в шину
		fmt.Printf(" -> Published Event 'SagaTimeoutFailed' for %s. Releasing locked items and refunding.\n", saga.ID)
	}
	return len(stuckList)
}

func main() {
	store := NewSweeperStore()

	// Сага 1: активная свежая сага (создана 1 минуту назад)
	store.sagas["saga-fresh-1"] = &SagaItem{
		ID:        "saga-fresh-1",
		Status:    "PENDING",
		UpdatedAt: time.Now().Add(-1 * time.Minute),
	}

	// Сага 2: зависшая в дедлоке сага (создана 15 минут назад)
	store.sagas["saga-deadlock-2"] = &SagaItem{
		ID:        "saga-deadlock-2",
		Status:    "PENDING",
		UpdatedAt: time.Now().Add(-15 * time.Minute),
	}

	sweeper := &DeadlockSweeper{
		store:   store,
		timeout: 10 * time.Minute,
	}

	// Запуск цикла очистки
	sweeper.RunSweepCycle(context.Background())

	// Проверяем итоговый статус в базе
	store.mu.Lock()
	fmt.Printf("\nFinal State of saga-deadlock-2: %s\n", store.sagas["saga-deadlock-2"].Status)
	fmt.Printf("Final State of saga-fresh-1: %s\n", store.sagas["saga-fresh-1"].Status)
	store.mu.Unlock()
}
```

ℹ️ Планировщик Sweeper для выявления и отката зависших саг при распределенных дедлоках

## Под капотом

В PostgreSQL выборка зависших саг выполняется с пропуском заблокированных строк:
`SELECT id FROM sagas WHERE status = 'PENDING' AND updated_at < NOW() - INTERVAL '10 minutes' FOR UPDATE SKIP LOCKED LIMIT 100;`
Конструкция `SKIP LOCKED` позволяет горизонтально масштабировать Sweeper на несколько инстансов: воркеры не мешают друг другу и не ловят взаимоблокировки при выборке пачек.

## Подводные камни

1. Гонка между запоздалым ответом и Sweeper: если ответ от банка придет ровно в момент отката по тайм-ауту, может возникнуть несогласованность. Перевод статуса в `TIMED_OUT` обязан быть атомарным compare-and-swap (`UPDATE sagas SET status = 'TIMED_OUT' WHERE id = $1 AND status = 'PENDING'`).
2. Слишком агрессивный интервал: установка порога 30 секунд при средних внешних задержках 25 секунд приведет к ложным отменам вполне живых заказов.

## На собеседовании

Вопрос: Почему распределенный дедлок в микросервисах разрешают через тайм-ауты, а не через граф ожидания (Wait-For Graph)?
Ответ: Построение распределенного графа ожидания требует централизованного реестра всех распределенных блокировок в реальном времени, что крайне дорого и создает узкое горлышко масштабируемости. Тайм-ауты (Time-based Deadlock Detection) — это проверенный индустриальный стандарт распределенных систем, гарантирующий верхнюю границу удержания ресурсов без усложнения топологии.
