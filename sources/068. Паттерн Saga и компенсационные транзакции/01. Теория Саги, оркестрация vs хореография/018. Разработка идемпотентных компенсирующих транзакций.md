# Разработка идемпотентных компенсирующих транзакций (Idempotent Compensations)

## Условие

### Исходная формулировка

**Разработка идемпотентных компенсирующих транзакций**: Напишите компенсирующие транзакции для Саги (например, возврат денег `RefundPayment` или снятие брони товара `CancelInventoryReservation`).

## Теория

Компенсирующие транзакции **ОБЯЗАНЫ быть строго идемпотентными**:
Многократный повторный вызов компенсации \(C_i(x)\) с одним и тем же аргументом должен приводить к точно такому же состоянию системы, как и однократный вызов, не создавая побочных эффектов:
$$C_i(C_i(x)) = C_i(x)$$

Почему компенсация может вызываться повторно:
- Сетевой сбой при возврате ответа от компенсирующего метода.
- Рестарт оркестратора посреди процедуры отката.
- Таймаут брокера сообщений и повторная доставка сообщения об отмене.

Паттерн реализации идемпотентной компенсации в Go:
1. Проверка наличия записи в таблице `applied_compensations (saga_id, step_name)`.
2. Если запись уже есть — немедленный возврат успешного статуса (`nil`).
3. Если записи нет — атомарное применение компенсации и сохранение записи в одной транзакции СУБД.

## Решение по шагам

1. Спроектируйте структуру идемпотентного компенсатора с защитой от повторов.
2. Смоделируйте 3 последовательных вызова одного и того же метода `Refund`.
3. Убедитесь, что баланс уменьшается ровно один раз.
4. Проверьте потокобезопасность при параллельных вызовах компенсации.
5. Напишите тест подтверждения идемпотентности.

## Код решения

**`idempotent_compensation.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type PaymentAccount struct {
	Balance float64
}

type IdempotentRefundManager struct {
	mu                   sync.Mutex
	appliedCompensations map[string]bool
	account              *PaymentAccount
}

func NewIdempotentRefundManager(acc *PaymentAccount) *IdempotentRefundManager {
	return &IdempotentRefundManager{
		appliedCompensations: make(map[string]bool),
		account:              acc,
	}
}

// RefundIdempotent возвращает средства ровно 1 раз независимо от числа вызовов
func (m *IdempotentRefundManager) RefundIdempotent(sagaID string, amount float64) error {
	m.mu.Lock()
	defer m.mu.Unlock()

	// 1. Проверка: была ли компенсация уже выполнена ранее
	if m.appliedCompensations[sagaID] {
		fmt.Printf("[Refund] ДУБЛИРУЮЩИЙ ВЫЗОВ для %s: Компенсация уже применена ранее. Пропуск!\n", sagaID)
		return nil // Идемпотентный возврат успеха
	}

	// 2. Первичное применение возврата средств
	m.account.Balance += amount
	m.appliedCompensations[sagaID] = true
	fmt.Printf("[Refund] ПЕРВИЧНЫЙ ВОЗВРАТ для %s: +%.2f руб. Новый баланс: %.2f руб.\n",
		sagaID, amount, m.account.Balance)
	return nil
}

func main() {
	acc := &PaymentAccount{Balance: 1000.0}
	mgr := NewIdempotentRefundManager(acc)

	sagaID := "saga-order-xyz-777"
	refundAmount := 500.0

	// Эмуляция 3 повторных сетевых вызовов компенсации
	fmt.Println("--- Попытка 1 ---")
	_ = mgr.RefundIdempotent(sagaID, refundAmount)

	fmt.Println("\n--- Попытка 2 (Сетевой ретрай брокера) ---")
	_ = mgr.RefundIdempotent(sagaID, refundAmount)

	fmt.Println("\n--- Попытка 3 (Сетевой ретрай оркестратора) ---")
	_ = mgr.RefundIdempotent(sagaID, refundAmount)

	fmt.Printf("\nИтог: Финальный баланс счета: %.2f руб. (Ожидалось: 1500.00)\n", acc.Balance)
}
```

ℹ️ Идемпотентная компенсирующая транзакция возврата средств с реестром дедупликации

## Под капотом

В распределенной системе компенсация может прийти **РАНЬШЕ**, чем прямое действие! Это так называемый феномен **Out-of-Order Execution**: запрос на списание завис в сети, сработал таймаут, оркестратор послал `Cancel`, сервис применил отмену, а затем отвисший прямой запрос пытается списать деньги. Для защиты сервис обязан сохранять запись об отмене: если приходит прямое действие для уже отмененной саги, оно немедленно отклоняется.

## Подводные камни

1. **Неидемпотентный инкремент/декремент**: Операции `balance = balance + amount` без ключа идемпотентности при каждом сетевом сбое дублируют начисление денег.
2. **Возврат ошибки на дубликат**: Если на повторный вызов компенсации вернуть ошибку `409 Conflict` или `Already refunded`, оркестратор может посчитать компенсацию неудачной и продолжит слать ретраи.

## На собеседовании

В банковских системах (Тинькофф, Сбер) это ключевой вопрос квалификации: 'Что такое семантика At-Least-Once в связке с идемпотентностью?' Ответ: Брокер гарантирует доставку сообщения хотя бы один раз (возможны дубликаты). Чтобы бизнес-логика сохранила семантику Exactly-Once, каждый потребитель и компенсирующий метод обязан быть идемпотентным, отсекая дубликаты по `idempotency_key`.
