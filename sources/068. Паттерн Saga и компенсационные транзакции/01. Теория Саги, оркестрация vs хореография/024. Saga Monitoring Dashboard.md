### Исходная формулировка

**Saga monitoring dashboard**: Визуализируйте active Sagas: текущий шаг, время выполнения, failed steps.

## Теория

Для обеспечения надежности распределенных транзакций в реальном времени необходим мониторинг следующих ключевых метрик:
1. `sagas_active_count`: Gauge-счетчик саг, находящихся в процессе выполнения прямо сейчас (позволяет заметить зависание очередей).
2. `sagas_total`: Counter всех инициированных саг с лейблами `status="completed"`, `status="compensated"`, `status="failed"`.
3. `saga_step_duration_seconds`: Histogram задержки каждого отдельного шага саги.
4. `saga_compensation_rate`: Процент транзакций, потребовавших отката (индикатор здоровья внешних провайдеров).

Визуализация этих метрик в Grafana позволяет дежурным инженерам мгновенно локализовать проблему: например, если `saga_step_duration_seconds{step="payment"}` выросла с 200 мс до 15 секунд, значит начались проблемы на стороне платежного шлюза банка.

## Решение по шагам

1. Создайте структуры метрик Prometheus: Gauge, Counter, Histogram.
2. Интегрируйте сбор метрик в жизненный цикл оркестратора.
3. Рассчитайте метрику процента успешных саг (Saga Success Rate).
4. Продемонстрируйте сбор статистики выполнения 10 саг.
5. Выведите итоговую сводку телеметрии.

## Код решения

**`saga_metrics.go`**

```go
package main

import (
	"fmt"
	"sync/atomic"
	"time"
)

type SagaMetrics struct {
	ActiveSagas       atomic.Int64
	CompletedSagas    atomic.Uint64
	CompensatedSagas  atomic.Uint64
	FailedSagas       atomic.Uint64
	TotalExecutionMs  atomic.Uint64
}

func (m *SagaMetrics) OnSagaStart() {
	m.ActiveSagas.Add(1)
}

func (m *SagaMetrics) OnSagaComplete(duration time.Duration) {
	m.ActiveSagas.Add(-1)
	m.CompletedSagas.Add(1)
	m.TotalExecutionMs.Add(uint64(duration.Milliseconds()))
}

func (m *SagaMetrics) OnSagaCompensated(duration time.Duration) {
	m.ActiveSagas.Add(-1)
	m.CompensatedSagas.Add(1)
	m.TotalExecutionMs.Add(uint64(duration.Milliseconds()))
}

func (m *SagaMetrics) PrintDashboard() {
	completed := m.CompletedSagas.Load()
	compensated := m.CompensatedSagas.Load()
	totalFinished := completed + compensated

	successRate := 0.0
	if totalFinished > 0 {
		successRate = (float64(completed) / float64(totalFinished)) * 100.0
	}

	fmt.Println("\n================ SAGA GRAFANA DASHBOARD ================")
	fmt.Printf("Активных саг в обработке (Active Gauge): %d\n", m.ActiveSagas.Load())
	fmt.Printf("Успешно завершено (Completed):            %d\n", completed)
	fmt.Printf("Скомпенсировано / Откачено (Compensated): %d\n", compensated)
	fmt.Printf("Success Rate (Успешность):                 %.2f%%\n", successRate)
	fmt.Println("========================================================")
}

func main() {
	metrics := &SagaMetrics{}

	// Симуляция потока 10 саг
	for i := 1; i <= 10; i++ {
		metrics.OnSagaStart()
		if i == 4 || i == 7 {
			// Саги 4 и 7 завершились сбоем и компенсацией
			metrics.OnSagaCompensated(250 * time.Millisecond)
		} else {
			// Остальные успешны
			metrics.OnSagaComplete(150 * time.Millisecond)
		}
	}

	metrics.PrintDashboard()
}
```

ℹ️ Потокобезопасный коллектор метрик производительности и успешности Саги

## Под капотом

Использование пакета `sync/atomic` (`atomic.Int64`, `atomic.Uint64`) обеспечивает максимальную производительность счетчиков метрик без блокировок мьютексами. Внутренние процессорные инструкции `LOCK XADD` на архитектурах x86/ARM исполняются за единицы наносекунд, не создавая накладных расходов при сотнях тысяч RPS.

## Подводные камни

1. **Утечка счетчика Active Sagas**: Если при панике (panic) или необработанной ошибке забыть вызвать `ActiveSagas.Add(-1)`, счетчик активных саг будет бесконечно расти, вызывая ложные алерты мониторинга. Всегда используйте `defer`.
2. **Высокая кардинальность (High Cardinality)**: Добавление `order_id` в качестве Prometheus лейбла приведет к мгновенному исчерпанию оперативной памяти сервера Prometheus (OOM). Лейблы должны иметь низкую кардинальность (только `status`, `step_name`).

## На собеседовании

В SRE-командах Тинькофф и Авито метрики саг привязаны к SLA бизнеса. Вопрос: 'Какой SLO (Service Level Objective) обычно устанавливается для платежных саг?' Ответ: Доступность `Success Rate >= 99.9%` (не более 1 сбоя на 1,000 транзакций) и `P99 Latency <= 3.0s`. Превышение порога компенсаций `compensation_rate > 1%` в течение 5 минут автоматически триггерит инцидент уровня P1.
