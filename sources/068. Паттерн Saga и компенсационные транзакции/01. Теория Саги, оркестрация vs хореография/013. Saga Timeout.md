# Saga Timeout: общий тайм-аут распределенной транзакции и детектирование зависших шагов

### Исходная формулировка

**Saga timeout**: Установите overall timeout для всей Saga (например, 30 минут). Если Saga не completed за это время — force compensation.

## Теория

Одной из самых опасных проблем в распределенных транзакциях являются **зависшие саги (Hanging Sagas)**:
- Внешний платежный шлюз или складской сервис не отвечает и не возвращает ошибку (соединение зависло на уровне сетевого сокета без таймаута).
- Пользователь закрыл браузер.
- Товар остается заблокированным на складе часами, принося прямой финансовый убыток бизнесу.

Для решения этой проблемы сага конфигурируется двумя уровнями таймаутов:
1. **Step Timeout (Тайм-аут шага)**: Ограничение на отдельный RPC вызов (например, 5–10 секунд).
2. **Overall Saga Timeout (Глобальный тайм-аут саги)**: Максимальное время жизни всего бизнес-процесса (например, 15–30 минут).

Если время жизни саги превышено, фоновый сторожевой таймер (Watchdog / Timeout Monitor) принудительно переводит сагу в статус `COMPENSATING`, прерывает зависшие контексты и запускает откат всех ранее подтвержденных шагов.

## Решение по шагам

1. Создайте структуру саги с дедлайном выполнения (`time.Time`).
2. Реализуйте контекст с общим таймаутом `context.WithTimeout`.
3. Смоделируйте долгий зависший шаг.
4. Настройте перехват `context.DeadlineExceeded` и запуск компенсирующих транзакций.
5. Продемонстрируйте автоматическое освобождение заблокированных ресурсов.

## Код решения

**`saga_timeout.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type TimeoutSagaCoordinator struct {
	overallTimeout time.Duration
}

func NewTimeoutSagaCoordinator(timeout time.Duration) *TimeoutSagaCoordinator {
	return &TimeoutSagaCoordinator{overallTimeout: timeout}
}

func (c *TimeoutSagaCoordinator) ExecuteSaga(parentCtx context.Context, sagaID string) error {
	// Создаем контекст с жестким глобальным дедлайном
	ctx, cancel := context.WithTimeout(parentCtx, c.overallTimeout)
	defer cancel()

	fmt.Printf("[Saga %s] Запуск с глобальным таймаутом: %v\n", sagaID, c.overallTimeout)

	// Шаг 1: Быстрое резервирование склада (50 мс)
	if err := c.stepReserveStock(ctx); err != nil {
		return err
	}

	// Шаг 2: Зависший шаг оплаты (пытается работать 5 секунд)
	if err := c.stepHangingPayment(ctx); err != nil {
		if errors.Is(err, context.DeadlineExceeded) {
			fmt.Printf("\n[TIMEOUT DETECTED] Сага %s превысила лимит времени %v!\n", sagaID, c.overallTimeout)
			c.compensateStock(context.Background()) // Откат с независимым контекстом!
		}
		return err
	}

	return nil
}

func (c *TimeoutSagaCoordinator) stepReserveStock(ctx context.Context) error {
	fmt.Println("  -> [Шаг 1] Склад: 1 шт. товара зарезервирована")
	return nil
}

func (c *TimeoutSagaCoordinator) stepHangingPayment(ctx context.Context) error {
	fmt.Println("  -> [Шаг 2] Оплата: Запрос отправлен в сторонний банк (ожидание ответа)...")
	select {
	case <-time.After(3 * time.Second): // Имитация долгого ответа банка
		fmt.Println("  -> [Шаг 2] Оплата подтверждена")
		return nil
	case <-ctx.Done():
		return ctx.Err() // Превышен дедлайн!
	}
}

func (c *TimeoutSagaCoordinator) compensateStock(ctx context.Context) {
	fmt.Println("  [КОМПЕНСАЦИЯ] Автоматическое снятие брони со склада по таймауту саги!")
}

func main() {
	coordinator := NewTimeoutSagaCoordinator(300 * time.Millisecond)

	err := coordinator.ExecuteSaga(context.Background(), "saga-timed-out-007")
	if err != nil {
		fmt.Printf("Итог выполнения саги: %v\n", err)
	}
}
```

ℹ️ Управление глобальным дедлайном саги с автоматической компенсацией по таймауту

## Под капотом

Обратите внимание на вызов `c.compensateStock(context.Background())`. Если при компенсации передать исходный просроченный контекст `ctx`, в котором сработал `DeadlineExceeded`, любые сетевые вызовы внутри компенсации немедленно завершатся ошибкой `context deadline exceeded`! Компенсация ОБЯЗАНА выполняться с новым независимым контекстом (обычно `context.WithoutCancel(ctx)` в Go 1.21+ либо новым `context.WithTimeout(context.Background(), 10*time.Second)`).

## Подводные камни

1. **Передача протухшего контекста в компенсацию**: Классический баг Go-разработчиков. Контекст саги протух, разработчик передает его в `Compensate(ctx)`, и откат не выполняется, оставляя ресурсы заблокированными.
2. **Слишком короткий глобальный таймаут**: Установка 5 секунд на сагу из 6 шагов приведет к тому, что в часы пик из-за нормального роста задержек 50% заказов будут ошибочно отменяться по таймауту.

## На собеседовании

В системах бронирования авиабилетов (Аэрофлот, Aviasales) бронь кресла в самолете держится 15 минут. Вопрос: 'Как реализовать 15-минутный таймаут саги на кластере из 50 серверов так, чтобы перезапуск нод не сбросил таймер?' Ответ: Использовать распределенный планировщик задач на базе Redis Sorted Sets (`ZREMRANGEBYSCORE` по timestamp дедлайна) или Temporal / Cadence Workflows с durable timer (`workflow.Sleep(ctx, 15*time.Minute)`). При падении любой ноды таймер сохраняется в персистентной БД.
