# Happy Path в Хореографии: цепочка PaymentSucceeded -> InventoryReserve -> OrderConfirmed

## Условие

10. **[Счастливый путь (Happy Path)]**: Если Payment успешен, он публикует `PaymentSucceeded`. Inventory слушает его и резервирует товар. Если резерв успешен, он шлет `InventoryReserved`. Order слушает его и меняет статус заказа на `Confirmed`.

### Исходная формулировка

**[Счастливый путь (Happy Path)]**: Если Payment успешен, он публикует `PaymentSucceeded`. Inventory слушает его и резервирует товар. Если резерв успешен, он шлет `InventoryReserved`. Order слушает его и меняет статус заказа на `Confirmed`.

## Теория

При проектировании хореографии ключевым требованием является детерминированное продвижение по цепочке событий в штатном режиме (Happy Path):
1. `OrderService` сохраняет заказ `ORD-1` в статусе `PENDING` и публикует событие `OrderCreated`.
2. `PaymentService` потребляет `OrderCreated`, списывает средства, сохраняет транзакцию `TX-1` и публикует `PaymentSucceeded { order_id: "ORD-1" }`.
3. `InventoryService` потребляет `PaymentSucceeded`, уменьшает остаток на складе и публикует `InventoryReserved { order_id: "ORD-1" }`.
4. `OrderService` потребляет `InventoryReserved` и переводит заказ в финальный успешный статус `CONFIRMED`.

Каждый участник хореографии ничего не знает о глобальной архитектуре системы: он знает лишь входящее событие (Trigger) и исходящее событие (Result).

## Решение по шагам

1. Опишите строго типизированные события формата CloudEvents.
2. Реализуйте логику обработки событий в каждом сервисе.
3. Продемонстрируйте прохождение штатной цепочки от `OrderCreated` до `OrderConfirmed`.
4. Зафиксируйте временные метки событий для сквозного аудита.

## Код решения

**`happy_choreography.go`**

```go
package main

import (
	"fmt"
	"time"
)

type CloudEvent struct {
	ID        string    `json:"id"`
	Type      string    `json:"type"`
	Source    string    `json:"source"`
	Timestamp time.Time `json:"timestamp"`
	Data      map[string]any
}

func EmitEvent(eventType, source string, data map[string]any) CloudEvent {
	ev := CloudEvent{
		ID:        fmt.Sprintf("evt-%d", time.Now().UnixNano()),
		Type:      eventType,
		Source:    source,
		Timestamp: time.Now(),
		Data:      data,
	}
	fmt.Printf("[%s] %s опубликовал событие: %s (OrderID=%v)\n",
		ev.Timestamp.Format("15:04:05.000"), ev.Source, ev.Type, ev.Data["order_id"])
	return ev
}

func main() {
	fmt.Println("=== Запуск сквозного Happy Path сценария хореографии ===")

	// Шаг 1: Клиент нажал оформить заказ
	e1 := EmitEvent("order.created", "OrderService", map[string]any{
		"order_id": "ORD-7700",
		"amount":   4990.0,
		"sku":      "HEADPHONES-BT",
	})
	time.Sleep(50 * time.Millisecond)

	// Шаг 2: Платежный сервис списал оплату
	_ = e1
	e2 := EmitEvent("payment.succeeded", "PaymentService", map[string]any{
		"order_id": "ORD-7700",
		"tx_id":    "PAY-992384",
	})
	time.Sleep(50 * time.Millisecond)

	// Шаг 3: Склад зарезервировал товар
	_ = e2
	e3 := EmitEvent("inventory.reserved", "InventoryService", map[string]any{
		"order_id":   "ORD-7700",
		"warehouse": "WH-MOSCOW-SOUTH",
	})
	time.Sleep(50 * time.Millisecond)

	// Шаг 4: Сервис заказов перевел статус в CONFIRMED
	_ = e3
	fmt.Printf("[OrderService] Заказ ORD-7700 успешно подтвержден (CONFIRMED). Клиент уведомлен!\n")
}
```

ℹ️ Сквозная цепочка CloudEvents событий успешного оформления заказа

## Под капотом

Использование стандарта CloudEvents (спецификация CNCF) гарантирует единообразие метаданных событий: поля `id`, `source`, `type`, `time`, `datacontenttype`. Это позволяет использовать единые фильтры маршрутизации в Kafka Connect, Knative Eventing или AWS EventBridge без необходимости декодирования содержимого поля `data`.

## Подводные камни

1. **Нарушение порядка событий в брокере (Out-of-Order Delivery)**: В многопартиционной Kafka событие `InventoryReserved` может обогнать `PaymentSucceeded`, если они попали в разные партиции. Решение: Всегда использовать `order_id` в качестве Partition Key сообщений!
2. **Потеря событий при рестарте консьюмера**: Если автокоммит оффсетов Kafka включен до фактической записи в БД сервиса, сбой процесса приведет к бесследной потере заказа.

## На собеседовании

В Avito и Lamoda при нагрузке 50,000 rps события текут через сотни топиков Kafka. Вопрос: 'Как гарантировать строгий порядок событий заказа (OrderCreated -> PaymentSucceeded -> InventoryReserved)?' Ответ: Сообщения одного заказа обязаны отправляться в один и тот же Kafka Topic с ключом партиционирования `Key = order_id`. Kafka гарантирует строгий порядок сообщений (FIFO) внутри одной партиции.
