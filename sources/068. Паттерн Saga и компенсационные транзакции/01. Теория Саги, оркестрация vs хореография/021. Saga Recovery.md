# Saga Recovery: восстановление после аварийной перезагрузки оркестратора (OOM / Crash)

## Условие

21. **Saga recovery**: При crash orchestrator (например, OOM kill) восстанавливайте Saga из БД и продолжайте выполнение.

### Исходная формулировка

**Saga recovery**: При crash orchestrator (например, OOM kill) восстанавливайте Saga из БД и продолжайте выполнение.

## Теория

В облачной среде Kubernetes поды могут перезапускаться в любой момент (OOMKilled из-за нехватки памяти, Eviction при ребалансировке нод, плановый rolling update нового релиза).

Если оркестратор упал в момент, когда 5,000 саг находились в промежуточных состояниях, система обязана восстановиться автоматически без вмешательства инженеров.

Алгоритм работы фонового демона восстановления (Recovery Worker):
1. Оркестратор стартует и запускает периодический тикер проверки незавершенных саг (`recovery_interval = 10s`).
2. Запрос в БД: `SELECT * FROM sagas WHERE status IN ('STARTED', 'COMPENSATING') AND updated_at < NOW() - INTERVAL '1 minute'`.
3. Зависшие саги лочатся через `FOR UPDATE SKIP LOCKED` (чтобы несколько реплик оркестратора не хватали одну сагу).
4. Оркестратор анализирует последний подтвержденный шаг и возобновляет выполнение либо запускает откат.

## Решение по шагам

1. Создайте структуру саги с полем `LastHeartbeat time.Time`.
2. Реализуйте функцию поиска 'осиротевших' (orphaned) саг.
3. Напишите процедуру безопасного захвата саги в обработку.
4. Продемонстрируйте доведение прерванной саги до компенсации.
5. Проверьте защиту от повторного захвата другими инстансами.

## Код решения

**`saga_recovery.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type RecoverableSaga struct {
	ID        string
	Status    string
	Step      int
	UpdatedAt time.Time
	LockedBy  string
}

type DistributedSagaStore struct {
	mu    sync.Mutex
	sagas map[string]*RecoverableSaga
}

func NewDistributedSagaStore() *DistributedSagaStore {
	return &DistributedSagaStore{sagas: make(map[string]*RecoverableSaga)}
}

// FindAndLockOrphanedSagas имитирует SQL: SELECT ... FOR UPDATE SKIP LOCKED
func (s *DistributedSagaStore) FindAndLockOrphanedSagas(workerID string, timeout time.Duration) []*RecoverableSaga {
	s.mu.Lock()
	defer s.mu.Unlock()

	threshold := time.Now().Add(-timeout)
	var acquired []*RecoverableSaga

	for _, saga := range s.sagas {
		if (saga.Status == "IN_PROGRESS" || saga.Status == "COMPENSATING") &&
			saga.UpdatedAt.Before(threshold) &&
			saga.LockedBy == "" {
			// Захватываем лок на сагу
			saga.LockedBy = workerID
			saga.UpdatedAt = time.Now()
			acquired = append(acquired, saga)
		}
	}
	return acquired
}

func RunRecoveryWorker(store *DistributedSagaStore, workerID string) {
	fmt.Printf("[RecoveryWorker %s] Поиск зависших саг...\n", workerID)
	orphans := store.FindAndLockOrphanedSagas(workerID, 2*time.Second)

	for _, saga := range orphans {
		fmt.Printf("[RecoveryWorker %s] Захвачена брошенная сага: %s (Шаг: %d, Статус: %s)\n",
			workerID, saga.ID, saga.Step, saga.Status)

		// Возобновляем компенсацию
		fmt.Printf("[RecoveryWorker %s] Принудительный запуск отката саги %s...\n", workerID, saga.ID)
		saga.Status = "COMPENSATED"
		saga.LockedBy = ""
		saga.UpdatedAt = time.Now()
		fmt.Printf("[RecoveryWorker %s] Сага %s успешно скомпенсирована и закрыта!\n", workerID, saga.ID)
	}
}

func main() {
	store := NewDistributedSagaStore()

	// Симулируем сагу, которая зависла 5 секунд назад из-за падения ноды
	store.sagas["saga-abandoned-1"] = &RecoverableSaga{
		ID:        "saga-abandoned-1",
		Status:    "IN_PROGRESS",
		Step:      2,
		UpdatedAt: time.Now().Add(-5 * time.Second),
	}

	RunRecoveryWorker(store, "node-worker-alpha")
}
```

ℹ️ Фоновый воркер восстановления зависших саг с безопасным захватом блокировки

## Под капотом

Ключевая конструкция в SQL — `FOR UPDATE SKIP LOCKED`. Без флага `SKIP LOCKED` все реплики оркестратора будут вставать в очередь и ждать разблокировки первой строки. С флагом `SKIP LOCKED` каждая реплика мгновенно пропускает уже занятые строки и забирает свободные, распределяя восстановление тысяч саг между всеми подами кластера равномерно.

## Подводные камни

1. **Zombie Sagas**: Если упавший под на самом деле не умер, а просто попал в длинную GC-паузу (Stop-The-World на 10 секунд), после выхода из паузы он продолжит выполнять сагу одновременно с рекавери-воркером! Защита — Fencing Tokens (монотонные версии записей).
2. **Слишком частый запуск воркера**: Запрос `SELECT` каждые 100 мс создаст избыточную нагрузку на мастер-базу данных.

## На собеседовании

На системном дизайне в Яндекс или Booking.com: 'Как избежать конфликта двух оркестраторов, восстанавливающих одну и ту же сагу?' Ответ: Использовать механизм оптимистической блокировки версий (Optimistic Locking) или распределенные аренды (Leases) в etcd/Redis с TTL: воркер обязан продлевать аренду Heartbeat-запросами каждые 5 секунд; если воркер завис, аренда истекает и сагу перехватывает другой узел.
