# Реализация методов компенсации: CancelOrder, ReleaseInventory и RefundPayment

## Условие

11. **Compensation implementation**: Реализуйте компенсационные методы в каждом сервисе: `ReserveInventory` ↔ `ReleaseInventory`, `ProcessPayment` ↔ `RefundPayment`.

### Исходная формулировка

**Compensation implementation**: Реализуйте компенсационные методы в каждом сервисе: `ReserveInventory` ↔ `ReleaseInventory`, `ProcessPayment` ↔ `RefundPayment`.

## Теория

Каждый микросервис, участвующий в распределенной Саге, обязан реализовать пару зеркальных методов:
1. **OrderService**:
   - Прямой: `CreateOrder(order_id, details)`
   - Компенсация: `CancelOrder(order_id, reason)` — перевод заказа в статус `CANCELLED`.
2. **InventoryService**:
   - Прямой: `ReserveInventory(order_id, items)` — уменьшение свободного остатка (`stock = stock - qty`, `reserved = reserved + qty`).
   - Компенсация: `ReleaseInventory(order_id)` — освобождение брони (`reserved = reserved - qty`, `stock = stock + qty`).
3. **PaymentService**:
   - Прямой: `ProcessPayment(order_id, amount)` — списание денег или холдирование.
   - Компенсация: `RefundPayment(order_id)` — возврат денег на счет пользователя или аннулирование холда (`AUTH_REVERSAL`).

Все компенсирующие методы обязаны обладать двумя фундаментальными свойствами: **Идемпотентность** и **Безусловная завершаемость (Must Not Fail)**.

## Решение по шагам

1. Опишите контракты микросервисов Order, Inventory и Payment.
2. Реализуйте прямое и компенсирующее действие для каждого сервиса.
3. Проверьте инвариант: сумма доступного и зарезервированного остатка склада не меняется.
4. Протестируйте компенсацию склада и платежа при отмене заказа.

## Код решения

**`compensation_methods.go`**

```go
package main

import (
	"fmt"
	"sync"
)

// 1. Складской сервис
type InventoryStock struct {
	Available int
	Reserved  int
}

type InventoryService struct {
	mu    sync.Mutex
	items map[string]*InventoryStock
}

func NewInventoryService() *InventoryService {
	s := &InventoryService{items: make(map[string]*InventoryStock)}
	s.items["IPHONE-16"] = &InventoryStock{Available: 10, Reserved: 0}
	return s
}

func (s *InventoryService) Reserve(sku string, qty int) error {
	s.mu.Lock()
	defer s.mu.Unlock()
	stock := s.items[sku]
	if stock.Available < qty {
		return fmt.Errorf("недостаточно товара %s на складе", sku)
	}
	stock.Available -= qty
	stock.Reserved += qty
	fmt.Printf("[Inventory] Зарезервировано %d шт. %s (Доступно: %d, В брони: %d)\n",
		qty, sku, stock.Available, stock.Reserved)
	return nil
}

func (s *InventoryService) Release(sku string, qty int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	stock := s.items[sku]
	stock.Reserved -= qty
	stock.Available += qty
	fmt.Printf("[Inventory] КОМПЕНСАЦИЯ: Снята бронь %d шт. %s (Доступно: %d, В брони: %d)\n",
		qty, sku, stock.Available, stock.Reserved)
}

// 2. Платежный сервис
type PaymentService struct {
	mu       sync.Mutex
	balances map[string]float64
}

func NewPaymentService() *PaymentService {
	p := &PaymentService{balances: make(map[string]float64)}
	p.balances["client_42"] = 10000.0
	return p
}

func (p *PaymentService) Charge(clientID string, amount float64) error {
	p.mu.Lock()
	defer p.mu.Unlock()
	if p.balances[clientID] < amount {
		return fmt.Errorf("недостаточно средств на счете клиента %s", clientID)
	}
	p.balances[clientID] -= amount
	fmt.Printf("[Payment] Списано %.2f руб. Баланс: %.2f\n", amount, p.balances[clientID])
	return nil
}

func (p *PaymentService) Refund(clientID string, amount float64) {
	p.mu.Lock()
	defer p.mu.Unlock()
	p.balances[clientID] += amount
	fmt.Printf("[Payment] КОМПЕНСАЦИЯ: Возврат %.2f руб. Баланс: %.2f\n", amount, p.balances[clientID])
}

func main() {
	inv := NewInventoryService()
	pay := NewPaymentService()

	// Шаг 1: Склад зарезервирован
	_ = inv.Reserve("IPHONE-16", 2)

	// Шаг 2: Оплата списана
	_ = pay.Charge("client_42", 5000.0)

	// Шаг 3: Логистический сервис дал сбой! Начинаем компенсации:
	fmt.Println("\n--- Сбой на шаге логистики! Запуск отката ---")
	pay.Refund("client_42", 5000.0)
	inv.Release("IPHONE-16", 2)

	fmt.Println("\nВсе компенсации выполнены. Балансы и остатки восстановлены 1 в 1.")
}
```

ℹ️ Реализация парных прямых и компенсирующих методов с сохранением балансовых инвариантов

## Под капотом

Компенсирующие методы должны быть спроектированы так, чтобы никогда не завершаться постоянной ошибкой. Если метод `ReleaseInventory` вернет ошибку 'Бронь не найдена', система окажется в рассогласованном состоянии. По этой причине компенсация проектируется идемпотентно: если бронь уже снята, метод возвращает `nil` (успех), а не ошибку.

## Подводные камни

1. **Отрицательные остатки при повторной компенсации**: Если дважды вызвать `ReleaseInventory` без проверки существования активной брони, остаток склада искусственно увеличится на +2 единицы из ниоткуда.
2. **Возврат денег до проверки списания**: Если платежный шлюз вернул ошибку, а оркестратор по ошибке дернул `Refund`, клиент получит деньги из резервного фонда компании.

## На собеседовании

В логистике Wildberries и Яндекс Маркета товар резервируется миллионами единиц. Вопрос на интервью: 'Что делать, если при вызове ReleaseInventory база склада зависла и не отвечает 10 минут?' Ответ: Оркестратор фиксирует статус компенсации `RELEASE_INVENTORY_PENDING` и отправляет задачу в фоновый воркер повторов с экспоненциальным backoff. Компенсация будет повторяться до тех пор, пока база не ответит подтверждением.
