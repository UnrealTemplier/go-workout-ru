# Триггер компенсации (Compensation Trigger): каскадный откат при сбое ProcessPayment

## Условие

9. **Compensation trigger**: Если `ProcessPayment` fails, запускайте компенсации в обратном порядке: `ReleaseInventory` → `CancelOrder`.

### Исходная формулировка

**Compensation trigger**: Если `ProcessPayment` fails, запускайте компенсации в обратном порядке: `ReleaseInventory` → `CancelOrder`.

## Теория

Когда распределенный процесс состоит из нескольких шагов (например, 1. Склад -> 2. Бонусы -> 3. Платеж), падение шага 3 (`ProcessPayment`) требует скоординированного каскадного отката всех предшествующих шагов.

Архитектура триггера компенсации:
1. **Detection (Обнаружение)**: Платежный сервис возвращает ошибку, признанную фатальной.
2. **State Freeze (Заморозка состояния)**: Оркестратор переводит сагу в статус `COMPENSATING`, блокируя любые попытки продвижения вперед.
3. **Rollback Dispatcher**: Оркестратор читает журнал саги, находит все шаги со статусом `SUCCESS` и вызывает их компенсирующие методы в порядке, обратном исполнению.
4. **Completion**: После того как ВСЕ компенсации подтверждены успехом, сага переходит в статус `FAILED`.

## Решение по шагам

1. Создайте структуру журнала выполнения шагов саги.
2. Реализуйте функцию `TriggerCompensation(sagaID)`.
3. Добавьте вызов компенсаций шагов бонусов и склада.
4. Обеспечьте логирование прогресса компенсации.
5. Протестируйте сценарий полного каскадного отката.

## Код решения

**`compensation_trigger.go`**

```go
package main

import (
	"fmt"
	"time"
)

type StepLog struct {
	StepName     string
	CompensateFn func() error
	Executed     bool
}

type SagaExecution struct {
	ID        string
	History   []StepLog
	IsAborted bool
}

func (s *SagaExecution) AddStep(name string, compFn func() error) {
	s.History = append(s.History, StepLog{
		StepName:     name,
		CompensateFn: compFn,
		Executed:     false,
	})
}

func (s *SagaExecution) MarkExecuted(stepName string) {
	for i := range s.History {
		if s.History[i].StepName == stepName {
			s.History[i].Executed = true
			return
		}
	}
}

// TriggerCompensation выполняет каскадный откат выполненных шагов
func (s *SagaExecution) TriggerCompensation(failureReason string) {
	s.IsAborted = true
	fmt.Printf("\n[TRIGGER] Сага %s прервана: %s. Старт каскадного отката!\n", s.ID, failureReason)

	// Идем с конца истории к началу (обратный порядок)
	for i := len(s.History) - 1; i >= 0; i-- {
		step := s.History[i]
		if step.Executed && step.CompensateFn != nil {
			fmt.Printf("  -> Компенсация шага [%s]...\n", step.StepName)
			err := step.CompensateFn()
			if err != nil {
				fmt.Printf("  [!] Ошибка отката шага %s: %v\n", step.StepName, err)
			} else {
				fmt.Printf("  [OK] Шаг [%s] успешно скомпенсирован\n", step.StepName)
			}
		}
	}
	fmt.Printf("[FINISH] Каскадная компенсация саги %s полностью завершена.\n", s.ID)
}

func main() {
	saga := &SagaExecution{ID: "saga-order-888"}

	// Регистрация шагов с их компенсационными процедурами
	saga.AddStep("1. ReserveInventory", func() error {
		fmt.Println("     [Склад] Товар возвращен на баланс доступных остатков"); return nil
	})
	saga.AddStep("2. DeductLoyaltyPoints", func() error {
		fmt.Println("     [Бонусы] 500 баллов лояльности возвращены на счет клиента"); return nil
	})
	saga.AddStep("3. ProcessPayment", func() error {
		fmt.Println("     [Платеж] Компенсация не требуется (списание не произошло)"); return nil
	})

	// Симуляция выполнения шагов
	fmt.Println("1. Выполнение ReserveInventory: Успех")
	saga.MarkExecuted("1. ReserveInventory")

	fmt.Println("2. Выполнение DeductLoyaltyPoints: Успех")
	saga.MarkExecuted("2. DeductLoyaltyPoints")

	fmt.Println("3. Выполнение ProcessPayment: СБОЙ (Отказ платежного шлюза)")
	// Шаг 3 НЕ помечается как Executed!

	// Запуск триггера компенсации
	saga.TriggerCompensation("Card declined: Insufficient funds")
}
```

## Под капотом

Если шаг \(K\) упал сам, его локальная транзакция в базе данных уже откатилась оператором `ROLLBACK` внутри самого сервиса. Поэтому компенсировать нужно только шаги от \(K-1\) до 1. Если ошибочно вызвать компенсацию для упавшего шага \(K\), сервис может вернуть ошибку `Transaction not found` либо, что еще хуже, по ошибке зачислить деньги, которые никогда не списывались.

## Подводные камни

1. **Компенсация несработавших шагов**: Вызов `RefundPayment` для транзакции, которая завершилась ошибкой авторизации, может привести к хищению средств компании.
2. **Несохранение причины сбоя**: Если не зафиксировать первопричину сбоя в общем журнале саги, техподдержка не сможет объяснить клиенту, почему его заказ был отменен.

## На собеседовании

В FinTech (Тинькофф, Ozon Банк) при каскадном откате критична прозрачность баланса. Вопрос: 'Пользователь списал 1000 бонусов и пытался доплатить 2000 руб картой. Карта отклонена. Что увидит пользователь в приложении в момент компенсации?' Ответ: В течение 1-2 секунд баланс бонусов может временно отображаться уменьшенным (Eventual Consistency). После завершения каскадного отката бонусы возвращаются, а в истории операций появляется запись 'Отмена списания бонусов к заказу №...'. В UI важно выводить статус 'Идет отмена заказа...'.
