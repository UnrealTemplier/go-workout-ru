# Обработка нехватки товара: Inventory отказ и откат созданного заказа

## Условие

17. **[Компенсационная транзакция]**: Сымитируй нехватку товара: Inventory не может зарезервировать товар и шлет `InventoryFailed`. Сервис Order должен слушать это событие и поменять статус заказа на `Cancelled`.

### Исходная формулировка

**[Компенсационная транзакция]**: Сымитируй нехватку товара: Inventory не может зарезервировать товар и шлет `InventoryFailed`. Сервис Order должен слушать это событие и поменять статус заказа на `Cancelled`.

## Теория

Сценарий нехватки товара на складе (Out-of-Stock) — наиболее частый бизнес-сбой в реальном ритейле:
1. Пользователь оформил заказ в мобильном приложении.
2. `OrderService` создал заказ со статусом `AWAITING_INVENTORY`.
3. `InventoryService` выполняет проверку физических остатков в БД склада (`SELECT stock FROM warehouse WHERE sku = $1 FOR UPDATE`).
4. Если `stock < requested_qty`:
   - Локальная транзакция склада отклоняет резервирование.
   - `InventoryService` возвращает ошибку `ErrOutOfStock`.
5. Инициируется компенсирующая транзакция `OrderService.CancelOrder()`:
   - Статус заказа переводится в `OUT_OF_STOCK_CANCELLED`.
   - Пользователю отправляется push-уведомление с предложением аналогов товара.

## Решение по шагам

1. Создайте модель склада с проверкой остатков.
2. Смоделируйте заказ товара в количестве, превышающем доступный остаток.
3. Реализуйте перехват ошибки нехватки товара.
4. Вызовите отмену заказа в сервисе Order.
5. Проверьте сохранность бизнес-метрик отказов.

## Код решения

**`out_of_stock_saga.go`**

```go
package main

import (
	"errors"
	"fmt"
)

var ErrOutOfStock = errors.New("out of stock: недостаточно остатков на складе")

type Warehouse struct {
	Stock map[string]int
}

func (w *Warehouse) TryReserve(sku string, qty int) error {
	available := w.Stock[sku]
	if available < qty {
		return fmt.Errorf("%w (запрошено: %d, доступно: %d)", ErrOutOfStock, qty, available)
	}
	w.Stock[sku] -= qty
	return nil
}

type OrderMgr struct {
	Orders map[string]string
}

func (m *OrderMgr) Create(orderID string) {
	m.Orders[orderID] = "PENDING"
	fmt.Printf("[OrderMgr] Создан заказ %s в статусе PENDING\n", orderID)
}

func (m *OrderMgr) MarkCancelled(orderID string, reason string) {
	m.Orders[orderID] = "CANCELLED: " + reason
	fmt.Printf("[OrderMgr] КОМПЕНСАЦИЯ: Заказ %s отменен! Статус: %s\n", orderID, m.Orders[orderID])
}

func main() {
	wh := &Warehouse{Stock: map[string]int{"PLAYSTATION-5": 2}}
	orders := &OrderMgr{Orders: make(map[string]string)}

	orderID := "ORD-PS5-900"
	requestedQty := 5 // Запрос 5 штук при наличии только 2!

	// Шаг 1: Создание заказа
	orders.Create(orderID)

	// Шаг 2: Попытка резерва склада
	err := wh.TryReserve("PLAYSTATION-5", requestedQty)
	if err != nil {
		fmt.Printf("[Inventory Alert] Сбой резерва склада: %v\n", err)
		// Запуск компенсации заказа
		orders.MarkCancelled(orderID, "Товар закончился на складе")
	}

	fmt.Printf("\nИтог: Состояние заказа в БД: '%s'\n", orders.Orders[orderID])
	fmt.Printf("Остаток на складе не поврежден: %d шт.\n", wh.Stock["PLAYSTATION-5"])
}
```

## Под капотом

В реляционных СУБД списание остатков склада требует строгого использования пессимистической блокировки `SELECT stock FROM inventory WHERE sku = $1 FOR UPDATE`. Без блокировки строки два параллельных заказа могут одновременно прочитать `stock = 1`, оба сочтут товар доступным и продадут 2 единицы товара при наличии 1 (Overselling / Овербукинг).

## Подводные камни

1. **Отрицательные остатки**: Если в БД нет ограничения `CHECK (stock >= 0)`, гонка данных может увести остаток в минус (`stock = -3`).
2. **Списание денег ДО проверки склада**: Если сначала списать деньги с карты, а потом обнаружить нехватку товара, бизнес несет расходы на банковскую комиссию за эквайринг и возврат.

Ответ: Перенести проверку и декремент остатков в Redis с использованием атомарных LUA-скриптов или Redis-команды `DECRBY`. Если результат `< 0`, немедленно делать `INCRBY` и возвращать отказ без похода в медленный PostgreSQL.
