# Saga Orchestration: центральный координатор и компенсация в обратном порядке

## Условие

2. **Saga Orchestration: центральный координатор.**: Реализуйте Saga-оркестратор, который выполняет последовательность шагов (сервисы A, B, C). Каждый шаг — вызов внешнего сервиса (заглушка). При успехе всех шагов транзакция завершается, при ошибке любого шага запускаются компенсационные транзакции в обратном порядке.

### Исходная формулировка

**Saga Orchestration: центральный координатор.**: Реализуйте Saga-оркестратор, который выполняет последовательность шагов (сервисы A, B, C). Каждый шаг — вызов внешнего сервиса (заглушка). При успехе всех шагов транзакция завершается, при ошибке любого шага запускаются компенсационные транзакции в обратном порядке.

## Теория

Оркестратор Саги управляет жизненным циклом распределенного бизнес-процесса по принципу **'Do-Compensate'**:
- Каждый шаг \(i\) представляет собой пару операций: прямое действие \(T_i\) (Transaction) и компенсирующее действие \(C_i\) (Compensating Transaction).
- Сага выполняет прямые действия последовательно: \(T_1 \rightarrow T_2 \rightarrow \dots \rightarrow T_n\).
- Если шаг \(T_k\) завершился фатальной ошибкой (например, `Payment` отклонен банком на шаге 3), оркестратор останавливает дальнейшее движение вперед и запускает компенсации в **строго обратном порядке**: \(C_{k-1} \rightarrow C_{k-2} \rightarrow \dots \rightarrow C_1\).
- Для шага, на котором произошел сбой (\(T_k\)), компенсация обычно не вызывается (так как локальная транзакция на нем откатилась сама в момент ошибки).

Свойство семантической компенсации: компенсация \(C_i\) не восстанавливает байтовое состояние БД 'как было', а совершает компенсирующее бизнес-действие (например, возврат денег на баланс или снятие брони с товара).

## Решение по шагам

1. Опишите интерфейс шага саги `SagaStep` с методами `Execute(ctx)` и `Compensate(ctx)`.
2. Реализуйте движок оркестратора, выполняющий шаги по очереди.
3. Сохраняйте список успешно выполненных шагов в стек.
4. При сбое на любом этапе извлекайте выполненные шаги из стека и вызывайте `Compensate` в обратном порядке (LIFO).
5. Протестируйте сценарий сбоя на третьем сервисе.

## Код решения

**`orchestrator.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

// SagaStep определяет контракт шага саги с прямым и компенсирующим действием
type SagaStep interface {
	Name() string
	Execute(ctx context.Context) error
	Compensate(ctx context.Context) error
}

type Orchestrator struct {
	steps []SagaStep
}

func NewOrchestrator(steps ...SagaStep) *Orchestrator {
	return &Orchestrator{steps: steps}
}

// Run выполняет сагу. При ошибке запускает компенсации в обратном порядке.
func (o *Orchestrator) Run(ctx context.Context) error {
	var executedSteps []SagaStep

	for _, step := range o.steps {
		fmt.Printf("[->] Выполнение прямого шага: %s\n", step.Name())
		if err := step.Execute(ctx); err != nil {
			fmt.Printf("[!] Сбой на шаге %s: %v. Запуск отката!\n", step.Name(), err)
			o.rollback(ctx, executedSteps)
			return fmt.Errorf("сага завершилась сбоем на шаге %s: %w", step.Name(), err)
		}
		executedSteps = append(executedSteps, step)
	}

	fmt.Println("[✓] Все шаги саги успешно выполнены!")
	return nil
}

func (o *Orchestrator) rollback(ctx context.Context, executedSteps []SagaStep) {
	// Разворот в обратном порядке (LIFO)
	for i := len(executedSteps) - 1; i >= 0; i-- {
		step := executedSteps[i]
		fmt.Printf("[<-] Компенсация шага: %s\n", step.Name())
		if err := step.Compensate(ctx); err != nil {
			// В продакшене: алерт в PagerDuty, запись в dead-letter queue
			fmt.Printf("[CRITICAL] Ошибка компенсации шага %s: %v\n", step.Name(), err)
		}
	}
}

// Заглушки шагов
type OrderStep struct{}
func (s *OrderStep) Name() string { return "CreateOrder" }
func (s *OrderStep) Execute(ctx context.Context) error { fmt.Println("  Order: Заказ создан в статусе PENDING"); return nil }
func (s *OrderStep) Compensate(ctx context.Context) error { fmt.Println("  Order: Заказ помечен как CANCELLED"); return nil }

type InventoryStep struct{}
func (s *InventoryStep) Name() string { return "ReserveInventory" }
func (s *InventoryStep) Execute(ctx context.Context) error { fmt.Println("  Inventory: Товар зарезервирован на складе"); return nil }
func (s *InventoryStep) Compensate(ctx context.Context) error { fmt.Println("  Inventory: Бронь товара снята"); return nil }

type PaymentStep struct{}
func (s *PaymentStep) Name() string { return "ProcessPayment" }
func (s *PaymentStep) Execute(ctx context.Context) error { return errors.New("недостаточно средств на банковской карте") }
func (s *PaymentStep) Compensate(ctx context.Context) error { fmt.Println("  Payment: Возврат средств (не требуется)"); return nil }

func main() {
	orchestrator := NewOrchestrator(
		&OrderStep{},
		&InventoryStep{},
		&PaymentStep{},
	)

	err := orchestrator.Run(context.Background())
	if err != nil {
		fmt.Printf("Итог работы оркестратора: %v\n", err)
	}
}
```

## Под капотом

Стек выполненных шагов моделирует LIFO-структуру. Почему компенсации обязаны запускаться в строго обратном порядке? Потому что каждый последующий шаг опирается на предусловия предыдущего. Например, нельзя отменить бронь склада до отмены списания средств, иначе покупатель может получить товар бесплатно при частичном сбое. Строгий обратный порядок гарантирует сохранение бизнес-инвариантов.

## Подводные камни

1. **Падение оркестратора во время компенсации**: Если процесс умер посреди вызова `rollback`, часть шагов останется скомпенсированной, а часть — нет. Для защиты статус каждого компенсирующего шага должен персистентно фиксироваться в БД до и после вызова.
2. **Нереверсивные шаги (Pivot Step)**: Шаг, после которого откат физически невозможен (например, отправка посылки курьером или SMS-уведомление пользователю). Он обязан быть последним шагом саги!

## На собеседовании

На системном интервью в Avito или Tinkoff соискателя спрашивают: 'Что делать, если сама компенсационная транзакция возвращает ошибку (например, сеть упала при попытке вернуть деньги)?' Ответ: Компенсация обязана быть **идемпотентной** и выполняться с бесконечными повторами (Exponential Backoff Retries). Если ошибка неустранима (4xx логическая ошибка), инцидент эскалируется в Dead-Letter Queue (DLQ) для ручного разбора инженерами поддержки (Manual Intervention).
