## Теория

В распределенной микросервисной архитектуре классические ACID-транзакции не масштабируются: протокол двухфазного коммита (2PC — Two-Phase Commit) блокирует ресурсы всех затронутых баз данных на время координации, создавая критическую точку отказа и снижая доступность системы (теорема CAP/PACELC).

Паттерн **Saga (Сага)**, впервые предложенный Гектором Гарсия-Молиной в 1987 году, заменяет одну распределенную транзакцию цепочкой локальных транзакций:
1. Каждый шаг саги обновляет данные в собственной изолированной БД микросервиса.
2. Первый шаг инициируется внешним запросом (например, создание заказа).
3. При успешном завершении каждого шага запускается следующий.
4. Если какой-либо шаг завершается ошибкой, запускается последовательность **компенсирующих транзакций (Compensating Transactions)** в строго обратном порядке, возвращающая систему в семантически согласованное состояние (Eventual Consistency).

**Оркестрируемая Сага (Orchestrated Saga)** использует центральный компонент — **Оркестратор (Saga Orchestrator)**. Он реализует Конечный Автомат (Finite State Machine, FSM), сохраняет текущее состояние в персистентный журнал (Saga Log), отправляет команды сервисам-исполнителям и принимает решения о переходе к следующему шагу или запуске компенсации.

## Код решения

**`saga_fsm.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type SagaState string

const (
	StateStarted           SagaState = "STARTED"
	StateOrderCreated      SagaState = "ORDER_CREATED"
	StateInventoryReserved SagaState = "INVENTORY_RESERVED"
	StatePaymentProcessed  SagaState = "PAYMENT_PROCESSED"
	StateCompensating      SagaState = "COMPENSATING"
	StateCompleted          SagaState = "COMPLETED"
	StateFailed            SagaState = "FAILED"
)

type SagaContext struct {
	OrderID     string
	CustomerID  string
	TotalAmount float64
	ItemIDs     []string
}

type SagaInstance struct {
	ID        string
	State     SagaState
	Payload   SagaContext
	UpdatedAt time.Time
	History   []SagaState
	mu        sync.RWMutex
}

func NewSagaInstance(id string, ctx SagaContext) *SagaInstance {
	return &SagaInstance{
		ID:        id,
		State:     StateStarted,
		Payload:   ctx,
		UpdatedAt: time.Now(),
		History:   []SagaState{StateStarted},
	}
}

// Transition выполняет потокобезопасный переход конечного автомата
func (s *SagaInstance) Transition(nextState SagaState) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Валидация допустимых переходов
	if !isValidTransition(s.State, nextState) {
		return fmt.Errorf("недопустимый переход из состояния %s в %s", s.State, nextState)
	}

	s.State = nextState
	s.UpdatedAt = time.Now()
	s.History = append(s.History, nextState)
	return nil
}

func isValidTransition(from, to SagaState) bool {
	switch from {
	case StateStarted:
		return to == StateOrderCreated || to == StateFailed
	case StateOrderCreated:
		return to == StateInventoryReserved || to == StateCompensating
	case StateInventoryReserved:
		return to == StatePaymentProcessed || to == StateCompensating
	case StatePaymentProcessed:
		return to == StateCompleted || to == StateCompensating
	case StateCompensating:
		return to == StateFailed || to == StateCompensating
	case StateCompleted, StateFailed:
		return false // Терминальные состояния
	default:
		return false
	}
}

func main() {
	saga := NewSagaInstance("saga-1001", SagaContext{
		OrderID:     "ord-77",
		CustomerID:  "cust-42",
		TotalAmount: 14990.0,
		ItemIDs:     []string{"sku-macbook", "sku-mouse"},
	})

	fmt.Printf("Сага %s запущена в состоянии: %s\n", saga.ID, saga.State)

	_ = saga.Transition(StateOrderCreated)
	_ = saga.Transition(StateInventoryReserved)
	_ = saga.Transition(StatePaymentProcessed)
	_ = saga.Transition(StateCompleted)

	fmt.Printf("Сага успешно финишировала: %s, История: %v\n", saga.State, saga.History)

	// Попытка перехода из терминального состояния
	err := saga.Transition(StateStarted)
	if err != nil {
		fmt.Printf("Защита FSM сработала: %v\n", err)
	}
}
```

## Под капотом

В производственных системах состояние саги никогда не хранится исключительно в оперативной памяти процесса. При каждом переходе состояния вызывается метод репозитория `SaveState(ctx, saga)`. Это гарантирует, что при внезапном падении пода (OOM, restart ноды K8s) вновь поднявшийся оркестратор прочитает последнюю зафиксированную точку в БД и продолжит выполнение саги или запуск компенсаций без потери бизнес-транзакции.

## Подводные камни

1. **Отсутствие терминальных состояний**: Если позволить саге переходить из `FAILED` или `COMPLETED` в активные состояния, возможен рекурсивный запуск шагов и повторное списание средств с клиента.
2. **Неатомарная фиксация состояния**: Если отправить команду внешнему сервису ДО сохранения записи в БД саги, падение оркестратора приведет к тому, что внешний сервис выполнил списание, а оркестратор 'забыл' об этом шаге.

## На собеседовании

В Ozon и Wildberries оформление заказа объединяет склад, процессинг карт, скидочные баллы и логистику. Вопрос на интервью: 'Почему мы выбираем Saga вместо классического 2PC распределенного транзакционного протокола?' Ответ: 2PC держит локи на строках в реляционных БД всех сервисов до конца глобального коммита. При задержках сети или отказе одного участника пропускная способность всей системы падает до нуля (Resource Exhaustion). Saga оперирует локальными транзакциями с асинхронной компенсацией, обеспечивая миллионные RPS без глобальных блокировок.
