# Saga вручную: взаимодействие сервисов Order и Payment (почему Happy Path не готов к продакшену)

## Условие

3. **Saga вручную: два сервиса.**: Реализуйте сервисы `Order` и `Payment`. Создайте заказ (`POST /orders`), затем вызовите `Payment` (`POST /payments`). При успехе обоих — заказ в статусе `confirmed`. Объясните, что это «happy path» Saga без компенсации, и почему он не production-ready.

### Исходная формулировка

**Saga вручную: два сервиса.**: Реализуйте сервисы `Order` и `Payment`. Создайте заказ (`POST /orders`), затем вызовите `Payment` (`POST /payments`). При успехе обоих — заказ в статусе `confirmed`. Объясните, что это «happy path» Saga без компенсации, и почему он не production-ready.

## Теория

Примитивная реализация распределенной цепочки без компенсаций — типичная ошибка начинающих разработчиков:
1. Сервис заказов (`OrderService`) сохраняет заказ в БД со статусом `confirmed`.
2. Затем делает синхронный HTTP POST запрос в платежный шлюз (`PaymentService`).
3. Если списание успешно — возвращаем клиенту 200 OK.

Почему этот 'счастливый путь' (Happy Path) категорически **не готов к продакшену (not production-ready)**:
- **Dual-Write Problem (Проблема двойной записи)**: Если заказ сохранен, но перед HTTP-запросом к `Payment` сервер перезагрузился (Kill -9, деплой новой версии), заказ навсегда останется в БД, но оплата никогда не произойдет.
- **Сетевой таймаут (Unknown Network State)**: Если запрос в `Payment` завис по таймауту (TCP timeout 30s), мы не знаем: списались деньги или нет! Ответить клиенту ошибкой 500 — значит рискнуть двойным списанием при повторе.
- **Отсутствие компенсирующего механизма**: При отказе платежа заказ остается в висящем состоянии без автоматической отмены.

## Решение по шагам

1. Реализуйте наивный хэндлер создания заказа с прямым вызовом оплаты.
2. Смоделируйте сетевой сбой (таймаут ответа платежного шлюза).
3. Проанализируйте рассинхронизацию состояний баз данных Order и Payment.
4. Сформулируйте архитектурные требования для перевода решения в Production-ready статус.

## Код решения

**`naive_saga.go`**

```go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

type Order struct {
	ID     string `json:"id"`
	Amount float64 `json:"amount"`
	Status string `json:"status"`
}

// Навный хэндлер, подверженный Dual-Write и потере консистентности
func NaiveOrderHandler(paymentURL string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		order := Order{ID: "ord-9901", Amount: 5000.0, Status: "PENDING"}

		// 1. Локальное сохранение заказа
		fmt.Printf("[OrderService] Заказ %s сохранен в БД со статусом PENDING\n", order.ID)

		// 2. Сетевой вызов платежного сервиса
		ctx, cancel := context.WithTimeout(r.Context(), 1*time.Second)
		defer cancel()

		req, _ := http.NewRequestWithContext(ctx, http.MethodPost, paymentURL+"/pay", nil)
		client := &http.Client{}
		resp, err := client.Do(req)

		if err != nil {
			// ПРОБЛЕМА: Деньги могли списаться, но ответ не дошел из-за сетевого сбоя!
			// В наивной реализации статус заказа остается PENDING, товар заблокирован,
			// а клиент получает 500 ошибку.
			fmt.Printf("[CRITICAL INCONSISTENCY] Сетевой сбой при обращении в Payment: %v\n", err)
			http.Error(w, "Payment Gateway Timeout", http.StatusGatewayTimeout)
			return
		}
		defer resp.Body.Close()

		if resp.StatusCode == http.StatusOK {
			order.Status = "CONFIRMED"
			fmt.Printf("[OrderService] Заказ %s успешно подтвержден (CONFIRMED)\n", order.ID)
			w.WriteHeader(http.StatusOK)
			_ = json.NewEncoder(w).Encode(order)
		} else {
			// ПРОБЛЕМА: Заказ в БД не отменен!
			http.Error(w, "Payment Rejected", http.StatusBadRequest)
		}
	}
}

func main() {
	// Эмуляция зависающего платежного шлюза
	mockPaymentServer := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		time.Sleep(2 * time.Second) // Имитация превышения таймаута
		w.WriteHeader(http.StatusOK)
	}))
	defer mockPaymentServer.Close()

	handler := NaiveOrderHandler(mockPaymentServer.URL)
	req := httptest.NewRequest(http.MethodPost, "/orders", nil)
	rec := httptest.NewRecorder()

	handler(rec, req)
	fmt.Printf("Результат наивного запроса: HTTP Status %d\n", rec.Code)
}
```

ℹ️ Демонстрация уязвимостей 'наивного happy-path' без оркестрации и компенсаций

## Под капотом

В распределенных системах существует фундаментальное правило: **Сетевой вызов имеет три исхода: Успех, Ошибка, Неизвестность (Timeout)**. В случае таймаута нельзя считать операцию неудавшейся. Единственный способ обеспечить согласованность — сделать метод `pay` строго идемпотентным (с передачей `Idempotency-Key: ord-9901`) и использовать фоновый оркестратор, опрашивающий статус транзакции.

## Подводные камни

1. **Попытка отката в блоке `catch/err` без гарантий**: Вызов `CancelOrder()` в обработчике ошибки HTTP-клиента упадет, если в этот момент упадет сам инстанс `OrderService`.
2. **Отсутствие таймаутов на HTTP клиенте**: Клиент `http.DefaultClient` не имеет таймаута. Зависший внешний сервис заморозит горутины и приведет к отказу всего Go-сервера по пулу горутин.

## На собеседовании

В Финтехе (Т-Банк, Яндекс Сплит) это классический вопрос секции 'Архитектура': 'Что произойдет, если пользователь нажал 'Оплатить', списание в банке прошло, но SMS-подтверждение зависло?' Ответ: Система переходит в состояние 'PENDING_PAYMENT'. Фоновый процесс Саги (Reconciliation Worker) проверяет статус транзакции через вебхук или поллинг банковского API по Idempotency Key и переводит заказ в 'CONFIRMED' либо инициирует возврат средств.
