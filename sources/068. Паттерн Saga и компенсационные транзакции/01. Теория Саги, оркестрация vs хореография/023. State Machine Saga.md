# State Machine Saga: жизненный цикл Started -> OrderCreated -> PaymentReserved -> InventoryConfirmed -> Finished

## Условие

23. **State Machine Saga.**: Определите состояния: `Started → OrderCreated → PaymentReserved → InventoryReserved → Completed` и ветку компенсации `... → Compensating → Compensated`. Храните состояние в PostgreSQL. Напишите SQL-таблицу `saga_instances` и Go-код переходов.

### Исходная формулировка

**State Machine Saga.**: Определите состояния: `Started → OrderCreated → PaymentReserved → InventoryReserved → Completed` и ветку компенсации `... → Compensating → Compensated`. Храните состояние в PostgreSQL. Напишите SQL-таблицу `saga_instances` и Go-код переходов.

## Теория

Формализация жизненного цикла распределенной бизнес-транзакции в виде математически строгого Конечного Автомата (Finite State Machine) — залог надежности Саги.

Канонический граф состояний e-commerce заказа:
1. `Started` (Инициализация транзакции).
2. `OrderCreated` (Черновик заказа зафиксирован в БД).
3. `PaymentReserved` (Средства захолдированы на счете).
4. `InventoryConfirmed` (Товар подтвержден и заблокирован на складе).
5. `Finished` (Заказ успешно подтвержден, чек отправлен клиенту).

Любое отклонение от штатного пути (отказ платежа, нехватка на складе) переводит автомата в соответствующие компенсирующие состояния:
`PaymentFailed` -> `OrderCancelling` -> `OrderCancelled`.

## Решение по шагам

1. Опишите состояния и события-триггеры автомата.
2. Создайте матрицу допустимых переходов `TransitionTable`.
3. Реализуйте метод `ApplyEvent(event)`.
4. Продемонстрируйте прохождение полного жизненного цикла.
5. Проверьте блокировку недопустимого события (например, попытка завершить заказ до оплаты).

## Код решения

**`fsm_lifecycle.go`**

```go
package main

import (
	"fmt"
)

type State string
type Event string

const (
	StateStarted            State = "Started"
	StateOrderCreated       State = "OrderCreated"
	StatePaymentReserved    State = "PaymentReserved"
	StateInventoryConfirmed State = "InventoryConfirmed"
	StateFinished           State = "Finished"
	StateCancelled          State = "Cancelled"
)

const (
	EventCreateOrder      Event = "CREATE_ORDER"
	EventReservePayment   Event = "RESERVE_PAYMENT"
	EventConfirmInventory Event = "CONFIRM_INVENTORY"
	EventFinalize         Event = "FINALIZE"
	EventAbort            Event = "ABORT"
)

type SagaFSM struct {
	Current State
}

func NewSagaFSM() *SagaFSM {
	return &SagaFSM{Current: StateStarted}
}

func (f *SagaFSM) Fire(ev Event) error {
	next, ok := f.getNextState(f.Current, ev)
	if !ok {
		return fmt.Errorf("НЕДОПУСТИМЫЙ ПЕРЕХОД: событие %s неприменимо к состоянию %s", ev, f.Current)
	}

	fmt.Printf("[FSM Transition] %s --(%s)--> %s\n", f.Current, ev, next)
	f.Current = next
	return nil
}

func (f *SagaFSM) getNextState(current State, ev Event) (State, bool) {
	switch current {
	case StateStarted:
		if ev == EventCreateOrder { return StateOrderCreated, true }
	case StateOrderCreated:
		if ev == EventReservePayment { return StatePaymentReserved, true }
		if ev == EventAbort { return StateCancelled, true }
	case StatePaymentReserved:
		if ev == EventConfirmInventory { return StateInventoryConfirmed, true }
		if ev == EventAbort { return StateCancelled, true }
	case StateInventoryConfirmed:
		if ev == EventFinalize { return StateFinished, true }
		if ev == EventAbort { return StateCancelled, true }
	}
	return "", false
}

func main() {
	fsm := NewSagaFSM()

	// Штатный цикл выполнения
	_ = fsm.Fire(EventCreateOrder)
	_ = fsm.Fire(EventReservePayment)
	_ = fsm.Fire(EventConfirmInventory)
	_ = fsm.Fire(EventFinalize)

	fmt.Printf("\nФинальное состояние FSM: %s\n", fsm.Current)

	// Попытка невалидного перехода
	err := fsm.Fire(EventCreateOrder)
	if err != nil {
		fmt.Printf("Защита сработала: %v\n", err)
	}
}
```

ℹ️ Матричный конечный автомат полного жизненного цикла заказа

## Под капотом

Табличная диспетчеризация переходов `getNextState` предотвращает спагетти-код из сотен условий `if/else`. В продакшене эта матрица переходов может быть представлена в виде плоской мапы `map[State]map[Event]State`, что дает мгновенную скорость проверки перехода \(O(1)\) и нулевые аллокации памяти.

## Подводные камни

1. **Пропуск валидации переходов**: Если просто обновлять статус без проверки текущего состояния, повторное сетевое событие может вернуть завершенный заказ `Finished` обратно в `PaymentReserved`.
2. **Несохранение истории в БД**: При аудите важно знать не только текущий статус, но и точный таймлайн всех промежуточных переходов с миллисекундной точностью.

## На собеседовании

На интервью уровня Senior Go Developer в Яндекс: 'Как обработать событие, пришедшее не вовремя (например, EventConfirmInventory пришел РАНЬШЕ EventReservePayment из-за сетевой задержки)?' Ответ: Паттерн Out-of-Order Buffer: если событие валидно для будущих состояний, оно временно складывается в буфер ожидания. Как только предыдущий шаг завершается, буфер проверяется и событие применяется автоматически.
