## Теория

При промышленном развертывании хореографии на базе Apache Kafka или RabbitMQ каждый микросервис развертывается в нескольких репликах (Consumer Group).

Архитектурные требования:
1. **At-Least-Once Delivery**: Брокер может доставить одно и то же сообщение дважды (при сетевых сбоях передачи `ACK`).
2. **Idempotent Consumer (Идемпотентный потребитель)**: Каждый сервис обязан вести таблицу обработанных сообщений: `CREATE TABLE processed_events (event_id VARCHAR PRIMARY KEY, processed_at TIMESTAMP)`.
3. **Partition Key**: Сообщения, относящиеся к одному заказу, обязаны отправляться в одну партицию Kafka (ключ сообщения `order_id`), чтобы гарантировать порядок обработки событий.
4. **Dead Letter Queue (DLQ)**: Если сообщение не может быть обработано из-за бага в коде (синтаксическая ошибка, panic), после 5 попыток оно сбрасывается в `orders.dlq` для предотвращения блокировки всей партиции.

## Решение по шагам

1. Создайте структуру идемпотентного консьюмера с реестром `processed_events`.
2. Смоделируйте дублирование входящего сообщения Kafka.
3. Убедитесь, что повторное сообщение отбрасывается без выполнения побочных эффектов.
4. Настройте отправку фатально сбойных сообщений в Dead Letter Queue.
5. Протестируйте надежность обработки потока событий.

## Код решения

**`kafka_choreography.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type Event struct {
	EventID string
	OrderID string
	Type    string
	Payload string
}

type IdempotentConsumer struct {
	processedEvents sync.Map
	dlq             []Event
	mu              sync.Mutex
}

func NewIdempotentConsumer() *IdempotentConsumer {
	return &IdempotentConsumer{}
}

func (c *IdempotentConsumer) HandleMessage(ctx context.Context, ev Event) error {
	// 1. Проверка идемпотентности (дедупликация)
	if _, loaded := c.processedEvents.LoadOrStore(ev.EventID, true); loaded {
		fmt.Printf("[Consumer] ДУБЛИКАТ обнаружен! Событие %s (Заказ %s) проигнорировано.\n", ev.EventID, ev.OrderID)
		return nil // Подтверждаем брокеру, что дубликат отработан
	}

	// 2. Обработка полезной нагрузки
	fmt.Printf("[Consumer] Обработка нового события %s (Тип: %s, Заказ: %s)...\n",
		ev.EventID, ev.Type, ev.OrderID)

	if ev.Payload == "corrupted_data" {
		c.sendToDLQ(ev, "Синтаксическая ошибка полезной нагрузки")
		return nil
	}

	fmt.Printf("[Consumer] Событие %s успешно применено к БД!\n", ev.EventID)
	return nil
}

func (c *IdempotentConsumer) sendToDLQ(ev Event, reason string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.dlq = append(c.dlq, ev)
	fmt.Printf("[DLQ ALERT] Событие %s сброшено в Dead Letter Queue! Причина: %s\n", ev.EventID, reason)
}

func main() {
	consumer := NewIdempotentConsumer()
	ctx := context.Background()

	event1 := Event{EventID: "evt-001", OrderID: "ORD-99", Type: "OrderCreated", Payload: "valid"}
	eventDuplicate := Event{EventID: "evt-001", OrderID: "ORD-99", Type: "OrderCreated", Payload: "valid"}
	eventPoison := Event{EventID: "evt-002", OrderID: "ORD-100", Type: "OrderCreated", Payload: "corrupted_data"}

	// Первое поступление сообщения
	_ = consumer.HandleMessage(ctx, event1)

	// Повторная доставка брокером (Network redelivery)
	_ = consumer.HandleMessage(ctx, eventDuplicate)

	// 'Ядовитое' сообщение (Poison pill)
	_ = consumer.HandleMessage(ctx, eventPoison)

	fmt.Printf("\nИтог: Сообщений в DLQ: %d\n", len(consumer.dlq))
}
```

ℹ️ Идемпотентный консьюмер событий хореографии с дедупликацией и отправкой в DLQ

## Под капотом

В реальных СУБД проверка `processed_events` и выполнение бизнес-логики обязаны выполняться **в рамках единой локальной транзакции PostgreSQL**:
```sql
BEGIN;
INSERT INTO processed_events (event_id) VALUES ($1); -- упадет по Primary Key при дубликате!
UPDATE orders SET status = 'PAID' WHERE id = $2;
COMMIT;
```
Если вставка `event_id` упадет с ошибкой `unique_violation`, транзакция откатится, предотвратив повторное применение изменений.

## Подводные камни

1. **In-Memory дедупликация в продакшене**: Использование `sync.Map` очищается при перезапуске пода, что приведет к повторной обработке сообщений из Kafka. Всегда сохраняйте `event_id` в персистентную БД.
2. **DLQ без мониторинга**: Сброс сбойных сообщений в DLQ без алерта в Telegram/Slack приведет к накоплению миллионов потерянных заказов незаметно для команды.

## На собеседовании

В распределенной архитектуре Ozon и Wildberries брокер Kafka передает терабайты сообщений в сутки. Вопрос: 'Что произойдет, если в партицию Kafka попадет poison pill (сообщение, на котором консьюмер падает в panic)?' Ответ: Если не перехватывать `recover()` и не сбрасывать сообщение в Dead Letter Queue, консьюмер будет падать по циклу (CrashLoopBackOff), и чтение ВСЕЙ партиции для миллионов пользователей остановится (Head-of-Line Blocking).
