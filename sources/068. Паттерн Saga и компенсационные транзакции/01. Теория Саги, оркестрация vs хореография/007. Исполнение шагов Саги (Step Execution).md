# Исполнение шагов Саги (Step Execution): отправка gRPC команд и сохранение стейта

## Условие

7. **Step execution**: Для каждого шага отправляйте команду в соответствующий сервис (gRPC/HTTP) и ждите ответ. Timeout + retry logic.

### Исходная формулировка

**Step execution**: Для каждого шага отправляйте команду в соответствующий сервис (gRPC/HTTP) и ждите ответ. Timeout + retry logic.

## Теория

При оркестрации каждый шаг представляет собой распределенную RPC-команду (`Command-Response`), отправляемую сервису-исполнителю по протоколу gRPC или HTTP.

Паттерн надежного исполнения шага:
1. **Предварительная фиксация (Pre-commit)**: Сохранение статуса `STEP_N_IN_PROGRESS` в Saga Log.
2. **Сетевой вызов (RPC Call)**: Отправка команды в сервис с передачей `saga_id`, `step_id` и дедлайна контекста (`grpc.Header`).
3. **Обработка ответа**:
   - `Success`: запись `STEP_N_SUCCESS` в БД, переход к шагу \(N+1\).
   - `Business Failure` (например, 4xx/InvalidArgument): немедленный запуск компенсаций.
   - `Transient Failure` (сетевой таймаут, HTTP 503): повтор вызова (Retry) с экспоненциальным backoff.

## Решение по шагам

1. Опишите структуру команды и ответа RPC-шага.
2. Реализуйте функцию исполнения шага с retry-политикой для сетевых сбоев.
3. Добавьте разграничение между бизнес-ошибками (нельзя ретраить) и сетевыми сбоями (нужно ретраить).
4. Протестируйте успешный повтор после временного сбоя сети.

## Код решения

**`step_executor.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

type StepCommand struct {
	SagaID  string
	StepNum int
	Payload any
}

type StepResult struct {
	Success     bool
	CanRetry    bool
	ErrorMsg    string
	Data        any
}

type RemoteServiceClient interface {
	Call(ctx context.Context, cmd StepCommand) StepResult
}

type StepExecutor struct {
	client RemoteServiceClient
}

func (e *StepExecutor) ExecuteWithRetry(ctx context.Context, cmd StepCommand, maxAttempts int) (*StepResult, error) {
	var lastResult StepResult

	for attempt := 1; attempt <= maxAttempts; attempt++ {
		select {
		case <-ctx.Done():
			return nil, ctx.Err()
		default:
		}

		fmt.Printf("[Saga %s] Попытка %d вызова шага %d...\n", cmd.SagaID, attempt, cmd.StepNum)
		lastResult = e.client.Call(ctx, cmd)

		if lastResult.Success {
			fmt.Printf("[Saga %s] Шаг %d успешно выполнен!\n", cmd.SagaID, cmd.StepNum)
			return &lastResult, nil
		}

		if !lastResult.CanRetry {
			// Бизнес-ошибка: ретраить бесполезно (например, неверный PIN-код или нет денег)
			fmt.Printf("[Saga %s] Фатальная бизнес-ошибка на шаге %d: %s (Ретраи отменены)\n",
				cmd.SagaID, cmd.StepNum, lastResult.ErrorMsg)
			return &lastResult, fmt.Errorf("business error: %s", lastResult.ErrorMsg)
		}

		// Сетевая ошибка: ждем перед повтором
		backoff := time.Duration(attempt*50) * time.Millisecond
		fmt.Printf("[Saga %s] Временный сбой: %s. Пауза %v перед ретраем\n", cmd.SagaID, lastResult.ErrorMsg, backoff)
		time.Sleep(backoff)
	}

	return &lastResult, fmt.Errorf("исчерпан лимит попыток (%d)", maxAttempts)
}

// Заглушка сервиса с временным сбоем
type MockFlakyClient struct {
	attempts int
}

func (m *MockFlakyClient) Call(ctx context.Context, cmd StepCommand) StepResult {
	m.attempts++
	if m.attempts < 3 {
		// Сетевой таймаут (Transient Error)
		return StepResult{Success: false, CanRetry: true, ErrorMsg: "503 Service Unavailable (TCP reset)"}
	}
	// На 3-й попытке успех
	return StepResult{Success: true, CanRetry: false, Data: "TX_CONFIRMED_991"}
}

func main() {
	executor := &StepExecutor{client: &MockFlakyClient{}}
	ctx := context.Background()

	cmd := StepCommand{SagaID: "saga-771", StepNum: 2, Payload: "Hold 1500 RUB"}
	res, err := executor.ExecuteWithRetry(ctx, cmd, 4)

	if err != nil {
		fmt.Printf("Итог: Ошибка: %v\n", err)
	} else {
		fmt.Printf("Итог: Успех! Данные: %v\n", res.Data)
	}
}
```

ℹ️ Исполнение шага саги с умной классификацией ошибок и экспоненциальным backoff

## Под капотом

Критически важно разделять ошибки на **Transient (Временные)** и **Non-Transient (Постоянные/Бизнес)**. Коды gRPC `Unavailable`, `DeadlineExceeded`, `ResourceExhausted` классифицируются как временные и требуют ретраев. Коды `InvalidArgument`, `NotFound`, `PermissionDenied`, `FailedPrecondition` являются бизнес-ошибками: повторный вызов с теми же параметрами гарантированно вернет ту же ошибку и приведет лишь к пустой трате ресурсов.

## Подводные камни

1. **Бесконечный ретрай бизнес-ошибок**: Если на шаге 'Списание баллов' баланс пользователя равен 0, ретрай 100 раз заблокирует оркестратор и вызовет каскадную деградацию.
2. **Отсутствие Jitter в backoff**: Если 1,000 саг одновременно получили сбой сетевого свитча и синхронно начнут слать повторы через ровно 1 секунду, они положат восстанавливающийся сервис повторной волной (Thundering Herd Problem).

## На собеседовании

В HighLoad системах Ozon и Авито сетевые сбои происходят непрерывно. Вопрос: 'Как предотвратить дублирование платежей при повторах сетевых ошибок в шагах Саги?' Ответ: Каждый шаг обязан передавать детерминированный `Idempotency-Key` (например, хэш от `saga_id + step_name`). Сервер платежей запоминает результат первой обработки и при повторах возвращает закэшированный ответ без повторного списания.
