# Event-Driven хореография Саги: Order, Payment и Inventory сервисы

## Условие

4. **[Хореография (Event-Driven)]**: Создай 3 сервиса (Order, Payment, Inventory). Сервис Order создает заказ и публикует событие `OrderCreated` в RabbitMQ. Payment слушает его и пытается списать деньги.

### Исходная формулировка

**[Хореография (Event-Driven)]**: Создай 3 сервиса (Order, Payment, Inventory). Сервис Order создает заказ и публикует событие `OrderCreated` в RabbitMQ. Payment слушает его и пытается списать деньги.

## Теория

В отличие от оркестрации, **Хореография (Choreography-based Saga)** не имеет центрального координатора. Сервисы общаются асинхронно через брокер сообщений (RabbitMQ, Apache Kafka, NATS):
1. `OrderService` создает заказ в локальной БД в статусе `PENDING` и публикует событие `OrderCreated`.
2. `PaymentService` слушает событие `OrderCreated`, списывает средства в своей БД и публикует `PaymentSucceeded` (или `PaymentFailed`).
3. `InventoryService` слушает `PaymentSucceeded`, резервирует товар на складе и публикует `InventoryReserved` (или `InventoryFailed`).
4. `OrderService` слушает финальное событие и переводит заказ в статус `CONFIRMED`.

При сбое на любом этапе публикуется событие ошибки (например, `PaymentFailed`), на которое реагируют предыдущие сервисы и локально откатывают свои изменения (например, `OrderService` помечает заказ как `CANCELLED`).

*Преимущества*: Высокая слабая связность (Loose Coupling), отсутствие единой точки отказа.
*Недостатки*: Сложность трассировки и риск циклических зависимостей при росте числа сервисов.

## Решение по шагам

1. Создайте структуры событий: `OrderCreatedEvent`, `PaymentSucceededEvent`, `PaymentFailedEvent`.
2. Реализуйте эмуляцию брокера сообщений через потокобезопасную шину событий (Event Bus).
3. Напишите подписчиков для каждого из 3 сервисов.
4. Продемонстрируйте прохождение цепочки событий от создания заказа до подтверждения оплаты.
5. Проверьте реакцию на событие сбоя.

## Код решения

**`choreography.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// События предметной области
type OrderCreatedEvent struct {
	OrderID string
	Amount  float64
}

type PaymentSucceededEvent struct {
	OrderID string
}

type PaymentFailedEvent struct {
	OrderID string
	Reason  string
}

type InventoryReservedEvent struct {
	OrderID string
}

// In-Memory шина событий (эмуляция Kafka/RabbitMQ)
type EventBus struct {
	subscribers map[string][]func(any)
	mu          sync.RWMutex
}

func NewEventBus() *EventBus {
	return &EventBus{subscribers: make(map[string][]func(any))}
}

func (b *EventBus) Subscribe(topic string, handler func(any)) {
	b.mu.Lock()
	b.subscribers[topic] = append(b.subscribers[topic], handler)
	b.mu.Unlock()
}

func (b *EventBus) Publish(topic string, event any) {
	b.mu.RLock()
	handlers := b.subscribers[topic]
	b.mu.RUnlock()

	for _, h := range handlers {
		go h(event) // Асинхронная доставка
	}
}

func main() {
	bus := NewEventBus()

	// 1. PaymentService слушает OrderCreated
	bus.Subscribe("order.created", func(e any) {
		ev := e.(OrderCreatedEvent)
		fmt.Printf("[PaymentService] Получено событие OrderCreated для %s на сумму %.2f\n", ev.OrderID, ev.Amount)
		// Проводим списание
		if ev.Amount > 10000 {
			fmt.Printf("[PaymentService] Лимит превышен! Публикация PaymentFailed для %s\n", ev.OrderID)
			bus.Publish("payment.failed", PaymentFailedEvent{OrderID: ev.OrderID, Reason: "Limit exceeded"})
		} else {
			fmt.Printf("[PaymentService] Оплата успешна. Публикация PaymentSucceeded для %s\n", ev.OrderID)
			bus.Publish("payment.succeeded", PaymentSucceededEvent{OrderID: ev.OrderID})
		}
	})

	// 2. InventoryService слушает PaymentSucceeded
	bus.Subscribe("payment.succeeded", func(e any) {
		ev := e.(PaymentSucceededEvent)
		fmt.Printf("[InventoryService] Товар зарезервирован для %s. Публикация InventoryReserved\n", ev.OrderID)
		bus.Publish("inventory.reserved", InventoryReservedEvent{OrderID: ev.OrderID})
	})

	// 3. OrderService слушает PaymentFailed (компенсация)
	bus.Subscribe("payment.failed", func(e any) {
		ev := e.(PaymentFailedEvent)
		fmt.Printf("[OrderService] Получено PaymentFailed! Заказ %s отменен (Причина: %s)\n", ev.OrderID, ev.Reason)
	})

	// Старт саги: создание заказа
	fmt.Println("=== Тест 1: Успешная хореография ===")
	bus.Publish("order.created", OrderCreatedEvent{OrderID: "ord-1", Amount: 2500.0})
	time.Sleep(100 * time.Millisecond)

	fmt.Println("\n=== Тест 2: Сбой с компенсацией ===")
	bus.Publish("order.created", OrderCreatedEvent{OrderID: "ord-2", Amount: 50000.0})
	time.Sleep(100 * time.Millisecond)
}
```

ℹ️ Реализация Event-Driven хореографии Саги через асинхронную шину сообщений

## Под капотом

В хореографии каждый микросервис подписывается только на интересующие его события. Отсутствие единого координатора означает, что логика бизнес-процесса распределена по всей системе ('размазана'). При 3-4 сервисах это просто и эффективно. Однако при 15 сервисах отследить полный граф переходов становится крайне трудно без распределенной трассировки OpenTelemetry.

## Подводные камни

1. **Циклические зависимости событий**: Сервис А слушает Б, который слушает В, который в случае ошибки шлет событие в А, порождая бесконечный шторм сообщений в брокере.
2. **Дублирование событий**: Брокеры сообщений гарантируют доставку `At-Least-Once`. Каждый сервис обязан проверять `event_id` в таблице идемпотентности перед выполнением действий.

## На собеседовании

Архитектурный вопрос в Яндексе: 'Когда предпочесть Хореографию, а когда Оркестрацию?' Ответ: Хореография идеальна для простых сценариев из 2-4 сервисов с линейной логикой, где важна максимальная развязанность. Для сложных бизнес-процессов (банковские переводы, оформление маркетплейс-заказа из 10 шагов с ветвлениями и таймаутами) оркестрация категорически предпочтительнее, так как состояние процесса централизовано и прозрачно.
