### Исходная формулировка

## Теория

Связка двух сервисов `Order` и `Payment` — минимальный полноценный полигон для отработки механизма компенсирующих транзакций:
1. Клиент инициирует создание заказа: `OrderService` сохраняет запись в БД со статусом `CREATED`.
2. `OrderService` вызывает `PaymentService.Charge(order_id, amount)`.
3. Если `PaymentService` вернул HTTP 4xx (недостаточно средств, карта просрочена) или 5xx после исчерпания ретраев, `OrderService` **не имеет права** оставить заказ в подвешенном состоянии.
4. Вызывается компенсирующая процедура `OrderService.CancelOrder(order_id, reason)`:
   - Статус заказа меняется на `CANCELLED`.
   - Записывается причина отмены для отображения пользователю.
   - Освобождаются локальные ресурсы.

## Решение по шагам

1. Создайте структуру сервиса заказов с методами `CreateOrder` и `CancelOrder`.
2. Смоделируйте отказ платежного шлюза.
3. Настройте перехват ошибки и автоматический вызов `CancelOrder`.
4. Проверьте, что в итоговом состоянии заказ переведен в `CANCELLED`.
5. Напишите тест подтверждения компенсации.

## Код решения

**`order_compensation.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type OrderStatus string

const (
	StatusCreated   OrderStatus = "CREATED"
	StatusPaid      OrderStatus = "PAID"
	StatusCancelled OrderStatus = "CANCELLED"
)

type OrderEntity struct {
	ID         string
	Amount     float64
	Status     OrderStatus
	CancelInfo string
}

type OrderService struct {
	mu     sync.Mutex
	orders map[string]*OrderEntity
}

func NewOrderService() *OrderService {
	return &OrderService{orders: make(map[string]*OrderEntity)}
}

func (s *OrderService) CreateOrder(id string, amount float64) *OrderEntity {
	s.mu.Lock()
	defer s.mu.Unlock()
	o := &OrderEntity{ID: id, Amount: amount, Status: StatusCreated}
	s.orders[id] = o
	fmt.Printf("[OrderService] Создан заказ %s в статусе %s\n", id, o.Status)
	return o
}

func (s *OrderService) MarkPaid(id string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if o, ok := s.orders[id]; ok {
		o.Status = StatusPaid
		fmt.Printf("[OrderService] Заказ %s оплачен! Статус -> %s\n", id, o.Status)
	}
}

// CancelOrder — компенсирующая транзакция
func (s *OrderService) CancelOrder(id string, reason string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if o, ok := s.orders[id]; ok {
		o.Status = StatusCancelled
		o.CancelInfo = reason
		fmt.Printf("[OrderService] КОМПЕНСАЦИЯ: Заказ %s отменен! Статус -> %s, Причина: %s\n", id, o.Status, reason)
	}
}

func (s *OrderService) Get(id string) *OrderEntity {
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.orders[id]
}

// Внешний платежный шлюз (возвращает сбой)
func ProcessPaymentMock(orderID string, amount float64) error {
	return fmt.Errorf("HTTP 402 Payment Required: карта заблокирована банком-эмитентом")
}

func HandleCheckout(orderSvc *OrderService, orderID string, amount float64) {
	// Шаг 1: Создание заказа
	orderSvc.CreateOrder(orderID, amount)

	// Шаг 2: Вызов оплаты
	err := ProcessPaymentMock(orderID, amount)
	if err != nil {
		fmt.Printf("[Checkout Flow] Ошибка оплаты: %v. Запуск компенсации...\n", err)
		// Запуск компенсирующей транзакции
		orderSvc.CancelOrder(orderID, err.Error())
		return
	}

	orderSvc.MarkPaid(orderID)
}

func main() {
	orderSvc := NewOrderService()

	HandleCheckout(orderSvc, "ORD-5501", 3400.0)

	finalOrder := orderSvc.Get("ORD-5501")
	fmt.Printf("\nИтоговое состояние заказа в БД: ID=%s, Status=%s, Ошибка='%s'\n",
		finalOrder.ID, finalOrder.Status, finalOrder.CancelInfo)
}
```

## Под капотом

В базах данных отмена заказа не должна физически удалять строку (`DELETE FROM orders`). Удаление уничтожает историю аудита. Компенсация обязана выполнять логическое аннулирование (`UPDATE orders SET status = 'CANCELLED', cancelled_at = NOW(), cancel_reason = $1`), сохраняя финансовый след для бухгалтерии и клиентской поддержки.

## Подводные камни

1. **Гонка статусов (State Race)**: Если параллельный запрос попытается повторно оплатить уже отмененный заказ, система может перевести его из `CANCELLED` в `PAID`. Метод `MarkPaid` обязан проверять: `WHERE id = $1 AND status = 'CREATED'`.
2. **Игнорирование ошибок в `CancelOrder`**: Если база заказов временно недоступна, вызов компенсации упадет. Оркестратор обязан поставить задачу на отмену в очередь ретраев.

## На собеседовании

В Wildberries и СберМаркете при отмене заказа требуется уведомить пользователя. Вопрос: 'Как гарантировать, что пользователь получит push-уведомление об отмене только после успешного завершения компенсирующей транзакции в БД?' Ответ: Использовать паттерн Transactional Outbox: событие `OrderCancelled` записывается в ту же транзакцию PostgreSQL, что и смена статуса заказа, и вычитывается CDC-демоном (Debezium/Kafka).
