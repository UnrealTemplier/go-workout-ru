# Базовая структура Saga: пайплайн CreateOrder -> ReserveInventory -> ProcessPayment -> ShipOrder

## Условие

5. **Базовая Saga структура**: Создайте orchestrator для e-commerce order flow: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — отдельный микросервис.

### Исходная формулировка

**Базовая Saga структура**: Создайте orchestrator для e-commerce order flow: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — отдельный микросервис.

## Теория

Классический enterprise-пайплайн электронной коммерции включает 4 последовательных этапа:
1. `CreateOrder`: валидация корзины, фиксация черновика заказа в статусе `PENDING`.
2. `ReserveInventory`: заморозка остатков на складе (резерв на 15 минут).
3. `ProcessPayment`: холдирование (авторизация) средств на карте покупателя через платежный шлюз.
4. `ShipOrder`: создание заявки в логистической службе доставки (СДЭК, Почта, Яндекс Доставка).

В архитектуре Go для такого пайплайна проектируется строго типизированная структура `OrderSagaPipeline`, где каждый шаг инкапсулирует вызовы gRPC-клиентов и методы компенсации.

## Решение по шагам

1. Опишите интерфейс шага саги с контекстом заказа.
2. Реализуйте все 4 шага: создание, склад, платеж, логистика.
3. Организуйте пайплайн с передачей контекста данных между шагами.
4. Добавьте замер времени выполнения каждого этапа.
5. Протестируйте сквозное прохождение пайплайна.

## Код решения

**`order_pipeline.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type OrderContext struct {
	OrderID        string
	SKU            string
	Quantity       int
	Amount         float64
	TrackingNumber string
}

type PipelineStep func(ctx context.Context, order *OrderContext) error

type Pipeline struct {
	steps []struct {
		name string
		fn   PipelineStep
	}
}

func NewPipeline() *Pipeline {
	return &Pipeline{}
}

func (p *Pipeline) AddStep(name string, fn PipelineStep) {
	p.steps = append(p.steps, struct {
		name string
		fn   PipelineStep
	}{name: name, fn: fn})
}

func (p *Pipeline) Execute(ctx context.Context, order *OrderContext) error {
	for _, step := range p.steps {
		start := time.Now()
		fmt.Printf("[Шаг] Запуск: %s...\n", step.name)
		if err := step.fn(ctx, order); err != nil {
			return fmt.Errorf("ошибка на шаге %s (%v): %w", step.name, time.Since(start), err)
		}
		fmt.Printf("[Шаг] %s успешно завершен за %v\n", step.name, time.Since(start))
	}
	return nil
}

func main() {
	p := NewPipeline()

	p.AddStep("1. CreateOrder", func(ctx context.Context, o *OrderContext) error {
		o.OrderID = "ORD-2026-X99"
		fmt.Printf("   -> Заказ %s зарегистрирован\n", o.OrderID)
		return nil
	})

	p.AddStep("2. ReserveInventory", func(ctx context.Context, o *OrderContext) error {
		fmt.Printf("   -> Склад: %d шт. SKU %s заблокировано\n", o.Quantity, o.SKU)
		return nil
	})

	p.AddStep("3. ProcessPayment", func(ctx context.Context, o *OrderContext) error {
		fmt.Printf("   -> Платеж: списано %.2f руб.\n", o.Amount)
		return nil
	})

	p.AddStep("4. ShipOrder", func(ctx context.Context, o *OrderContext) error {
		o.TrackingNumber = "TRACK-RU-789012"
		fmt.Printf("   -> Логистика: трек-номер %s присвоен\n", o.TrackingNumber)
		return nil
	})

	order := &OrderContext{
		SKU:      "IPHONE-16-PRO",
		Quantity: 1,
		Amount:   129990.0,
	}

	err := p.Execute(context.Background(), order)
	if err != nil {
		fmt.Printf("Пайплайн завершился ошибкой: %v\n", err)
	} else {
		fmt.Printf("Заказ %s готов к отправке, трек: %s\n", order.OrderID, order.TrackingNumber)
	}
}
```

ℹ️ Структурированный 4-этапный пайплайн оформления e-commerce заказа

## Под капотом

Передача указателя `*OrderContext` позволяет накапливать результаты предыдущих шагов (например, сгенерированный `OrderID` нужен шагу оплаты, а `TrackingNumber` — финальному шагу). Однако контекст обязан быть изолирован для каждого отдельного экземпляра саги во избежание состояния гонки данных (Data Race) между конкурентными запросами пользователей.

## Подводные камни

1. **Мутация контекста при параллельных сагах**: Использование глобального объекта вместо выделенного инстанса контекста на каждый вызов приведет к перезаписи данных чужого заказа.
2. **Отсутствие таймаутов на шаг**: Шаг вызова внешнего сервиса доставки может зависнуть на 60 секунд, блокируя весь пайплайн. Всегда оборачивайте контекст шага в `context.WithTimeout`.

## На собеседовании

В маркетплейсах (Wildberries, Ozon) заказ состоит из товаров от 10 разных продавцов. Вопрос: 'Как масштабировать шаг ReserveInventory, если товары лежат на 5 разных складах?' Ответ: Шаг `ReserveInventory` внутри себя запускает параллельные подсаги (Sub-Sagas) с использованием `errgroup.Group`. Если хотя бы один склад не смог зарезервировать товар, компенсируются только зарезервированные подсаги.
