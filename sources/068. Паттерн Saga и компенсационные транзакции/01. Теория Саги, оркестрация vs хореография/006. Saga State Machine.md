# Saga State Machine: персистентные состояния и обработка сбоев

## Условие

6. **Saga state machine**: Реализуйте state machine для Saga с состояниями: `Started`, `Step1Executing`, `Step1Completed`, `Step2Executing`, ..., `Completed`, `Compensating`, `Failed`.

### Исходная формулировка

**Saga state machine**: Реализуйте state machine для Saga с состояниями: `Started`, `Step1Executing`, `Step1Completed`, `Step2Executing`, ..., `Completed`, `Compensating`, `Failed`.

## Теория

Для обеспечения высокой надежности оркестратор Саги моделируется как конечный автомат с персистентным журналом состояний (Saga Log).

Граф состояний:
- `Started`: Сага инициализирована.
- `Step1Success` (`OrderCreated`): Заказ создан.
- `Step2Success` (`InventoryReserved`): Склад зарезервирован.
- `Step3Failed` (`PaymentFailed`): Ошибка платежа.
- `Compensating`: Оркестратор производит откат предыдущих шагов.
- `Completed`: Все шаги успешно завершены.
- `Failed`: Сага отменена, компенсация завершена.

Ключевой инвариант Саги: состояние в базе данных обновляется **ДО** отправки команды во внешний сервис (Write-Ahead State Logging). Если оркестратор упадет, он восстановится из последнего записанного состояния.

## Решение по шагам

1. Создайте интерфейс репозитория состояний саги `SagaRepository`.
2. Реализуйте переход с атомарным обновлением записи в БД.
3. Смоделируйте аварийное завершение процесса (Crash Simulation).
4. Напишите метод восстановления (Recovery): вычитка незавершенных саг и возобновление работы.
5. Протестируйте восстановление саги из промежуточного состояния.

## Код решения

**`persistent_fsm.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type State string

const (
	StateInit         State = "INIT"
	StateOrderDone    State = "ORDER_DONE"
	StateStockDone    State = "STOCK_DONE"
	StatePaymentDone  State = "PAYMENT_DONE"
	StateCompensating State = "COMPENSATING"
	StateCompleted    State = "COMPLETED"
	StateAborted      State = "ABORTED"
)

type SagaRecord struct {
	SagaID    string
	Current   State
	Data      string
	UpdatedAt time.Time
}

type MemorySagaRepo struct {
	mu      sync.RWMutex
	records map[string]*SagaRecord
}

func NewMemorySagaRepo() *MemorySagaRepo {
	return &MemorySagaRepo{records: make(map[string]*SagaRecord)}
}

func (r *MemorySagaRepo) Save(rec *SagaRecord) {
	r.mu.Lock()
	defer r.mu.Unlock()
	rec.UpdatedAt = time.Now()
	// Копирование для имитации изоляции БД
	copied := *rec
	r.records[rec.SagaID] = &copied
}

func (r *MemorySagaRepo) Get(id string) (*SagaRecord, bool) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	rec, ok := r.records[id]
	if !ok {
		return nil, false
	}
	copied := *rec
	return &copied, true
}

func (r *MemorySagaRepo) GetPendingSagas() []*SagaRecord {
	r.mu.RLock()
	defer r.mu.RUnlock()
	var pending []*SagaRecord
	for _, rec := range r.records {
		if rec.Current != StateCompleted && rec.Current != StateAborted {
			copied := *rec
			pending = append(pending, &copied)
		}
	}
	return pending
}

func main() {
	repo := NewMemorySagaRepo()

	// 1. Создание саги и фиксация шага 1
	saga := &SagaRecord{SagaID: "saga-crash-test", Current: StateStockDone, Data: "Заказ 500, Склад OK"}
	repo.Save(saga)

	fmt.Printf("[Crash Simulation] Сервис аварийно перезагружен. В БД сохранено состояние: %s\n", saga.Current)

	// 2. Процесс восстановления (Recovery Worker)
	pending := repo.GetPendingSagas()
	fmt.Printf("[Recovery] Найдено незавершенных саг: %d\n", len(pending))

	for _, p := range pending {
		fmt.Printf("[Recovery] Возобновление саги %s с шага %s...\n", p.SagaID, p.Current)
		if p.Current == StateStockDone {
			// Продолжаем со следующего шага (Оплата)
			fmt.Println("[Recovery] Выполнение шага Payment...")
			p.Current = StatePaymentDone
			repo.Save(p)
			p.Current = StateCompleted
			repo.Save(p)
			fmt.Printf("[Recovery] Сага %s успешно завершена!\n", p.SagaID)
		}
	}
}
```

ℹ️ Персистентный конечный автомат с процедурой восстановления после падения процесса

## Под капотом

В реальных СУБД (PostgreSQL) таблица `saga_instances` содержит столбцы `id UUID PRIMARY KEY`, `state VARCHAR`, `payload JSONB`, `version INT` и `updated_at TIMESTAMP`. Использование версионирования (`Optimistic Locking`) предотвращает одновременное обновление одной и той же саги двумя репликами оркестратора: `UPDATE saga_instances SET state = 'COMPENSATING', version = version + 1 WHERE id = $1 AND version = $2`.

## Подводные камни

1. **Split-Brain при параллельных оркестраторах**: Две ноды оркестратора одновременно пытаются продолжить одну сагу. Без пессимистических блокировок (`SELECT FOR UPDATE`) или optimistic concurrency control произойдет дублирование операций.
2. **Забытый индекс на статус**: Запрос `WHERE state NOT IN ('COMPLETED', 'FAILED')` для поиска зависших саг при миллионах записей вызовет Full Table Scan, если нет частичного индекса `CREATE INDEX ON saga_instances (state) WHERE state NOT IN (...)`.

## На собеседовании

В распределенных транзакционных координаторах Яндекса и VK вопрос восстановления — центральный: 'Что делать, если нода упала ровно в момент, когда внешний HTTP-запрос оплаты ушел, но ответ еще не получен?' Ответ: При рекавери оркестратор не имеет права сразу слать повторный запрос на списание. Он сначала вызывает метод проверки статуса платежа (`GetPaymentStatus(order_id)`) по идемпотентному ключу.
