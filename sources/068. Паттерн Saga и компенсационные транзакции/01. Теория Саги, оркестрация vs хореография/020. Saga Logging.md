# Saga Logging: структурированное логирование с correlation_id и задержками

## Условие

20. **Saga logging**: Логируйте каждый шаг: `Saga started`, `Step 1 executing`, `Step 1 completed`, `Step 2 failed`, `Compensation started`, `Compensation completed`.

### Исходная формулировка

**Saga logging**: Логируйте каждый шаг: `Saga started`, `Step 1 executing`, `Step 1 completed`, `Step 2 failed`, `Compensation started`, `Compensation completed`.

## Теория

В системах с тысячами одновременных распределенных транзакций текстовые логи вида `fmt.Println("step done")` абсолютно бесполезны: строки от сотен параллельных заказов перемешиваются в stdout.

Стандарт структурированного логирования Саги:
- Использование JSON-логгеров (`log/slog` в Go 1.21+).
- Обязательное присутствие контекстных атрибутов в каждой записи:
  - `saga_id`: Уникальный UUID саги.
  - `order_id`: Бизнес-идентификатор сущности.
  - `step`: Название текущего шага.
  - `action`: `EXECUTE` или `COMPENSATE`.
  - `duration_ms`: Время выполнения шага в миллисекундах.
  - `trace_id`: Сквозной ID W3C TraceContext для связи с OpenTelemetry.

## Решение по шагам

1. Настройте `slog.NewJSONHandler` для вывода структурированных JSON логов.
2. Оберните выполнение каждого шага с замером задержки `time.Since()`.
3. Добавьте сквозные атрибуты `saga_id` и `step`.
4. Продемонстрируйте вывод логов для успешных шагов и компенсаций.
5. Убедитесь в отсутствии потери контекста.

## Код решения

**`saga_logging.go`**

```go
package main

import (
	"context"
	"log/slog"
	"os"
	"time"
)

type StepRunner struct {
	logger *slog.Logger
	sagaID string
}

func NewStepRunner(sagaID string) *StepRunner {
	// Инициализация структурированного JSON логгера
	handler := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo})
	logger := slog.New(handler).With(slog.String("saga_id", sagaID))
	return &StepRunner{logger: logger, sagaID: sagaID}
}

func (r *StepRunner) RunStep(ctx context.Context, stepName string, fn func() error) error {
	start := time.Now()
	r.logger.Info("Старт выполнения шага",
		slog.String("step", stepName),
		slog.String("status", "STARTED"),
	)

	err := fn()
	duration := time.Since(start)

	if err != nil {
		r.logger.Error("Сбой при выполнении шага",
			slog.String("step", stepName),
			slog.String("status", "FAILED"),
			slog.Int64("duration_ms", duration.Milliseconds()),
			slog.String("error", err.Error()),
		)
		return err
	}

	r.logger.Info("Шаг успешно завершен",
		slog.String("step", stepName),
		slog.String("status", "SUCCESS"),
		slog.Int64("duration_ms", duration.Milliseconds()),
	)
	return nil
}

func main() {
	runner := NewStepRunner("saga-uuid-998822")
	ctx := context.Background()

	_ = runner.RunStep(ctx, "CheckBalance", func() error {
		time.Sleep(45 * time.Millisecond)
		return nil
	})

	_ = runner.RunStep(ctx, "ReserveSeats", func() error {
		time.Sleep(120 * time.Millisecond)
		return nil
	})
}
```

ℹ️ Структурированное JSON логирование саги на стандартной библиотеке slog

## Под капотом

Использование `slog.New(...).With(...)` создает дочерний логгер с предварительно сериализованными байтами постоянных атрибутов (`saga_id`). Это исключает лишний маршалинг общих полей на каждый последующий лог, снижая нагрузку на процессор и сборщик мусора Go в высоконагруженных циклах.

## Подводные камни

1. **Логирование персональных данных (PII)**: Запись полных номеров кредитных карт (PAN) или паспортных данных клиентов в JSON-логи саги является нарушением стандартов безопасности PCI-DSS и ФЗ-152. Всегда маскируйте чувствительные данные (`4111****1111`).
2. **Синхронный вывод логов при медленном диске**: Использование стандартного `os.Stdout` при блокировке сокета демона логов может затормозить весь Go-сервер. В проде используйте асинхронные буферизированные писатели.
