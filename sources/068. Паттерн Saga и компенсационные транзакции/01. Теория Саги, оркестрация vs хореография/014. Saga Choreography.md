# Saga Choreography: события как координатор бизнес-процесса

## Условие

14. **Saga Choreography: события как координатор.**: Реализуйте ту же бизнес-логику, но без оркестратора: сервис A публикует событие `A.Completed`, сервис B слушает его и выполняет своё действие, публикуя `B.Completed`, и т.д. При ошибке сервис публикует событие `*.Failed`, на которое подписаны компенсационные обработчики.

### Исходная формулировка

**Saga Choreography: события как координатор.**: Реализуйте ту же бизнес-логику, но без оркестратора: сервис A публикует событие `A.Completed`, сервис B слушает его и выполняет своё действие, публикуя `B.Completed`, и т.д. При ошибке сервис публикует событие `*.Failed`, на которое подписаны компенсационные обработчики.

## Теория

При реализации **Saga Choreography (Хореография Саги)** отсутствует единая точка координации: каждый микросервис подписывается на доменные события других сервисов и самостоятельно принимает решение о выполнении локальной транзакции и публикации следующего события.

Ключевые принципы взаимодействия:
1. **События успеха (Forward Flow)**:
   - `OrderService` -> `OrderCreated`
   - `PaymentService` слушает `OrderCreated`, списывает средства -> публикует `PaymentSucceeded`
   - `InventoryService` слушает `PaymentSucceeded`, бронирует товар -> публикует `InventoryReserved`
   - `OrderService` слушает `InventoryReserved` -> переводит заказ в `CONFIRMED`.
2. **События отката (Compensating Flow)**:
   - Если `InventoryService` не находит остатков, он публикует `InventoryFailed`.
   - `PaymentService` слушает `InventoryFailed` -> возвращает деньги на баланс -> публикует `PaymentRefunded`.
   - `OrderService` слушает `PaymentRefunded` -> переводит заказ в `CANCELLED`.

Слабая связность (Loose Coupling) достигается за счет изоляции: сервисы знают только структуру контракта событий, но не адреса или методы друг друга.

## Решение по шагам

1. Создайте доменные события для прямого и компенсирующего потока.
2. Реализуйте обработчики событий в сервисах Order, Payment и Inventory.
3. Продемонстрируйте прохождение компенсирующего потока при отказе инвентаря.
4. Убедитесь в отсутствии циклических вызовов.
5. Протестируйте итоговую консистентность состояния сервисов.

## Код решения

**`choreography_flow.go`**

```go
package main

import (
	"fmt"
	"time"
)

type EventBus struct {
	handlers map[string][]func(payload any)
}

func NewEventBus() *EventBus {
	return &EventBus{handlers: make(map[string][]func(any))}
}

func (b *EventBus) On(event string, fn func(any)) {
	b.handlers[event] = append(b.handlers[event], fn)
}

func (b *EventBus) Emit(event string, payload any) {
	fmt.Printf("[BUS] Опубликовано событие: %s\n", event)
	for _, fn := range b.handlers[event] {
		go fn(payload)
	}
}

func main() {
	bus := NewEventBus()

	// 1. PaymentService слушает OrderCreated
	bus.On("OrderCreated", func(p any) {
		orderID := p.(string)
		fmt.Printf("[PaymentService] Списание средств для %s: УСПЕХ\n", orderID)
		bus.Emit("PaymentSucceeded", orderID)
	})

	// 2. InventoryService слушает PaymentSucceeded
	bus.On("PaymentSucceeded", func(p any) {
		orderID := p.(string)
		fmt.Printf("[InventoryService] Проверка склада для %s: ТОВАРА НЕТ В НАЛИЧИИ!\n", orderID)
		bus.Emit("InventoryFailed", orderID)
	})

	// 3. PaymentService слушает InventoryFailed (Компенсация оплаты)
	bus.On("InventoryFailed", func(p any) {
		orderID := p.(string)
		fmt.Printf("[PaymentService] КОМПЕНСАЦИЯ: Возврат списанных средств для %s\n", orderID)
		bus.Emit("PaymentRefunded", orderID)
	})

	// 4. OrderService слушает PaymentRefunded (Финальная отмена заказа)
	bus.On("PaymentRefunded", func(p any) {
		orderID := p.(string)
		fmt.Printf("[OrderService] КОМПЕНСАЦИЯ: Заказ %s помечен как CANCELLED\n", orderID)
	})

	// Запуск саги
	fmt.Println("=== Старт Саги Хореографии с отказом на шаге Склада ===")
	bus.Emit("OrderCreated", "ORD-12345")

	time.Sleep(200 * time.Millisecond)
	fmt.Println("\nХореографический откат успешно завершен.")
}
```

## Под капотом

В отличие от синхронных HTTP-вызовов, асинхронная хореография не блокирует потоки операционной системы и позволяет выдерживать всплески трафика (Traffic Spikes) за счет естественной буферизации сообщений в брокере Kafka/RabbitMQ. Каждый микросервис обрабатывает события со своей собственной скоростью (Backpressure control).

## Подводные камни

1. **Скрытая сложность отладки (Spaghetti Events)**: В больших системах хореография из 20 событий превращается в 'спагетти-архитектуру', где никто не может восстановить полный путь движения заказа без Distributed Tracing.
2. **Потеря финального события**: Если сервис OrderService упадет до получения `PaymentRefunded`, заказ останется в статусе `PENDING` навсегда.

## На собеседовании

В архитектурных секциях Ozon и Авито часто спрашивают: 'Как понять, что в хореографии произошел сбой и сага зависла?' Ответ: Сервис, инициировавший сагу (OrderService), запускает локальный отложенный таймер (Dead Man's Switch / Timeout Event). Если в течение 10 минут финальное событие `InventoryReserved` или `PaymentRefunded` не получено, сервис инициирует процедуру аудита и оповещает мониторинг.
