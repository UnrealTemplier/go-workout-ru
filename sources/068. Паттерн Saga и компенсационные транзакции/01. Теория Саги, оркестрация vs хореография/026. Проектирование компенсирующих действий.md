# Проектирование компенсирующих действий (Compensating Actions) для сложных операций

## Условие

26. **Компенсационные транзакции (Compensating Actions).**: Для каждого шага реализуйте не только прямое действие, но и компенсирующее (например, `ReserveInventory` → `ReleaseInventory`, `ChargePayment` → `RefundPayment`). Покажите, что при сбое на шаге 3 откатываются шаги 2 и 1.

### Исходная формулировка

**Компенсационные транзакции (Compensating Actions).**: Для каждого шага реализуйте не только прямое действие, но и компенсирующее (например, `ReserveInventory` → `ReleaseInventory`, `ChargePayment` → `RefundPayment`). Покажите, что при сбое на шаге 3 откатываются шаги 2 и 1.

## Теория

Не для всех операций в реальном мире существует простое очевидное обратное действие:
- Как компенсировать отправку SMS-сообщения пользователю? (Нельзя 'отозвать' уже доставленное SMS).
- Как компенсировать списание физического топлива из цистерны?
- Как компенсировать запрос в Бюро кредитных историй?

Классификация шагов в архитектуре Саги (по Hector Garcia-Molina):
1. **Compensable Transactions (Компенсируемые)**: Шаги, для которых существует гарантированное семантическое обратное действие (\(T_i\) имеет \(C_i\)). Например, бронь склада, холд карты.
2. **Pivot Transaction (Поворотная транзакция)**: Критическая точка невозврата. Если Pivot шаг успешен — сага **ОБЯЗАНА** завершиться успехом до конца; откат назад больше невозможен.
3. **Retriable Transactions (Повторяемые/Гарантированные)**: Шаги, следующие ПОСЛЕ Pivot шага. Они не могут быть скомпенсированы, поэтому обязаны выполняться с бесконечными ретраями до победного конца (например, печать чека, отправка уведомления).

## Решение по шагам

1. Классифицируйте шаги вашего бизнес-процесса на Compensable, Pivot и Retriable.
2. Реализуйте архитектуру пайплайна с фиксацией точки невозврата (Pivot Point).
3. Докажите невозможность отката после прохождения Pivot шага.
4. Продемонстрируйте гарантированное дожатие шагов после точки невозврата.
5. Протестируйте поведение системы.

## Код решения

**`pivot_saga.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type StepType string

const (
	StepCompensable StepType = "COMPENSABLE"
	StepPivot       StepType = "PIVOT"
	StepRetriable   StepType = "RETRIABLE"
)

type AdvancedStep struct {
	Name string
	Type StepType
	Exec func() error
	Comp func() error
}

func main() {
	steps := []AdvancedStep{
		{
			Name: "1. LockAccount",
			Type: StepCompensable,
			Exec: func() error { fmt.Println("  [1] Аккаунт временно заблокирован"); return nil },
			Comp: func() error { fmt.Println("  [<-1] Аккаунт разблокирован"); return nil },
		},
		{
			Name: "2. DeductBalance (PIVOT)",
			Type: StepPivot, // ТОЧКА НЕВОЗВРАТА!
			Exec: func() error { fmt.Println("  [2] PIVOT: Деньги безвозвратно списаны со счета"); return nil },
			Comp: nil, // После Pivot откат назад запрещен!
		},
		{
			Name: "3. SendActivationEmail",
			Type: StepRetriable, // ОБЯЗАН ДОЖАТЬСЯ
			Exec: func() error { fmt.Println("  [3] RETRIABLE: Email с активацией успешно отправлен"); return nil },
			Comp: nil,
		},
	}

	fmt.Println("=== Выполнение Саги с явной Pivot-точкой ===")
	pivotPassed := false

	for _, step := range steps {
		fmt.Printf("Выполнение шага: %s (Тип: %s)...\n", step.Name, step.Type)
		err := step.Exec()
		if err != nil {
			if pivotPassed {
				fmt.Printf("[CRITICAL] Ошибка после Pivot шага! Откат невозможен, только RETRY: %v\n", err)
			} else {
				fmt.Println("[ROLLBACK] Ошибка до точки невозврата. Запуск компенсации...")
			}
			return
		}

		if step.Type == StepPivot {
			pivotPassed = true
			fmt.Println("  >>> ТОЧКА НЕВОЗВРАТА (PIVOT) ПРОЙДЕНА. САГА ДОЛЖНА БЫТЬ ЗАВЕРШЕНА! <<<")
		}
	}

	fmt.Println("\nСага успешно завершена!")
}
```

ℹ️ Классификация шагов саги: Compensable, Pivot Point и Retriable

## Под капотом

Разделение на Compensable и Retriable шаги относительно Pivot-транзакции — ключевой паттерн проектирования Саг в enterprise-системах. Поворотный шаг должен быть ровно один во всей цепочке. Попытка иметь два Pivot-шага превращает систему в недетерминированный хаос при сбое между ними.

## Подводные камни

1. **Попытка отката после Pivot шага**: Разработчик пытается компенсировать шаг, который уже физически необратим (например, реальная выдача наличных в банкомате).
2. **Неретраиваемый шаг после Pivot**: Если шаг после поворотной точки может завершиться фатальной ошибкой (например, валидация DTO), сага зависнет навсегда. Все шаги после Pivot обязаны быть идемпотентными и защищенными от постоянных ошибок.

## На собеседовании

На защите системной архитектуры в банках уровня Т-Банк, ВТБ, Сбер: 'Где в цепочке перевода денег по СБП (Система быстрых платежей) находится Pivot-шаг?' Ответ: Pivot-шаг — это списание средств со счета отправителя в ЦБ РФ. До этого момента (резервирование в банке) операция компенсируема. После подтверждения ЦБ РФ операция необратима, и банк получателя обязан дожать зачисление бесконечными повторами.
