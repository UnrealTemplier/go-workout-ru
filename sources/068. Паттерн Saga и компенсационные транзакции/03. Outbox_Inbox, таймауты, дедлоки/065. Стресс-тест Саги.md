### Исходная формулировка

## Теория

Финальная проверка надежности промышленной Саги:
Что произойдет, если в середине выполнения транзакции контейнер оркестратора будет внезапно принудительно остановлен командой `docker stop -t 0` (SIGKILL)?

Критерии успешности системы:
1. Состояние транзакции не повреждается.
2. После перезапуска контейнера оркестратор:
   - Обнаруживает незавершенную транзакцию в БД.
   - Проверяет статус во внешних сервисах.
   - Доводит процесс до `COMPLETED` или корректно разворачивает компенсации в `CANCELLED`.
3. Никаких утечек денег, броней товаров или зависших навсегда заказов!

## Решение по шагам

1. Смоделируйте прерывание процесса в момент между шагами.
2. Зафиксируйте частичное состояние в базе данных.
3. Запустите процедуру аварийного старта нового инстанса.
4. Выполните дочитку и корректный откат транзакции.
5. Подтвердите целостность системы.

## Код решения

**`docker_kill_simulation.go`**

```go
package main

import (
	"fmt"
	"time"
)

type PersistentRecord struct {
	SagaID      string
	Step        int
	Status      string
	OrderAmount float64
}

// Эмуляция персистентного диска PostgreSQL
var persistentDB = map[string]*PersistentRecord{
	"SAGA-KILL-TEST-1": {
		SagaID:      "SAGA-KILL-TEST-1",
		Step:        2, // Успел сделать шаг 1 и 2
		Status:      "IN_PROGRESS",
		OrderAmount: 7990.0,
	},
}

func SimulateContainerRestart() {
	fmt.Println("=== СИМУЛЯЦИЯ: Контейнер Оркестратора убит по SIGKILL (docker stop -t 0) ===")
	fmt.Println("[OS] Процесс мгновенно завершен. Память очищена. Сервер перезагружается...")
	time.Sleep(100 * time.Millisecond)

	fmt.Println("\n[BOOT] Новый экземпляр оркестратора стартовал. Запуск Crash Recovery Scan...")

	// Вычитка зависших саг из персистентной базы данных
	for id, record := range persistentDB {
		if record.Status == "IN_PROGRESS" {
			fmt.Printf("[RECOVERY] Найдена прерванная сага: %s на шаге %d!\n", id, record.Step)
			fmt.Println("[RECOVERY] Анализ статуса: Шаг 2 (Оплата) выполнен, Шаг 3 (Склад) не начат.")

			// Безопасный каскадный откат
			fmt.Printf("  <- [Компенсация шага 2] Возврат %.2f руб. клиенту\n", record.OrderAmount)
			fmt.Println("  <- [Компенсация шага 1] Аннулирование черновика заказа")

			record.Status = "COMPENSATED_AFTER_CRASH"
			fmt.Printf("[RECOVERY SUCCESS] Сага %s успешно скомпенсирована и закрыта в БД!\n", id)
		}
	}
}

func main() {
	SimulateContainerRestart()
	fmt.Printf("\nФинальный статус в БД: %s\n", persistentDB["SAGA-KILL-TEST-1"].Status)
}
```

ℹ️ Симуляция выживания Саги при принудительном убийстве контейнера оркестратора

## Под капотом

Команда `docker stop -t 0` посылает процессу сигнал `SIGKILL` (сигнал 9). В отличие от `SIGTERM`, сигнал `SIGKILL` невозможно перехватить в коде Go через `os/signal`: операционная система мгновенно выгружает страницы памяти процесса и освобождает сокеты. Единственное, что выживает — это байты, сброшенные на диск через `fsync()` в базе данных PostgreSQL.

## Подводные камни

1. **Буферизация записи статуса в памяти**: Если статус шага сбрасывался в БД не синхронно, при `SIGKILL` запись потеряется.
2. **Отсутствие проверки зависших саг при старте**: Если оркестратор ищет зависшие саги только по крону раз в час, после рестарта клиенты будут ждать отмены заказа целый час.
