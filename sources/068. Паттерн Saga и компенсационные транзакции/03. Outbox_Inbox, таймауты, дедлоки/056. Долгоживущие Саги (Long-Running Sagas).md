# Долгоживущие Саги (Long-Running Sagas): ожидание доставки курьером 3 дня

## Условие

56. **Долгоживущие Saga.**: Реализуйте шаг «Ожидание доставки» (3 дня). Состояние Saga — `AwaitingExternalEvent`. Сервис не должен держать ресурсы (блокировки, соединения). Объясните, как event от внешней системы (webhook от службы доставки) возобновляет Saga.

### Исходная формулировка

**Долгоживущие Saga.**: Реализуйте шаг «Ожидание доставки» (3 дня). Состояние Saga — `AwaitingExternalEvent`. Сервис не должен держать ресурсы (блокировки, соединения). Объясните, как event от внешней системы (webhook от службы доставки) возобновляет Saga.

## Теория

Большинство традиционных транзакций длятся миллисекунды. Однако в реальном бизнесе Сага может длиться **дни, недели или месяцы**:
- Ожидание подтверждения бронирования отеля туроператором (до 24 часов).
- Ожидание доставки товара курьером в руки покупателю (до 3 дней).
- 14-дневный период возврата товара (Return Period).

Проблемы долгоживущих саг:
1. Соединение HTTP/TCP невозможно держать открытым 3 дня.
2. Сервер оркестратора перезапустится десятки раз за это время.
3. Ресурсы памяти не могут быть заняты простаивающими горутинами.

Решение: Сага переходит в пассивный персистентный статус `AWAITING_DELIVERY` и выгружается из оперативной памяти. Процесс возобновляется внешним вебхуком или сигналом курьерской службы `POST /webhooks/delivery-status`.

## Решение по шагам

1. Опишите состояние саги с флагом долгоживущего ожидания.
2. Реализуйте переход в статус `SUSPENDED_AWAITING_DELIVERY`.
3. Создайте обработчик вебхука для возобновления процесса.
4. Продемонстрируйте завершение саги спустя время.
5. Напишите тест сценария отмены заказа во время ожидания доставки.

## Код решения

**`long_running_saga.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type LongSagaState string

const (
	StateCreated          LongSagaState = "CREATED"
	StatePaid             LongSagaState = "PAID"
	StateAwaitingDelivery LongSagaState = "AWAITING_DELIVERY"
	StateDelivered        LongSagaState = "DELIVERED"
	StateReturned         LongSagaState = "RETURNED_REFUNDED"
)

type LongRunningSaga struct {
	ID        string
	State     LongSagaState
	DaysInWait int
	mu        sync.Mutex
}

type LongSagaManager struct {
	mu    sync.RWMutex
	sagas map[string]*LongRunningSaga
}

func NewLongSagaManager() *LongSagaManager {
	return &LongSagaManager{sagas: make(map[string]*LongRunningSaga)}
}

func (m *LongSagaManager) StartSaga(id string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	saga := &LongRunningSaga{ID: id, State: StateAwaitingDelivery}
	m.sagas[id] = saga
	fmt.Printf("[LongSaga %s] Заказ оплачен. Сага переведена в долгий сон: %s (Ожидание курьера до 3 дней)\n",
		id, saga.State)
}

// HandleCourierWebhook возобновляет сагу по внешнему вебхуку от службы доставки
func (m *LongSagaManager) HandleCourierWebhook(id string, delivered bool) {
	m.mu.RLock()
	saga, exists := m.sagas[id]
	m.mu.RUnlock()

	if !exists {
		fmt.Printf("[Webhook] Сага %s не найдена\n", id)
		return
	}

	saga.mu.Lock()
	defer saga.mu.Unlock()

	if delivered {
		saga.State = StateDelivered
		fmt.Printf("\n[COURIER WEBHOOK] Сага %s ПРОСНУЛАСЬ! Посылка успешно вручена клиенту. Статус: %s\n",
			id, saga.State)
	} else {
		saga.State = StateReturned
		fmt.Printf("\n[COURIER WEBHOOK] Сага %s: Курьер не застал клиента. Старт компенсации и возврата денег: %s\n",
			id, saga.State)
	}
}

func main() {
	mgr := NewLongSagaManager()
	sagaID := "SAGA-PARCEL-3DAYS-88"

	// 1. Старт саги и засыпание
	mgr.StartSaga(sagaID)

	// Имитация: прошло 3 дня реального времени...
	fmt.Println("... Имитация прохождения 3 дней в режиме сна (память свободна, стейт в БД) ...")
	time.Sleep(100 * time.Millisecond)

	// 2. Курьер отсканировал QR-код у двери покупателя
	mgr.HandleCourierWebhook(sagaID, true)
}
```

ℹ️ Долгоживущая Сага с переходом в спящий режим и пробуждением по вебхуку доставки

## Под капотом

В платформах Durable Execution (Temporal) долгоживущая сага пишется буквально в одну строчку: `workflow.Sleep(ctx, 3*24*time.Hour)`. Temporal не держит открытый процесс: он сохраняет таймер в БД, закрывает горутину, а через 3 дня серверная часть Temporal отправляет задачу воркеру, который возобновляет выполнение кода со следующей строки!

## Подводные камни

1. **Удержание соединения или горутины в памяти на дни**: Вызов `time.Sleep(72 * time.Hour)` в обычной горутине приведет к утечке памяти и гибели саги при первом же перезапуске пода Kubernetes.
2. **Отсутствие граничного таймаута на вебхук**: Если курьерская служба потеряет посылку и не пришлет вебхук, сага останется в статусе `AWAITING_DELIVERY` навсегда.

## На собеседовании

В сервисах аренды жилья (Суточно.ру, Airbnb) сага бронирования длится от момента предоплаты до момента выезда гостя через неделю. Вопрос: 'Как реализовать автоматический перевод денег арендодателю через 24 часа после заселения гостя?' Ответ: Запланировать Durable Timer в Temporal или отложенную задачу в PostgreSQL (таблица `scheduled_tasks` с полем `run_at = checkin_time + INTERVAL '24 hours'`), которую вычитывает фоновый крон-воркер.
