### Исходная формулировка

**Saga + Temporal + Outbox:**
* Temporal workflow как orchestrator
* Temporal activities используют Outbox для publishing events
* Temporal даёт persistence, retries, visibility
* Outbox даёт reliable event publishing

## Теория

Temporal (или Cadence) представляет собой платформу оркестрации распределенных рабочих процессов (Workflow-as-Code). В отличие от самописных стейт-машин в реляционной СУБД, Temporal Workflow детерминированно восстанавливает свое состояние путем воспроизведения истории событий (Event Sourcing / Replay). Каждый шаг Саги инкапсулируется в Temporal Activity. Если Activity выполняет запись в локальную БД сервиса и одновременно должна уведомить внешние брокеры сообщений (Kafka, RabbitMQ), возникает классическая проблема Dual Write. Интеграция паттерна Outbox внутри Activity решает эту дилемму: Activity выполняет бизнес-логику и в рамках той же транзакции БД сохраняет событие в таблицу outbox_events. Фоновый debezium/CDC или poller доставляет событие в Kafka. Если же активность падает, Temporal перезапускает ее с гарантией идемпотентности по Activity Task Token, а Outbox гарантирует отсутствие потерянных или несогласованных событий.

func RunSagaWorkflow(ctx context.Context, act *ActivityOutboxRecorder, sagaID, orderID string, amount float64) error {
	saga := &OrderSagaState{
		SagaID:  sagaID,
		OrderID: orderID,
		Amount:  amount,
	}

	// Шаг 1: Оплата
	if err := act.ReservePaymentActivity(ctx, saga.SagaID, saga.OrderID, saga.Amount); err != nil {
		return fmt.Errorf("payment failed: %w", err)
	}
	// Регистрируем компенсацию шага 1
	saga.Compensations = append(saga.Compensations, func(c context.Context) error {
		return act.CompensatePaymentActivity(c, saga.SagaID, saga.OrderID)
	})

	// Шаг 2: Склад
	if err := act.ReserveInventoryActivity(ctx, saga.SagaID, saga.OrderID); err != nil {
		fmt.Printf("[Temporal Workflow] Step failed: %v. Running %d compensations in LIFO order...\n", err, len(saga.Compensations))
		for i := len(saga.Compensations) - 1; i >= 0; i-- {
			if compErr := saga.Compensations[i](ctx); compErr != nil {
				fmt.Printf("[CRITICAL] Compensation failed: %v\n", compErr)
			}
		}
		return fmt.Errorf("saga aborted and compensated: %w", err)
	}

	fmt.Println("[Temporal Workflow] All steps successfully completed!")
	return nil
}

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)

	if err != nil {

	} else {

	}
}

## Под капотом

Temporal использует движок на базе Event Sourcing. Когда воркер падает посреди саги, другой воркер подхватывает Workflow Execution, воспроизводя историю событий с самого начала (Replay). Код воркфлоу должен быть строго детерминированным: нельзя использовать прямой `time.Now()` или `rand.Int()`, вместо этого вызываются функции Temporal SDK (`workflow.Now(ctx)`). Сочетание с Outbox внутри Activities устраняет рассинхронизацию между базой микросервиса и шиной событий: даже если процесс упал сразу после коммита в БД, Temporal повторит Activity с idempotency token, а локальный Outbox гарантирует Exactly-Once семантику на уровне брокера.

## Подводные камни

1. Недетерминированность кода Workflow: использование горутин, прямых сетевых вызовов или чтения БД напрямую в функции воркфлоу вместо Activities приведет к панике `workflow non-deterministic error` при Replay.
2. Падение компенсации в Outbox: если компенсирующая активность не может записать outbox-событие, Temporal будет бесконечно повторять ее (Infinite Retry) согласно RetryPolicy, пока баг не будет устранен.

## На собеседовании

Вопрос: Зачем нужен Outbox внутри Temporal Activities, если Temporal сам гарантирует надежность выполнения?
Ответ: Temporal гарантирует надежность вызова и статус выполнения Activity, но если внутри Activity нужно атомарно изменить состояние реляционной БД сервиса (например, списать баланс) и опубликовать событие в Apache Kafka, отсутствие Outbox приведет к риску Dual Write. База может закоммитить списание, но воркер упадет до отправки в Kafka. Outbox внутри транзакции локальной СУБД устраняет этот разрыв.
