# Outbox + Idempotency: дедупликация при публикации событий в Kafka

## Условие

75. **Outbox + Idempotency**: Outbox poller использует idempotency keys для Kafka publishing. Повторная публикация того же event не создаёт duplicate в Kafka.

### Исходная формулировка

**Outbox + Idempotency**: Outbox poller использует idempotency keys для Kafka publishing. Повторная публикация того же event не создаёт duplicate в Kafka.

## Теория

Когда Outbox Poller (или CDC-коннектор) вычитывает события из таблицы outbox и отправляет их в Apache Kafka, процесс может упасть сразу после отправки сообщения, но до того, как в базе успеет выполниться `UPDATE outbox SET processed = true`. В результате после рестарта poller прочитает то же событие повторно и отправит дубликат в Kafka. Чтобы этого не произошло, необходимо использовать: 1) Идемпотентный продюсер Kafka (`enable.idempotence=true`), защищающий от дублей внутри одной сессии; 2) Передачу детерминированного ключа сообщения (`Record Key`) и Idempotency-хеша в Headers; 3) Транзакционный продюсер Kafka (Transactional Producer API), если требуется атомарность между несколькими партициями.

## Решение по шагам

1. Создайте структуру `KafkaBrokerMock` с поддержкой дедупликации по заголовку `Idempotency-Key`.
2. Реализуйте структуру `OutboxPoller`, опрашивающую локальное хранилище событий.
3. Симулируйте падение poller'а после отправки, но до коммита статуса `processed`.
4. Запустите poller повторно и убедитесь, что Kafka отклонила или отфильтровала повторную публикацию.
5. Продемонстрируйте логи работы дедупликации продюсера.

## Код решения

**`outbox_idempotent_publisher.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type OutboxRow struct {
	ID        int
	EventID   string // UUID события, используемый как Idempotency Key
	Topic     string
	Payload   string
	Processed bool
}

type KafkaBrokerMock struct {
	mu           sync.Mutex
	publishedMap map[string]bool
	messages     []string
}

func NewKafkaBrokerMock() *KafkaBrokerMock {
	return &KafkaBrokerMock{publishedMap: make(map[string]bool)}
}

func (k *KafkaBrokerMock) PublishWithIdempotency(eventID, topic, payload string) error {
	k.mu.Lock()
	defer k.mu.Unlock()

	// Проверка на уровне брокера/партиции
	if k.publishedMap[eventID] {
		fmt.Printf("[Kafka Broker] DUPLICATE DETECTED for EventID: %s. Acknowledged without storing duplicate.\n", eventID)
		return nil
	}

	k.publishedMap[eventID] = true
	k.messages = append(k.messages, fmt.Sprintf("[%s] %s: %s", topic, eventID, payload))
	fmt.Printf("[Kafka Broker] Successfully accepted new event: %s -> %s\n", eventID, topic)
	return nil
}

type OutboxPublisher struct {
	broker *KafkaBrokerMock
	dbRows []*OutboxRow
}

func (p *OutboxPublisher) PollAndPublish(ctx context.Context, crashBeforeCommit bool) {
	for _, row := range p.dbRows {
		if row.Processed {
			continue
		}

		fmt.Printf("[Outbox Poller] Processing outbox row ID=%d (EventID=%s)\n", row.ID, row.EventID)
		err := p.broker.PublishWithIdempotency(row.EventID, row.Topic, row.Payload)
		if err != nil {
			fmt.Printf("[Outbox Poller] Error: %v\n", err)
			return
		}

		if crashBeforeCommit {
			fmt.Println("[Outbox Poller CRASH] Process crashed before updating 'processed=true' in DB!")
			return
		}

		// Успешный коммит статуса
		row.Processed = true
		fmt.Printf("[Outbox DB] Row ID=%d marked as PROCESSED\n", row.ID)
	}
}

func main() {
	broker := NewKafkaBrokerMock()

	// Таблица Outbox с одним неотправленным событием
	rows := []*OutboxRow{
		{ID: 1, EventID: "evt-uuid-555", Topic: "order-events", Payload: "{\"order\":\"created\"}", Processed: false},
	}

	poller := &OutboxPublisher{broker: broker, dbRows: rows}

	fmt.Println("--- Iteration 1: Poller publishes but crashes before DB commit ---")
	poller.PollAndPublish(context.Background(), true)

	fmt.Println("\n--- Iteration 2: Poller restarts and re-processes the uncommitted row ---")
	poller.PollAndPublish(context.Background(), false)

	fmt.Printf("\nTotal unique messages stored in Kafka: %d\n", len(broker.messages))
}
```

ℹ️ Идемпотентная публикация из Outbox в Kafka с защитой от дублирования

## Под капотом

В Kafka Idempotent Producer каждому продюсеру присваивается `Producer ID` (PID), а каждому отправляемому сообщению внутри партиции — монотонно возрастающий `Sequence Number`. Брокер отклоняет любое сообщение, чей Sequence Number меньше или равен уже принятому для данного PID. При падении процесса продюсера создается новый PID, поэтому для долгосрочной дедупликации в заголовок сообщения помещается глобальный UUID события из Outbox.

## Подводные камни

1. Изменение порядка сообщений при ретраях: если `max.in.flight.requests.per.connection > 1` без включенного `enable.idempotence=true`, ретрай упавшего пакета может записаться в Kafka ПОСЛЕ следующего пакета, нарушая порядок событий.
2. Нагрузка на память брокера: хранение фильтра дедупликации в брокере ограничено окном sequence numbers.

## На собеседовании

Вопрос: Чем отличается идемпотентный продюсер Kafka от транзакционного (Transactional Producer)?
Ответ: Идемпотентный продюсер гарантирует отсутствие дубликатов сообщений только внутри одной партиции и одной сессии продюсера (PID). Транзакционный продюсер (`InitTransactions`, `BeginTx`, `CommitTx`) позволяет атомарно записывать сообщения в несколько разных топиков и партиций, а также коммитить потребительские оффсеты (read-process-write pattern).
