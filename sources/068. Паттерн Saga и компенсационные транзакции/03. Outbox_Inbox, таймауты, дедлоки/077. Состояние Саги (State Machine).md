# Состояние Саги (State Machine): таблица saga_states и персистенция FSM перед внешними вызовами

## Условие

77. **Состояние Саги (State Machine)**: Оркестратор может упасть (перезагрузиться). Создай БД для оркестратора: таблица `saga_states (saga_id, current_step, status)`. Перед каждым вызовом внешнего микросервиса сохраняй стейт (`Executing_Payment`, `Executing_Inventory`).

### Исходная формулировка

**Состояние Саги (State Machine)**: Оркестратор может упасть (перезагрузиться). Создай БД для оркестратора: таблица `saga_states (saga_id, current_step, status)`. Перед каждым вызовом внешнего микросервиса сохраняй стейт (`Executing_Payment`, `Executing_Inventory`).

## Теория

Золотое правило надежной оркестрации: состояние саги должно персистироваться ДО того, как оркестратор инициирует внешнее сетевое взаимодействие. Если оркестратор сначала выполнит сетевой вызов (например, вызов Billing API), а затем упадет до записи в базу `saga_states`, система забудет, что запрос уже был отправлен. После рестарта оркестратор повторит запрос, что может привести к двойному списанию. Паттерн Intent Recording требует: 1) Записать состояние `EXECUTING_PAYMENT`; 2) Выполнить вызов; 3) Записать состояние `PAYMENT_COMPLETED`. При перезагрузке статус `EXECUTING_*` сигнализирует о необходимости проверки статуса шага (Status Inquiry) или безопасного повтора с Idempotency Key.

## Решение по шагам

1. Спроектируйте структуру таблицы `SagaState` (SagaID, CurrentStep, Status, UpdatedAt).
2. Реализуйте переход состояний FSM: `PENDING` -> `EXECUTING_PAYMENT` -> `PAYMENT_DONE` -> `EXECUTING_INVENTORY`.
3. Сохраняйте состояние в хранилище перед каждым сетевым обращением.
4. Реализуйте механизм проверки незавершенных саг со статусом `EXECUTING_*` при рестарте.
5. Продемонстрируйте логирование каждого перехода состояний в консоль.

## Код решения

**`saga_state_machine.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type StepStatus string

const (
	StepPending            StepStatus = "PENDING"
	StepExecutingPayment   StepStatus = "EXECUTING_PAYMENT"
	StepPaymentSuccess     StepStatus = "PAYMENT_SUCCESS"
	StepExecutingInventory StepStatus = "EXECUTING_INVENTORY"
	StepInventorySuccess   StepStatus = "INVENTORY_SUCCESS"
	StepSagaCompleted      StepStatus = "COMPLETED"
	StepSagaFailed         StepStatus = "FAILED"
)

type SagaStateRecord struct {
	SagaID      string
	CurrentStep StepStatus
	UpdatedAt   time.Time
}

type StateDatabase struct {
	mu      sync.Mutex
	records map[string]SagaStateRecord
}

func NewStateDatabase() *StateDatabase {
	return &StateDatabase{records: make(map[string]SagaStateRecord)}
}

func (db *StateDatabase) Transition(sagaID string, newStatus StepStatus) {
	db.mu.Lock()
	defer db.mu.Unlock()
	rec := SagaStateRecord{
		SagaID:      sagaID,
		CurrentStep: newStatus,
		UpdatedAt:   time.Now(),
	}
	db.records[sagaID] = rec
	fmt.Printf("[DB WAL] Saga %s transitioned to -> %s\n", sagaID, newStatus)
}

func (db *StateDatabase) Get(sagaID string) SagaStateRecord {
	db.mu.Lock()
	defer db.mu.Unlock()
	return db.records[sagaID]
}

type ReliableOrchestrator struct {
	db *StateDatabase
}

func (o *ReliableOrchestrator) RunSaga(ctx context.Context, sagaID string) error {
	// 1. Инициализация
	o.db.Transition(sagaID, StepPending)

	// 2. Намерение: списываем оплату
	o.db.Transition(sagaID, StepExecutingPayment)
	// Внешний сетевой вызов
	fmt.Printf("[Network] Calling Billing Service for %s...\n", sagaID)
	// Успешный ответ
	o.db.Transition(sagaID, StepPaymentSuccess)

	// 3. Намерение: резервируем склад
	o.db.Transition(sagaID, StepExecutingInventory)
	// Внешний сетевой вызов
	fmt.Printf("[Network] Calling Inventory Service for %s...\n", sagaID)
	// Успешный ответ
	o.db.Transition(sagaID, StepInventorySuccess)

	// 4. Финал
	o.db.Transition(sagaID, StepSagaCompleted)
	fmt.Printf("[Orchestrator] Saga %s successfully completed!\n", sagaID)
	return nil
}

func main() {
	db := NewStateDatabase()
	orch := &ReliableOrchestrator{db: db}

	_ = orch.RunSaga(context.Background(), "saga-order-888")

	finalState := db.Get("saga-order-888")
	fmt.Printf("\n[Verification] Final recorded state in DB: %s (Time: %s)\n",
		finalState.CurrentStep, finalState.UpdatedAt.Format("15:04:05"))
}
```

ℹ️ Персистенция FSM саги перед внешними вызовами по принципу Write-Ahead Intent

## Под капотом

Паттерн Intent Logging гарантирует, что если процесс упадет во время ожидания сетевого ответа от Billing, recovery-процесс прочитает `EXECUTING_PAYMENT`. Он поймет, что сетевой пакет мог дойти или не дойти, и безопасно отправит повторный запрос с тем же `saga_id` в качестве Idempotency Key, либо запросит статус операции через `GET /payments/{saga_id}`.

## Подводные камни

1. Запись состояния после сетевого ответа: самая грубая ошибка архитектуры. При падении сети оркестратор не знает, был ли совершен вызов, и повторный запуск приводит к двойным списаниям.
2. Блокировки строк таблицы `saga_states`: при большом RPS необходимо оптимистическое версионирование (`UPDATE saga_states SET status = $1, version = version + 1 WHERE id = $2 AND version = $3`), чтобы несколько реплик оркестратора не перезаписывали состояние друг друга.

## На собеседовании

Вопрос: Что делать Recovery-воркеру, если он видит запись в статусе `EXECUTING_PAYMENT`, которая не менялась 10 минут?
Ответ: Зависший статус `EXECUTING` означает падение пода оркестратора или зависание внешнего сервиса. Recovery-воркер берет распределенную блокировку на данную сагу и выполняет статусную пробу (Health/Status Check) в Billing API. Если транзакция там найдена — сага переводится в `PAYMENT_SUCCESS` и продолжается. Если транзакции нет — инициируется отмена или повтор.
