# Dead Letter Queue (DLQ) для failed events: обработка ядовитых сообщений в саге

## Условие

69. **Dead letter queue для failed events**: Events, которые не удалось обработать после N retries, отправляются в DLQ для manual inspection.

### Исходная формулировка

**Dead letter queue для failed events**: Events, которые не удалось обработать после N retries, отправляются в DLQ для manual inspection.

## Теория

В распределенной асинхронной саге сообщения о событиях или командах могут вызывать неисправимые ошибки: поврежденный JSON, нарушение бизнес-инвариантов, баг в коде потребителя (Poison Pill). Если консьюмер бесконечно падает и возвращает Nack в очередь, обработка всей партиции блокируется (Head-of-Line Blocking). Паттерн Dead Letter Queue (DLQ) изолирует такие сообщения: после исчерпания лимита повторных попыток (Max Retries) сообщение вместе с метаданными ошибки (стектрейс, количество попыток, время) перемещается в специальную очередь DLQ, а основной поток обработки продолжает движение. Сага переводится в статус `MANUAL_INTERVENTION_REQUIRED`.

## Решение по шагам

1. Создайте структуру `Message` с идентификатором саги, полезной нагрузкой и счетчиком попыток `RetryCount`.
2. Создайте структуру `DLQMessage` с дополнительными полями причины сбоя и временной метки.
3. Реализуйте функцию потребителя `ConsumeWithDLQ`, ограничивающую число повторов константой `maxRetries = 3`.
4. При превышении лимита отправьте сообщение в канал/таблицу DLQ и залогируйте алерт.
5. Протестируйте работу с валидным сообщением и 'ядовитым' сообщением.

## Код решения

**`dlq_handler.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"strings"
	"time"
)

type EventMessage struct {
	ID         string
	SagaID     string
	Payload    string
	RetryCount int
}

type DLQEnvelope struct {
	EventMessage
	FailedAt  time.Time
	LastError string
}

type MessageConsumer struct {
	maxRetries int
	dlqChan    chan DLQEnvelope
}

func NewMessageConsumer(maxRetries int) *MessageConsumer {
	return &MessageConsumer{
		maxRetries: maxRetries,
		dlqChan:    make(chan DLQEnvelope, 100),
	}
}

func (c *MessageConsumer) ProcessEvent(ctx context.Context, msg EventMessage) error {
	// Эмуляция бизнес-логики: если payload содержит "corrupt", кидаем ошибку
	if strings.Contains(msg.Payload, "corrupt") {
		return errors.New("unmarshal error: payload contains invalid corrupted bytes")
	}
	fmt.Printf("[Consumer] Successfully processed event %s for saga %s\n", msg.ID, msg.SagaID)
	return nil
}

func (c *MessageConsumer) HandleIncoming(ctx context.Context, msg EventMessage) {
	for {
		err := c.ProcessEvent(ctx, msg)
		if err == nil {
			return
		}

		msg.RetryCount++
		fmt.Printf("[Retry] Event %s failed (attempt %d/%d): %v\n", msg.ID, msg.RetryCount, c.maxRetries, err)

		if msg.RetryCount >= c.maxRetries {
			fmt.Printf("[DLQ ROUTING] Max retries reached for event %s. Moving to DLQ!\n", msg.ID)
			c.dlqChan <- DLQEnvelope{
				EventMessage: msg,
				FailedAt:     time.Now(),
				LastError:    err.Error(),
			}
			return
		}
		time.Sleep(50 * time.Millisecond) // Backoff
	}
}

func main() {
	consumer := NewMessageConsumer(3)
	ctx := context.Background()

	// Валидное сообщение
	validMsg := EventMessage{ID: "evt-01", SagaID: "saga-1", Payload: "{\"order_id\": 101}"}
	consumer.HandleIncoming(ctx, validMsg)

	// Ядовитое сообщение (Poison Pill)
	poisonMsg := EventMessage{ID: "evt-02", SagaID: "saga-2", Payload: "corrupt_data_payload"}
	consumer.HandleIncoming(ctx, poisonMsg)

	// Проверяем содержимое DLQ
	select {
	case dlqItem := <-consumer.dlqChan:
		fmt.Printf("\n[DLQ INSPECTION] Captured poison pill:\n"+
			" - EventID: %s\n - SagaID: %s\n - Payload: %s\n - Retries: %d\n - Error: %s\n",
			dlqItem.ID, dlqItem.SagaID, dlqItem.Payload, dlqItem.RetryCount, dlqItem.LastError)
	default:
		fmt.Println("DLQ is empty")
	}
}
```

## Под капотом

В Kafka DLQ реализуется как отдельный топик (например, `order-saga-dlq`). Консьюмер коммитит оффсет проблемного сообщения в основном топике только ПОСЛЕ того, как гарантированно записал его копию в топик DLQ. Если продюсер DLQ упадет, оффсет не коммитится. Для каждого сообщения в заголовки Kafka Headers добавляются `x-death-reason`, `x-original-topic`, `x-retry-count`.

## Подводные камни

1. Забытый DLQ: если DLQ не мониторится метриками и алертами, сообщения накапливаются там терабайтами, а клиенты часами ждут завершения саги. Необходим алерт `rate(dlq_messages_total[5m]) > 0`.
2. Потеря контекста трассировки: при отправке в DLQ важно копировать все заголовки OpenTelemetry (W3C TraceParent), иначе инженеры не смогут связать запись в DLQ с логами исходного запроса.

## На собеседовании

Вопрос: Что делать с сагой, событие которой оказалось в DLQ? Как безопасно перезапустить процесс?
Ответ: Сага переводится в статус `MANUAL_REQUIRED`. В админ-панели инженер анализирует причину сбоя, при необходимости применяет фикс кода или патчит данные сообщения. Затем запускается DLQ Replay: сообщение заново отправляется в рабочий топик, либо через UI оркестратора вызывается принудительная компенсация.
