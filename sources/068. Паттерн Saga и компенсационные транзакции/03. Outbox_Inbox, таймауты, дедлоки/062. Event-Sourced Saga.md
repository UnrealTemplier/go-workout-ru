# Event-Sourced Saga: восстановление состояния процесса через свертку событий (Fold)

## Теория

В парадигме **Event-Sourced Saga** состояние саги не сохраняется в виде статической строки в таблице (`status = 'PAID'`). Вместо этого единственным источником истины является **поток событий (Event Stream)**.

Формула вычисления текущего состояния:
$$\text{CurrentState} = \text{Fold}(\text{InitialState}, [\text{Event}_1, \text{Event}_2, \dots, \text{Event}_n])$$

Преимущества Event-Sourced Саги:
1. **Абсолютный аудит**: Мы знаем не просто текущий статус, а полную историю: во сколько миллисекунд произошел каждый переход и кто его инициировал.
2. **Путешествие во времени (Time Travel)**: Возможность восстановить состояние саги на любую секунду в прошлом для ретроспективного анализа.
3. **Бесконфликтная репликация**: Записи событий добавляются только в режиме Append-Only, что исключает дедлоки на строках БД.

## Решение по шагам

1. Создайте структуру агрегата саги `OrderSagaAggregate`.
2. Опишите события: `SagaStarted`, `StockReserved`, `PaymentFailed`, `SagaCompensated`.
3. Реализуйте метод `ApplyEvent` (мутация состояния без побочных эффектов).
4. Напишите функцию свертки (Fold) для восстановления агрегата из среза событий.
5. Протестируйте восстановление состояния саги.

## Код решения

**`event_sourced_saga.go`**

```go
package main

import (
	"fmt"
	"time"
)

type EventType string

const (
	EvtStarted     EventType = "SAGA_STARTED"
	EvtStockHold   EventType = "STOCK_HELD"
	EvtPaymentFail EventType = "PAYMENT_FAILED"
	EvtCompensated EventType = "SAGA_COMPENSATED"
)

type HistoryEvent struct {
	Type      EventType
	Timestamp time.Time
	Payload   string
}

type OrderSagaAggregate struct {
	SagaID      string
	Status      string
	IsStockHeld bool
	ErrorReason string
	Version     int
}

// ApplyEvent производит чистую мутацию состояния (Pure Function)
func (a *OrderSagaAggregate) ApplyEvent(e HistoryEvent) {
	a.Version++
	switch e.Type {
	case EvtStarted:
		a.Status = "ACTIVE"
	case EvtStockHold:
		a.IsStockHeld = true
	case EvtPaymentFail:
		a.Status = "FAILED"
		a.ErrorReason = e.Payload
	case EvtCompensated:
		a.Status = "COMPENSATED"
		a.IsStockHeld = false
	}
}

// Fold восстанавливает состояние агрегата из истории событий
func ReconstituteSaga(sagaID string, history []HistoryEvent) *OrderSagaAggregate {
	agg := &OrderSagaAggregate{SagaID: sagaID, Status: "NEW", Version: 0}
	for _, event := range history {
		agg.ApplyEvent(event)
	}
	return agg
}

func main() {
	sagaID := "ES-SAGA-99001"

	// История событий, извлеченная из Kafka или EventStoreDB
	eventStream := []HistoryEvent{
		{Type: EvtStarted, Timestamp: time.Now().Add(-3 * time.Minute), Payload: "ORD-99001"},
		{Type: EvtStockHold, Timestamp: time.Now().Add(-2 * time.Minute), Payload: "SKU-IPHONE"},
		{Type: EvtPaymentFail, Timestamp: time.Now().Add(-1 * time.Minute), Payload: "Card Expired"},
		{Type: EvtCompensated, Timestamp: time.Now(), Payload: "Stock Released"},
	}

	// Восстановление через Fold
	aggregate := ReconstituteSaga(sagaID, eventStream)

	fmt.Printf("=== Восстановленный Event-Sourced Агрегат Саги ===\n")
	fmt.Printf("SagaID:       %s\n", aggregate.SagaID)
	fmt.Printf("Финальный статус:  %s\n", aggregate.Status)
	fmt.Printf("Бронь склада: %v (освобождена!)\n", aggregate.IsStockHeld)
	fmt.Printf("Причина ошибки: %s\n", aggregate.ErrorReason)
	fmt.Printf("Версия агрегата:   %d (событий применено)\n", aggregate.Version)
}
```

ℹ️ Event-Sourced Сага: восстановление агрегата через чистую функцию свертки истории

## Под капотом

В Event Sourcing метод `ApplyEvent` обязан быть строго детерминированной чистой функцией: никаких сетевых запросов, генерации случайных чисел или вызовов `time.Now()` внутри `ApplyEvent`. Время берется строго из поля `e.Timestamp` самого исторического события. Это гарантирует, что повторный прогон истории через 5 лет даст абсолютно идентичный результат.

## Подводные камни

1. **Слишком длинная история событий (Long Event Streams)**: Если сага порождает 10,000 событий, восстановление агрегата через fold замедлит систему. Для ускорения создаются **Снапшоты (Snapshots)** каждые 100 событий.
2. **Сложность изменения схемы событий (Schema Evolution)**: При переименовании полей старые события в БД нельзя изменить. Требуются адаптеры (Upcasters).

## На собеседовании

В финтех-платформах (Revolut, Stripe, Тинькофф): 'Зачем использовать Event Sourcing для Саг вместо обычной таблицы со статусом?' Ответ: Event Sourcing обеспечивает 100% математическую доказуемость любого состояния (Audit Trail), упрощает расследование финансовых инцидентов и исключает потери данных при сбоях, так как события пишутся только в режиме Append-Only.
