# Хореография (Choreography): децентрализованная сага на событиях без единого координатора

## Условие

70. **Хореография (Choreography - Децентрализованная Сага)**: Напиши 3 микросервиса. `Order` создает заказ (статус PENDING) и шлет событие. `Billing` ловит событие, списывает деньги и шлет свое. `Inventory` ловит событие биллинга, резервирует товар и шлет `InventoryReserved`. `Order` ловит это и ставит статус APPROVED. Реализуй этот 'танец' событий.

### Исходная формулировка

**Хореография (Choreography - Децентрализованная Сага)**: Напиши 3 микросервиса. `Order` создает заказ (статус PENDING) и шлет событие. `Billing` ловит событие, списывает деньги и шлет свое. `Inventory` ловит событие биллинга, резервирует товар и шлет `InventoryReserved`. `Order` ловит это и ставит статус APPROVED. Реализуй этот "танец" событий.

## Теория

Хореография (Choreography) — это подход к реализации саги, при котором отсутствует центральный контроллер или координатор. Каждый микросервис реагирует на доменные события других сервисов, выполняет свою локальную транзакцию и публикует новые доменные события в общую шину (Event Bus / Kafka / RabbitMQ). Этот подход исключает единую точку отказа и жесткую связанность (tight coupling), но усложняет мониторинг и понимание сквозного потока выполнения, создавая неявный 'танец' событий (event pinball).

## Решение по шагам

1. Создайте доменные события: `OrderCreatedEvent`, `PaymentProcessedEvent`, `InventoryReservedEvent`.
2. Реализуйте сервис `OrderService`, который создает заказ и публикует `OrderCreatedEvent`.
3. Реализуйте сервис `BillingService`, слушающий создание заказа и публикующий `PaymentProcessedEvent`.
4. Реализуйте сервис `InventoryService`, слушающий оплату и публикующий `InventoryReservedEvent`.
5. Добавьте хэндлер в `OrderService`, переводящий заказ в `APPROVED` при получении `InventoryReservedEvent`.

## Код решения

**`choreography_saga.go`**

```go
package main

import (
	"fmt"
	"sync"
)

// Event Bus для передачи доменных событий
type EventBus struct {
	mu          sync.RWMutex
	subscribers map[string][]func(payload interface{})
}

func NewEventBus() *EventBus {
	return &EventBus{subscribers: make(map[string][]func(payload interface{}))}
}

func (b *EventBus) Subscribe(topic string, handler func(payload interface{})) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.subscribers[topic] = append(b.subscribers[topic], handler)
}

func (b *EventBus) Publish(topic string, payload interface{}) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for _, h := range b.subscribers[topic] {
		go h(payload)
	}
}

// Доменные события
type OrderCreatedEvent struct {
	OrderID string
	Amount  float64
}

type PaymentProcessedEvent struct {
	OrderID string
	Amount  float64
}

type InventoryReservedEvent struct {
	OrderID string
}

func main() {
	bus := NewEventBus()
	var wg sync.WaitGroup
	wg.Add(1)

	// Сервис 1: Order Service
	orderStatuses := make(map[string]string)
	var orderMu sync.Mutex

	bus.Subscribe("InventoryReserved", func(payload interface{}) {
		evt := payload.(InventoryReservedEvent)
		orderMu.Lock()
		orderStatuses[evt.OrderID] = "APPROVED"
		fmt.Printf("[OrderService] Order %s APPROVED! Saga dance complete.\n", evt.OrderID)
		orderMu.Unlock()
		wg.Done()
	})

	// Сервис 2: Billing Service
	bus.Subscribe("OrderCreated", func(payload interface{}) {
		evt := payload.(OrderCreatedEvent)
		fmt.Printf("[BillingService] Debited $%.2f for Order %s -> Publishing PaymentProcessed\n", evt.Amount, evt.OrderID)
		bus.Publish("PaymentProcessed", PaymentProcessedEvent{OrderID: evt.OrderID, Amount: evt.Amount})
	})

	// Сервис 3: Inventory Service
	bus.Subscribe("PaymentProcessed", func(payload interface{}) {
		evt := payload.(PaymentProcessedEvent)
		fmt.Printf("[InventoryService] Reserved items for Order %s -> Publishing InventoryReserved\n", evt.OrderID)
		bus.Publish("InventoryReserved", InventoryReservedEvent{OrderID: evt.OrderID})
	})

	// Инициация Саги клиентом
	orderID := "ord-777"
	orderMu.Lock()
	orderStatuses[orderID] = "PENDING"
	orderMu.Unlock()

	fmt.Printf("[OrderService] Order %s created with status PENDING -> Publishing OrderCreated\n", orderID)
	bus.Publish("OrderCreated", OrderCreatedEvent{OrderID: orderID, Amount: 120.50})

	wg.Wait()
}
```

ℹ️ Хореография саги: децентрализованный обмен событиями между тремя микросервисами

**`output.txt`**

```bash
[OrderService] Order ord-777 created with status PENDING -> Publishing OrderCreated
[BillingService] Debited $120.50 for Order ord-777 -> Publishing PaymentProcessed
[InventoryService] Reserved items for Order ord-777 -> Publishing InventoryReserved
[OrderService] Order ord-777 APPROVED! Saga dance complete.
```

## Под капотом

В хореографии каждый сервис автономен и слушает только нужные ему топики Kafka. Связанность ослаблена, но возникает циклическая топологическая зависимость на уровне схем данных: Order знает о событиях Inventory, Inventory знает о Billing, Billing знает об Order. Для отслеживания всего пути сообщения обязательно передается единый сквозной `Correlation-ID` в метаданных каждого сообщения.

## Подводные камни

1. Циклические зависимости событий: если сервис А шлет событие сервису Б, а Б в ответ шлет событие сервису А, легко получить бесконечный шторм сообщений (message storm).
2. Сложность тестирования и дебага: невозможно понять текущий статус саги, посмотрев в одно место — приходится собирать распределенные логи из нескольких систем.

## На собеседовании

Вопрос: Когда следует выбирать Choreography вместо Orchestration?
Ответ: Хореография идеальна для простых процессов (2–4 участника), где поток строго линеен и маловероятны сложные ветвления и многоступенчатые компенсации. Как только количество шагов превышает 5–6 или возникают параллельные ветви и компенсации с ожиданием таймеров, хореография превращается в неуправляемый спагетти-код, и следует переходить на оркестрацию.
