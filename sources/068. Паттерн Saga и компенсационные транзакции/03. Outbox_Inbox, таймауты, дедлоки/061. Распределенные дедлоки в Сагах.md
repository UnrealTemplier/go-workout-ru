# Распределенные дедлоки в Сагах (Distributed Deadlocks) и Resource Ordering

## Условие

61. **[Высокая сложность — Saga с Deadlocks]**: Две саги пытаются зарезервировать один и тот же товар одновременно. Реализуй блокировку ресурса (через Redis `SETNX` или `SELECT FOR UPDATE` в БД), чтобы вторая сага ждала или падала с ошибкой, требуя ретрая.

### Исходная формулировка

**[Высокая сложность — Saga с Deadlocks]**: Две саги пытаются зарезервировать один и тот же товар одновременно. Реализуй блокировку ресурса (через Redis `SETNX` или `SELECT FOR UPDATE` в БД), чтобы вторая сага ждала или падала с ошибкой, требуя ретрая.

## Теория

Когда множество параллельных Саг конкурируют за одни и те же разделяемые ресурсы, возникает угроза классического **Распределенного взаимного блокирования (Distributed Deadlock)**.

Сценарий взаимной блокировки:
- **Сага 1**: Покупает набор (Товар А + Товар Б).
  - Шаг 1: Заблокировала Товар А на Складе 1.
  - Шаг 2: Пытается заблокировать Товар Б на Складе 2 (ждет освобождения).
- **Сага 2**: Покупает набор (Товар Б + Товар А).
  - Шаг 1: Заблокировала Товар Б на Складе 2.
  - Шаг 2: Пытается заблокировать Товар А на Складе 1 (ждет освобождения).

Обе саги взаимно блокируют друг друга навсегда!

Решение проблемы — фундаментальный алгоритмический паттерн **Global Resource Ordering (Канонический порядок ресурсов)**:
Перед началом блокировки ресурсов сага **ОБЯЗАНА отсортировать идентификаторы ресурсов** в строгом алфавитном или числовом порядке:
$$\text{Sort}([\text{SKU-B}, \text{SKU-A}]) \rightarrow [\text{SKU-A}, \text{SKU-B}]$$
Если ВСЕ саги всегда захватывают ресурсы строго по возрастанию ключа (\(A \rightarrow B\)), возникновение цикла блокировок математически невозможно!

## Решение по шагам

1. Смоделируйте захват ресурсов двумя сагами.
2. Реализуйте алгоритм сортировки идентификаторов ресурсов перед захватом.
3. Продемонстрируйте устранение риска взаимной блокировки.
4. Добавьте таймаут ожидания лока (Lock Acquisition Timeout) в качестве второго эшелона защиты.
5. Протестируйте конкурентный захват ресурсов.

## Код решения

**`deadlock_prevention.go`**

```go
package main

import (
	"fmt"
	"sort"
	"sync"
	"time"
)

type ResourceManager struct {
	mu    sync.Mutex
	locks map[string]string // resourceID -> sagaID
}

func NewResourceManager() *ResourceManager {
	return &ResourceManager{locks: make(map[string]string)}
}

// AcquireResourcesOrdered захватывает ресурсы строго в каноническом (отсортированном) порядке!
func (m *ResourceManager) AcquireResourcesOrdered(sagaID string, items []string) bool {
	// 1. Сортировка ресурсов по возрастанию ключа — УСТРАНЕНИЕ ДЕДЛОКА!
	sortedItems := make([]string, len(items))
	copy(sortedItems, items)
	sort.Strings(sortedItems)

	fmt.Printf("[Saga %s] Канонический порядок захвата: %v\n", sagaID, sortedItems)

	m.mu.Lock()
	defer m.mu.Unlock()

	// Проверяем доступность всех ресурсов
	for _, item := range sortedItems {
		if owner, locked := m.locks[item]; locked && owner != sagaID {
			fmt.Printf("[Saga %s] Конфликт! Ресурс %s уже занят сагой %s\n", sagaID, item, owner)
			return false
		}
	}

	// Захватываем
	for _, item := range sortedItems {
		m.locks[item] = sagaID
	}
	fmt.Printf("[Saga %s] Все ресурсы успешно заблокированы!\n", sagaID)
	return true
}

func main() {
	mgr := NewResourceManager()

	// Сага 1 хочет заблокировать [SKU-Z, SKU-A]
	// Сага 2 хочет заблокировать [SKU-A, SKU-Z]
	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		_ = mgr.AcquireResourcesOrdered("SAGA-1", []string{"SKU-Z", "SKU-A"})
	}()

	go func() {
		defer wg.Done()
		time.Sleep(10 * time.Millisecond)
		_ = mgr.AcquireResourcesOrdered("SAGA-2", []string{"SKU-A", "SKU-Z"})
	}()

	wg.Wait()
	fmt.Println("\nОбе саги завершили попытки захвата. Дедлок исключен благодаря канонической сортировке!")
}
```

ℹ️ Устранение распределенных дедлоков через канонический порядок сортировки ресурсов

## Под капотом

В теории операционных систем (Dijkstra's Resource Hierarchy Solution) для возникновения Deadlock необходимы 4 условия Коффмана (Coffman conditions): взаимное исключение, удержание и ожидание, отсутствие принудительного отчуждения, и **циклическое ожидание**. Сортировка ресурсов гарантирует ацикличность графа ожидания (DAG), математически разрушая 4-е условие Коффмана.

## Подводные камни

1. **Захват ресурсов по мере поступления**: Блокировать товар А в 10:00, а товар Б в 10:05 — верный путь к дедлоку. Все ресурсы заказа должны определяться и лочиться пакетно.
2. **Отсутствие таймаута на лок**: Если сервер зависнет, удерживая лок, без TTL ресурс будет заблокирован навсегда.

## На собеседовании

В банках и биржах (Мосбиржа, Тинькофф): 'Два пользователя одновременно переводят деньги друг другу: User1 -> User2 (100 руб) и User2 -> User1 (500 руб). Как избежать взаимной блокировки строк в БД?' Ответ: В транзакции блокировать счета (`SELECT FOR UPDATE`) строго в порядке возрастания их идентификаторов: `first = min(id1, id2); second = max(id1, id2)`. Блокировать сначала `first`, затем `second`. Дедлок невозможен.
