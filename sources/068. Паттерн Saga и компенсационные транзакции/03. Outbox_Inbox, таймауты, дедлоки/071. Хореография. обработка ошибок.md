# Хореография: обработка ошибок и компенсирующие события (Compensating Flow)

## Условие

71. **Хореография (Компенсация)**: В упр. 821 захардкодь нехватку товара на Складе. `Inventory` должен отправить событие `InventoryFailed`.
    * `Billing` должен поймать его и вернуть деньги (компенсирующая транзакция).
    * `Order` должен поймать его и изменить статус на `CANCELLED`. Реализуй этот флоу возврата.

### Исходная формулировка

**Хореография (Компенсация)**: В упр. 821 захардкодь нехватку товара на Складе. `Inventory` должен отправить событие `InventoryFailed`.
* `Billing` должен поймать его и вернуть деньги (компенсирующая транзакция).
* `Order` должен поймать его и изменить статус на `CANCELLED`. Реализуй этот флоу возврата.

## Теория

При сбое на одном из этапов децентрализованной саги участник, обнаруживший невозможность продолжения операции, публикует событие сбоя (Failure Event, например `InventoryFailedEvent`). Все предшествующие участники, уже выполнившие прямые действия, обязаны подписаться на это событие и запустить свои компенсирующие транзакции (Compensating Transactions). В отличие от оркестратора, знающего порядок выполнения, в хореографии каждый сервис должен самостоятельно знать, какие именно события ошибок требуют от него отката.

## Решение по шагам

1. Создайте структуру события сбоя `InventoryFailedEvent` с причиной ошибки.
2. На складе сэмулируйте ошибку остатка и опубликуйте `InventoryFailedEvent`.
3. В сервисе `BillingService` добавьте подписку на `InventoryFailedEvent` с вызовом функции возврата средств.
4. В сервисе `OrderService` добавьте подписку на `InventoryFailedEvent` с переводом статуса в `CANCELLED`.
5. Запустите флоу и убедитесь, что деньги возвращены, а заказ отменен.

## Код решения

**`choreography_compensation.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type EventBus struct {
	mu          sync.RWMutex
	subscribers map[string][]func(payload interface{})
}

func NewEventBus() *EventBus {
	return &EventBus{subscribers: make(map[string][]func(payload interface{}))}
}

func (b *EventBus) Subscribe(topic string, handler func(payload interface{})) {
	b.mu.Lock()
	defer b.mu.Unlock()
	b.subscribers[topic] = append(b.subscribers[topic], handler)
}

func (b *EventBus) Publish(topic string, payload interface{}) {
	b.mu.RLock()
	defer b.mu.RUnlock()
	for _, h := range b.subscribers[topic] {
		go h(payload)
	}
}

type OrderCreatedEvent struct {
	OrderID string
	Amount  float64
}

type PaymentProcessedEvent struct {
	OrderID string
	Amount  float64
}

type InventoryFailedEvent struct {
	OrderID string
	Reason  string
}

func main() {
	bus := NewEventBus()
	var wg sync.WaitGroup
	wg.Add(2) // Ожидаем компенсацию от Billing и отмену в Order

	// 1. Order Service
	bus.Subscribe("InventoryFailed", func(payload interface{}) {
		evt := payload.(InventoryFailedEvent)
		fmt.Printf("[OrderService] Received InventoryFailed for %s (reason: %s) -> Status: CANCELLED\n", evt.OrderID, evt.Reason)
		wg.Done()
	})

	// 2. Billing Service: подписка на прямое событие и на откат
	bus.Subscribe("OrderCreated", func(payload interface{}) {
		evt := payload.(OrderCreatedEvent)
		fmt.Printf("[BillingService] Debited $%.2f for Order %s\n", evt.Amount, evt.OrderID)
		bus.Publish("PaymentProcessed", PaymentProcessedEvent{OrderID: evt.OrderID, Amount: evt.Amount})
	})

	bus.Subscribe("InventoryFailed", func(payload interface{}) {
		evt := payload.(InventoryFailedEvent)
		fmt.Printf("[BillingService COMPENSATION] Refunding payment for Order %s due to inventory failure\n", evt.OrderID)
		wg.Done()
	})

	// 3. Inventory Service: нехватка товара
	bus.Subscribe("PaymentProcessed", func(payload interface{}) {
		evt := payload.(PaymentProcessedEvent)
		fmt.Printf("[InventoryService] Checking stock for Order %s: OUT OF STOCK!\n", evt.OrderID)
		bus.Publish("InventoryFailed", InventoryFailedEvent{
			OrderID: evt.OrderID,
			Reason:  "Item out of stock in warehouse",
		})
	})

	// Инициация
	orderID := "ord-fail-999"
	fmt.Printf("[Client] Creating Order %s...\n", orderID)
	bus.Publish("OrderCreated", OrderCreatedEvent{OrderID: orderID, Amount: 499.00})

	wg.Wait()
	fmt.Println("[Saga] Choreographed compensation successfully executed.")
}
```

## Под капотом

В хореографии компенсация не может быть отменена, если компенсирующее событие потеряно. Поэтому все события сбоев обязаны доставляться с гарантией At-Least-Once. Если сервис Billing упадет в момент обработки `InventoryFailed`, после перезапуска он должен перечитать событие из топика и выполнить возврат. Идемпотентность достигается проверкой: `IF payment.status == 'REFUNDED' THEN RETURN OK`.

## Подводные камни

1. Несинхронный приход компенсирующего события раньше прямого: из-за задержек в сети `InventoryFailed` может прийти в Billing раньше, чем завершится списание. Billing должен уметь обработать такую инверсию (сохранить маркер отмены заранее).
2. Рассинхронизация семантики отката: если один из трех сервисов забыл подписаться на событие сбоя, система останется в несогласованном состоянии без каких-либо алертов.

## На собеседовании

Вопрос: Что произойдет в хореографии, если компенсирующая транзакция в Billing Service упадет с 500 Internal Error?
Ответ: Компенсирующая транзакция в Саге по определению обязана завершиться успехом (semantic guarantee). Сервис должен повторять компенсацию с экспоненциальным backoff. Если ошибка фатальна (баг валидации), событие отправляется в Dead Letter Queue, а дежурному инженеру отправляется PagerDuty алерт для ручного проведения транзакции.
