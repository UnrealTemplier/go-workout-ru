# Event Replay: воспроизведение истории событий из Kafka для отладки и восстановления

## Условие

53. **Event replay**: Для debugging и recovery реализуйте возможность replay events из Kafka с определённого offset.

### Исходная формулировка

**Event replay**: Для debugging и recovery реализуйте возможность replay events из Kafka с определённого offset.

## Теория

Возможность повторного воспроизведения истории событий (**Event Replay**) — одно из сильнейших преимуществ событийных систем (Event-Driven Architecture) на базе Apache Kafka.

В отличие от традиционных очередей сообщений (RabbitMQ, SQS), где сообщение удаляется сразу после вызова `ACK`, в Kafka лог сообщений **персистентен и неизменяем**: сообщения хранятся в течение настроенного периода (Retention Period, например, 30 дней) или бесконечно (`compacted topics`).

Сценарии применения Event Replay в Сагах:
1. **Disaster Recovery (Аварийное восстановление)**: Если реплика базы данных оркестратора была повреждена, мы можем поднять пустую БД и сбросить смещение консьюмера на начало топика (`offset = 0` / `--from-beginning`). Сервис последовательно переиграет все события и восстановит 100% точное актуальное состояние всех саг.
2. **Post-Mortem Debugging (Анализ инцидентов)**: Разработчик может запустить тестовый экземпляр сервиса на локальной машине, направить его на сохраненный лог событий сбойного заказа и локально под отладчиком пошагово воспроизвести баг.

## Решение по шагам

1. Создайте структуру хранилища неизменяемого журнала событий.
2. Реализуйте сброс курсора чтения на начало лога.
3. Напишите функцию восстановления состояния сущности (Event Sourcing Projection).
4. Продемонстрируйте воспроизведение событий для отладки инцидента.
5. Убедитесь в полной идентичности восстановленного состояния.

## Код решения

**`event_replay.go`**

```go
package main

import (
	"fmt"
	"time"
)

type DomainEvent struct {
	Offset    int64
	EventType string
	Data      map[string]any
}

type KafkaTopicLog struct {
	events []DomainEvent
}

func (l *KafkaTopicLog) Append(eventType string, data map[string]any) {
	ev := DomainEvent{
		Offset:    int64(len(l.events)),
		EventType: eventType,
		Data:      data,
	}
	l.events = append(l.events, ev)
}

// Replay считывает события от начального до конечного оффсета
func (l *KafkaTopicLog) Replay(fromOffset int64, handler func(DomainEvent)) {
	fmt.Printf("\n[KAFKA REPLAY] Сброс оффсета на позицию %d. Старт воспроизведения...\n", fromOffset)
	for _, ev := range l.events {
		if ev.Offset >= fromOffset {
			handler(ev)
		}
	}
	fmt.Println("[KAFKA REPLAY] Воспроизведение успешно завершено.")
}

type OrderStateView struct {
	Status      string
	PaidAmount  float64
	WarehouseID string
}

func (v *OrderStateView) Apply(ev DomainEvent) {
	switch ev.EventType {
	case "OrderCreated":
		v.Status = "PENDING"
	case "PaymentReceived":
		v.PaidAmount = ev.Data["amount"].(float64)
	case "StockAllocated":
		v.WarehouseID = ev.Data["wh"].(string)
		v.Status = "CONFIRMED"
	}
	fmt.Printf("  [Event Applied @ offset=%d] %-16s -> Текущий статус: %s (Оплачено: %.2f, Склад: %s)\n",
		ev.Offset, ev.EventType, v.Status, v.PaidAmount, v.WarehouseID)
}

func main() {
	topic := &KafkaTopicLog{}

	// Запись реальных событий в топик
	topic.Append("OrderCreated", map[string]any{"order_id": "ORD-REPLAY-1"})
	topic.Append("PaymentReceived", map[string]any{"amount": 18900.0})
	topic.Append("StockAllocated", map[string]any{"wh": "SPB-NORTH"})

	// Восстановление состояния 'с нуля' через Replay
	restoredState := &OrderStateView{}
	topic.Replay(0, func(ev DomainEvent) {
		restoredState.Apply(ev)
	})

	fmt.Printf("\nИтоговое состояние после Replay: Статус=%s, Сумма=%.2f, Склад=%s\n",
		restoredState.Status, restoredState.PaidAmount, restoredState.WarehouseID)
}
```

ℹ️ Восстановление состояния саги через воспроизведение персистентного лога событий

## Под капотом

Сброс оффсета в Kafka выполняется утилитой `kafka-consumer-groups --reset-offsets --to-earliest --group my-saga-tracker --execute`. Консьюмер начинает вычитывать исторический лог со скоростью сотен тысяч сообщений в секунду, восстанавливая состояние в локальной RocksDB или оперативной памяти без нагрузки на продюсеров.

## Подводные камни

1. **Повторная отправка побочных эффектов (Side Effects Replay)**: Главная катастрофа при Replay — если сервис во время проигрывания истории начнет заново слать реальные HTTP-запросы в банк или отправлять SMS клиентам! Во время Replay внешние сайд-эффекты должны быть строго отключены (режим read-only projection).
2. **Неидемпотентная обработка событий**: Если функция применения событий не чистая (pure function), повторный прогон даст искаженное состояние.

## На собеседовании

В финтех-командах (Тинькофф, Stripe, Adyen): 'Как безопасно накатить новую версию проекции Саги без риска для продакшена?' Ответ: Паттерн Blue-Green Projections: поднимается новая версия консьюмера с новым `group_id`, вычитывает всю историю Kafka от оффсета 0 в новую таблицу БД. Когда она догоняет актуальный оффсет (Lag = 0), трафик чтения переключается на новую таблицу.
