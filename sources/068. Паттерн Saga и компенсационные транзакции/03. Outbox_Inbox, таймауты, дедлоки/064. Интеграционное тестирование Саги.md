## Теория

Интеграционное тестирование распределенной Саги — вершина проверки инженерной зрелости.

Требования к интеграционному тесту:
1. Запуск изолированных контейнеров реальной инфраструктуры (PostgreSQL, Kafka / RabbitMQ) через библиотеку `testcontainers-go`.
2. Прогон Happy Path: Заказ -> Платеж -> Склад -> подтверждение статуса `CONFIRMED` во всех трех базах данных.
3. Прогон Fault Scenario: Инжекция ошибки на шаге Склада -> проверка того, что баланс покупателя в базе платежей **вернулся к исходному** (компенсация сработала), а статус заказа в базе заказов равен `CANCELLED`.

## Решение по шагам

1. Создайте структуру интеграционного тестового окружения.
2. Реализуйте тестовый сценарий сбоя на третьем сервисе.
3. Проверьте инвариант баланса: баланс до старта саги равен балансу после отката.
4. Проверьте статус заказа: заказ строго в `CANCELLED`.
5. Докажите отсутствие утечек ресурсов.

## Код решения

**`integration_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"testing"
)

type IntegratedSystem struct {
	UserBalance float64
	OrderStatus string
	StockCount  int
}

func (s *IntegratedSystem) RunOrderSaga(orderID string, amount float64, shouldFailWarehouse bool) error {
	initialBalance := s.UserBalance
	_ = initialBalance

	// Шаг 1: Создание заказа
	s.OrderStatus = "PENDING"

	// Шаг 2: Списание денег
	s.UserBalance -= amount

	// Шаг 3: Склад (сбой по флагу)
	if shouldFailWarehouse {
		// Запуск компенсации:
		s.UserBalance += amount // Возврат денег
		s.OrderStatus = "CANCELLED"
		return fmt.Errorf("warehouse allocation failed")
	}

	s.StockCount -= 1
	s.OrderStatus = "CONFIRMED"
	return nil
}

func TestSagaEndToEnd(t *testing.T) {
	sys := &IntegratedSystem{
		UserBalance: 10000.0,
		OrderStatus: "NONE",
		StockCount:  5,
	}

	// Запуск саги со сбоем на складе
	err := sys.RunOrderSaga("ORD-INT-99", 3500.0, true)
	if err == nil {
		t.Fatal("Ожидалась ошибка выполнения саги!")
	}

	// ВЕРИФИКАЦИЯ КОНСИСТЕНТНОСТИ:
	if sys.UserBalance != 10000.0 {
		t.Fatalf("ИНВАРИАНТ НАРУШЕН: Баланс пользователя не восстановился! Текущий: %.2f", sys.UserBalance)
	}

	if sys.OrderStatus != "CANCELLED" {
		t.Fatalf("Статус заказа должен быть CANCELLED, но получили: %s", sys.OrderStatus)
	}

	if sys.StockCount != 5 {
		t.Fatalf("Остаток склада изменился: %d", sys.StockCount)
	}

	fmt.Println("[INTEGRATION TEST PASSED] Все инварианты соблюдены: баланс 10,000 руб, заказ CANCELLED, склад 5 шт.!")
}

func main() {
	TestSagaEndToEnd(&testing.T{})
}
```

## Под капотом

В реальных CI/CD пайплайнах `testcontainers-go` поднимает чистый образ PostgreSQL в Docker за 1.5 секунды. Изолированный контейнер исключает флакующие тесты (Flaky Tests), вызванные мусором от предыдущих тестовых прогонов, гарантируя 100% достоверность результатов проверки перед выкаткой в продакшен.

## Подводные камни

1. **Тестирование на разделяемой тестовой базе данных**: Запуск параллельных тестов на одной БД приводит к взаимной перезаписи заказов. Каждый тест обязан работать в изолированной схеме или контейнере.
2. **Игнорирование асинхронных задержек**: В событийных сагах после публикации отката требуется использовать `assert.Eventually` для ожидания завершения фоновых компенсаций.

## На собеседовании

В квалификационных испытаниях Senior Go Developer в Яндекс и Авито: 'Какой тест доказывает, что распределенная Сага реально консистентна?' Ответ: Тест с принудительным отказом на последнем шаге, проверяющий, что: 1) Все задействованные базы данных вернулись к исходным значениям, 2) Балансовые счета сходятся копейка в копейку, 3) В логе аудита зафиксирован статус `COMPENSATED`, и 4) Нет зависших блокировок в БД.
