# Saga versioning: версионирование сценариев и поддержка in-flight транзакций

## Условие

68. **Saga versioning**: При изменении flow Saga (добавление нового шага) поддерживайте старые версии для in-flight Sagas.

### Исходная формулировка

**Saga versioning**: При изменении flow Saga (добавление нового шага) поддерживайте старые версии для in-flight Sagas.

## Теория

В долгоживущих распределенных сагах (от нескольких секунд до дней, например, при одобрении ипотеки или согласовании контракта) бизнес-логика шагов неизбежно меняется. Релиз новой версии микросервиса не должен ломать транзакции, находящиеся в процессе исполнения (in-flight sagas). Если оркестратор обновился и ожидает 4 шага вместо 3, а в БД лежит запись от старого сценария, попытка десериализации или выполнение неизвестной компенсации приведет к критическому сбою. Версионирование сценариев саг (Saga Workflow Versioning) реализуется через явное сохранение `WorkflowVersion` в записи саги и фабрику шагов, выбирающую соответствующий pipeline для каждой версии.

## Решение по шагам

1. Объявите константы версий саги (`VersionV1 = 1`, `VersionV2 = 2`).
2. Создайте реестр `SagaRegistry`, связывающий версию саги со списком ее шагов.
3. Определите структуру `OrderSagaInstance` с полем `Version`.
4. Реализуйте метод оркестратора, диспетчеризирующий выполнение в соответствии с версией инстанса.
5. Продемонстрируйте параллельную обработку старой саги (v1) и новой саги (v2 с шагом антифрода).

## Код решения

**`saga_versioning.go`**

```go
package main

import (
	"context"
	"fmt"
)

type Step struct {
	Name string
	Run  func(ctx context.Context, id string) error
}

type VersionedPipeline struct {
	Version int
	Steps   []Step
}

type SagaRegistry struct {
	pipelines map[int]VersionedPipeline
}

func NewSagaRegistry() *SagaRegistry {
	return &SagaRegistry{pipelines: make(map[int]VersionedPipeline)}
}

func (r *SagaRegistry) Register(p VersionedPipeline) {
	r.pipelines[p.Version] = p
}

func (r *SagaRegistry) Get(version int) (VersionedPipeline, bool) {
	p, ok := r.pipelines[version]
	return p, ok
}

type SagaExecution struct {
	ID          string
	Version     int
	CurrentStep int
}

func ExecuteSaga(ctx context.Context, reg *SagaRegistry, exec *SagaExecution) error {
	pipeline, ok := reg.Get(exec.Version)
	if !ok {
		return fmt.Errorf("unknown saga version: %d for saga %s", exec.Version, exec.ID)
	}

	fmt.Printf("[Engine] Running Saga %s (Schema V%d) from step %d...\n", exec.ID, exec.Version, exec.CurrentStep)
	for i := exec.CurrentStep; i < len(pipeline.Steps); i++ {
		step := pipeline.Steps[i]
		fmt.Printf(" -> [V%d] Step %d: %s\n", exec.Version, i, step.Name)
		if err := step.Run(ctx, exec.ID); err != nil {
			return err
		}
		exec.CurrentStep = i + 1
	}
	fmt.Printf("[Engine] Saga %s (V%d) completed successfully!\n", exec.ID, exec.Version)
	return nil
}

func main() {
	reg := NewSagaRegistry()

	// Версия 1: Оплата -> Доставка
	reg.Register(VersionedPipeline{
		Version: 1,
		Steps: []Step{
			{Name: "Payment", Run: func(ctx context.Context, id string) error { return nil }},
			{Name: "Delivery", Run: func(ctx context.Context, id string) error { return nil }},
		},
	})

	// Версия 2: Антифрод -> Оплата -> Склад -> Доставка
	reg.Register(VersionedPipeline{
		Version: 2,
		Steps: []Step{
			{Name: "AntifraudCheck", Run: func(ctx context.Context, id string) error { return nil }},
			{Name: "Payment", Run: func(ctx context.Context, id string) error { return nil }},
			{Name: "WarehouseReserve", Run: func(ctx context.Context, id string) error { return nil }},
			{Name: "Delivery", Run: func(ctx context.Context, id string) error { return nil }},
		},
	})

	ctx := context.Background()

	// In-flight сага старой версии, начатая до релиза V2
	oldInFlight := &SagaExecution{ID: "order-v1-99", Version: 1, CurrentStep: 1}
	_ = ExecuteSaga(ctx, reg, oldInFlight)

	// Новая сага версии 2
	newOrder := &SagaExecution{ID: "order-v2-100", Version: 2, CurrentStep: 0}
	_ = ExecuteSaga(ctx, reg, newOrder)
}
```

ℹ️ Поддержка версий саг для обеспечения обратной совместимости in-flight транзакций

[Engine] Saga order-v1-99 (V1) completed successfully!

## Под капотом

При изменении контракта саги создается новый идентификатор схемы workflow. В Temporal для этого используется API `workflow.GetVersion(ctx, changeID, minSupported, maxSupported)`. Temporal сохраняет маркер версии в историю воркфлоу, гарантируя, что при реплее старый инстанс пойдет по ветке `minSupported`, а новые запуски выберут `maxSupported`. В кастомных СУБД-оркестраторах в таблицу саг добавляется колонка `schema_version`, которая маршрутизирует исполнение к соответствующему набору хэндлеров.

## Подводные камни

1. Удаление кода старой версии до завершения всех in-flight саг: если деплой удалит обработчики V1, старые саги зависнут с ошибкой неизвестного шага.
2. Изменение сигнатуры компенсаций: если при переходе на V2 изменить структуру полезной нагрузки для отката шага V1, компенсация упадет с ошибкой unmarshal.

## На собеседовании

Вопрос: Как безопасно провести миграцию бизнес-процесса саги, если в системе тысячи зависших саг старой версии?
Ответ: Применяется техника Blue-Green Workflow Deployment и версионирование схем. Код оркестратора поддерживает обе версии (V1 и V2). Новые саги стартуют исключительно с `version = 2`, а воркеры продолжают обслуживать `version = 1` до полного истощения очереди in-flight транзакций. Метрика Prometheus `saga_active_instances{version='1'}` отслеживается до нуля, после чего легаси-код объявляется deprecated и удаляется.
