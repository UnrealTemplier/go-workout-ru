# Inbox + Idempotency: таблица Inbox как механизм дедупликации через Unique Constraint

## Условие

76. **Inbox + Idempotency**: Inbox table сама по себе является idempotency mechanism (через unique constraint на message_id).

### Исходная формулировка

**Inbox + Idempotency**: Inbox table сама по себе является idempotency mechanism (через unique constraint на message_id).

## Теория

Таблица Inbox в реляционной базе данных — это не просто буфер входящих сообщений, а надежный механизм идемпотентности, опирающийся на свойства ACID реляционной СУБД. За счет объявления первичного ключа `message_id VARCHAR PRIMARY KEY`, попытка повторно вставить то же самое сообщение приводит к мгновенной ошибке нарушения уникальности (Unique Key Violation). При правильной реализации консьюмер выполняет вставку в Inbox в той же транзакции, что и изменение доменных таблиц. Если транзакция закоммичена — сообщение гарантированно обработано. Если транзакция откатилась — записи в Inbox тоже нет, что позволяет безопасно повторить обработку при следующем ретрае брокера.

## Решение по шагам

1. Создайте SQL-схему для таблицы `inbox_messages` с первичным ключом `message_id`.
2. Реализуйте метод транзакционной обработки `ProcessInboxMessage`.
3. В рамках транзакции выполните `INSERT INTO inbox_messages ...`.
4. При ошибке дубликата ключа перехватите ошибку и сделайте безопасный `Ack` брокеру без повторного списания.
5. Продемонстрируйте обработку дублирующихся сообщений.

## Код решения

**`inbox_unique_constraint.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
)

var ErrDuplicateMessage = errors.New("unique constraint violation: message_id already exists")

// MockDatabase эмулирует реляционную базу данных с ограничением UNIQUE
type MockDatabase struct {
	mu           sync.Mutex
	inboxTable   map[string]bool
	accountFunds map[string]float64
}

func NewMockDatabase() *MockDatabase {
	return &MockDatabase{
		inboxTable:   make(map[string]bool),
		accountFunds: map[string]float64{"acc-1": 1000.0},
	}
}

// TransactionalExecution выполняет атомарно проверку Inbox и изменение баланса
func (db *MockDatabase) TransactionalExecution(ctx context.Context, msgID, accountID string, amount float64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// 1. Проверка UNIQUE CONSTRAINT на message_id
	if db.inboxTable[msgID] {
		return ErrDuplicateMessage
	}

	// 2. Бизнес-логика: списание средств
	currentBalance := db.accountFunds[accountID]
	if currentBalance < amount {
		return fmt.Errorf("insufficient funds on account %s", accountID)
	}
	db.accountFunds[accountID] = currentBalance - amount

	// 3. Фиксация в Inbox
	db.inboxTable[msgID] = true

	fmt.Printf("[DB TX COMMIT] Success: Debited $%.2f from %s. Recorded msg %s in Inbox. New balance: $%.2f\n",
		amount, accountID, msgID, db.accountFunds[accountID])
	return nil
}

// MessageConsumer обрабатывает сообщения из очереди
type MessageConsumer struct {
	db *MockDatabase
}

func (c *MessageConsumer) Consume(ctx context.Context, msgID, accountID string, amount float64) {
	fmt.Printf("[Consumer] Received message %s for processing...\n", msgID)
	err := c.db.TransactionalExecution(ctx, msgID, accountID, amount)
	if err != nil {
		if errors.Is(err, ErrDuplicateMessage) {
			// Дубликат: это норма в At-Least-Once. Делаем Ack брокеру, бизнес-логику не повторяем.
			fmt.Printf("[Consumer ACK] Message %s was already processed. Committing offset (ACK) to Kafka.\n\n", msgID)
			return
		}
		fmt.Printf("[Consumer ERROR] Failed to process message: %v\n\n", err)
		return
	}
	fmt.Printf("[Consumer ACK] Message %s processed successfully. Committing offset (ACK).\n\n", msgID)
}

func main() {
	db := NewMockDatabase()
	consumer := &MessageConsumer{db: db}
	ctx := context.Background()

	msgID := "kafka-offset-10293-uuid"

	// Первичная обработка сообщения
	consumer.Consume(ctx, msgID, "acc-1", 150.0)

	// Сетевой дубликат от брокера сообщений
	consumer.Consume(ctx, msgID, "acc-1", 150.0)

	// Еще один дубликат
	consumer.Consume(ctx, msgID, "acc-1", 150.0)
}
```

ℹ️ Использование Inbox с ограничением уникальности как гаранта идемпотентности

[DB TX COMMIT] Success: Debited $150.00 from acc-1. Recorded msg kafka-offset-10293-uuid in Inbox. New balance: $850.00

## Под капотом

В PostgreSQL транзакция выглядит так:
`BEGIN;`
`INSERT INTO inbox (message_id, created_at) VALUES ($1, NOW());`
`UPDATE balances SET amount = amount - $2 WHERE user_id = $3;`
`COMMIT;`
Если строка с `message_id` уже существует, Postgres мгновенно выбрасывает ошибку `23505 (unique_violation)`. Транзакция откатывается полностью, баланс не меняется, а приложение получает прозрачный сигнал дублирования.

## Подводные камни

1. Разделение транзакций: выполнение `INSERT INTO inbox` в одной транзакции, а обновления баланса в другой разрушает гарантию идемпотентности. Если сервис упадет между ними, сообщение застрянет.
2. Очистка старых записей Inbox: удалять записи из Inbox можно только по истечении срока гарантированного хранения сообщений в брокере (Message Retention Period, например, 7 дней).

## На собеседовании

Вопрос: Что будет, если консьюмер выполнит Ack в Kafka, но запись в Inbox упадет из-за переполнения диска БД?
Ответ: Консьюмер не должен коммитить оффсет в Kafka до успешного коммита транзакции БД! Если БД упала, транзакция откатывается, консьюмер возвращает Nack или падает сам. Kafka переназначит партицию другому воркеру, который повторит попытку после восстановления СУБД.
