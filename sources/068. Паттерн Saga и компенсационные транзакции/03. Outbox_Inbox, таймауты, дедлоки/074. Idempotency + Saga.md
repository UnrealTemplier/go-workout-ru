# Idempotency + Saga: обеспечение идемпотентности шагов через ключи идемпотентности

## Условие

74. **Idempotency + Saga**: Каждый шаг Saga идемпотентен через idempotency keys. Retry шага не вызывает side effects дважды.

### Исходная формулировка

**Idempotency + Saga**: Каждый шаг Saga идемпотентен через idempotency keys. Retry шага не вызывает side effects дважды.

## Теория

Идемпотентность — фундаментальное требование к шагам Саги. Поскольку сетевые сбои неизбежны, оркестратор обязан повторять отправку команды при отсутствии ответа (таймаут). Участник не может отличить первичный запрос от повторного без уникального ключа — Idempotency Key. В качестве ключа обычно выступает комбинация `{saga_id}:{step_name}` или сгенерированный UUID. Сервис-участник сохраняет результат первой успешной обработки под этим ключом. Повторный запрос с тем же ключом не выполняет финансовые или складские операции повторно, а мгновенно возвращает ранее сохраненный результат (Cached Response).

## Решение по шагам

1. Создайте структуру `IdempotentStore` для хранения статуса и ответа запроса по ключу.
2. Реализуйте метод `ExecuteIdempotentStep`, принимающий `idempotencyKey`.
3. При первом вызове выполните бизнес-действие (списание средств) и сохраните статус `SUCCESS` и результат.
4. При повторном вызове с тем же ключом верните закешированный результат без изменения баланса.
5. Продемонстрируйте повторные вызовы шага и подтвердите неизменность баланса аккаунта.

## Код решения

**`idempotent_step.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type StepResponse struct {
	Success bool
	Message string
}

type IdempotencyManager struct {
	mu      sync.Mutex
	records map[string]StepResponse
	balance float64
}

func NewIdempotencyManager(initialBalance float64) *IdempotencyManager {
	return &IdempotencyManager{
		records: make(map[string]StepResponse),
		balance: initialBalance,
	}
}

func (m *IdempotencyManager) ExecutePaymentStep(ctx context.Context, key string, amount float64) (StepResponse, bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	// Проверяем, исполнялся ли уже шаг с таким Idempotency Key
	if resp, exists := m.records[key]; exists {
		fmt.Printf("[Idempotency Cache HIT] Key %s already executed. Returning saved response. Balance unchanged: $%.2f\n", key, m.balance)
		return resp, true
	}

	// Бизнес-логика списания
	if m.balance < amount {
		resp := StepResponse{Success: false, Message: "insufficient funds"}
		m.records[key] = resp
		return resp, false
	}

	m.balance -= amount
	resp := StepResponse{Success: true, Message: fmt.Sprintf("charged $%.2f", amount)}
	m.records[key] = resp
	fmt.Printf("[Action Executed] First time execution for key %s. Debited $%.2f. New Balance: $%.2f\n", key, amount, m.balance)
	return resp, false
}

func main() {
	mgr := NewIdempotencyManager(1000.0)
	ctx := context.Background()

	idempotencyKey := "saga-123:step-charge-card"

	// Попытка 1: Успешное выполнение
	fmt.Println("Attempt 1 (Original request):")
	resp1, cached1 := mgr.ExecutePaymentStep(ctx, idempotencyKey, 300.0)
	fmt.Printf("Result 1: Success=%v, Cached=%v, Msg=%s\n\n", resp1.Success, cached1, resp1.Message)

	// Попытка 2: Сетевой ретрай оркестратора из-за таймаута
	fmt.Println("Attempt 2 (Network retry with same key):")
	resp2, cached2 := mgr.ExecutePaymentStep(ctx, idempotencyKey, 300.0)
	fmt.Printf("Result 2: Success=%v, Cached=%v, Msg=%s\n\n", resp2.Success, cached2, resp2.Message)

	// Попытка 3: Еще один ретрай
	fmt.Println("Attempt 3 (Another retry):")
	resp3, cached3 := mgr.ExecutePaymentStep(ctx, idempotencyKey, 300.0)
	fmt.Printf("Result 3: Success=%v, Cached=%v, Msg=%s\n", resp3.Success, cached3, resp3.Message)
}
```

## Под капотом

Для реализации идемпотентности в распределенных сервисах используется паттерн Insert-If-Absent в Redis (`SET key payload NX EX 86400`) или уникальный индекс в PostgreSQL (`CREATE UNIQUE INDEX ON idempotency_keys(key)`). Если параллельно приходят два одинаковых запроса (Race Condition), первый успешно захватывает ключ, а второй ждет окончания обработки первым или получает `409 Conflict / Request in progress`.

## Подводные камни

1. Хранение незавершенных результатов: если упасть посреди обработки запроса, не сохранив ошибку, повторный запрос может зависнуть на проверке 'запрос уже в процессе'. Нужен таймаут блокировки ключа.
2. Переиспользование ключа для разных данных: если клиент отправит тот же idempotency key с другой суммой или другим получателем, сервер должен вернуть ошибку `422 Unprocessable Entity: Idempotency Key payload mismatch`.

## На собеседовании

Вопрос: Как правильно формировать Idempotency Key в оркестраторе саги?
Ответ: Ключ должен быть детерминированным и отражать контекст шага. Канонический формат: `hash(saga_id + '_' + step_name + '_' + step_iteration)`. Наличие `step_iteration` требуется, если в рамках саги разрешен контролируемый повтор логики шага с новыми параметрами.
