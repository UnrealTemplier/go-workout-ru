### Исходная формулировка

## Теория

Оркестрация (Orchestration) концентрирует всю логику выполнения бизнес-процесса в одном компоненте — Saga Orchestrator. Оркестратор представляет собой Конечный Автомат (FSM), который пошагово отправляет команды участникам (Point-to-Point вызовы по gRPC/HTTP или персональные очереди команд) и получает синхронные или асинхронные ответы. Участники ничего не знают о существовании других сервисов и о самом процессе Саги — они просто выполняют пришедшую команду (`DebitCard`, `ReserveItems`). Это обеспечивает прозрачную трассировку, простой аудит и легкое добавление новых шагов.

## Решение по шагам

1. Опишите интерфейсы удаленных сервисов: `BillingClient` и `InventoryClient`.
2. Создайте FSM оркестратора с состояниями: `Pending`, `BillingReserved`, `InventoryReserved`, `Compensating`, `Finished`.
3. Реализуйте метод оркестрации, последовательно вызывающий клиентов.
4. В случае сбоя инвентаря переведите FSM в `Compensating` и вызовите `Refund` у BillingClient.
5. Продемонстрируйте исполнение сценария и логирование смены состояний FSM.

## Код решения

**`fsm_orchestrator.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

type FSMState string

const (
	StateNew             FSMState = "NEW"
	StatePaymentReserved FSMState = "PAYMENT_RESERVED"
	StateStockReserved   FSMState = "STOCK_RESERVED"
	StateCompensating    FSMState = "COMPENSATING"
	StateFailed          FSMState = "FAILED"
	StateCompleted       FSMState = "COMPLETED"
)

type BillingService interface {
	Debit(ctx context.Context, orderID string, amount float64) error
	Refund(ctx context.Context, orderID string) error
}

type InventoryService interface {
	Reserve(ctx context.Context, orderID string) error
	Release(ctx context.Context, orderID string) error
}

type MockBilling struct{}

func (b *MockBilling) Debit(ctx context.Context, orderID string, amount float64) error {
	fmt.Printf("[Remote Billing] Debit $%.2f for order %s -> OK\n", amount, orderID)
	return nil
}

func (b *MockBilling) Refund(ctx context.Context, orderID string) error {
	fmt.Printf("[Remote Billing] Refund for order %s -> OK\n", orderID)
	return nil
}

type MockInventory struct {
	fail bool
}

func (i *MockInventory) Reserve(ctx context.Context, orderID string) error {
	if i.fail {
		fmt.Printf("[Remote Inventory] Reserve for order %s -> ERROR: No inventory\n", orderID)
		return errors.New("insufficient inventory")
	}
	fmt.Printf("[Remote Inventory] Reserve for order %s -> OK\n", orderID)
	return nil
}

func (i *MockInventory) Release(ctx context.Context, orderID string) error {
	fmt.Printf("[Remote Inventory] Release for order %s -> OK\n", orderID)
	return nil
}

type SagaOrchestrator struct {
	billing   BillingService
	inventory InventoryService
}

func NewSagaOrchestrator(b BillingService, inv InventoryService) *SagaOrchestrator {
	return &SagaOrchestrator{billing: b, inventory: inv}
}

func (o *SagaOrchestrator) Run(ctx context.Context, orderID string, amount float64) error {
	state := StateNew
	fmt.Printf("[Orchestrator] Starting Saga for %s. State: %s\n", orderID, state)

	// Шаг 1: Оплата
	if err := o.billing.Debit(ctx, orderID, amount); err != nil {
		state = StateFailed
		fmt.Printf("[Orchestrator] Payment failed. Final State: %s\n", state)
		return err
	}
	state = StatePaymentReserved
	fmt.Printf("[Orchestrator] State transition -> %s\n", state)

	// Шаг 2: Склад
	if err := o.inventory.Reserve(ctx, orderID); err != nil {
		fmt.Printf("[Orchestrator] Inventory failed. Starting compensation!\n")
		state = StateCompensating

		_ = o.billing.Refund(ctx, orderID)

		state = StateFailed
		fmt.Printf("[Orchestrator] Final State: %s\n", state)
		return err
	}
	state = StateStockReserved
	fmt.Printf("[Orchestrator] State transition -> %s\n", state)

	state = StateCompleted
	fmt.Printf("[Orchestrator] Final State: %s (Success)\n", state)
	return nil
}

func main() {
	ctx := context.Background()

	billing := &MockBilling{}
	inventory := &MockInventory{fail: true} // Сэмулируем ошибку инвентаря

	orchestrator := NewSagaOrchestrator(billing, inventory)
	_ = orchestrator.Run(ctx, "order-abc-123", 250.00)
}
```

ℹ️ Централизованный FSM оркестратор с явным управлением микросервисами

[Remote Billing] Debit $250.00 for order order-abc-123 -> OK
[Orchestrator] State transition -> PAYMENT_RESERVED
[Remote Inventory] Reserve for order order-abc-123 -> ERROR: No inventory
[Orchestrator] Inventory failed. Starting compensation!
[Remote Billing] Refund for order order-abc-123 -> OK
[Orchestrator] Final State: FAILED

## Под капотом

Оркестратор изолирует бизнес-правила внутри себя. Сервисы-участники превращаются в чистые RPC-воркеры. Для устойчивости FSM переходы состояний должны атомарно сохраняться в БД оркестратора (`UPDATE saga SET state = 'PAYMENT_RESERVED' WHERE id = ?`). Это исключает повторные некорректные переходы при сбоях и позволяет оркестратору безопасно перезапускаться.

## Подводные камни

1. Превращение оркестратора в God Object: перенос всей логики доменов внутрь оркестратора лишает сервисы самостоятельности. Оркестратор должен только управлять последовательностью, а не рассчитывать налоги или скидки.
2. Синхронные таймауты: если оркестратор держит HTTP-соединение с клиентом во время долгих синхронных вызовов участников, клиент отвалится по таймауту 504 Gateway Timeout. Сага должна стартовать асинхронно с возвратом `202 Accepted`.

## На собеседовании

Вопрос: В чем ключевое преимущество оркестрации над хореографией с точки зрения Observability?
Ответ: В оркестраторе состояние саги, время выполнения каждого шага и причины сбоев локализованы в одной таблице БД или дашборде оркестратора. Можно мгновенно узнать, сколько саг сейчас в статусе `COMPENSATING`, на каком шаге они зависли, и визуализировать весь граф исполнения, тогда как в хореографии для этого требуется сложная распределенная трассировка Jaeger/OpenTelemetry по спанам.
