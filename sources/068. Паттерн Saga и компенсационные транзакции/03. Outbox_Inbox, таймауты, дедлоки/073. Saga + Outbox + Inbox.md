# Saga + Outbox + Inbox: сквозная гарантия доставки (End-to-End Reliability)

## Условие

73. **Saga + Outbox + Inbox:**
    * Orchestrator использует Outbox для publishing commands
    * Each service uses Inbox для consuming commands
    * Each service uses Outbox для publishing events
    * Orchestrator uses Inbox для consuming events
    Это даёт end-to-end reliability.

### Исходная формулировка

**Saga + Outbox + Inbox:**
* Orchestrator использует Outbox для publishing commands
* Each service uses Inbox для consuming commands
* Each service uses Outbox для publishing events
* Orchestrator uses Inbox для consuming events
Это даёт end-to-end reliability.

## Теория

Комбинация Transactional Outbox и Transactional Inbox устраняет все точки потери сообщений и дублирования на сетевом стыке между оркестратором и участниками. Оркестратор не делает ненадежных прямых сетевых вызовов: он сохраняет состояние саги и команду участнику в таблицу `outbox_commands` в одной транзакции СУБД. Релей доставляет команду в брокер. Сервис-участник принимает команду и вставляет ее в таблицу `inbox_messages` (с уникальным ключом `message_id`). Затем участник выполняет локальную транзакцию, помечает inbox-сообщение как обработанное и пишет событие-ответ в свою таблицу `outbox_events`. Оркестратор потребляет событие через свой Inbox. Это гарантирует семантику Exactly-Once Processing на уровне прикладной логики.

## Решение по шагам

1. Определите схемы таблиц `outbox` и `inbox` с уникальными ограничениями.
2. Реализуйте функцию оркестратора, отправляющую команду через запись в Outbox.
3. Реализуйте консьюмер участника: дедупликация через Inbox -> выполнение бизнес-логики -> запись ответа в Outbox.
4. Реализуйте консьюмер оркестратора: дедупликация через Inbox -> продвижение FSM саги.
5. Продемонстрируйте сценарий с повторной доставкой команды и подтвердите отсутствие дублирования.

## Код решения

**`end_to_end_reliability.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type OutboxRecord struct {
	ID        string
	SagaID    string
	Command   string
	Payload   string
	Published bool
}

type InboxRecord struct {
	MessageID string
	Processed bool
}

// Orchestrator Node
type OrchestratorNode struct {
	mu     sync.Mutex
	outbox []OutboxRecord
	inbox  map[string]bool
}

func (o *OrchestratorNode) SendCommand(sagaID, cmd, payload string) string {
	o.mu.Lock()
	defer o.mu.Unlock()
	msgID := fmt.Sprintf("cmd-%s-%s", sagaID, cmd)
	rec := OutboxRecord{
		ID:      msgID,
		SagaID:  sagaID,
		Command: cmd,
		Payload: payload,
	}
	o.outbox = append(o.outbox, rec)
	fmt.Printf("[Orchestrator] Saved command to Outbox: %s (MsgID: %s)\n", cmd, msgID)
	return msgID
}

// Participant Service
type ParticipantService struct {
	name   string
	mu     sync.Mutex
	inbox  map[string]bool
	outbox []OutboxRecord
}

func NewParticipant(name string) *ParticipantService {
	return &ParticipantService{
		name:  name,
		inbox: make(map[string]bool),
	}
}

func (p *ParticipantService) HandleCommand(msgID, sagaID, cmd, payload string) {
	p.mu.Lock()
	defer p.mu.Unlock()

	// 1. Проверка Inbox на дубликат (Idempotency check)
	if p.inbox[msgID] {
		fmt.Printf("[%s INBOX] Duplicate detected for message %s. Skipping execution!\n", p.name, msgID)
		return
	}

	// 2. Выполнение локальной бизнес-транзакции
	fmt.Printf("[%s] Executing command %s for Saga %s with payload %s\n", p.name, cmd, sagaID, payload)

	// 3. Сохранение в Inbox и Outbox атомарно
	p.inbox[msgID] = true
	replyEvent := OutboxRecord{
		ID:      fmt.Sprintf("evt-%s-success", msgID),
		SagaID:  sagaID,
		Command: cmd + "Success",
		Payload: "{\"status\":\"ok\"}",
	}
	p.outbox = append(p.outbox, replyEvent)
	fmt.Printf("[%s] State saved: Inbox marked processed, response event saved to Outbox\n", p.name)
}

func main() {
	orch := &OrchestratorNode{inbox: make(map[string]bool)}
	billing := NewParticipant("BillingService")

	// Оркестратор отправляет команду списания
	msgID := orch.SendCommand("saga-999", "ReservePayment", "{\"amount\": 1500}")

	// Брокер доставляет команду в BillingService
	fmt.Println("\n--- First Delivery Attempt ---")
	billing.HandleCommand(msgID, "saga-999", "ReservePayment", "{\"amount\": 1500}")

	// Сеть дублирует сообщение (Retry брокера)
	fmt.Println("\n--- Network Duplicate Delivery ---")
	billing.HandleCommand(msgID, "saga-999", "ReservePayment", "{\"amount\": 1500}")
}
```

ℹ️ Сквозная надежность: дедупликация через Inbox и транзакционный Outbox

## Под капотом

В реляционной СУБД таблица `inbox` имеет первичный ключ `message_id VARCHAR PRIMARY KEY`. При попытке вставки дубликата транзакция падает с ошибкой `UniqueConstraintViolation` (Postgres код `23505`), что позволяет консьюмеру мгновенно распознать дубликат и отправить брокеру `Ack`, не выполняя бизнес-логику. Запись в `inbox` и `outbox` в одной транзакции с бизнес-таблицей гарантирует ACID-консистентность.

## Подводные камни

1. Неочищенный Inbox: если не настроить TTL или партиционирование таблицы `inbox_messages`, она вырастет до сотен миллионов строк, замедляя вставки и создание индексов B-Tree.
2. Падение до записи в Inbox: если консьюмер сначала выполнит внешний HTTP-вызов, а потом попытается записать в Inbox, при сбое сети повторный запрос выполнит внешний вызов дважды. Все сторонние вызовы должны передавать Idempotency Key.

## На собеседовании

Вопрос: Почему связка Outbox + Inbox считается эталоном надежности для распределенных транзакций?
Ответ: Потому что она преобразует ненадежную сетевую семантику брокеров (At-Least-Once Delivery) в надежную прикладную семантику (Exactly-Once Execution) без тяжелых блокировок 2PC. Outbox исключает потерю исходящих сообщений, а Inbox исключает повторное исполнение входящих сообщений.
