## Теория

Промышленная разработка Саг в компаниях уровня Uber, Netflix, Stripe и Яндекса базируется на платформе **Temporal**.

Архитектурные преимущества Temporal SDK:
1. **Durable Code**: Разработчик пишет обычный последовательный Go-код. Temporal гарантирует выполнение каждой строки даже при физическом взрыве дата-центра (перезапуск на резервном ЦОД).
2. **Автоматический Replay**: При сбоях Temporal восстанавливает стек переменных воркфлоу, проигрывая историю сохраненных событий.
3. **Бесконечные ретраи активностей**: Каждая активность ретраится с сохранением состояния.
4. **Визуализация в UI**: В веб-консоли Temporal виден точный граф выполнения каждого заказа, входные/выходные параметры активностей и стек ошибок.

## Код решения

**`temporal_industrial.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

// Контракт активностей микросервисов
type Activities struct{}

func (a *Activities) CreateOrder(ctx context.Context, orderID string) error {
	fmt.Printf("[Activity] CreateOrder: Заказ %s зафиксирован в PostgreSQL\n", orderID)
	return nil
}

func (a *Activities) CancelOrder(ctx context.Context, orderID string) error {
	fmt.Printf("[Activity Compensation] CancelOrder: Заказ %s аннулирован\n", orderID)
	return nil
}

func (a *Activities) HoldPayment(ctx context.Context, orderID string, amount float64) error {
	fmt.Printf("[Activity] HoldPayment: %.2f руб. захолдировано в банке\n", amount)
	return nil
}

func (a *Activities) ReleasePayment(ctx context.Context, orderID string) error {
	fmt.Printf("[Activity Compensation] ReleasePayment: Холд средств снят\n", orderID)
	return nil
}

func (a *Activities) ReserveStock(ctx context.Context, sku string) error {
	return fmt.Errorf("SKU '%s' закончился на складе", sku) // Имитация сбоя!
}

// OrderSagaWorkflow — эталонный воркфлоу в стиле Temporal
func RunIndustrialSaga(orderID string, amount float64, sku string) error {
	act := &Activities{}
	ctx := context.Background()

	// Стек зарегистрированных компенсаций
	var compensations []func(context.Context) error

	// Шаг 1: Создание заказа
	if err := act.CreateOrder(ctx, orderID); err != nil {
		return err
	}
	compensations = append(compensations, func(c context.Context) error {
		return act.CancelOrder(c, orderID)
	})

	// Шаг 2: Холдирование оплаты
	if err := act.HoldPayment(ctx, orderID, amount); err != nil {
		runRollback(compensations)
		return err
	}
	compensations = append(compensations, func(c context.Context) error {
		return act.ReleasePayment(c, orderID)
	})

	// Шаг 3: Склад (Сбой!)
	if err := act.ReserveStock(ctx, sku); err != nil {
		fmt.Printf("\n[Workflow Error] Шаг ReserveStock завершился сбоем: %v\n", err)
		runRollback(compensations)
		return err
	}

	fmt.Println("Воркфлоу успешно завершен!")
	return nil
}

func runRollback(compensations []func(context.Context) error) {
	fmt.Println(">>> Старт выполнения компенсирующих активностей Temporal (LIFO) <<<")
	for i := len(compensations) - 1; i >= 0; i-- {
		_ = compensations[i](context.Background())
	}
}

func main() {
	_ = RunIndustrialSaga("ORD-TEMPORAL-2026", 45000.0, "PLAYSTATION-PRO")
}
```

## Под капотом

В реальном Temporal Go SDK для компенсаций используется встроенный пакет `go.temporal.io/sdk/workflow`:
```go
var saga workflow.Saga
saga.AddCompensation(act.CancelOrder, orderID)
saga.AddCompensation(act.ReleasePayment, orderID)
if err != nil {
    return saga.Compensate(ctx)
}
```
Метод `saga.Compensate(ctx)` автоматически исполняет все зарегистрированные компенсации в строго обратном порядке параллельно или последовательно.

## Подводные камни

1. **Использование глобальных переменных в Workflow**: Приводит к повреждению данных при параллельном выполнении тысяч воркфлоу на одном Worker процессе.
2. **Горутины внутри Workflow без `workflow.Go`**: Использование обычного ключевого слова `go` внутри воркфлоу ломает детерминизм Temporal. Используйте только `workflow.Go(ctx, ...)`.

## На собеседовании

В компаниях Tier-1 (Uber, Datadog, Сбер): 'Как Temporal гарантирует надежность при падении сервера во время выполнения воркфлоу?' Ответ: Сервер Temporal сохраняет историю событий в PostgreSQL/Cassandra. Когда Worker поднимается заново, он запрашивает историю событий и детерминированно восстанавливает локальное состояние воркфлоу (State Replay), пропуская уже выполненные активности.
