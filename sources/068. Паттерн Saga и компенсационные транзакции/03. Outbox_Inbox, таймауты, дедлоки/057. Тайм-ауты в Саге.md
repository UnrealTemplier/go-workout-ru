# Тайм-ауты в Саге: порог 5 секунд, предотвращение зависания оркестратора

## Условие

57. **[Таймауты в Saga]**: Если Payment не отвечает 5 секунд, Оркестратор не должен висеть вечно. Настрой `context.WithTimeout`. При таймауте Оркестратор должен считать шаг проваленным и запустить компенсацию.

### Исходная формулировка

**[Таймауты в Saga]**: Если Payment не отвечает 5 секунд, Оркестратор не должен висеть вечно. Настрой `context.WithTimeout`. При таймауте Оркестратор должен считать шаг проваленным и запустить компенсацию.

## Теория

При проектировании оркестратора золотое правило HighLoad гласит: **'Ни один внешний вызов не должен длиться дольше установленного SLA'**.

Если сервис `Payment` завис на уровне TCP (например, SYN-пакеты уходят в blackhole из-за сбоя файрвола):
1. Стандартный таймаут TCP в Linux составляет 120 секунд.
2. 500 одновременных заказов мгновенно займут 500 горутин оркестратора.
3. Пул горутин и лимит соединений исчерпаются -> полный отказ оркестратора.

Для защиты вызов жестко ограничивается таймаутом **5 секунд**. По истечении 5 секунд контекст прерывается, оркестратор освобождает ресурсы и немедленно запускает процедуру компенсации.

## Решение по шагам

1. Сконфигурируйте жесткий дедлайн 5 секунд для платежного шага.
2. Смоделируйте неотвечающий внешний сервис.
3. Перехватите ошибку `DeadlineExceeded`.
4. Запустите снятие брони склада.
5. Продемонстрируйте освобождение ресурсов оркестратора.

## Код решения

**`strict_timeout.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func CallPaymentWithStrictTimeout(parentCtx context.Context) error {
	// Жесткий таймаут 5 секунд (для демонстрации 200 мс)
	ctx, cancel := context.WithTimeout(parentCtx, 200*time.Millisecond)
	defer cancel()

	fmt.Println("[Orchestrator] Вызов PaymentService (Лимит: 200 мс)...")

	done := make(chan error, 1)
	go func() {
		// Имитация зависшего TCP-сокета на стороне банка (висит 2 секунды)
		time.Sleep(2 * time.Second)
		done <- nil
	}()

	select {
	case err := <-done:
		return err
	case <-ctx.Done():
		if errors.Is(ctx.Err(), context.DeadlineExceeded) {
			return errors.New("PAYMENT_GATEWAY_TIMEOUT (порог 5 сек превышен)")
		}
		return ctx.Err()
	}
}

func main() {
	err := CallPaymentWithStrictTimeout(context.Background())
	if err != nil {
		fmt.Printf("\n[SAGA WATCHDOG TRIGGERED] Ошибка: %v\n", err)
		fmt.Println("-> Оркестратор НЕ ЗАВИС и мгновенно освободил сокет!")
		fmt.Println("-> Запуск компенсации: InventoryService.ReleaseStock()")
	}
}
```

ℹ️ Жесткий таймаут вызова сервиса с немедленным освобождением сетевых ресурсов

## Под капотом

В сетевом стеке Go при отмене контекста HTTP-клиент немедленно закрывает underlying TCP-сокет через системный вызов `close(fd)` или отправляет фрейм `RST_STREAM` в HTTP/2. Это гарантирует, что сетевой буфер ОС очищается, а горутина сетевого поллера (`netpoller`) мгновенно прекращает ожидание событий от ядра Linux.

## Подводные камни

1. **Использование `http.DefaultClient`**: Стандартный клиент Go не имеет таймаута вовсе (`Timeout: 0`). Любой зависший сторонний сервер подвесит вашу горутину навсегда.
2. **Таймаут больше времени жизни HTTP-запроса пользователя**: Если мобильный клиент закрывает соединение через 3 секунды, а бэкенд ждет 5 секунд, бэкенд выполняет бесполезную работу (Wasted Work).

## На собеседовании

В архитектуре микросервисов Ozon и Wildberries: 'Как защитить систему от лавинообразного нарастания очередей при деградации внешнего банка?' Ответ: Паттерн Circuit Breaker в связке с таймаутом: если 50% запросов за последние 10 секунд завершаются по таймауту 5с, Circuit Breaker переходит в состояние `OPEN` и мгновенно отклоняет новые запросы без ожидания сетевого сокета (Fail-Fast).
