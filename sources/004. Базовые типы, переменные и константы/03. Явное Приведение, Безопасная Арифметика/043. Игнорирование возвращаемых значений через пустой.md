# Игнорирование возвращаемых значений через пустой идентификатор _

## Условие

**Отбрасывание значений (Blank Identifier)**: Вызови функцию, возвращающую два значения (например, из упр. 21 `fmt.Scan`), но проигнорируй ошибку с помощью `_`.

## Теория

Пустой идентификатор `_`:
- Принимает любое значение, не выделяя под него память;
- Позволяет удовлетворить требование компилятора по обработке всех возвращаемых значений функции.

## Решение по шагам

1. Создаем функцию `fetchData() (int, error)`.
2. Игнорируем ошибку через `val, _ := fetchData()`.

## Код решения

**`main.go`**

```go
package main

import "fmt"

func parseCoordinate() (int, int, error) {
	return 100, 200, nil
}

func main() {
	// Нам нужны только координаты X и Y, ошибку отбрасываем:
	x, y, _ := parseCoordinate()

	fmt.Printf("Координаты: X = %d, Y = %d\n", x, y)
}
```

ℹ️ Игнорирование значений через _

**`Терминал`**

```bash
go run main.go
# Координаты: X = 100, Y = 200
```

ℹ️ Вывод

## Под капотом

Компилятор оптимизирует регистр возврата: значение из регистра не переносится в память стека.

## Подводные камни

- Игнорирование критических ошибок в продакшене (`f, _ := os.Open("file.txt")`): если файл не существует, `f` будет `nil`, и последующий вызов `f.Read()` приведет к панике.

## На собеседовании

**Вопрос с собеседования:** «В каких случаях допустимо игнорировать `error` через `_` в промышленном коде?»
**Ответ:** 1) При записи в `bytes.Buffer` (метод `Write` буфера в памяти никогда не возвращает ошибку); 2) В `defer file.Close()` для файлов, открытых только на чтение; 3) При закрытии тела HTTP-ответа `defer resp.Body.Close()`.
