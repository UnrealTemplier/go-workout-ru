# Наблюдение за лидерством (Election.Observe) и разрешение конфликтов

## Условие

Используйте `Election.Observe` для отслеживания текущего лидера. При обнаружении конфликта (два узла считают себя лидерами) узел с меньшей revision добровольно уступает.

### Исходная формулировка

**Наблюдение за лидерством и разрешение конфликтов.**: Используйте `Election.Observe` для получения имени текущего лидера. При потере соединения или истечении сессии другой узел вступает в кампанию. Реализуйте логику graceful shutdown с отзывом лидерства.

## Теория

Канал `Election.Observe(ctx)` в etcd возвращает стрим изменений лидера (`<-chan mvccpb.KeyValue`).
Это позволяет узлам не только знать текущего хозяина ресурса, но и разрешать скрытые коллизии:
Если локальный узел считает себя лидером с ревизией \(R_{local}\), но канал `Observe` сообщает о существовании другого активного лидера с ревизией \(R_{remote}\):
- Правило разрешения конфликта в etcd: узел с **меньшей** `CreateRevision` является легитимным первоочередным лидером.
- Если узел обнаруживает, что \(R_{remote} < R_{local}\), его собственная заявка была создана позже, и он обязан немедленно сложить полномочия (`Yield/Resign`).
Такая процедура гарантирует сходимость к единственному истинному лидеру даже при параллельных транзакциях в условиях нестабильной сети.

## Решение по шагам

1. Создаем структуру LeaderObservation с данными идентификатора и ревизии.
2. Реализуем менеджер ConflictResolver с методом HandleObservation.
3. Если текущий узел считает себя лидером, но полученная ревизия меньше собственной, вызывается StepDown().
4. Проверяем сценарий корректного отступления более молодого узла перед старшим.
5. Выводим результаты проверки.

## Код решения

**`election_observe_resolver.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type LeaderRecord struct {
	LeaderID       string
	CreateRevision int64
}

type NodeCandidate struct {
	mu           sync.Mutex
	nodeID       string
	isLeader     bool
	myRevision   int64
	cancelLeader context.CancelFunc
}

func NewNodeCandidate(id string) *NodeCandidate {
	return &NodeCandidate{
		nodeID: id,
	}
}

func (n *NodeCandidate) ClaimLeadership(rev int64, cancel context.CancelFunc) {
	n.mu.Lock()
	defer n.mu.Unlock()
	n.isLeader = true
	n.myRevision = rev
	n.cancelLeader = cancel
	fmt.Printf("[%s] Claimed leadership at revision %d\n", n.nodeID, rev)
}

func (n *NodeCandidate) HandleObservation(record LeaderRecord) {
	n.mu.Lock()
	defer n.mu.Unlock()

	if !n.isLeader {
		fmt.Printf("[%s] Observed current leader: %s (rev: %d)\n", n.nodeID, record.LeaderID, record.CreateRevision)
		return
	}

	// Если мы считаем себя лидером, но пришла информация о другом лидере
	if record.LeaderID != n.nodeID {
		fmt.Printf("[%s] CONFLICT DETECTED! Another leader claims role: %s (rev: %d vs mine: %d)\n",
			n.nodeID, record.LeaderID, record.CreateRevision, n.myRevision)

		// etcd инвариант: побеждает наименьшая CreateRevision
		if record.CreateRevision < n.myRevision {
			fmt.Printf("[%s] Remote leader is older (lower revision). Yielding leadership!\n", n.nodeID)
			n.isLeader = false
			if n.cancelLeader != nil {
				n.cancelLeader()
			}
		} else {
			fmt.Printf("[%s] My revision is lower/equal. Maintaining leadership.\n", n.nodeID)
		}
	}
}

func main() {
	nodeYounger := NewNodeCandidate("pod-younger")

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	// Молодой узел ошибочно решил, что он лидер с ревизией 500
	nodeYounger.ClaimLeadership(500, func() {
		fmt.Println("[pod-younger] Action: Stopped leader routines.")
	})

	// Через Observe приходит известие о старшем лидере с ревизией 250
	olderRecord := LeaderRecord{
		LeaderID:       "pod-senior-0",
		CreateRevision: 250,
	}

	nodeYounger.HandleObservation(olderRecord)

	nodeYounger.mu.Lock()
	fmt.Printf("\nVerification: Is younger node still leader? %v\n", nodeYounger.isLeader)
	nodeYounger.mu.Unlock()
}
```

## Под капотом

`Election.Observe(ctx)` внутри использует `clientv3.NewWatcher` с фильтром по префиксу. Он получает все события `PUT` и `DELETE` ключей выборов. При получении каждого события etcd клиент обновляет внутреннее поле `e.leaderRev`. Если клиент видит, что ключ с минимальной ревизией изменился, он шлет новое значение в канал наружу. Это позволяет фоловерам обновлять адреса для маршрутизации трафика без поллинга.

## Подводные камни

Блокировка на чтении канала `Observe`: если буфер канала `Observe` переполняется (медленный потребитель), горутина etcd-клиента блокируется или начинает отбрасывать события. Обработку событий из канала `Observe` следует выносить в отдельную легковесную горутину без тяжелых синхронных вызовов.

## На собеседовании

В: Почему в распределенных системах сравнивают именно `CreateRevision`, а не `ModRevision` ключа?
О: `CreateRevision` неизменна на протяжении всего времени существования ключа от момента создания до удаления. `ModRevision` инкрементируется при каждом обновлении значения (KeepAlive / Touch). Сравнение по `CreateRevision` гарантирует честный FIFO порядок регистрации претендентов без влияния последующих модификаций.
