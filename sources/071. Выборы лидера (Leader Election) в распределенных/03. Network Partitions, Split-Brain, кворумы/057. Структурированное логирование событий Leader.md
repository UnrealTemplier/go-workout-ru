# Структурированное логирование событий Leader Election

## Условие

Логируйте каждое election event: `Election started`, `Elected as leader (lease=%d)`, `Lease renewed (remaining=%v)`, `Stepped down (reason=%s)`, `New leader detected (identity=%s)`. Используйте structured logging (`log/slog`).

### Исходная формулировка

**Leader election observability**: Логируйте каждое election event: `Election started`, `Leader elected: instance-2`, `Leader resigned`, `Failover triggered`.

## Теория

При расследовании инцидентов в распределенных системах (Post-Mortem / RCA) текстовые неструктурированные логи не позволяют быстро восстановить хронологию событий с точностью до миллисекунды.
Использование стандартного пакета Go `log/slog` (начиная с Go 1.21+) позволяет привязать к каждому событию выборов структурированные атрибуты:
- `event`: тип события (`election_started`, `leader_elected`, `lease_renewed`, `stepped_down`, `leader_changed`).
- `node_id`: идентификатор текущего пода.
- `lease_id`: шестнадцатеричный или числовой дескриптор аренды.
- `duration_ms`: задержка операции обновления.
- `reason`: причина сложения полномочий (`context_cancelled`, `lease_expired`, `manual_resignation`, `partition_suspected`).
Такой подход позволяет в Logstash/Vector/Fluentbit мгновенно отфильтровать аномалии и визуализировать граф переходов лидерства в Grafana Loki или Elasticsearch.

## Решение по шагам

1. Настраиваем `slog.NewJSONHandler` для генерации машиночитаемых логов в формате JSON.
2. Создаем структуру ElectionEventLogger с типизированными методами логирования каждого этапа жизненного цикла.
3. Добавляем контекстные атрибуты (node_id, namespace).
4. Проверяем корректный вывод всех 5 обязательных событий.
5. Проверяем, что в логах присутствуют все ключевые поля.

## Код решения

**`election_slog.go`**

```go
package main

import (
	"context"
	"log/slog"
	"os"
	"time"
)

type ElectionLogger struct {
	logger *slog.Logger
	nodeID string
}

func NewElectionLogger(nodeID string) *ElectionLogger {
	handler := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
		Level: slog.LevelInfo,
	})
	return &ElectionLogger{
		logger: slog.New(handler).With("node_id", nodeID, "component", "leader_elector"),
		nodeID: nodeID,
	}
}

func (l *ElectionLogger) LogElectionStarted(ctx context.Context, prefix string) {
	l.logger.InfoContext(ctx, "Election campaign started",
		slog.String("event", "election_started"),
		slog.String("prefix", prefix),
	)
}

func (l *ElectionLogger) LogElected(ctx context.Context, leaseID int64, ttl time.Duration) {
	l.logger.InfoContext(ctx, "Node successfully elected as leader",
		slog.String("event", "leader_elected"),
		slog.Int64("lease_id", leaseID),
		slog.Duration("lease_ttl", ttl),
	)
}

func (l *ElectionLogger) LogLeaseRenewed(ctx context.Context, leaseID int64, remaining time.Duration, latency time.Duration) {
	l.logger.DebugContext(ctx, "Leader lease renewed successfully",
		slog.String("event", "lease_renewed"),
		slog.Int64("lease_id", leaseID),
		slog.Duration("remaining_ttl", remaining),
		slog.Duration("rtt_latency", latency),
	)
}

func (l *ElectionLogger) LogSteppedDown(ctx context.Context, reason string, duration time.Duration) {
	l.logger.WarnContext(ctx, "Node stepped down from leadership",
		slog.String("event", "stepped_down"),
		slog.String("reason", reason),
		slog.Duration("total_tenure", duration),
	)
}

func (l *ElectionLogger) LogNewLeaderDetected(ctx context.Context, identity string, revision int64) {
	l.logger.InfoContext(ctx, "Discovered active cluster leader",
		slog.String("event", "leader_changed"),
		slog.String("leader_identity", identity),
		slog.Int64("revision", revision),
	)
}

func main() {
	ctx := context.Background()
	elLog := NewElectionLogger("order-svc-pod-7b9f8")

	elLog.LogElectionStarted(ctx, "/elections/order-processor")
	time.Sleep(50 * time.Millisecond)

	leaseID := int64(0x3a889b412)
	elLog.LogElected(ctx, leaseID, 10*time.Second)

	elLog.LogLeaseRenewed(ctx, leaseID, 9200*time.Millisecond, 12*time.Millisecond)

	elLog.LogSteppedDown(ctx, "SIGTERM_graceful_shutdown", 45*time.Second)

	elLog.LogNewLeaderDetected(ctx, "order-svc-pod-2c1a4", 10482)
}
```

## Под капотом

`slog` оптимизирован по аллокациям: вызовы методов с `slog.Attr` и `With()` конструируют внутренние цепочки групп без лишнего выделения памяти на куче. В высоконагруженных сценариях частое обновление аренды (`lease_renewed`) регистрируется на уровне `slog.LevelDebug`. Если уровень логирования в проде установлен в `Info`, форматирование строк и работа с каналами вывода полностью подавляются на уровне проверки порога уровня в handler.

## Подводные камни

Логирование `LeaseRenewed` на уровне `INFO` при частоте heartbeat 1 раз в секунду. В кластере из 100 микросервисов это порождает 8.6 млн бесполезных log lines в сутки, перегружая Elastic/Loki. События продления аренды должны логироваться строго как `DEBUG`, а как `INFO`/`WARN` — только события смены состояния, задержки RTT выше нормы или пропуски тактов.

## На собеседовании

В: Как в BigTech системах коррелируют логи смены лидера с метриками Prometheus?
О: При регистрации событий смены лидера логируется единый атрибут `trace_id` или `election_epoch` (номер каденции). Этот же `epoch` передается в лейблах метрик Prometheus (`leader_election_epoch{epoch="42"}`). При расследовании инцидента инженер берет спайк на графике метрик и по `epoch` находит точную строчку лога с причиной сбоя.
