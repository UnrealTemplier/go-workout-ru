# Функции обратного вызова жизненного цикла: OnStartedLeading и OnStoppedLeading

## Условие

Реализуйте callbacks: `OnStartedLeading()`, `OnStoppedLeading()`, `OnNewLeader(identity string)`. Гарантируйте, что OnStoppedLeading вызывается ВСЕГДА, даже при панике внутри OnStartedLeading.

### Исходная формулировка

**Leader election callbacks**: Реализуйте callbacks: `OnStartedLeading()`, `OnStoppedLeading()`, `OnNewLeader()`.

## Теория

Паттерн жизненного цикла лидерства, принятый в Kubernetes (`client-go/tools/leaderelection`) и корпоративных распределенных фреймворках, строится вокруг трех базовых хуков:
1. `OnStartedLeading(ctx context.Context)`: вызывается строго после успешного завоевания лидерства. Контекст `ctx` сигнализирует об отмене полномочий.
2. `OnStoppedLeading()`: вызывается при потере лидерства (истечение аренды, сетевая ошибка, context cancelled, паника).
3. `OnNewLeader(identity string)`: уведомляет узел о том, кто в данный момент является актуальным лидером кластера.
Критическое требование надежности: хук `OnStoppedLeading()` обязан выполниться детерминированно, даже если в бизнес-логике `OnStartedLeading` произошла некорректная операция или паника (`panic`). В противном случае сервис останется в «полуживом» состоянии: фоновые горутины зависнут, блокировки не освободятся, а метрики будут ложно рапортовать об активном лидере.

## Решение по шагам

1. Создаем структуру LeaderCallbacks с полями функций OnStartedLeading, OnStoppedLeading, OnNewLeader.
2. Оборачиваем вызов OnStartedLeading в блок с `defer recover()`, перехватывающий паники.
3. Регистрируем вызов OnStoppedLeading в отложенном блоке `defer`, гарантируя выполнение при любом исходе.
4. Проверяем, что контекст лидерства отменяется до того, как начнет исполняться OnStoppedLeading.
5. Пишем тестовый сценарий с паникой и проверяем, что OnStoppedLeading был вызван ровно один раз.

## Код решения

**`election_callbacks.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type LeaderCallbacks struct {
	OnStartedLeading func(ctx context.Context)
	OnStoppedLeading func()
	OnNewLeader      func(identity string)
}

type ElectionRunner struct {
	nodeID    string
	callbacks LeaderCallbacks
	isLeading atomic.Bool
}

func NewElectionRunner(nodeID string, callbacks LeaderCallbacks) *ElectionRunner {
	return &ElectionRunner{
		nodeID:    nodeID,
		callbacks: callbacks,
	}
}

func (r *ElectionRunner) RunLeaderLifecycle(parent context.Context, duration time.Duration, triggerPanic bool) {
	ctx, cancel := context.WithCancel(parent)
	defer cancel()

	r.isLeading.Store(true)
	fmt.Printf("[%s] Elected leader! Invoking OnStartedLeading...\n", r.nodeID)

	// Гарантируем вызов OnStoppedLeading даже при панике
	defer func() {
		r.isLeading.Store(false)
		if p := recover(); p != nil {
			fmt.Printf("[%s] PANIC intercepted inside OnStartedLeading: %v\n", r.nodeID, p)
		}
		if r.callbacks.OnStoppedLeading != nil {
			fmt.Printf("[%s] Invoking OnStoppedLeading cleanup hook...\n", r.nodeID)
			r.callbacks.OnStoppedLeading()
		}
	}()

	if r.callbacks.OnStartedLeading != nil {
		done := make(chan struct{})
		go func() {
			defer close(done)
			defer func() {
				if p := recover(); p != nil {
					fmt.Printf("[%s] Background leading panic: %v\n", r.nodeID, p)
					cancel()
				}
			}()

			if triggerPanic {
				time.Sleep(300 * time.Millisecond)
				panic("unhandled nil pointer dereference in business logic")
			}

			// Имитация полезной работы
			select {
			case <-ctx.Done():
			case <-time.After(duration):
			}
		}()

		select {
		case <-ctx.Done():
		case <-done:
		}
	}
}

func main() {
	var stoppedCalled atomic.Bool
	var wg sync.WaitGroup

	callbacks := LeaderCallbacks{
		OnStartedLeading: func(ctx context.Context) {
			fmt.Println("[App] Starting background cron and transaction processors...")
		},
		OnStoppedLeading: func() {
			stoppedCalled.Store(true)
			fmt.Println("[App] Flushed pending buffers, closed leader TCP sockets.")
		},
		OnNewLeader: func(identity string) {
			fmt.Printf("[App] Discovered active leader: %s\n", identity)
		},
	}

	runner := NewElectionRunner("node-k8s-pod-1", callbacks)

	wg.Add(1)
	go func() {
		defer wg.Done()
		runner.RunLeaderLifecycle(context.Background(), 2*time.Second, true)
	}()

	wg.Wait()
	fmt.Printf("Was OnStoppedLeading called successfully after panic? %v\n", stoppedCalled.Load())
}
```

## Под капотом

В библиотеке `k8s.io/client-go/tools/leaderelection` функция `RunOrDie` запускает бесконечный цикл обновления Lease ресурса (или ConfigMap/Endpoint). Когда аренда продлевается, создается отдельный дочерний контекст `leaderCtx`, передаваемый в `OnStartedLeading`. Если обновление аренды терпит неудачу, вызывается `cancel()`, ожидается завершение горутин и следом синхронно выполняется `OnStoppedLeading()`. Дополнительно проверяется, что сервис может совершить `os.Exit(1)` (Fail-Fast), чтобы kubelet перезапустил сбойный под.

## Подводные камни

Если внутри `OnStoppedLeading` запускаются длительные блокирующие операции (например, синхронное закрытие сотен соединений без таймаута), процесс зависает. В этот момент другой инстанс уже перехватил лидерство и начал обрабатывать трафик. Решение — оборачивать cleanup логику в жесткий дедлайн через `context.WithTimeout` (не более 1-2 секунд).

## На собеседовании

В: Почему в Kubernetes принято завершать процесс (`os.Exit(1)`) при вызове `OnStoppedLeading`?
О: Семантика Crash-Only Software: распределенная система находится в неопределенном внутреннем состоянии после потери лидерства (возможны утечки горутин, подвисшие транзакции или десинхронизация кэша). Надежнее позволить поду аварийно завершиться, дав оркестратору (K8s) перезапустить чистый контейнер в состоянии Standby.
