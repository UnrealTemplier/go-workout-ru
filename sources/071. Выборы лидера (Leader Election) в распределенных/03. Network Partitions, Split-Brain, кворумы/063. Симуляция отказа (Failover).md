# Симуляция отказа (Failover) и Active-Passive воркер

## Условие

Напишите фоновую задачу (например, воркер, читающий очередь). Задача должна работать ТОЛЬКО на лидере. Запустите 2 инстанса. Убейте лидера (simulate crash). Покажите, что второй инстанс подхватывает задачу.

### Исходная формулировка

**Симуляция отказа (Failover) и Active-Passive воркер**: Напишите фоновую задачу (например, сборщик метрик), которая должна запускаться *строго* на одном узле кластера. Сэмулируйте распределенное окружение: запустите три экземпляра вашей программы на разных портах. Настройте пассивные узлы на наблюдение за ключом лидера (Watcher в etcd или регулярный опрос блокировки в Consul). Принудительно убейте процесс лидера (`SIGKILL`) и убедитесь, что один из пассивных узлов мгновенно обнаружил потерю аренды и объявил себя новым лидером, продолжив сбор метрик.

## Теория

Классическая задача отказоустойчивой обработки очередей (Kafka, RabbitMQ, SQS): если несколько воркеров читают одну и ту же партицию без партиционирования брокера, нарушается порядок сообщений.
Паттерн Active-Passive Worker гарантирует:
1. Только Active инстанс удерживает соединение с очередью и читает сообщения.
2. Passive инстанс находится в режиме горячего резерва (Hot Standby): он инициализировал подключения к БД и кэшам, но консьюмер сообщений остановлен.
3. При внезапном краше Active (симулируется отменой контекста / SIGKILL) блокировка в etcd сбрасывается.
4. Standby инстанс просыпается, запускает свой цикл консьюминга и продолжает обработку ровно с того места, где остановился упавший воркер.

## Решение по шагам

1. Создаем структуру QueueWorker с каналами управления стартом и остановкой.
2. Реализуем метод RunWorkerLoop(), выполняющий чтение задач только при флаге isLeader.
3. Моделируем работу узла A (Active) и узла B (Standby).
4. Убиваем узел A и передаем сигнал лидерства узлу B.
5. Убеждаемся, что узел B бесшовно подхватил обработку оставшихся сообщений.

## Код решения

**`failover_queue_worker.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type TaskItem struct {
	ID string
}

type ActivePassiveWorker struct {
	nodeID   string
	inbox    <-chan TaskItem
	isLeader bool
	mu       sync.Mutex
	stopChan chan struct{}
}

func NewActivePassiveWorker(nodeID string, inbox <-chan TaskItem) *ActivePassiveWorker {
	return &ActivePassiveWorker{
		nodeID:   nodeID,
		inbox:    inbox,
		stopChan: make(chan struct{}),
	}
}

func (w *ActivePassiveWorker) StartLeading(ctx context.Context) {
	w.mu.Lock()
	w.isLeader = true
	w.stopChan = make(chan struct{})
	w.mu.Unlock()

	fmt.Printf("[%s] PROMOTED TO LEADER: Starting message consumption...\n", w.nodeID)

	go func() {
		for {
			select {
			case <-ctx.Done():
				return
			case <-w.stopChan:
				fmt.Printf("[%s] STOPPED consuming messages.\n", w.nodeID)
				return
			case task, ok := <-w.inbox:
				if !ok {
					return
				}
				fmt.Printf("[%s] Processed task: %s\n", w.nodeID, task.ID)
				time.Sleep(100 * time.Millisecond)
			}
		}
	}()
}

func (w *ActivePassiveWorker) StopLeading() {
	w.mu.Lock()
	defer w.mu.Unlock()
	if !w.isLeader {
		return
	}
	w.isLeader = false
	close(w.stopChan)
}

func main() {
	taskQueue := make(chan TaskItem, 20)
	for i := 1; i <= 6; i++ {
		taskQueue <- TaskItem{ID: fmt.Sprintf("order-item-%03d", i)}
	}

	workerA := NewActivePassiveWorker("worker-instance-A", taskQueue)
	workerB := NewActivePassiveWorker("worker-instance-B", taskQueue)

	ctxA, cancelA := context.WithCancel(context.Background())
	ctxB, cancelB := context.WithCancel(context.Background())
	defer cancelB()

	// Инстанс A стартует как лидер
	workerA.StartLeading(ctxA)
	time.Sleep(250 * time.Millisecond)

	// Имитируем падение инстанса A (SIGKILL)
	fmt.Println("\n>>> SIMULATING CRASH OF WORKER A <<<")
	cancelA()
	workerA.StopLeading()

	// Инстанс B мгновенно перехватывает роль
	fmt.Println(">>> FAILOVER: Worker B takes over leadership <<<")
	workerB.StartLeading(ctxB)

	time.Sleep(400 * time.Millisecond)
	close(taskQueue)
	workerB.StopLeading()
}
```

## Под капотом

При смене лидера в Kafka-консьюмере важно не только остановить локальный цикл, но и корректно управлять смещением (Consumer Offset). Если упавший узел взял сообщение в обработку, но упал до коммита оффсета, новый лидер перечитает это сообщение. Поэтому бизнес-обработчик обязан быть идемпотентным (сохранять `processed_task_id` в таблице PostgreSQL с ограничением `PRIMARY KEY`).

## Подводные камни

Состояние гонки при получении сообщений: если старый воркер A ещё не завершил горутину обработки последнего сообщения, а воркер B уже начал читать следующее, они могут параллельно изменять одну и ту же сущность в БД. Необходима синхронизация сброса (Draining) перед передачей лидерства.

## На собеседовании

В: В чем преимущество модели Active-Passive по сравнению с моделью балансировки очередей (Consumer Groups)?
О: Consumer Groups распределяют партиции между несколькими активными инстансами. Однако если данные строго упорядочены глобально (Single FIFO stream) или обработчик требует монопольного владения внешним ресурсом (например, эксклюзивный доступ к оборудованию или шлюзу), схема Active-Passive является единственно возможной.
