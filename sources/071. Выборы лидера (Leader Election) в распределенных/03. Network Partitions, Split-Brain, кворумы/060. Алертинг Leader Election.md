# Алертинг Leader Election: Детекция Flapping и Split-Brain

## Условие

Настройте правила алертинга: (1) частые failovers (>3 за час) — признак нестабильности, (2) отсутствие лидера >15 сек — split-brain или deadlock, (3) множественные лидеры (sum(is_leader) > 1) — split-brain.

### Исходная формулировка

**Leader election alerting**: Алерт при:
* Частые failover (>3 за час) — признак нестабильности
* Нет leader > 2x TTL — quorum lost
* Leader tenure < 1 min — признак crash loop

## Теория

Мониторинг распределенного консенсуса должен генерировать алерты трех критических категорий:
1. `HighElectionChurn` (Flapping): если лидер сменяется чаще 3 раз за час, сервис находится в состоянии перманентной деградации (thrashing), сбрасывая кэши, перезапуская консьюмеры и создавая всплески latency.
2. `NoLeaderAlert`: если в кластере в течение \(T > 15\) секунд `sum(leader_election_is_leader) == 0`, система полностью парализована: фоновые задачи не исполняются, мутирующие API отдают 503.
3. `SplitBrainAlert`: если `sum(leader_election_is_leader) > 1`, нарушен фундаментальный инвариант распределенного исключения. Немедленно требуется изоляция сбойных узлов (Fencing / STONITH), иначе произойдет порча данных (Data Corruption).

## Решение по шагам

1. Создаем структуру AlertRuleEngine с правилами проверки агрегированных метрик.
2. Реализуем метод CheckHealth(), анализирующий текущее количество лидеров и частоту переходов.
3. Генерируем тестовые сценарии: нормальное состояние, потеря лидера, множественные лидеры, частый flapping.
4. Валидируем генерацию соответствующих алертов с правильными уровнями критичности (WARN, CRITICAL, EMERGENCY).
5. Проверяем детерминированность обнаружения аномалий.

## Код решения

**`election_alerter.go`**

```go
package main

import (
	"fmt"
	"time"
)

type Severity string

const (
	SeverityWarning   Severity = "WARNING"
	SeverityCritical  Severity = "CRITICAL"
	SeverityEmergency Severity = "EMERGENCY"
)

type Alert struct {
	Name        string
	Severity    Severity
	Description string
	TriggeredAt time.Time
}

type ClusterElectionSnapshot struct {
	ActiveLeadersCount int
	TransitionsLastHour int
	NoLeaderDuration    time.Duration
}

type ElectionAlertEngine struct {
	maxTransitionsPerHour int
	noLeaderThreshold     time.Duration
}

func NewElectionAlertEngine() *ElectionAlertEngine {
	return &ElectionAlertEngine{
		maxTransitionsPerHour: 3,
		noLeaderThreshold:     15 * time.Second,
	}
}

func (e *ElectionAlertEngine) Evaluate(s ClusterElectionSnapshot) []Alert {
	alerts := make([]Alert, 0)
	now := time.Now()

	// Правило 1: Split-Brain (Множественные лидеры)
	if s.ActiveLeadersCount > 1 {
		alerts = append(alerts, Alert{
			Name:        "ClusterSplitBrainDetected",
			Severity:    SeverityEmergency,
			Description: fmt.Sprintf("CRITICAL: Detected %d concurrent leaders! Immediate data corruption risk.", s.ActiveLeadersCount),
			TriggeredAt: now,
		})
	}

	// Правило 2: Отсутствие лидера (No Leader)
	if s.ActiveLeadersCount == 0 && s.NoLeaderDuration > e.noLeaderThreshold {
		alerts = append(alerts, Alert{
			Name:        "ClusterLeaderMissing",
			Severity:    SeverityCritical,
			Description: fmt.Sprintf("Cluster has no leader for %v (threshold=%v). Mutating traffic blocked.", s.NoLeaderDuration, e.noLeaderThreshold),
			TriggeredAt: now,
		})
	}

	// Правило 3: Flapping (Частая смена лидера)
	if s.TransitionsLastHour > e.maxTransitionsPerHour {
		alerts = append(alerts, Alert{
			Name:        "LeaderFlappingUnstable",
			Severity:    SeverityWarning,
			Description: fmt.Sprintf("Frequent failovers detected: %d transitions in last hour (limit=%d). Possible CPU throttling or network jitter.", s.TransitionsLastHour, e.maxTransitionsPerHour),
			TriggeredAt: now,
		})
	}

	return alerts
}

func main() {
	engine := NewElectionAlertEngine()

	// Сценарий 1: Нормальное состояние (1 лидер, 1 смена за час)
	snapNormal := ClusterElectionSnapshot{
		ActiveLeadersCount: 1,
		TransitionsLastHour: 1,
	}
	fmt.Printf("Scenario 1 (Normal): Alerts triggered: %d\n", len(engine.Evaluate(snapNormal)))

	// Сценарий 2: Split-Brain (2 лидера)
	snapSplitBrain := ClusterElectionSnapshot{
		ActiveLeadersCount: 2,
	}
	alerts := engine.Evaluate(snapSplitBrain)
	fmt.Printf("Scenario 2 (Split-Brain): [%s] %s: %s\n", alerts[0].Severity, alerts[0].Name, alerts[0].Description)

	// Сценарий 3: Подвисшие выборы (нет лидера 20 сек)
	snapNoLeader := ClusterElectionSnapshot{
		ActiveLeadersCount: 0,
		NoLeaderDuration:   20 * time.Second,
	}
	alerts = engine.Evaluate(snapNoLeader)
	fmt.Printf("Scenario 3 (No Leader): [%s] %s: %s\n", alerts[0].Severity, alerts[0].Name, alerts[0].Description)

	// Сценарий 4: Частая смена лидера (5 переходов за час)
	snapFlapping := ClusterElectionSnapshot{
		ActiveLeadersCount: 1,
		TransitionsLastHour: 5,
	}
	alerts = engine.Evaluate(snapFlapping)
	fmt.Printf("Scenario 4 (Flapping): [%s] %s: %s\n", alerts[0].Severity, alerts[0].Name, alerts[0].Description)
}
```

## Под капотом

В Prometheus правила алертинга описываются через PromQL:
```yaml
- alert: ClusterSplitBrain
  expr: sum(leader_election_is_leader) > 1
  for: 0s
  labels:
    severity: page
  annotations:
    summary: "Multiple leaders detected"

- alert: LeaderMissing
  expr: sum(leader_election_is_leader) == 0
  for: 15s
  labels:
    severity: page
```
Обратите внимание на `for: 0s` для Split-Brain: в отличие от обычных алертов, алерт на split-brain должен стрелять мгновенно без сглаживания интервалом `for`.

## Подводные камни

Ложные срабатывания при rolling restart: если старый под ещё не успел отправить метрику `is_leader=0`, а новый уже отправил `is_leader=1`, на графике Prometheus на один интервал скрейпинга (15s) появится сумма `2`. Чтобы исключить ложные алерты при плановом деплое, алерт на split-brain проверяет пересечение lease-id либо требует `for: 5s`.

О: Узел должен немедленно перевести себя в режим аварийного Read-Only или завершить процесс через `os.Exit(1)` (Fail-Stop model). Продолжать работу в условиях раздвоения лидерства категорически недопустимо.
