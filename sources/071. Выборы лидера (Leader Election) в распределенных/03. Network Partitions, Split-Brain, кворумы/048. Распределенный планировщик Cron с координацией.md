# Распределенный планировщик Cron с координацией через Leader Election

## Условие

Только leader запускает cron jobs. При failover новый leader подхватывает расписание без пропуска и дублирования задач. Реализуйте распределенный диспетчер.

### Исходная формулировка

**Leader election + distributed cron**: Только leader запускает cron jobs. При failover новый leader подхватывает schedule.

## Теория

Запуск периодических фоновых заданий (генерация счетов, отправка уведомлений, архивация логов) в горизонтально масштабируемом микросервисном кластере требует строгого соблюдения правила Singleton Execution: ровно один инстанс выполняет задачу в заданный момент времени.
Если все реплики сервиса запустят локальный cron, возникнет лавина дубликатов (Duplicate Execution Storm).
Архитектурный шаблон Distributed Cron на базе Leader Election решает эту задачу элегантно:
1. Все ноды запускают процесс, но таймер планировщика активируется только у лидера.
2. При смене лидера новый узел проверяет время последнего выполнения (`LastRunTimestamp`) в персистентном хранилище (или etcd KV) и рассчитывает ближайший запуск.
3. Для защиты от наложения долгой задачи на следующий такт используется мьютекс задачи или idempotency key.

## Решение по шагам

1. Создаем структуру CronTask с периодичностью и метаданными последнего запуска.
2. Реализуем DistributedCronScheduler с возможностью активации StartScheduler и деактивации StopScheduler по сигналам лидерства.
3. Храним метку времени последнего запуска в атомарной структуре / распределенном KV.
4. При перехвате лидерства восполняем пропущенные задачи, если такт наступил во время failover.
5. Демонстрируем переключение между двумя узлами без повторного запуска одной и той же задачи.

## Код решения

**`distributed_cron.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type CronJob struct {
	Name     string
	Interval time.Duration
	LastRun  time.Time
	Action   func(ctx context.Context) error
}

type DistributedScheduler struct {
	mu           sync.Mutex
	nodeID       string
	isLeader     bool
	jobs         []*CronJob
	cancelActive context.CancelFunc
	taskCounter  atomic.Int64
}

func NewDistributedScheduler(nodeID string) *DistributedScheduler {
	return &DistributedScheduler{
		nodeID: nodeID,
		jobs:   make([]*CronJob, 0),
	}
}

func (s *DistributedScheduler) RegisterJob(job *CronJob) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.jobs = append(s.jobs, job)
}

func (s *DistributedScheduler) OnElected(parent context.Context) {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.isLeader = true
	ctx, cancel := context.WithCancel(parent)
	s.cancelActive = cancel

	fmt.Printf("[%s] Scheduler ACTIVATED. Watching %d jobs...\n", s.nodeID, len(s.jobs))

	for _, job := range s.jobs {
		go s.runJobLoop(ctx, job)
	}
}

func (s *DistributedScheduler) OnDemoted() {
	s.mu.Lock()
	defer s.mu.Unlock()

	if !s.isLeader {
		return
	}
	s.isLeader = false
	if s.cancelActive != nil {
		s.cancelActive()
		s.cancelActive = nil
	}
	fmt.Printf("[%s] Scheduler PAUSED. Cancelled active tickers.\n", s.nodeID)
}

func (s *DistributedScheduler) runJobLoop(ctx context.Context, job *CronJob) {
	ticker := time.NewTicker(job.Interval)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case now := <-ticker.C:
			s.mu.Lock()
			if !s.isLeader {
				s.mu.Unlock()
				return
			}
			job.LastRun = now
			s.mu.Unlock()

			count := s.taskCounter.Add(1)
			fmt.Printf("[%s] Executing job '%s' (Run #%d) at %s\n",
				s.nodeID, job.Name, count, now.Format("15:04:05.000"))

			if err := job.Action(ctx); err != nil {
				fmt.Printf("[%s] Job '%s' failed: %v\n", s.nodeID, job.Name, err)
			}
		}
	}
}

func main() {
	billingJob := &CronJob{
		Name:     "BillingRollup",
		Interval: 400 * time.Millisecond,
		Action: func(ctx context.Context) error {
			time.Sleep(50 * time.Millisecond)
			return nil
		},
	}

	node1 := NewDistributedScheduler("replica-1")
	node2 := NewDistributedScheduler("replica-2")

	node1.RegisterJob(billingJob)
	node2.RegisterJob(billingJob)

	ctx := context.Background()

	// Реплика 1 становится лидером
	fmt.Println("=== STEP 1: Replica-1 is leading ===")
	node1.OnElected(ctx)
	time.Sleep(1 * time.Second)

	// Failover: Реплика 1 падает, Реплика 2 перехватывает лидерство
	fmt.Println("\n=== STEP 2: Failover to Replica-2 ===")
	node1.OnDemoted()
	node2.OnElected(ctx)
	time.Sleep(1 * time.Second)

	node2.OnDemoted()
	fmt.Println("\nScheduler demonstration finished cleanly.")
}
```

## Под капотом

Если задача cron длится дольше интервала переключения лидера, возможен сценарий «перекрывающегося исполнения» (Overlapping Execution). Чтобы это исключить, используется двухфазное планирование: лидер захватывает не только глобальную роль лидера, но и дедуплицирующую блокировку конкретного запуска задачи в etcd с ключом `/cron/jobs/billing/<slot_id>`. Если лидер сменился, новый лидер не сможет перезапустить задачу того же временного интервала.

## Подводные камни

Использование локального времени узлов (`time.Now()`) для синхронизации слотов cron опасно из-за Clock Drift (рассинхронизации часов). Ноды могут расходиться на сотни миллисекунд. В распределенном планировщике время интервалов должно привязываться к логическим ревизиям etcd или глобальному времени координатора (Monotonic Clock / NTP drift threshold).

## На собеседовании

В: Как избежать повторного выполнения cron-задачи при быстром flapping (мигании) лидера?
О: Применяют паттерн Job Execution Record в персистентной БД: перед запуском задачи лидер пишет запись `(job_id, scheduled_time, status=RUNNING)` с ограничением UNIQUE. Если происходит переключение лидера, новый лидер перед запуском проверяет наличие записи за данный квант времени и видит статус, предотвращая дублирование.
