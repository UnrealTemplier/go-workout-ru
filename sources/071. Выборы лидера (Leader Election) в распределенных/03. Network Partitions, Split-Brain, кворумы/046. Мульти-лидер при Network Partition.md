# Мульти-лидер при Network Partition и проблема истечения Lease

## Условие

Сымитируйте network partition (iptables DROP между двумя группами узлов). Покажите, что minority (1 из 3) не может избрать лидера в etcd (quorum=2), но может думать, что он лидер, если lease ещё не истёк. Объясните, почему это не проблема etcd, а проблема приложения, которое не проверяет connectivity.

### Исходная формулировка

**Мульти-лидер в partition.**: Сымитируйте network partition (iptables DROP между двумя группами узлов). Покажите, что minority (1 из 3) не может избрать лидера в etcd (quorum=2), но может думать, что он лидер, если lease ещё не истёк. Объясните, почему это не проблема etcd, а проблема приложения, которое не проверяет connectivity.

## Теория

В распределённых системах сетевая изоляция (network partition) разделяет кластер на подмножества узлов. В кластере etcd из 3 узлов для кворума требуется \(\lfloor 3/2 \rfloor + 1 = 2\) узла.
Если узел \(A\) изолирован в меньшинстве (minority partition), он теряет связь с кворумом. Однако если \(A\) ранее был признан лидером и владел арендой (lease) с TTL=10 сек, локальный процесс приложения на узле \(A\) может продолжать считать себя лидером в течение оставшегося времени жизни аренды (lease remaining TTL), пока таймер не истечет или пока heartbeat keep-alive не завершится таймаутом.
В это же время узлы большинства \(B\) и \(C\) после обнаружения таймаута лидера избирают нового лидера узла \(B\).
Возникает временное состояние дуализма (Split-Brain на уровне приложения): старый лидер ещё считает себя лидером, а новый уже избран большинством.
Это фундаментальное свойство асинхронных сетей (теорема FLP). etcd гарантирует, что запись в KV с привязкой к старой аренде либо завершится ошибкой таймаута кворума Raft, либо будет отвергнута. Но если старый лидер выполняет внешние побочные эффекты (отправка email, списание средств, вызов внешнего REST API) без проверки живости канала или кворума, он нанесет ущерб. Поэтому приложение обязано либо непрерывно проверять статус канала связи через context cancellation от KeepAlive, либо использовать Fencing Tokens.

## Решение по шагам

1. Создаем структуру PartitionDetector с каналами мониторинга статуса KeepAlive.
2. Запускаем горутину HeartbeatMonitor, отслеживающую входящие ответы KeepAliveResp от etcd.
3. Если за интервал LeaseTTL/3 ответы от etcd перестают приходить, немедленно переводим локальный узел в статус Degraded/SteppingDown, не дожидаясь полного истечения TTL аренды.
4. Отменяем активный LeaderContext для немедленного прекращения фоновых задач мутации данных.
5. Проверяем поведение узла в изоляции: запись блокируется таймаутом контекста, а задачи останавливаются.

## Код решения

**`partition_guard.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrPartitionDetected = errors.New("network partition detected: keepalive stalled")
	ErrNotLeader          = errors.New("node is not leading")
)

type LeaseStatus struct {
	ID        int64
	TTL       time.Duration
	LastAlive time.Time
}

type NodeGuard struct {
	mu           sync.RWMutex
	nodeID       string
	isLeader     bool
	lease        LeaseStatus
	cancelLeader context.CancelFunc
}

func NewNodeGuard(nodeID string, ttl time.Duration) *NodeGuard {
	return &NodeGuard{
		nodeID: nodeID,
		lease: LeaseStatus{
			ID:  1001,
			TTL: ttl,
		},
	}
}

func (g *NodeGuard) AssumeLeadership(parent context.Context) context.Context {
	g.mu.Lock()
	defer g.mu.Unlock()

	ctx, cancel := context.WithCancel(parent)
	g.isLeader = true
	g.lease.LastAlive = time.Now()
	g.cancelLeader = cancel
	return ctx
}

func (g *NodeGuard) OnKeepAliveResponse() {
	g.mu.Lock()
	defer g.mu.Unlock()
	g.lease.LastAlive = time.Now()
}

func (g *NodeGuard) MonitorPartition(ctx context.Context, checkInterval time.Duration) {
	ticker := time.NewTicker(checkInterval)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			g.mu.Lock()
			if !g.isLeader {
				g.mu.Unlock()
				continue
			}

			// Если ответ keepalive не приходил дольше половины TTL,
			// считаем себя отрезанными от большинства etcd и сбрасываем полномочия
			elapsed := time.Since(g.lease.LastAlive)
			if elapsed > g.lease.TTL/2 {
				fmt.Printf("[%s] WARNING: Partition suspected! No keepalive for %v (TTL=%v). Stepping down!\n",
					g.nodeID, elapsed, g.lease.TTL)
				g.isLeader = false
				if g.cancelLeader != nil {
					g.cancelLeader()
				}
				g.mu.Unlock()
				return
			}
			g.mu.Unlock()
		}
	}
}

func (g *NodeGuard) ExecuteMutation(action func() error) error {
	g.mu.RLock()
	defer g.mu.RUnlock()

	if !g.isLeader {
		return ErrNotLeader
	}
	if time.Since(g.lease.LastAlive) > g.lease.TTL/2 {
		return ErrPartitionDetected
	}
	return action()
}

func main() {
	guard := NewNodeGuard("node-A-minority", 4*time.Second)
	leaderCtx := guard.AssumeLeadership(context.Background())

	go guard.MonitorPartition(leaderCtx, 500*time.Millisecond)

	// Имитация успешных keepalive в течение 1 секунды
	for i := 0; i < 2; i++ {
		time.Sleep(500 * time.Millisecond)
		guard.OnKeepAliveResponse()
		fmt.Println("[node-A] Keepalive renewed successfully")
	}

	// Имитация сетевой изоляции (iptables DROP): ответы перестают приходить
	fmt.Println("[node-A] Network partition occurs (iptables DROP etcd traffic)...")

	// Пытаемся выполнять операции
	for i := 0; i < 6; i++ {
		time.Sleep(500 * time.Millisecond)
		err := guard.ExecuteMutation(func() error {
			fmt.Println("[node-A] Critical state mutation executed")
			return nil
		})
		if err != nil {
			fmt.Printf("[node-A] Operation rejected: %v\n", err)
		}
	}
}
```

## Под капотом

В протоколе Raft узел etcd не может подтвердить продление аренды без согласия кворума. Запрос `LeaseKeepAlive` проходит через машину состояний Raft: лидер etcd отправляет AppendEntries фоловерам. Если узел изолирован от большинства, запрос зависает или завершается ошибкой `context.DeadlineExceeded`. Однако приложение, удерживающее клиентское соединение, обязано слушать канал `<-chan *clientv3.LeaseKeepAliveResponse`. Если канал закрывается или не выдает событий в течение safety margin (обычно \(TTL / 2\) или \(TTL / 3\)), лидер обязан сложить полномочия локально.

## Подводные камни

Главная ошибка — полагаться на то, что `Lease` защитит от дублирования исполнения сторонних задач. Если задача обращается к базе данных PostgreSQL без проверки версий или отправляет HTTP-запрос внешнему банку, узел etcd никак не сможет отменить этот запрос задним числом. Использование Lease без превентивного heartbeat-таймера и fencing tokens неизбежно приведет к фантомным записям при возникновении сетевых разделений.

## На собеседовании

В: Что произойдет, если лидер etcd потеряет сеть с приложением-лидером, но приложение продолжит работать?
О: etcd по истечении TTL аренды (lease expiration) удалит ключ лидера и позволит другому узлу выиграть выборы. Но приложение на старом узле не узнает об этом мгновенно, если не слушает канал KeepAlive с таймаутом. Чтобы исключить split-brain на прикладном уровне, Go-воркер обязан привязать свой жизненный цикл к контексту аренды (`clientv3.LeaseKeepAlive`) и прекращать работу задолго до истечения TTL (safety buffer = TTL / 3).
