# Прогрев кэша при старте: Паттерн Leader Cache Warming

## Условие

Только leader прогревает кэш при startup. Остальные инстансы ждут сигнала готовности кэша через etcd watch или Redis pub/sub.

### Исходная формулировка

**Leader election + cache warming**: Только leader прогревает кэш при startup. Остальные инстансы ждут сигнала от leader'а.

## Теория

При старте крупного распределенного сервиса обращение к холодному кэшу (Cache Miss Storm) может мгновенно обрушить первичную реляционную базу данных тысячами параллельных тяжелых SQL-запросов (Cache Stampede).
Решением является паттерн Leader Cache Warming:
1. При развертывании новой версии сервиса все поды запускаются, но не начинают обслуживание пользовательского трафика.
2. Лидер захватывает распределенную блокировку инициализации и выполняет тяжелые запросы в СУБД, заполняя распределенный Redis/KeyDB кэш.
3. По завершении прогрева лидер записывает ключ готовности в etcd: `/cache/warmed = <unix_timestamp>`.
4. Все фоловеры, подписанные через `clientv3.Watch`, получают уведомление о готовности кэша и только после этого открывают свои readiness-пробы Kubernetes (`/readyz` -> 200 OK).

## Решение по шагам

1. Создаем структуру CacheWarmer с методами WarmUpAsLeader и AwaitWarmupAsFollower.
2. Лидер симулирует чтение справочников из БД и запись в распределенный кэш.
3. По окончании лидер шлет широковещательный сигнал в канал готовности.
4. Фоловеров блокирует вызов WaitReady(), ожидающий события готовности с таймаутом.
5. Проверяем, что трафик разрешается только после окончания прогрева лидера.

## Код решения

**`leader_cache_warmer.go`**

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

type SharedCacheStore struct {
	mu    sync.RWMutex
	items map[string]string
}

func (s *SharedCacheStore) Set(k, v string) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.items[k] = v
}

func (s *SharedCacheStore) Get(k string) (string, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	val, ok := s.items[k]
	return val, ok
}

type CacheCoordinator struct {
	mu           sync.Mutex
	isWarmed     bool
	readyChannel chan struct{}
	store        *SharedCacheStore
}

func NewCacheCoordinator(store *SharedCacheStore) *CacheCoordinator {
	return &CacheCoordinator{
		readyChannel: make(chan struct{}),
		store:        store,
	}
}

func (c *CacheCoordinator) WarmUpAsLeader(ctx context.Context, nodeID string) error {
	fmt.Printf("[%s] LEADER: Starting cache pre-warming from primary DB...\n", nodeID)

	// Имитируем тяжелый прогрев таблиц
	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-time.After(800 * time.Millisecond):
		c.store.Set("config:geo_zones", "EU,US,APAC")
		c.store.Set("config:fee_schedule", "tier_gold:0.01")
	}

	c.mu.Lock()
	c.isWarmed = true
	close(c.readyChannel)
	c.mu.Unlock()

	fmt.Printf("[%s] LEADER: Cache warming complete. Signalled followers via etcd event.\n", nodeID)
	return nil
}

func (c *CacheCoordinator) AwaitWarmup(ctx context.Context, nodeID string) error {
	fmt.Printf("[%s] FOLLOWER: Waiting for leader to complete cache warming...\n", nodeID)

	select {
	case <-ctx.Done():
		return ctx.Err()
	case <-c.readyChannel:
		fmt.Printf("[%s] FOLLOWER: Cache ready signal received! Enabling K8s readiness probe.\n", nodeID)
		return nil
	case <-time.After(3 * time.Second):
		return errors.New("timeout waiting for cache warming")
	}
}

func main() {
	sharedStore := &SharedCacheStore{items: make(map[string]string)}
	coord := NewCacheCoordinator(sharedStore)

	var wg sync.WaitGroup

	// Запуск 2 фоловеров
	for _, fID := range []string{"pod-follower-1", "pod-follower-2"} {
		wg.Add(1)
		go func(id string) {
			defer wg.Done()
			if err := coord.AwaitWarmup(context.Background(), id); err != nil {
				fmt.Printf("[%s] Error: %v\n", id, err)
			}
		}(fID)
	}

	time.Sleep(100 * time.Millisecond)

	// Лидер запускает прогрев
	wg.Add(1)
	go func() {
		defer wg.Done()
		if err := coord.WarmUpAsLeader(context.Background(), "pod-leader-0"); err != nil {
			fmt.Printf("Leader warmup failed: %v\n", err)
		}
	}()

	wg.Wait()

	val, _ := sharedStore.Get("config:geo_zones")
	fmt.Printf("\nVerification: Cache content 'config:geo_zones' = %s\n", val)
}
```

## Под капотом

В крупном кластере ключ готовности `/cache/warmed` сопровождается хэшем версии схемы данных (Schema Hash или Git Commit SHA). Если фоловер видит, что ключ в etcd прогрет для предыдущей версии (`v1.4`), а текущий бинарник требует схему `v1.5`, он отвергает сигнал готовности и ожидает, пока новый лидер развернет и прогреет соответствующую версию данных.

## Подводные камни

Deadlock при падении лидера во время прогрева: если лидер упал на 90% прогрева кэша, ключ в etcd не запишется, и все фоловеры зависнут в ожидании готовности. Обязательно ограничивайте `AwaitWarmup` жестким таймаутом с fallback-перевыборами лидера.

## На собеседовании

В: Как избежать повторного прогрева кэша при rolling-update перезапуске подов?
О: Ключ статуса в etcd сохраняют с TTL и метаданными ревизии. Новый под проверяет наличие свежего ключа прогрева: если кэш уже прогрет предыдущим подом менее N минут назад, этап повторного прогрева пропускается (Fast Path Startup).
