# Координатор очереди задач: Leader-Worker с динамическим распределением

## Условие

Leader координирует распределение задач между workers. При падении воркера лидер переназначает задачу. При падении лидера новый лидер инспектирует статус очереди в etcd.

### Исходная формулировка

**Leader election + task queue**: Leader координирует распределение задач между worker'ами. При failover новый leader перераспределяет задачи.

## Теория

Паттерн Leader-Worker (Master-Worker) является классической моделью распределенных вычислений. Лидер отвечает за глобальный стейт: чтение входящей очереди задач, мониторинг здоровья пула воркеров через heartbeat, распределение батчей и переназначение зависших задач при падении исполнителей.
Ключевые принципы надежности:
1. Состояние распределения хранится в консистентном хранилище (etcd/Postgres), а не в оперативной памяти лидера.
2. Воркеры регистрируются во временной ветке KV (эфемерен через Lease).
3. Каждая задача имеет статус: `PENDING`, `ASSIGNED(worker_id, deadline)`, `COMPLETED`.
4. Если воркер падает (истек lease или таймаут исполнения), лидер возвращает задачу в пул `PENDING`.
5. Если падает сам лидер, новый лидер при вступлении в должность сканирует активные задачи, проверяет доступность назначенных воркеров и продолжает координацию.

## Решение по шагам

1. Описываем структуру Task со статусом, исполнителем и дедлайном.
2. Реализуем менеджер LeaderCoordinator, управляющий жизненным циклом очереди.
3. Добавляем метод ReassignStaleTasks(), сканирующий задачи с истекшим дедлайном.
4. Симулируем отказ воркера и автоматическое переназначение задачи другому исполнителю.
5. Симулируем смену лидера и валидацию восстановления очереди новым лидером.

## Код решения

**`leader_task_coordinator.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type TaskStatus string

const (
	StatusPending   TaskStatus = "PENDING"
	StatusAssigned  TaskStatus = "ASSIGNED"
	StatusCompleted TaskStatus = "COMPLETED"
)

type Task struct {
	ID        string
	Payload   string
	Status    TaskStatus
	WorkerID  string
	Heartbeat time.Time
}

type Coordinator struct {
	mu       sync.Mutex
	leaderID string
	tasks    map[string]*Task
	workers  map[string]time.Time
}

func NewCoordinator(leaderID string) *Coordinator {
	return &Coordinator{
		leaderID: leaderID,
		tasks:    make(map[string]*Task),
		workers:  make(map[string]time.Time),
	}
}

func (c *Coordinator) SubmitTask(id, payload string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.tasks[id] = &Task{
		ID:      id,
		Payload: payload,
		Status:  StatusPending,
	}
}

func (c *Coordinator) RegisterWorkerHeartbeat(workerID string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.workers[workerID] = time.Now()
}

func (c *Coordinator) DispatchTasks() {
	c.mu.Lock()
	defer c.mu.Unlock()

	now := time.Now()
	// Ищем живых воркеров (heartbeat < 2s)
	activeWorkers := make([]string, 0)
	for wID, lastBeat := range c.workers {
		if now.Sub(lastBeat) < 2*time.Second {
			activeWorkers = append(activeWorkers, wID)
		}
	}

	if len(activeWorkers) == 0 {
		return
	}

	wIdx := 0
	for _, task := range c.tasks {
		if task.Status == StatusPending {
			worker := activeWorkers[wIdx%len(activeWorkers)]
			wIdx++
			task.Status = StatusAssigned
			task.WorkerID = worker
			task.Heartbeat = now
			fmt.Printf("[%s] Assigned Task %s to Worker %s\n", c.leaderID, task.ID, worker)
		}
	}
}

func (c *Coordinator) ReassignStaleTasks(timeout time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()

	now := time.Now()
	for _, task := range c.tasks {
		if task.Status == StatusAssigned {
			lastBeat, workerAlive := c.workers[task.WorkerID]
			if !workerAlive || now.Sub(lastBeat) > timeout {
				fmt.Printf("[%s] Worker %s STALLED for task %s! Reassigning to PENDING...\n",
					c.leaderID, task.WorkerID, task.ID)
				task.Status = StatusPending
				task.WorkerID = ""
			}
		}
	}
}

func main() {
	coord := NewCoordinator("leader-node-alpha")

	coord.SubmitTask("task-101", "RenderVideoSegment_1")
	coord.SubmitTask("task-102", "RenderVideoSegment_2")

	// Регистрируем воркеров
	coord.RegisterWorkerHeartbeat("worker-A")
	coord.RegisterWorkerHeartbeat("worker-B")

	coord.DispatchTasks()

	// Воркер B терпит сбой (нет heartbeat)
	fmt.Println("\n... Simulating Worker B crash (network down) ...")
	time.Sleep(1500 * time.Millisecond)

	// Воркер A продолжает жить
	coord.RegisterWorkerHeartbeat("worker-A")

	// Проверяем зависшие задачи с порогом 1 секунда
	coord.ReassignStaleTasks(1 * time.Second)

	// Повторное распределение
	coord.DispatchTasks()
}
```

## Под капотом

В производственных системах координатор сохраняет распределение задач в etcd с использованием транзакций `clientv3.Txn`. Каждое назначение задачи сопровождается инкрементом `lease_id` воркера. При падении воркера etcd удаляет ephemeral ключ воркера `/workers/<id>`. Координатор подписан на префикс через `clientv3.Watch`: событие DELETE инициирует немедленный rebalancing без ожидания периодического сканирования таймером.

## Подводные камни

Опасность «Зомби-воркера»: воркер завис на длинной GC-паузе, лидер счел его мертвым и переназначил задачу другому воркеру. После выхода из паузы старый воркер завершает расчеты и записывает результат, перезатирая работу нового исполнителя. Для предотвращения необходим версионный контроль (CAS в БД или generation tokens).
