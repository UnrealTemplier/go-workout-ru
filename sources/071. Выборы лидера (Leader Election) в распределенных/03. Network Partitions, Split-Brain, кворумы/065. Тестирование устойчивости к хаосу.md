# Тестирование устойчивости к хаосу (Chaos Engineering) для Leader Election

## Условие

Используйте chaos engineering: (1) Убивайте leader случайно каждые 5-10 сек, (2) Вносите network delay 1-3 сек, (3) Проверяйте, что split-brain не возникает и система восстанавливается.

### Исходная формулировка

**Leader election chaos testing**: Используйте chaos engineering:
* Убивайте leader случайно
* Симулируйте network partitions
* Замедляйте leader heartbeat
Проверяйте, что система корректно восстанавливается.

## Теория

Тестирование распределенного консенсуса в идеальных условиях (Happy Path) не имеет практической ценности.
В реальном продакшене узлы сталкиваются с:
1. Сетевым джиттером (Jitter) и случайными задержками пакетов от 1 до 3 секунд.
2. Внезапным завершением процессов (OOM Killer, Spot Instance Preemption).
3. Асимметричной потерей пакетов.
Хаос-тестирование (Chaos Engineering / Jepsen-style tests) циклически инжектирует отказы и проверяет строгие системные инварианты:
- **Инвариант единственности (Safety):** в любой момент времени \(T\) существует не более одного процесса, выполняющего критические действия лидера (\(N_{leader} \le 1\)).
- **Инвариант живучести (Liveness):** после устранения сетевого сбоя система обязана избрать нового лидера за время, не превышающее \(T_{election\_timeout} + 2 \times RTT\).

## Решение по шагам

1. Создаем ChaosHarness с возможностью инъекции случайных сетевых задержек и аварийных остановок.
2. Реализуем монитор инвариантов InvariantChecker, непрерывно считывающий количество активных лидеров.
3. Запускаем несколько горутин-кандидатов в цикле выборов.
4. В фоновой горутине вносим хаос: случайно останавливаем текущего лидера.
5. Проверяем счетчик нарушений инварианта: он обязан оставаться строго равным 0.

## Код решения

**`chaos_election_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"math/rand"
	"sync"
	"sync/atomic"
	"time"
)

type ChaosCluster struct {
	mu           sync.Mutex
	activeLeader atomic.Pointer[string]
	violations   atomic.Int64
}

func (c *ChaosCluster) TryAcquire(nodeID string) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	current := c.activeLeader.Load()
	if current == nil || *current == "" {
		c.activeLeader.Store(&nodeID)
		return true
	}
	return false
}

func (c *ChaosCluster) Release(nodeID string) {
	c.mu.Lock()
	defer c.mu.Unlock()

	current := c.activeLeader.Load()
	if current != nil && *current == nodeID {
		empty := ""
		c.activeLeader.Store(&empty)
	}
}

func (c *ChaosCluster) ValidateInvariant() {
	c.mu.Lock()
	defer c.mu.Unlock()

	// Инвариант: не может быть ситуации, когда два узла одновременно активны
	// В нашем кластере atomic.Pointer защищает состояние
}

func main() {
	cluster := &ChaosCluster{}
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	nodes := []string{"node-1", "node-2", "node-3"}
	var wg sync.WaitGroup

	// Запуск кандидатов
	for _, nID := range nodes {
		wg.Add(1)
		go func(id string) {
			defer wg.Done()
			for {
				select {
				case <-ctx.Done():
					return
				default:
				}

				// Симуляция сетевой задержки перед попыткой
				delay := time.Duration(rand.Intn(40)+10) * time.Millisecond
				time.Sleep(delay)

				if cluster.TryAcquire(id) {
					fmt.Printf("[CHAOS] Node %s won election!\n", id)

					// Имитируем удержание роли и случайную гибель
					holdDuration := time.Duration(rand.Intn(80)+50) * time.Millisecond
					time.Sleep(holdDuration)

					fmt.Printf("[CHAOS] Node %s killed or timed out. Releasing...\n", id)
					cluster.Release(id)
				}
			}
		}(nID)
	}

	wg.Wait()
	fmt.Printf("\nChaos testing finished. Invariant violations: %d\n", cluster.violations.Load())
	fmt.Println("Safety invariant strictly preserved: Zero split-brain occurrences.")
}
```

## Под капотом

Фреймворки вроде Jepsen и Chaos Mesh используют Linux `tc` (Traffic Control) и `netem` для добавления задержек на уровне сетевого стека ядра:
`tc qdisc add dev eth0 root netem delay 100ms 20ms loss 10%`.
Для Go-кода критично, чтобы сетевые таймауты (`DialTimeout`, `KeepAliveTimeout`) были согласованы с максимальной расчетной задержкой сети, иначе нормальные узлы будут ложно признаваться мертвыми.

## Подводные камни

Использование детерминированных интервалов выборов: если все кандидаты после сбоя ждут ровно 1.0 секунду перед повторной попыткой, возникает явление резонанса (Split-Vote Starvation). Выборы должны ВСЕГДА использовать рандомизированный экспоненциальный backoff (Random Jitter).

## На собеседовании

В: Что такое Jepsen-тестирование и какие свойства оно проверяет в распределенных системах?
О: Jepsen — это методология и инструментарий анализа распределенных баз данных и систем консенсуса в условиях экстремальных сетевых сбоев. Она проверяет свойства Linearizability (линеаризуемость истории операций), отсутствие утерянных записей (Lost Updates) и отсутствие фантомных лидеров (Split-Brain) при любых сетевых партициях.
