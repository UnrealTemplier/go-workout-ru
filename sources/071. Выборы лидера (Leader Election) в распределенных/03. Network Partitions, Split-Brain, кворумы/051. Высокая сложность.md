# Высокая сложность: Active/Passive Failover с контролем здоровья и перехватом

## Условие

Создай систему из двух инстансов: Active и Standby. Active пишет heartbeat в etcd. Standby наблюдает. Если Active не обновил lease за 3 сек — Standby становится Active. Покажи переключение.

### Исходная формулировка

**[Высокая сложность — Active/Passive Failover]**: Создай систему из двух инстансов: Active и Passive. Passive стоит в режиме горячей замены. Когда Active падает, Passive выигрывает выборы, проматывает локальный кэш/состояние и становится новым Active, начиная принимать трафик.

## Теория

Схема Active/Passive (Primary-Standby) с автоматическим переключением при сбое (Automatic Failover) лежит в основе отказоустойчивости высоконагруженных баз данных и брокеров сообщений (PostgreSQL Patroni, Redis Sentinel, etcd clusters).
Ключевая проблема любого Active-Passive failover — гарантировать, что в каждый момент времени существует не более одного пишущего узла.
В etcd это реализуется через комбинацию двух механизмов:
1. `Lease with KeepAlive`: Active держит аренду с коротким TTL (например, 3 секунды).
2. `Watch`: Standby подписывается на ключ лидерства через `clientv3.Watch`.
При сбое Active (краш ОС, остановка процесса, обрыв сети) аренда истекает. etcd удаляет ключ и шлет событие `mvccpb.DELETE`. Standby получает событие и немедленно инициирует транзакцию захвата лидерства (`clientv3.Compare`), предотвращая состояние «висящего кластера».

## Решение по шагам

1. Создаем структуру FailoverNode с полями состояния (RoleActive, RoleStandby).
2. Реализуем функцию RunActiveLoop, регулярно обновляющую аренду.
3. Реализуем функцию RunStandbyWatch, блокирующуюся на канале событий etcd Watcher.
4. При получении события DELETE или закрытии канала Standby совершает переход в состояние Active.
5. Проверяем процесс передачи полномочий в тесте с эмуляцией отключения таймера Active.

## Код решения

**`active_passive_failover.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type Role string

const (
	RoleActive  Role = "ACTIVE"
	RoleStandby Role = "STANDBY"
)

type ClusterEvent struct {
	Type     string // "HEARTBEAT", "EXPIRED"
	LeaderID string
}

type FailoverNode struct {
	nodeID      string
	role        Role
	mu          sync.Mutex
	isCancelled atomic.Bool
}

func NewFailoverNode(id string, initialRole Role) *FailoverNode {
	return &FailoverNode{
		nodeID: id,
		role:   initialRole,
	}
}

func (n *FailoverNode) Run(ctx context.Context, bus chan ClusterEvent) {
	n.mu.Lock()
	currentRole := n.role
	n.mu.Unlock()

	if currentRole == RoleActive {
		n.runActive(ctx, bus)
	} else {
		n.runStandby(ctx, bus)
	}
}

func (n *FailoverNode) runActive(ctx context.Context, bus chan ClusterEvent) {
	ticker := time.NewTicker(800 * time.Millisecond)
	defer ticker.Stop()

	fmt.Printf("[%s] Started as ACTIVE leader. Emitting heartbeats...\n", n.nodeID)

	for {
		select {
		case <-ctx.Done():
			fmt.Printf("[%s] ACTIVE stopped. Graceful step down.\n", n.nodeID)
			bus <- ClusterEvent{Type: "EXPIRED", LeaderID: n.nodeID}
			return
		case <-ticker.C:
			if n.isCancelled.Load() {
				fmt.Printf("[%s] CRASH simulated! Ceasing heartbeats...\n", n.nodeID)
				return // Молча умираем, имитируя SIGKILL
			}
			bus <- ClusterEvent{Type: "HEARTBEAT", LeaderID: n.nodeID}
			fmt.Printf("[%s] Heartbeat sent.\n", n.nodeID)
		}
	}
}

func (n *FailoverNode) runStandby(ctx context.Context, bus chan ClusterEvent) {
	fmt.Printf("[%s] Started as STANDBY. Monitoring leader health...\n", n.nodeID)
	timeout := 2 * time.Second
	timer := time.NewTimer(timeout)
	defer timer.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case event := <-bus:
			if event.Type == "HEARTBEAT" {
				// Сбрасываем таймер при получении пульса
				if !timer.Stop() {
					select {
					case <-timer.C:
					default:
					}
				}
				timer.Reset(timeout)
			} else if event.Type == "EXPIRED" {
				fmt.Printf("[%s] Received explicit EXPIRED event. Promoting immediately!\n", n.nodeID)
				n.promoteToActive(ctx, bus)
				return
			}
		case <-timer.C:
			fmt.Printf("[%s] LEADER TIMEOUT! No heartbeat for %v. Promoting to ACTIVE!\n", n.nodeID, timeout)
			n.promoteToActive(ctx, bus)
			return
		}
	}
}

func (n *FailoverNode) promoteToActive(ctx context.Context, bus chan ClusterEvent) {
	n.mu.Lock()
	n.role = RoleActive
	n.mu.Unlock()
	fmt.Printf("[%s] >>> PROMOTION SUCCESSFUL. Node is now ACTIVE <<<\n", n.nodeID)
	n.runActive(ctx, bus)
}

func main() {
	eventBus := make(chan ClusterEvent, 10)
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	activeNode := NewFailoverNode("pod-primary-0", RoleActive)
	standbyNode := NewFailoverNode("pod-standby-1", RoleStandby)

	go activeNode.Run(ctx, eventBus)
	go standbyNode.Run(ctx, eventBus)

	// Даем поработать в штатном режиме
	time.Sleep(2 * time.Second)

	// Симулируем внезапную смерть активного узла
	fmt.Println("\n>>> Triggering simulated crash on primary node <<<")
	activeNode.isCancelled.Store(true)

	// Ждем пока Standby обнаружит отсутствие пульса и промоутится
	time.Sleep(3 * time.Second)
	fmt.Println("Failover simulation complete.")
}
```

## Под капотом

В реальном etcd клиент Standby использует `clientv3.Watch(ctx, "/leader/key")`. Когда Active узел погибает, etcd расторгает Lease, удаляет ключ и генерирует событие ревизии. Standby реагирует на это событие за миллисекунды (RTT сети), не дожидаясь длительного polling-таймаута. Таймер выступает лишь fallback-защитой на случай разрыва сокета между Standby и etcd.

## Подводные камни

Критическая уязвимость: Flapping Failover. Если сеть между Standby и etcd нестабильна, Standby может ошибочно решить, что лидер упал, и попытаться перехватить роль, вызывая конфликт. Поэтому операция захвата лидерства ВСЕГДА должна быть транзакцией `Txn().If(Compare(CreateRevision("/leader/key"), "=", 0))`, чтобы исключить гонку при живом лидере.

## На собеседовании

В: В чем разница между failover на основе Watch и failover на основе Polling?
О: Watch основан на push-уведомлениях по HTTP/2 gRPC streaming: задержка переключения составляет единицы миллисекунд (sub-RTT), а нагрузка на сервер минимальна. Polling создает периодические запросы (GET/HEAD), что либо создает задержку в половину интервала опроса, либо перегружает etcd/БД частыми запросами при масштабировании пула нод.
