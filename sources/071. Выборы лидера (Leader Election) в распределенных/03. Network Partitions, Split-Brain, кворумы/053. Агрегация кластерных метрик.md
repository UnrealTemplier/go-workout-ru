# Агрегация кластерных метрик: Паттерн Leader-Aggregator

## Условие

Только leader агрегирует метрики со всех инстансов и отправляет их во внешнюю систему (DataDog, VictoriaMetrics). Остальные инстансы только собирают локально.

### Исходная формулировка

**Leader election + metrics aggregation**: Только leader агрегирует метрики со всех инстансов и публикует в Prometheus.

## Теория

При мониторинге крупных микросервисных кластеров (сотни реплик) прямая отправка высокочастотных метрик во внешние Time-Series СУБД (DataDog, InfluxDB, Prometheus pushgateway) приводит к:
1. Превышению лимитов rate-limiting и квот внешнего API.
2. Существенным финансовым затратам на тарификацию ingest metrics.
3. Сетевой перегрузке внешних шлюзов.
Паттерн Leader-Aggregator разделяет сбор и публикацию:
- Все реплики собирают локальные счетчики (локальный `prometheus.Registry`).
- Каждая реплика отдает свои метрики по внутреннему эндпоинту (pull) либо шлет лидеру по gRPC стриму (push).
- Только лидер выполняет дедупликацию, суммирование (rollup/aggregation) и единый батчевый пуш во внешнюю систему с фиксированным интервалом.

## Решение по шагам

1. Создаем структуру NodeMetrics с локальными счетчиками запросов и ошибок.
2. Создаем LeaderAggregator, хранящий статус лидерства и агрегированное состояние.
3. Реализуем метод Ingest(nodeID, metrics) для приема телеметрии от реплик.
4. Метод FlushToExternalSystem() проверяет статус лидерства: отправка блокируется, если узел не является лидером.
5. Демонстрируем объединение метрик от трех нод и успешную отправку лидером.

## Код решения

**`leader_metrics_aggregator.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type LocalMetrics struct {
	NodeID       string
	Requests     int64
	Errors       int64
	CollectedAt  time.Time
}

type AggregatedSummary struct {
	TotalRequests int64
	TotalErrors   int64
	NodeCount     int
	Timestamp     time.Time
}

type MetricsCollector struct {
	mu          sync.Mutex
	isLeader    atomic.Bool
	buffer      map[string]LocalMetrics
	externalBus chan AggregatedSummary
}

func NewMetricsCollector() *MetricsCollector {
	return &MetricsCollector{
		buffer:      make(map[string]LocalMetrics),
		externalBus: make(chan AggregatedSummary, 5),
	}
}

func (c *MetricsCollector) SetLeader(leading bool) {
	c.isLeader.Store(leading)
}

func (c *MetricsCollector) Report(m LocalMetrics) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.buffer[m.NodeID] = m
}

func (c *MetricsCollector) Flush(ctx context.Context) error {
	if !c.isLeader.Load() {
		return fmt.Errorf("passive replica: external metric shipping is disabled")
	}

	c.mu.Lock()
	defer c.mu.Unlock()

	var totalReq, totalErr int64
	for _, m := range c.buffer {
		totalReq += m.Requests
		totalErr += m.Errors
	}
	summary := AggregatedSummary{
		TotalRequests: totalReq,
		TotalErrors:   totalErr,
		NodeCount:     len(c.buffer),
		Timestamp:     time.Now(),
	}

	// Очищаем буфер после успешного объединения
	c.buffer = make(map[string]LocalMetrics)

	select {
	case c.externalBus <- summary:
		return nil
	default:
		return fmt.Errorf("external shipping channel buffer is full")
	}
}

func main() {
	collector := NewMetricsCollector()

	// Реплики отправляют свои данные
	collector.Report(LocalMetrics{NodeID: "worker-01", Requests: 1200, Errors: 4})
	collector.Report(LocalMetrics{NodeID: "worker-02", Requests: 3400, Errors: 1})
	collector.Report(LocalMetrics{NodeID: "worker-03", Requests: 2100, Errors: 0})

	// Попытка отправки узлом, пока он не лидер
	err := collector.Flush(context.Background())
	fmt.Printf("[Replica State] Flush attempt result: %v\n", err)

	// Узел становится лидером
	fmt.Println("\n>>> Node promoted to Leader <<<")
	collector.SetLeader(true)

	// Успешная агрегация и отправка
	if err := collector.Flush(context.Background()); err != nil {
		fmt.Printf("Flush error: %v\n", err)
	} else {
		summary := <-collector.externalBus
		fmt.Printf("[Leader Sent to External TSDB]: Nodes=%d, TotalRequests=%d, TotalErrors=%d at %s\n",
			summary.NodeCount, summary.TotalRequests, summary.TotalErrors, summary.Timestamp.Format("15:04:05"))
	}
}
```

## Под капотом

При сборе кластерных метрик через Leader-Aggregator критически важна семантика Counter vs Gauge. Нельзя просто складывать абсолютные значения кумулятивных счетчиков, так как при рестарте любого пода его счетчик сбрасывается в ноль (Counter Reset). Агрегатор обязан вычислять дельты (\(\Delta = Current - Previous\)) за отчетный интервал времени и суммировать исключительно приращения.

## Подводные камни

Утечка памяти в буфере: если нода была выведена из эксплуатации (K8s scale down), её старая запись может остаться в мапе `buffer` лидера навечно. Всегда сопровождайте хранение метрик TTL-метками (LastSeenAt) и очищайте записи узлов, от которых не поступало сигналов дольше 2-3 интервалов сбора.

## На собеседовании

В: Почему в классическом Prometheus используется модель Pull с каждого пода вместо Leader-Push в центральный шлюз?
О: Модель Pull децентрализована: сервер мониторинга сам знает список целей из Service Discovery Kubernetes и контролирует частоту скрейпинга. При падении конкретного пода Prometheus сразу видит метрику `up == 0`. Модель Leader-Push требует лидерства и скрывает статус отдельных подов за агрегированной суммой.
