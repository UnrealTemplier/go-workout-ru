# Использование etcd для распределенного конфигурационного хранилища

## Условие

Помимо лидерства, используйте etcd как распределенное KV хранилище конфигураций. Реализуйте dynamic reload конфигурации через `clientv3.Watch` без перезапуска приложения.

### Исходная формулировка

**Использование etcd для распределенного конфигурационного хранилища.**: Помимо лидерства, храните общую конфигурацию в etcd. Лидер обновляет ключи `/config` через транзакции (STP), а остальные узлы следят за изменениями (`Watch`).

## Теория

etcd проектировался как надежное распределенное хранилище критических метаданных (Distributed Key-Value Store).
В архитектуре микросервисов etcd часто совмещает две ключевые функции:
1. Выборы лидера (Leader Election) для координации.
2. Источник истины для динамических конфигураций (Dynamic Configuration Store).
Механизм `clientv3.Watch`:
Вместо периодических опросов (polling), нагружающих сеть и БД, клиент etcd открывает долгоживущий двунаправленный gRPC-стрим HTTP/2. Когда оператор или сервис-лидер обновляет значение ключа `/config/database/max_conns`, etcd передает дельту ревизии всем подписанным клиентам с минимальной задержкой. Приложение парсит новое значение и обновляет пул коннектов без рестарта процесса (Zero-Downtime Reload).

## Решение по шагам

1. Создаем структуру DatabaseConfig с динамическими параметрами пула.
2. Реализуем конфигурационный менеджер EtcdConfigStore с локальным кэшем.
3. Запускаем горутину WatchPrefix, реагирующую на события PUT и DELETE.
4. Демонстрируем изменение конфигурационного параметра и его автоматическое применение.
5. Проверяем корректность обновления данных в оперативной памяти.

## Код решения

**`etcd_dynamic_config.go`**

```go
package main

import (
	"context"
	"fmt"
	"strconv"
	"sync"
	"time"
)

type ConfigUpdateEvent struct {
	Key   string
	Value string
	Type  string // "PUT", "DELETE"
}

type EtcdConfigWatcher struct {
	mu       sync.RWMutex
	settings map[string]string
	eventBus chan ConfigUpdateEvent
}

func NewEtcdConfigWatcher() *EtcdConfigWatcher {
	return &EtcdConfigWatcher{
		settings: make(map[string]string),
		eventBus: make(chan ConfigUpdateEvent, 10),
	}
}

func (w *EtcdConfigWatcher) Get(key string) string {
	w.mu.RLock()
	defer w.mu.RUnlock()
	return w.settings[key]
}

func (w *EtcdConfigWatcher) GetInt(key string, defaultVal int) int {
	w.mu.RLock()
	defer w.mu.RUnlock()
	val, ok := w.settings[key]
	if !ok {
		return defaultVal
	}
	parsed, err := strconv.Atoi(val)
	if err != nil {
		return defaultVal
	}
	return parsed
}

func (w *EtcdConfigWatcher) StartWatching(ctx context.Context) {
	go func() {
		for {
			select {
			case <-ctx.Done():
				return
			case ev := <-w.eventBus:
				w.mu.Lock()
				if ev.Type == "PUT" {
					w.settings[ev.Key] = ev.Value
					fmt.Printf("[etcd-watcher] Config updated: %s = %s\n", ev.Key, ev.Value)
				} else if ev.Type == "DELETE" {
					delete(w.settings, ev.Key)
					fmt.Printf("[etcd-watcher] Config deleted: %s\n", ev.Key)
				}
				w.mu.Unlock()
			}
		}
	}()
}

func (w *EtcdConfigWatcher) SimulateEtcdPut(key, value string) {
	w.eventBus <- ConfigUpdateEvent{Key: key, Value: value, Type: "PUT"}
}

func main() {
	watcher := NewEtcdConfigWatcher()
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	watcher.StartWatching(ctx)

	// Инициализируем начальную конфигурацию
	watcher.SimulateEtcdPut("/config/db/max_open_conns", "25")
	time.Sleep(50 * time.Millisecond)

	fmt.Printf("Current DB MaxOpenConns: %d\n", watcher.GetInt("/config/db/max_open_conns", 10))

	// На лету меняем параметр в etcd (например, DBA увеличил пул под ночную нагрузку)
	fmt.Println("\n>>> SRE updates /config/db/max_open_conns to 100 via etcdctl <<<")
	watcher.SimulateEtcdPut("/config/db/max_open_conns", "100")
	time.Sleep(50 * time.Millisecond)

	fmt.Printf("Updated DB MaxOpenConns without restart: %d\n", watcher.GetInt("/config/db/max_open_conns", 10))
}
```

## Под капотом

В `clientv3.Watch(ctx, key, opts...)` клиент передает номер ревизии `WithRev(startRev)`. Если соединение с etcd прерывалось на 5 секунд, клиент при переподключении запрашивает события начиная с последней полученной ревизии (`lastRev + 1`). etcd воспроизводит все пропущенные события из своего кольцевого буфера истории (MVCC history). Если же история была сжата (`compacted`), клиент получает ошибку `ErrCompacted` и обязан выполнить полный перечит (Full Snapshot Resync).

## Подводные камни

Ошибка `ErrCompacted`: если периодический etcd auto-compaction удалил старые ревизии, а watcher долго находился в дисконнекте, вызов `Watch` вернет ошибку. Не обработав `ErrCompacted`, сервис навсегда останется со старой версией конфигурации. Обработчик обязан перехватывать эту ошибку и делать полный `clientv3.Get()` с актуальной ревизии.

## На собеседовании

В: Почему etcd не рекомендуется использовать как хранилище больших файлов или блобов?
О: etcd оптимизирован для небольших метаданных (до 1.5 МБ на ключ-значение по умолчанию `max-request-bytes`). Каждая запись проходит через Raft-лог и реплицируется в оперативную память всех членов кластера. Хранение больших объектов вызовет разрастание BoltDB, частые GC-паузы и деградацию времени отклика консенсуса.
