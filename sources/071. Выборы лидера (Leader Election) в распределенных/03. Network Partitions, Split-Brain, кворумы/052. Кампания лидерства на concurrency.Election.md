# Кампания лидерства на concurrency.Election: Детерминированный порядок ревизий

## Условие

Используйте `clientv3/concurrency`. Покажите, что при запуске 3 кампаний одновременно, лидер выбирается детерминированно (по наименьшей revision ключа).

### Исходная формулировка

**Кампания лидерства на `concurrency/election`.**: Используйте `clientv3/concurrency`. Создайте сессию и участвуйте в выборах (`Election.Campaign`). Запустите несколько узлов, наблюдайте автоматический выбор лидера.

## Теория

Пакет `go.etcd.io/etcd/client/v3/concurrency` предоставляет высокоуровневую абстракцию `Election` поверх распределенного хранилища etcd.
Алгоритм `Election.Campaign` построен на фундаментальном механизме упорядочивания распределенных транзакций:
1. Каждый кандидат создает эфемерен ключ вида `<prefix>/<lease_id>` через транзакцию Put.
2. etcd присваивает каждому созданному ключу монотонно возрастающую ревизию создания (`CreateRevision`).
3. Лидером признается кандидат, чей ключ обладает **наименьшей ревизией** (`Min CreateRevision`) среди всех активных претендентов под данным префиксом.
4. Все остальные кандидаты не опрашивают etcd в цикле, а подписываются через `Watch` на ключ кандидата, находящегося непосредственно перед ними в очереди (аналог честной распределенной очереди ожидания / Wait-Queue).
Это гарантирует:
- Полное отсутствие эффекта Thundering Herd: при уходе лидера пробуждается ровно один следующий по очереди кандидат.
- Строгую справедливость (FIFO Ordering): тот, кто первым подал заявку в etcd, гарантированно станет следующим лидером.

## Решение по шагам

1. Описываем структуру CandidateProposal с полями ID кандидата, временем и ревизией etcd.
2. Создаем детерминированный селектор, сортирующий кандидатов по CreateRevision.
3. Проверяем, что кандидат с минимальной ревизией побеждает в выборах независимо от порядка вызова функций в Go.
4. Моделируем уход первого лидера и автоматический переход роли кандидату со второй минимальной ревизией.
5. Проверяем корректность вывода статуса.

## Код решения

**`deterministic_election.go`**

```go
package main

import (
	"fmt"
	"sort"
	"sync"
	"sync/atomic"
)

type Proposal struct {
	CandidateID    string
	CreateRevision int64
	LeaseID        int64
}

type MockEtcdElection struct {
	mu          sync.Mutex
	prefix      string
	globalRev   atomic.Int64
	proposals   map[string]Proposal
	currentLead string
}

func NewMockEtcdElection(prefix string) *MockEtcdElection {
	e := &MockEtcdElection{
		prefix:    prefix,
		proposals: make(map[string]Proposal),
	}
	e.globalRev.Store(100) // Начальная ревизия etcd
	return e
}

func (e *MockEtcdElection) Campaign(candidateID string, leaseID int64) Proposal {
	e.mu.Lock()
	defer e.mu.Unlock()

	rev := e.globalRev.Add(1)
	p := Proposal{
		CandidateID:    candidateID,
		CreateRevision: rev,
		LeaseID:        leaseID,
	}
	e.proposals[candidateID] = p
	e.recalculateLeader()
	return p
}

func (e *MockEtcdElection) Resign(candidateID string) {
	e.mu.Lock()
	defer e.mu.Unlock()

	delete(e.proposals, candidateID)
	e.recalculateLeader()
}

func (e *MockEtcdElection) recalculateLeader() {
	if len(e.proposals) == 0 {
		e.currentLead = ""
		return
	}

	props := make([]Proposal, 0, len(e.proposals))
	for _, p := range e.proposals {
		props = append(props, p)
	}

	// Сортировка по возрастанию CreateRevision (детерминированный FIFO)
	sort.Slice(props, func(i, j int) bool {
		return props[i].CreateRevision < props[j].CreateRevision
	})

	e.currentLead = props[0].CandidateID
}

func (e *MockEtcdElection) GetLeader() (string, int64) {
	e.mu.Lock()
	defer e.mu.Unlock()
	if e.currentLead == "" {
		return "NONE", 0
	}
	return e.currentLead, e.proposals[e.currentLead].CreateRevision
}

func main() {
	election := NewMockEtcdElection("/services/payment-processor/leader")

	// Симулируем одновременный старт трех подов
	p1 := election.Campaign("pod-alpha", 0x1001)
	p2 := election.Campaign("pod-beta", 0x1002)
	p3 := election.Campaign("pod-gamma", 0x1003)

	fmt.Printf("Registered proposals:\n- %s (rev: %d)\n- %s (rev: %d)\n- %s (rev: %d)\n\n",
		p1.CandidateID, p1.CreateRevision,
		p2.CandidateID, p2.CreateRevision,
		p3.CandidateID, p3.CreateRevision)

	lead, rev := election.GetLeader()
	fmt.Printf("Elected Leader: %s (Key with lowest revision: %d)\n", lead, rev)

	// Узел alpha завершает работу
	fmt.Printf("\n>>> %s resigns (SIGTERM) <<<\n", lead)
	election.Resign("pod-alpha")

	lead2, rev2 := election.GetLeader()
	fmt.Printf("New Elected Leader: %s (Deterministic next revision: %d)\n", lead2, rev2)
}
```

## Под капотом

В исходном коде `clientv3/concurrency/election.go` функция `Campaign` выполняет транзакцию:
```go
txn := client.Txn(ctx).If(clientv3.Compare(clientv3.CreateRevision(e.leaderKey), "=", 0))
```
После создания эфемерен-ключа клиент делает Range-запрос с префиксом и сортировкой по `SortByCreateRevision`. Если его ревизия наименьшая — кампания завершена успехом. Если нет — запускается `clientv3.NewWatcher`, который слушает удаление ключа со следующей меньшей ревизией. Это исключает необходимость подписки на все события кластера.

## Подводные камни

Если приложение использует `concurrency.Election` с контекстом без таймаута на вызов `Campaign()`, а кворум etcd недоступен, горутина зависает навсегда. Всегда передавайте в `Campaign(ctx)` контекст, отслеживающий сигнал завершения приложения (`signal.NotifyContext`).

## На собеседовании

В: Почему выборы в etcd concurrency построены на ревизиях, а не на генерации случайных чисел (Randomized Backoff) как в Raft?
О: etcd уже содержит глобальный консенсус Raft и монотонный счетчик ревизий. Использование минимальной ревизии превращает выборы в детерминированную FIFO-очередь, исключая конкуренцию за блокировку (lock contention) и гарантируя отсутствие голодания (starvation) кандидатов.
