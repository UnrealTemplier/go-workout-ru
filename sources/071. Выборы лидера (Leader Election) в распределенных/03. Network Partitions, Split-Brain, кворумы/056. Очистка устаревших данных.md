# Очистка устаревших данных: Паттерн Leader Garbage Collection

## Условие

Только leader запускает cleanup jobs (удаление expired сессий, soft-deleted записей). Фоновые воркеры на других репликах не создают нагрузку на БД.

### Исходная формулировка

**Leader election + garbage collection**: Только leader запускает cleanup jobs (удаление старых записей, orphaned resources).

## Теория

Периодическая очистка устаревших записей (Garbage Collection / Data Retention Cleanup) — классический источник деградации производительности СУБД (PostgreSQL, MySQL, MongoDB).
Если каждая реплика микросервиса запустит собственный цикл `DELETE FROM sessions WHERE expires_at < NOW()`, возникнут:
1. Deadlocks на уровне строк/страниц БД из-за одновременных конфликтующих блокировок `ROW EXCLUSIVE`.
2. Высокая нагрузка на дисковый ввод-вывод (IOPS) и генерация гигантских объемов WAL логов.
3. Проблемы с репликационным лагом (Replication Lag) на фоловерах базы данных.
Паттерн Leader Garbage Collection делегирует очистку строго текущему лидеру с порционным удалением (Chunking / Batched Deletion) и задержкой между пачками (Throttling).

## Решение по шагам

1. Создаем структуру CleanupWorker с ограничением batch size и задержкой между итерациями.
2. Проверяем статус лидерства перед каждой пачкой: если лидерство утеряно в процессе удаления, немедленно прерываем цикл.
3. Реализуем удаление пакетами по N записей с `time.Sleep` для снижения утилизации CPU базы.
4. Проверяем поведение системы при отзыве лидерства прямо во время процедуры очистки.

## Код решения

**`leader_gc_cleanup.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"
)

type DatabaseRecord struct {
	ID        int
	ExpiredAt time.Time
}

type MockDB struct {
	records []DatabaseRecord
}

func (db *MockDB) DeleteExpiredBatch(now time.Time, limit int) int {
	retained := make([]DatabaseRecord, 0, len(db.records))
	deleted := 0

	for _, r := range db.records {
		if deleted < limit && r.ExpiredAt.Before(now) {
			deleted++
		} else {
			retained = append(retained, r)
		}
	}
	db.records = retained
	return deleted
}

type LeaderGarbageCollector struct {
	nodeID    string
	isLeader  atomic.Bool
	batchSize int
	throttle  time.Duration
	db        *MockDB
}

func NewLeaderGarbageCollector(nodeID string, batchSize int, throttle time.Duration, db *MockDB) *LeaderGarbageCollector {
	return &LeaderGarbageCollector{
		nodeID:    nodeID,
		batchSize: batchSize,
		throttle:  throttle,
		db:        db,
	}
}

func (c *LeaderGarbageCollector) SetLeader(leading bool) {
	c.isLeader.Store(leading)
}

func (c *LeaderGarbageCollector) RunCleanup(ctx context.Context) (int, error) {
	if !c.isLeader.Load() {
		return 0, fmt.Errorf("[%s] Not a leader: skipping GC cycle", c.nodeID)
	}

	totalDeleted := 0
	fmt.Printf("[%s] LEADER GC: Starting batched cleanup loop (batchSize=%d)...\n", c.nodeID, c.batchSize)

	for {
		select {
		case <-ctx.Done():
			return totalDeleted, ctx.Err()
		default:
		}

		// Проверяем статус лидера перед каждым пакетом
		if !c.isLeader.Load() {
			fmt.Printf("[%s] Leadership lost mid-cleanup! Halting operations.\n", c.nodeID)
			return totalDeleted, nil
		}

		deleted := c.db.DeleteExpiredBatch(time.Now(), c.batchSize)
		totalDeleted += deleted

		if deleted > 0 {
			fmt.Printf("[%s] Deleted chunk of %d expired records. Sleeping %v for DB throttle...\n",
				c.nodeID, deleted, c.throttle)
		}

		if deleted < c.batchSize {
			// Все устаревшие записи удалены
			break
		}

		time.Sleep(c.throttle)
	}

	fmt.Printf("[%s] LEADER GC: Completed. Total purged: %d\n", c.nodeID, totalDeleted)
	return totalDeleted, nil
}

func main() {
	now := time.Now()
	// Создаем базу данных с 15 просроченными записями
	records := make([]DatabaseRecord, 15)
	for i := 0; i < 15; i++ {
		records[i] = DatabaseRecord{
			ID:        i + 1,
			ExpiredAt: now.Add(-1 * time.Hour),
		}
	}

	db := &MockDB{records: records}
	gc := NewLeaderGarbageCollector("worker-pod-0", 5, 50*time.Millisecond, db)

	// Запуск в роли фоловера
	_, err := gc.RunCleanup(context.Background())
	fmt.Printf("Initial run result: %v\n\n", err)

	// Получение лидерства и запуск порционной очистки
	gc.SetLeader(true)
	purged, _ := gc.RunCleanup(context.Background())
	fmt.Printf("Final verification: Purged %d records, remaining in DB: %d\n", purged, len(db.records))
}
```

## Под капотом

Почему порционное удаление (`LIMIT batch_size`) обязательно для реляционных БД? Запрос `DELETE FROM table WHERE expired_at < NOW()` без лимита накладывает эксклюзивную блокировку на всю таблицу или гигантский диапазон индексов (Gap Locks в InnoDB), что парализует транзакции пользователей. Порционное удаление короткими транзакциями позволяет планировщику СУБД вставлять пользовательские транзакции между чанками и запускать autovacuum без всплесков задержки.

## Подводные камни

Потеря лидерства в середине долгой транзакции: если удаление выполняется в одной нераздельной транзакции на 1 миллион строк, а узел потерял связь с etcd, транзакция в БД все равно закоммитится, создав фантомную конкуренцию с новым лидером. Всегда коммитьте каждую небольшую пачку отдельно (`autocommit` per batch).

## На собеседовании

В: Как организовать очистку миллиардов устаревших записей в HighLoad PostgreSQL?
О: Вместо `DELETE` используют партиционирование по времени (Declarative Time-based Table Partitioning, например, по дням). Очистка вчерашних данных превращается в моментальную DDL-операцию `DROP TABLE orders_2025_01_01`, которая не генерирует WAL логов и завершается за доли миллисекунды без блокировки строк.
