# Комплексный чек-лист Failover-тестирования в CI/CD пайплайнах

## Условие

Регулярно тестируйте failover: убивайте leader, проверяйте zero duplicate processing, замеряйте downtime. Сформируйте автоматизированный интеграционный тест.

### Исходная формулировка

**Leader failover testing.**: Регулярно тестируйте failover: убивайте leader, проверяйте, что новый leader избирается в течение TTL.

## Теория

Интеграционное тестирование отказоустойчивости (Failover Integration Testing) — обязательный этап Continuous Delivery для критических сервисов.
Тестовый сценарий проверки отказоустойчивости включает 4 строгие фазы:
1. **Steady State Baseline:** замер пропускной способности (RPS) и задержки в нормальном режиме с одним лидером.
2. **Chaos Injection:** принудительное уничтожение процесса лидера (`SIGKILL` / `kill -9`).
3. **Failover Invariant Assertions:**
   - Zero Data Loss: ни одна подтвержденная транзакция не потеряна.
   - Zero Duplicate Processing: ни одна операция не выполнена дважды.
   - Bounded Downtime: новый лидер избран за время \(T_{down} \le TTL + \epsilon\).
4. **Recovery & Stability:** восстановление узла и проверка его мирного возвращения в роли фоловера.

## Решение по шагам

1. Создаем структуру FailoverTestHarness с метриками дубликатов и времени простоя.
2. Запускаем поток задач в фоновом режиме.
3. В середине теста симулируем резкое уничтожение лидера.
4. Фиксируем момент избрания нового лидера и рассчитываем точный даунтайм.
5. Проверяем счетчик дубликатов: он обязан быть равен строго 0.

## Код решения

**`automated_failover_test.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type FailoverReport struct {
	TotalProcessed     int64
	DuplicateCount     int64
	DowntimeDuration   time.Duration
	FailoverSuccessful bool
}

type ResilientClusterTest struct {
	mu            sync.Mutex
	activeLeader  string
	processedMap  map[string]string
	duplicates    atomic.Int64
	totalOps      atomic.Int64
	isClusterDown atomic.Bool
}

func NewResilientClusterTest() *ResilientClusterTest {
	return &ResilientClusterTest{
		activeLeader: "leader-node-01",
		processedMap: make(map[string]string),
	}
}

func (c *ResilientClusterTest) ProcessOperation(taskID string, payload string) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	if c.isClusterDown.Load() || c.activeLeader == "" {
		return false
	}

	if prevWorker, exists := c.processedMap[taskID]; exists {
		fmt.Printf("FAILOVER ASSERTION ERROR: Task %s was already processed by %s! Duplicate by %s!\n",
			taskID, prevWorker, c.activeLeader)
		c.duplicates.Add(1)
		return false
	}

	c.processedMap[taskID] = c.activeLeader
	c.totalOps.Add(1)
	return true
}

func (c *ResilientClusterTest) KillActiveLeader() {
	c.mu.Lock()
	defer c.mu.Unlock()
	fmt.Printf("\n>>> CHAOS INJECTED: Terminating %s with SIGKILL <<<\n", c.activeLeader)
	c.activeLeader = ""
	c.isClusterDown.Store(true)
}

func (c *ResilientClusterTest) ElectNewLeader(newLeaderID string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.activeLeader = newLeaderID
	c.isClusterDown.Store(false)
	fmt.Printf(">>> ELECTION RESOLVED: %s elected as NEW LEADER <<<\n\n", newLeaderID)
}

func main() {
	test := NewResilientClusterTest()

	// 1. Успешная обработка первых задач
	for i := 1; i <= 3; i++ {
		test.ProcessOperation(fmt.Sprintf("tx-%03d", i), "payload")
	}

	// 2. Внезапный сбой лидера
	killTime := time.Now()
	test.KillActiveLeader()

	// Имитируем попытку записи в момент отсутствия лидера
	ok := test.ProcessOperation("tx-004", "payload")
	fmt.Printf("Write attempt during downtime: Success = %v (Correctly rejected/queued)\n", ok)

	// Время на обнаружение и выборы (350 мс)
	time.Sleep(350 * time.Millisecond)
	test.ElectNewLeader("standby-node-02")
	downtime := time.Since(killTime)

	// 3. Продолжение работы новым лидером
	for i := 4; i <= 6; i++ {
		test.ProcessOperation(fmt.Sprintf("tx-%03d", i), "payload")
	}

	report := FailoverReport{
		TotalProcessed:     test.totalOps.Load(),
		DuplicateCount:     test.duplicates.Load(),
		DowntimeDuration:   downtime,
		FailoverSuccessful: test.duplicates.Load() == 0,
	}

	fmt.Println("=== AUTOMATED FAILOVER TEST REPORT ===")
	fmt.Printf("Total operations committed: %d\n", report.TotalProcessed)
	fmt.Printf("Duplicate executions: %d (Zero tolerance requirement)\n", report.DuplicateCount)
	fmt.Printf("Measured cluster downtime: %v\n", report.DowntimeDuration)
	fmt.Printf("Test Result: PASSED = %v\n", report.FailoverSuccessful)
}
```

## Под капотом

В enterprise CI/CD такие тесты запускаются в ephemeral окружениях через Testcontainers-Go или KinD (Kubernetes-in-Docker). Тест использует Docker API для отправки `docker kill --signal=SIGKILL <container_id>` и проверяет, что клиентский gRPC SDK автоматически выполнил failover на резервные адреса из resolver без возврата постоянных ошибок пользователю.

## Подводные камни

Тестирование только штатного `SIGTERM` без тестирования `SIGKILL`: при `SIGTERM` лидер вызывает `Resign()`, и тест проходит идеально. Но в продакшене узлы чаще погибают от OOM-killer (`SIGKILL`) или зависания сети, где `Resign` не выполняется. Тестируйте жесткое отключение питания (Hard Kill).
