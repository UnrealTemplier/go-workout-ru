# Архитектурная связь: Leader Election и Fencing Tokens (Блок 25 и 27)

## Условие

Блок 27 (Distributed Locks) — проходите параллельно с Leader Election, так как оба решают задачу mutual exclusion. Покажите генерацию и валидацию Fencing Token.

### Исходная формулировка

**Блок 27 (Distributed Locks)**: — проходите параллельно с Leader Election, так как оба используют etcd/Consul и сталкиваются с одной проблемой: lease expiration + network delay. Fencing Tokens — это мост между блокировками и консистентностью.

## Теория

Leader Election и Distributed Locking (Блоки 25 и 27) — две стороны одной медали:
- **Leader Election** — это долгоживущая распределенная блокировка (Coarse-grained long-held lock), удерживаемая процессом на протяжении минут или часов для координации всего кластера.
- **Distributed Lock** — это короткоживущая мелкогранулярная блокировка (Fine-grained short-lived lock), захватываемая на доли секунды для мутации конкретного ресурса (например, конкретного заказа).
Общая уязвимость обоих примитивов:
В асинхронных распределенных сетях ни один алгоритм блокировок (ни etcd, ни Redlock, ни Consul) не может гарантировать взаимное исключение при наличии сетевых пауз без **Fencing Tokens**.
Fencing Token — это монотонно возрастающее число (\(Token_{k+1} > Token_k\)), выдаваемое координатором каждому новому владельцу замка. Принимающая сторона (БД, S3, файловая система) отбрасывает любые запросы с токеном ниже уже зафиксированного.

## Решение по шагам

1. Создаем генератор FencingTokenGenerator на базе атомарных ревизий.
2. Реализуем модель базы данных с контролем версий fencing token.
3. Выдаем токен 1 Лидеру A, токен 2 Лидеру B.
4. Проверяем успешную запись Лидера B.
5. Проверяем автоматическое блокирование запоздалого пакета от Лидера A.

## Код решения

**`fencing_token_deep_dive.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
)

var (
	ErrStaleTokenFencing = errors.New("fencing error: transaction token is superseded by newer leader")
)

type FencingTokenDispenser struct {
	counter atomic.Int64
}

func (d *FencingTokenDispenser) NextToken() int64 {
	return d.counter.Add(1)
}

type DatabaseWithFencing struct {
	mu              sync.Mutex
	lastFencingSeen int64
	balance         int
}

func (db *DatabaseWithFencing) UpdateBalance(token int64, newBalance int) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	// Проверка барьера (Fencing Barrier)
	if token <= db.lastFencingSeen {
		return fmt.Errorf("%w: attempted token %d <= active token %d",
			ErrStaleTokenFencing, token, db.lastFencingSeen)
	}

	db.lastFencingSeen = token
	db.balance = newBalance
	fmt.Printf("[DB] Balance updated to $%d using Fencing Token #%d\n", newBalance, token)
	return nil
}

func main() {
	dispenser := &FencingTokenDispenser{}
	db := &DatabaseWithFencing{balance: 100}

	// Лидер 1 побеждает на выборах и получает Fencing Token 1
	token1 := dispenser.NextToken()
	fmt.Printf("Leader 1 elected with Fencing Token: %d\n", token1)

	// Лидер 1 завис... Происходят перевыборы.
	// Лидер 2 побеждает и получает Fencing Token 2
	token2 := dispenser.NextToken()
	fmt.Printf("Leader 2 elected with Fencing Token: %d\n", token2)

	// Лидер 2 успешно обновляет БД
	_ = db.UpdateBalance(token2, 200)

	// Старый Лидер 1 отмирает и пытается применить свои данные с токеном 1
	fmt.Println("\n>>> Zombie Leader 1 attempts to write with old token 1 <<<")
	err := db.UpdateBalance(token1, 150)

	if errors.Is(err, ErrStaleTokenFencing) {
		fmt.Printf("Security barrier worked: %v\n", err)
		fmt.Printf("Final DB state preserved: Balance=$%d\n", db.balance)
	}
}
```

## Под капотом

В etcd ревизия `Header.Revision` возвращается в ответе на каждую операцию `clientv3.Txn`. Это 64-битное монотонно возрастающее целое число, которое идеально подходит в качестве глобального Fencing Token. Передавая `res.Header.Revision` во все внешние вызовы, приложение получает математическую гарантию от split-brain.

## Подводные камни

Использование Unix-времени (`time.Now().UnixNano()`) в качестве Fencing Token: часы на серверах могут идти назад при синхронизации через NTP (NTP backwards slewing / stepping). Fencing Token ОБЯЗАН формироваться исключительно логическими часами (Logical Clocks / Lamport Timestamps / Raft Terms).

## На собеседовании

В: Почему распределенный замок без проверки токена на сервере хранения считается фундаментально небезопасным?
О: Потому что клиент не может знать, удерживает ли он замок в тот момент, когда его сетевой пакет фактически достигнет сервера хранения. Задержка в сети или пауза GC делают любые проверки на стороне клиента неактуальными. Только принимающая сторона (хранилище) может принять решение о допуске операции на основе монотонного токена.
