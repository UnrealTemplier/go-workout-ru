# API наблюдения за выборами (Observe): Эндпоинт /leader и проверка роли

## Условие

Напиши API-эндпоинт `/leader`, который возвращает: (1) имя текущего Лидера, (2) статус текущего инстанса (`is_leader: true/false`), (3) время с момента последнего обновления lease.

### Исходная формулировка

**Наблюдение за выборами (Observe)**: Напиши API-эндпоинт `/leader`, который возвращает, кто сейчас главный. Используй метод `election.Observe()`, который возвращает канал обновлений. Все узлы должны всегда знать имя текущего лидера (например, для перенаправления к нему трафика).

## Теория

В распределенной системе оркестраторам (Kubernetes, Consul, Nomad) и сервисным шлюзам (Ingress / API Gateway) требуется знать точный статус каждого экземпляра приложения:
Эндпоинт `/leader` или `/v1/cluster/role` предоставляет исчерпывающую информацию:
1. `leader_identity`: сетевое имя или ID текущего лидера кластера (позволяет клиентам перенаправлять запросы).
2. `is_leader`: булевый флаг роли текущего пода.
3. `lease_age_ms`: время с момента последнего подтверждения аренды в миллисекундах.
4. `lease_ttl_ms`: исходный TTL аренды.
Эти данные используются L7-балансировщиками для динамической маршрутизации трафика на легитимного лидера без лишних редиректов.

## Решение по шагам

1. Создаем структуру LeaderStatusResponse для JSON-сериализации.
2. Создаем HTTP-хэндлер LeaderInfoHandler с потокобезопасным чтением статуса.
3. Тестируем эндпоинт через `httptest.NewRecorder` для инстанса-лидера.
4. Тестируем эндпоинт для инстанса-фоловера.
5. Валидируем корректность формируемого JSON-ответа.

## Код решения

**`leader_http_status.go`**

```go
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"sync"
	"time"
)

type LeaderStatusResponse struct {
	CurrentLeader string `json:"current_leader"`
	IsLeader      bool   `json:"is_leader"`
	NodeID        string `json:"node_id"`
	LeaseAgeMs    int64  `json:"lease_age_ms"`
	LeaseTTLMs    int64  `json:"lease_ttl_ms"`
}

type NodeStatusProvider struct {
	mu            sync.RWMutex
	nodeID        string
	currentLeader string
	isLeader      bool
	lastHeartbeat time.Time
	leaseTTL      time.Duration
}

func (p *NodeStatusProvider) LeaderStatusHandler(w http.ResponseWriter, r *http.Request) {
	p.mu.RLock()
	defer p.mu.RUnlock()

	leaseAge := time.Since(p.lastHeartbeat).Milliseconds()
	resp := LeaderStatusResponse{
		CurrentLeader: p.currentLeader,
		IsLeader:      p.isLeader,
		NodeID:        p.nodeID,
		LeaseAgeMs:    leaseAge,
		LeaseTTLMs:    p.leaseTTL.Milliseconds(),
	}

	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(resp)
}

func main() {
	providerLeader := &NodeStatusProvider{
		nodeID:        "pod-order-svc-0",
		currentLeader: "pod-order-svc-0",
		isLeader:      true,
		lastHeartbeat: time.Now().Add(-120 * time.Millisecond),
		leaseTTL:      5 * time.Second,
	}

	providerFollower := &NodeStatusProvider{
		nodeID:        "pod-order-svc-1",
		currentLeader: "pod-order-svc-0",
		isLeader:      false,
		lastHeartbeat: time.Now().Add(-340 * time.Millisecond),
		leaseTTL:      5 * time.Second,
	}

	// 1. Проверяем ответ от Лидера
	req := httptest.NewRequest(http.MethodGet, "/leader", nil)
	recLeader := httptest.NewRecorder()
	providerLeader.LeaderStatusHandler(recLeader, req)
	fmt.Println("=== Response from LEADER node ===")
	fmt.Println(recLeader.Body.String())

	// 2. Проверяем ответ от Фоловера
	recFollower := httptest.NewRecorder()
	providerFollower.LeaderStatusHandler(recFollower, req)
	fmt.Println("=== Response from FOLLOWER node ===")
	fmt.Println(recFollower.Body.String())
}
```

## Под капотом

В микросервисной архитектуре эти данные отдаются через `clientv3.Election.Leader(ctx)`. Вызов `Leader(ctx)` делает чтение ключа префикса с сортировкой по `CreateRevision`. Для максимальной производительности статус текущего лидера кэшируется в оперативной памяти через постоянную подписку `Election.Observe(ctx)`, чтобы эндпоинт `/leader` отдавал ответ за доли микросекунды из RAM без обращения к сети.

## Подводные камни

Вызов синхронного сетевого RPC к etcd на каждый HTTP-запрос к `/leader`: если эндпоинт опрашивается балансировщиком каждые 100 мс от десятков клиентов, синхронный запрос в etcd перегрузит кластер координации. Всегда отдавайте статус из локального потокобезопасного кэша памяти, обновляемого через Watcher.

## На собеседовании

В: Как использовать эндпоинт `/leader` для реализации Zero-Downtime Blue/Green деплоя?
О: Балансировщик направляет трафик на поды, у которых `is_leader: true`. При обновлении версии сначала поднимается новый кластер Green. Когда он готов, старый Blue лидер слагает полномочия (`Resign`), Green захватывает лидерство, а балансировщик по ответу `/leader` мгновенно переключает весь входящий поток на новый Green-кластер.
