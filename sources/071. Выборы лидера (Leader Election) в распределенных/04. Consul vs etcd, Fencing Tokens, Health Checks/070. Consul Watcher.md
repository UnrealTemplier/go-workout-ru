# Consul Watcher: Отслеживание лидера через блокирующие запросы (Blocking Queries)

## Условие

Напиши логику Фоловера в Consul. Он должен использовать 'блокирующий запрос' (Blocking Query с `WaitIndex`), чтобы мгновенно узнать, когда текущий Лидер упадет и ключ освободится.

### Исходная формулировка

**Consul Watcher (Отслеживание)**: Напиши логику Фоловера. Он должен использовать "блокирующий запрос" (Blocking Query) в Consul, чтобы висеть в ожидании и следить за ключом `service/billing/leader`. Как только Лидер падает (ключ освобождается), Фоловеры просыпаются и пытаются сделать `Acquire`.

## Теория

В HashiCorp Consul для эффективного отслеживания изменений ключей используется механизм Blocking Queries (HTTP Long Polling с индексами Raft).
Как работает Blocking Query:
1. Клиент делает GET-запрос к Consul KV: `KV.Get(key, &api.QueryOptions{WaitIndex: lastIndex, WaitTime: 10 * time.Minute})`.
2. Сервер Consul смотрит на внутренний индекс ревизии ключа (`ModifyIndex`).
3. Если текущий индекс ключа \(\le WaitIndex\), сервер Consul **НЕ отвечает сразу**, а подвешивает HTTP-соединение.
4. В момент, когда лидер падает или освобождает сессию, Consul атомарно инкрементирует `ModifyIndex` ключа и немедленно отправляет HTTP-ответ клиенту.
5. Клиент фоловера моментально пробуждается и инициирует `KV.Acquire()`.
Это исключает постоянный опрос (busy-wait polling) и снижает сетевой трафик практически до нуля.

## Решение по шагам

1. Создаем структуру ConsulBlockingClient с эмуляцией Blocking Query.
2. Реализуем метод WatchKey(ctx, key, lastIndex) с каналом пробуждения.
3. Фоновый воркер Standby вызывает WatchKey и засыпает до изменения индекса.
4. Моделируем падение лидера: ModifyIndex инкрементируется, фоловер пробуждается.
5. Проверяем переход фоловера к процедуре выборов.

## Код решения

**`consul_blocking_watcher.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type ConsulKVPair struct {
	Key         string
	Value       string
	Session     string
	ModifyIndex uint64
}

type MockConsulServer struct {
	mu        sync.Mutex
	entry     ConsulKVPair
	listeners map[chan struct{}]uint64
}

func NewMockConsulServer(key string) *MockConsulServer {
	return &MockConsulServer{
		entry: ConsulKVPair{
			Key:         key,
			Value:       "node-primary",
			Session:     "session-lead-999",
			ModifyIndex: 100,
		},
		listeners: make(map[chan struct{}]uint64),
	}
}

func (s *MockConsulServer) BlockingGet(ctx context.Context, waitIndex uint64) (ConsulKVPair, error) {
	s.mu.Lock()
	if s.entry.ModifyIndex > waitIndex {
		// Индекс уже изменился, отдаем немедленно
		pair := s.entry
		s.mu.Unlock()
		return pair, nil
	}

	notifyCh := make(chan struct{})
	s.listeners[notifyCh] = waitIndex
	s.mu.Unlock()

	defer func() {
		s.mu.Lock()
		delete(s.listeners, notifyCh)
		s.mu.Unlock()
	}()

	select {
	case <-ctx.Done():
		return ConsulKVPair{}, ctx.Err()
	case <-notifyCh:
		s.mu.Lock()
		pair := s.entry
		s.mu.Unlock()
		return pair, nil
	}
}

func (s *MockConsulServer) InvalidateLeaderSession() {
	s.mu.Lock()
	defer s.mu.Unlock()

	s.entry.Session = ""
	s.entry.Value = ""
	s.entry.ModifyIndex++
	fmt.Printf("[Consul Server] Session expired! New ModifyIndex=%d. Waking up watchers...\n", s.entry.ModifyIndex)

	for ch := range s.listeners {
		close(ch)
	}
	s.listeners = make(map[chan struct{}]uint64)
}

func FollowerWatcherLoop(ctx context.Context, srv *MockConsulServer, followerID string) {
	var lastIndex uint64 = 100
	fmt.Printf("[%s] Starting Blocking Query watch on leader key with WaitIndex=%d...\n", followerID, lastIndex)

	pair, err := srv.BlockingGet(ctx, lastIndex)
	if err != nil {
		fmt.Printf("[%s] Watch error: %v\n", followerID, err)
		return
	}

	fmt.Printf("[%s] WOKE UP! Consul index changed to %d. Active session: '%s'\n",
		followerID, pair.ModifyIndex, pair.Session)

	if pair.Session == "" {
		fmt.Printf("[%s] Leader lock is VACANT! Initiating KV.Acquire() immediately!\n", followerID)
	}
}

func main() {
	server := NewMockConsulServer("service/order-scheduler/leader")
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	// Запуск фоловера в фоне
	done := make(chan struct{})
	go func() {
		FollowerWatcherLoop(ctx, server, "follower-node-beta")
		close(done)
	}()

	time.Sleep(300 * time.Millisecond)

	// Симулируем смерть сессии лидера на сервере Consul
	server.InvalidateLeaderSession()

	<-done
	fmt.Println("Consul blocking query watcher pattern successfully verified.")
}
```

## Под капотом

Под капотом Consul держит список горутин `blockingQuery` на каждый префикс. Запрос использует TCP HTTP/1.1 Keep-Alive соединение. Если в течение `WaitTime` (обычно до 10 минут) изменений не произошло, Consul возвращает клиенту HTTP 200 с текущим неизменным `X-Consul-Index`. Клиент Go SDK в цикле `for` немедленно повторяет запрос с тем же индексом. Это гарантирует непрерывную бдительность при минимальном расходе процессорного времени.

## Подводные камни

Отсутствие таймаута соединения (TCP Idle Timeout): если промежуточный облачный балансировщик (AWS ALB / Cloudflare) молча разрывает idle TCP-сокет через 60 секунд, клиентский `http.Client` может бесконечно висеть на мертвом сокете, не получая событий. Обязательно настраивайте `WaitTime: 60s` и `net.Dialer.KeepAlive: 15s`.

## На собеседовании

В: В чем разница между gRPC Watch в etcd и Blocking Query в Consul?
О: etcd использует постоянный HTTP/2 gRPC стрим: одно соединение мультиплексирует сотни подписок, а события приходят в виде push-фреймов. Consul использует HTTP Long Polling: на каждое ожидание открывается отдельный HTTP-запрос, который завершается при первом же событии, после чего клиент обязан инициировать новый HTTP-запрос.
