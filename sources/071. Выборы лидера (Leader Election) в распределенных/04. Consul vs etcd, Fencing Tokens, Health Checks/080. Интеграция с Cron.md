# Интеграция с Cron: Планировщик фоновых джоб под защитой Лидера

## Условие

Возьми библиотеку `github.com/robfig/cron/v3`. Напиши джобу, которая выполняется каждые 10 секунд, но ТОЛЬКО если узел в данный момент является Лидером. Если лидер сменился — джоба на старом узле не стреляет.

### Исходная формулировка

**Интеграция с Cron**: Возьми библиотеку `github.com/robfig/cron/v3`. Напиши джобу, которая выполняется каждую минуту. Внутри джобы добавь проверку: `if !IsLeader() { return }`. Запусти 3 инстанса сервиса и убедись, что джоба выполняется строго 1 раз в минуту одним сервисом.

## Теория

Библиотека `robfig/cron/v3` — стандарт де-факто для планирования cron-задач в Go-приложениях.
Однако стандартный `cron.Cron` ничего не знает о распределенном окружении: он запускает зарегистрированные таймеры локально в каждом процессе.
Для интеграции cron с Leader Election применяется паттерн Decorator / Guarded Job:
1. Создается обертка `LeaderGuardedJob`, реализующая интерфейс `cron.Job` (метод `Run()`).
2. Внутри метода `Run()` перед вызовом полезной нагрузки проверяется атомарный статус лидерства:
```go
if !leaderProvider.IsLeader() {
    return // Пропускаем такт на фоловере
}
```
3. Если статус `isLeader == true`, джоба выполняется.
4. При смене лидера на фоловере cron продолжает тикать, но все вызовы мгновенно выходят без побочных эффектов. Новый лидер при следующем такте cron автоматически берет выполнение на себя.

## Решение по шагам

1. Создаем структуру LeaderJobWrapper с проверкой статуса лидерства.
2. Создаем симулятор Cron-планировщика, запускающего джобы каждые N миллисекунд.
3. Запускаем две ноды: Node-A (лидер) и Node-B (фоловер).
4. Наблюдаем исполнение задач строго на Node-A.
5. Переключаем лидерство на Node-B и подтверждаем прекращение выполнения на Node-A и старт на Node-B.

## Код решения

**`cron_leader_integration.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"
)

type LeaderProvider interface {
	IsLeader() bool
}

type GuardedCronJob struct {
	name     string
	provider LeaderProvider
	action   func()
}

func NewGuardedCronJob(name string, provider LeaderProvider, action func()) *GuardedCronJob {
	return &GuardedCronJob{
		name:     name,
		provider: provider,
		action:   action,
	}
}

func (j *GuardedCronJob) Run() {
	if !j.provider.IsLeader() {
		// Реплика в режиме ожидания: такт пропускается
		return
	}
	j.action()
}

type ClusterInstance struct {
	nodeID   string
	isLeader atomic.Bool
}

func (c *ClusterInstance) IsLeader() bool {
	return c.isLeader.Load()
}

func (c *ClusterInstance) SetLeader(v bool) {
	c.isLeader.Store(v)
}

func main() {
	nodeA := &ClusterInstance{nodeID: "node-A"}
	nodeB := &ClusterInstance{nodeID: "node-B"}

	nodeA.SetLeader(true) // Node A изначально лидер
	nodeB.SetLeader(false)

	jobA := NewGuardedCronJob("InvoiceAggregation", nodeA, func() {
		fmt.Printf("[%s] CRON TRIGGERED: Executing invoice batch aggregation!\n", nodeA.nodeID)
	})

	jobB := NewGuardedCronJob("InvoiceAggregation", nodeB, func() {
		fmt.Printf("[%s] CRON TRIGGERED: Executing invoice batch aggregation!\n", nodeB.nodeID)
	})

	// Симулируем 3 такта cron
	fmt.Println("=== Round 1 & 2: Node A is Leader ===")
	jobA.Run()
	jobB.Run()

	time.Sleep(100 * time.Millisecond)
	jobA.Run()
	jobB.Run()

	// Переключение лидера (Failover)
	fmt.Println("\n>>> FAILOVER OCCURS: Node A demoted, Node B promoted <<<")
	nodeA.SetLeader(false)
	nodeB.SetLeader(true)

	fmt.Println("\n=== Round 3: Node B is Leader ===")
	jobA.Run()
	jobB.Run()
}
```

## Под капотом

Для предотвращения гонок при долгих задачах (когда задача началась на лидере, но в процессе ее выполнения узел потерял лидерство), в метод `Run()` передается `context.Context`, привязанный к лидерскому контексту. Если лидер теряет аренду в etcd, контекст отменяется, прерывая SQL-запросы или HTTP-вызовы внутри джобы (`db.QueryContext(ctx, ...)`).

## Подводные камни

Запуск тяжелой джобы без проверки контекста внутри: если задача выполняется 5 минут, а лидер сменился на 30-й секунде, новый лидер через минуту запустит ту же задачу. Оба узла будут параллельно выполнять одну и ту же тяжелую обработку. Долгие cron-задачи обязаны периодически опрашивать `ctx.Err()` или проверять статус лидерства перед каждой пачкой данных.

## На собеседовании

В: Как гарантировать, что cron-джоба выполнится строго один раз (Exactly Once) даже при смене лидера в момент запуска?
О: Применяют паттерн Distributed Distributed Lock с уникальным ключом кванта времени (Time-Slot Lock), например: `/cron/locks/daily_report/2025-06-01-14:00`. Захват замка через CAS в etcd или Redis гарантирует, что даже если два лидера попытаются стартовать джобу за один и тот же час, замок получит только один из них.
