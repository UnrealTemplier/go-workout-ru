# Обязательность Leader Election для Singleton-задач

## Условие

Если задача должна выполняться ровно одним инстансом (например, генерация отчетов, списание денег) — Leader Election обязателен. Не полагайтесь на cron на каждом инстансе.

### Исходная формулировка

**Leader election обязателен для singleton задач.**: Если задача должна выполняться ровно одним инстансом (cron jobs, migrations, reconciliation) — используйте leader election через Consul/etcd.

## Теория

В микросервисной архитектуре запуск нескольких реплик одного сервиса — стандарт высокой доступности (High Availability).
Однако задачи класса Singleton (Singleton Tasks) категорически несовместимы с параллельным исполнением:
- Биллинг: периодическое списание абонентской платы с банковских карт.
- Генерация регуляторной отчетности в налоговую или ЦБ.
- Внешняя синхронизация со сторонними складами через неидемпотентный API.
Антипаттерн:
Развернуть 3 реплики сервиса и в каждой настроить `time.Ticker` на 00:00. В полночь все 3 реплики одновременно спишут деньги со всех пользователей трижды!
Единственное архитектурно корректное решение — централизованная координация через Leader Election. Все реплики активны, но Singleton-воркер запускается строго на инстансе, победившем в выборах.

## Решение по шагам

1. Создаем структуру BillingProcessor с флагом роли.
2. Реализуем метод ProcessMonthlyBilling(), выбрасывающий ошибку при попытке вызова non-leader узлом.
3. Запускаем 3 симулированных инстанса приложения.
4. Проверяем, что только избранный лидер выполняет списания.
5. Валидируем полное отсутствие повторных списаний.

## Код решения

**`singleton_billing_guard.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"sync/atomic"
)

var (
	ErrNonLeaderExecutionForbidden = errors.New("forbidden: singleton task must only execute on the elected leader")
)

type SingletonBillingProcessor struct {
	nodeID          string
	isLeader        bool
	processedLedger map[string]int
	mu              sync.Mutex
}

func NewBillingProcessor(nodeID string, isLeader bool) *SingletonBillingProcessor {
	return &SingletonBillingProcessor{
		nodeID:          nodeID,
		isLeader:        isLeader,
		processedLedger: make(map[string]int),
	}
}

func (p *SingletonBillingProcessor) ExecuteBillingBatch(customerID string, amount int) error {
	p.mu.Lock()
	defer p.mu.Unlock()

	if !p.isLeader {
		return ErrNonLeaderExecutionForbidden
	}

	p.processedLedger[customerID] += amount
	fmt.Printf("[%s] Charged customer %s: $%d (Total billed: $%d)\n",
		p.nodeID, customerID, amount, p.processedLedger[customerID])
	return nil
}

func main() {
	// Кластер из 3 реплик: только pod-0 является лидером
	instances := []*SingletonBillingProcessor{
		NewBillingProcessor("billing-pod-0", true),  // LEADER
		NewBillingProcessor("billing-pod-1", false), // FOLLOWER
		NewBillingProcessor("billing-pod-2", false), // FOLLOWER
	}

	var executionSuccess atomic.Int64
	var rejectedCount atomic.Int64

	fmt.Println("=== DISPATCHING BILLING EVENT TO ALL 3 REPLICAS ===")
	for _, inst := range instances {
		err := inst.ExecuteBillingBatch("cust-789", 50)
		if err == nil {
			executionSuccess.Add(1)
		} else {
			rejectedCount.Add(1)
			fmt.Printf("[%s] Blocked duplicate execution: %v\n", inst.nodeID, err)
		}
	}

	fmt.Printf("\nResult: Successfully executed by %d leader(s), Rejected by %d follower(s).\n",
		executionSuccess.Load(), rejectedCount.Load())
	fmt.Println("Singleton guarantee strictly enforced: Zero duplicate billing events.")
}
```

## Под капотом

В облачных средах (AWS, GCP, Yandex Cloud) для singleton-задач иногда используют Kubernetes CronJob с параметром `concurrencyPolicy: Forbid`. Однако запуск нового пода на каждый такт cron создает задержку в 5-15 секунд на подтягивание образов и старт JVM/Go-процесса. Постоянно запущенный демон с Leader Election реагирует за миллисекунды и держит прогретые пулы коннектов.

## Подводные камни

Полагаться на локальный `sync.Mutex` внутри процесса: мьютекс Go защищает от гонок между горутинами одного процесса, но абсолютно бесполезен против параллельных процессов на разных физических серверах или подах Kubernetes.

## На собеседовании

В: Почему паттерн Leader Election предпочтительнее распределенной блокировки Redis для тяжелых singleton-задач?
О: Распределенная блокировка Redis (SETNX) требует постоянного продления (heartbeat) по сети во время работы. Если GC задержит продление, блокировка снимется, и второй воркер начнет параллельную работу. Leader Election в etcd с сессиями обеспечивает непрерывный контроль роли и гарантированное уведомление об отставке через контекст.
