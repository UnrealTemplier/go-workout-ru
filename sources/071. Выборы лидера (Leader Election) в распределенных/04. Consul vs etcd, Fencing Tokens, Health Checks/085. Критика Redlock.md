# Критика Redlock: Почему Redlock — это best-effort, а не распределенный консенсус

## Условие

Redlock — это best-effort, не consensus: Redlock подходит для non-critical locks (rate limiting, deduplication). Для критических данных (financial transactions) используйте etcd/ZooKeeper/Raft с fencing tokens.

### Исходная формулировка

**Redlock — это best-effort, не consensus.**: Redlock подходит для non-critical locks. Для critical data используйте etcd/Consul locks или Raft.

## Теория

Известная полемика между Мартином Клеппманом (Martin Kleppmann, автор 'Designing Data-Intensive Applications') и Сальваторе Санфилиппо (antirez, автор Redis) о надежности алгоритма Redlock:
Почему Redlock фундаментально ненадежен для критических финансовых систем:
1. **Зависимость от физических часов (Synchronized Physical Clocks):** Redlock вычисляет валидность замка вычитанием времени \(TTL - (T_{end} - T_{start})\). Однако в распределенных системах физические часы подвержены скачкам (NTP jumps, leap seconds, clock drift).
2. **Паузы процесса (GC STW / VM Freeze):** Если процесс засыпает на GC-паузу сразу после захвата замка на 5 узлах Redis, замок истекает на серверах. Другой клиент захватывает замок. Старый клиент просыпается и считает замок своим!
3. **Отсутствие монотонных Fencing Tokens:** Redis не генерирует строгий монотонный `CreateRevision`, который можно проверить на целевом хранилище (PostgreSQL).
Вывод: Redlock идеален для задач оптимизации (дедупликация кэша, rate-limiting), но категорически запрещен для корректности данных без Fencing Tokens.

## Решение по шагам

1. Создаем структуру FencedStorage с защитой по номеру токена.
2. Реализуем метод WriteWithFencingToken(token, data), отвергающий токены меньше текущего.
3. Моделируем захват блокировки Клиентом 1 (токен 101).
4. Клиент 1 засыпает на длинную паузу; в это время Клиент 2 захватывает блокировку (токен 102) и пишет данные.
5. Клиент 1 просыпается и пытается записать свои устаревшие данные: хранилище отвергает запись.

## Код решения

**`fencing_token_protection.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

var (
	ErrStaleFencingToken = errors.New("storage rejected write: stale fencing token detected (split-brain prevented)")
)

type FencedDataStore struct {
	mu           sync.Mutex
	lastToken    int64
	storedValue  string
	rejectedRuns int
}

func NewFencedDataStore() *FencedDataStore {
	return &FencedDataStore{
		lastToken: 0,
	}
}

func (s *FencedDataStore) WriteData(token int64, val string) error {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Фундаментальное правило: токен обязан быть СТРОГО больше последнего примененного
	if token <= s.lastToken {
		s.rejectedRuns++
		fmt.Printf("[Storage Guard] REJECTED write from stale client! Incoming token=%d <= LastAppliedToken=%d\n",
			token, s.lastToken)
		return ErrStaleFencingToken
	}

	s.lastToken = token
	s.storedValue = val
	fmt.Printf("[Storage Guard] ACCEPTED write with Fencing Token %d: Value='%s'\n", token, val)
	return nil
}

func main() {
	storage := NewFencedDataStore()

	// Клиент 1 получил блокировку и токен 101
	tokenClient1 := int64(101)

	// Клиент 1 завис на паузе GC...
	fmt.Println("--- Client 1 acquired lock with Token 101, but freezes in GC pause ---")

	// Блокировка истекла по тайм-ауту. Клиент 2 захватывает блокировку и получает токен 102
	tokenClient2 := int64(102)
	fmt.Println("--- Client 2 acquires lock with higher Token 102 and writes immediately ---")
	_ = storage.WriteData(tokenClient2, "Data_from_Client_2")

	// Клиент 1 отмирает после GC и пытается отправить свою запись со старым токеном 101
	fmt.Println("\n--- Client 1 wakes up from GC and attempts to write with stale Token 101 ---")
	err := storage.WriteData(tokenClient1, "Data_from_Client_1")

	if errors.Is(err, ErrStaleFencingToken) {
		fmt.Printf("\nSUCCESS: Catastrophic data corruption prevented by Fencing Token!\n")
	}
}
```

## Под капотом

В исследовании Мартина Клеппмана 'How to do distributed locking' доказано: никакой алгоритм распределенного замка на клиенте не способен гарантировать безопасность (Safety), если ресурс на стороне хранилища не проверяет монотонно возрастающий Fencing Token. В PostgreSQL это реализуется через `CHECK (fencing_token > current_token)` или `WHERE fencing_token < $new_token`.

## Подводные камни

Использование Redlock в финансовых проводках без Fencing Tokens: надежда на то, что «у нас быстрый Redis и GC длится не более 5 мс», обязательно разобьется при первой же сетевой деградации в AWS/GCP, приведя к задвоению проводок.

## На собеседовании

В: В чем состояла суть спора Мартина Клеппмана и Сальваторе Санфилиппо касательно Redlock?
О: Клеппман доказал, что Redlock делает нереалистичные предположения о синхронности физических часов и отсутствии пауз выполнения. Если замок используется для эффективности (efficiency) — Redlock избыточен (достаточно одного Redis). Если для корректности (correctness) — Redlock недостаточен, так как без Fencing Tokens на стороне хранилища он не защищает от гонок при паузах клиентов.
