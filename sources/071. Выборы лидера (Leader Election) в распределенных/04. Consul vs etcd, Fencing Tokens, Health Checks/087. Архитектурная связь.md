# Архитектурная связь: Leader Election и идемпотентность (Блок 24 и 25)

## Условие

Блок 25 (Leader Election) — начните после Блока 24 (Idempotency), так как leader failover может дублировать запросы. Продемонстрируйте связку Leader Election с Idempotency Key.

### Исходная формулировка

**Блок 25 (Leader Election)**: — начните после Блока 24 (Idempotency), так как leader election — это частный случай координации, требующий понимания TTL и race conditions. Знания из Блока 1 (GMP, `sync`) помогут понять, почему in-memory leader election не работает при распределении.

## Теория

Почему Leader Election бессмыслен без идемпотентности (Idempotency)?
В распределенной системе существует фундаментальная граница неопределенности при сетевом сбое (Two Generals Problem):
1. Лидер получил запрос от клиента на списание $100.
2. Лидер отправил команду в платежный шлюз банка. Шлюз списал деньги.
3. До того, как лидер успел отправить клиенту ответ или записать факт в базу, сервер лидера теряет питание (Crash).
4. Кластер выбирает Нового Лидера.
5. Клиент, не получив ответа (Network Timeout), отправляет повторный запрос (Retry) на Нового Лидера.
Если Новый Лидер не обладает таблицей идемпотентности (`Idempotency-Key` в PostgreSQL), он повторно спишет деньги!
Архитектурная синергия: Leader Election обеспечивает единственность координатора, а Idempotency Keys обеспечивают безопасность повторных попыток при смене лидера.

## Решение по шагам

1. Создаем структуру IdempotentPaymentCoordinator.
2. Храним историю выполненных операций по уникальным Idempotency-Key.
3. Моделируем прерывание обработки на старом лидере.
4. Новый лидер принимает повторный запрос от клиента с тем же ключом.
5. Проверяем, что повторная операция возвращает сохраненный результат без повторного списания.

## Код решения

**`leader_idempotency_bridge.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type PaymentResult struct {
	TxID   string
	Status string
	Amount int
}

type SharedIdempotencyStore struct {
	mu      sync.Mutex
	records map[string]PaymentResult
}

func NewSharedIdempotencyStore() *SharedIdempotencyStore {
	return &SharedIdempotencyStore{
		records: make(map[string]PaymentResult),
	}
}

func (s *SharedIdempotencyStore) ExecuteIdempotent(idempotencyKey string, amount int, processFn func() string) (PaymentResult, bool) {
	s.mu.Lock()
	defer s.mu.Unlock()

	// Проверяем, не была ли операция выполнена ранее
	if existing, found := s.records[idempotencyKey]; found {
		return existing, true // true = дубликат перехвачен
	}

	// Выполняем полезную мутацию
	txID := processFn()
	res := PaymentResult{
		TxID:   txID,
		Status: "COMMITTED",
		Amount: amount,
	}
	s.records[idempotencyKey] = res
	return res, false
}

func main() {
	sharedDB := NewSharedIdempotencyStore()
	idempotencyKey := "req-uuid-8849-ab12"

	// 1. Старый Лидер обрабатывает первый запрос
	fmt.Println("=== 1. Old Leader receives transaction ===")
	res1, isDup1 := sharedDB.ExecuteIdempotent(idempotencyKey, 250, func() string {
		fmt.Println("[Old-Leader] Executed external banking payment RPC.")
		return "bank-tx-99901"
	})
	fmt.Printf("[Old-Leader] Processed: TxID=%s, Duplicate=%v\n", res1.TxID, isDup1)

	// Старый лидер падает до возврата ответа клиенту!
	fmt.Println("\n>>> Old Leader crashes! Failover elected New Leader. Client retries... <<<")

	// 2. Клиент повторяет запрос на Нового Лидера с тем же ключом
	fmt.Println("\n=== 2. New Leader receives retry request ===")
	res2, isDup2 := sharedDB.ExecuteIdempotent(idempotencyKey, 250, func() string {
		fmt.Println("[New-Leader] CRITICAL BUG: Re-executing banking payment!")
		return "bank-tx-DUPLICATE"
	})
	fmt.Printf("[New-Leader] Processed: TxID=%s, Duplicate=%v\n", res2.TxID, isDup2)

	fmt.Println("\nSynergy verified: Leader Failover + Idempotency prevents duplicate state mutation.")
}
```

## Под капотом

В базах данных шаблон Idempotent Consumer реализуется через оператор `INSERT INTO idempotency_keys (key, response_payload, created_at) VALUES ($1, $2, NOW()) ON CONFLICT (key) DO NOTHING`. Вся полезная работа и вставка ключа объединяются в одну атомарную ACID-транзакцию (`BEGIN ... COMMIT`).

## Подводные камни

Сохранение Idempotency Key в оперативной памяти лидера: при краше лидера вся память стирается. Новый лидер не будет знать об обработанных ключах. Таблица идемпотентности ОБЯЗАНА находиться в персистентном отказоустойчивом хранилище (PostgreSQL / CockroachDB / Cassandra).

## На собеседовании

В: Почему в распределенных системах нельзя полагаться только на Leader Election без Idempotency?
О: Сеть ненадежна. Лидер может упасть ровно в момент между фиксацией транзакции и отправкой сетевого ответа клиенту (Crash-after-Commit). Клиент не знает, выполнена ли операция, и обязан сделать retry. Без проверки идемпотентности новый лидер повторит мутацию.
