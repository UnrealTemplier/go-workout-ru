# Защита от Split-Brain: Паттерн Double Check перед критической операцией

## Условие

Перед выполнением критической операции Лидер должен сделать 'double check': убедиться, что его lease в etcd всё ещё валиден. Если lease истек прямо перед операцией — операция отклоняется.

### Исходная формулировка

**Split-Brain защита (Double Check)**: Перед выполнением критической операции, Лидер должен убедиться, что он *всё еще* лидер. Вызови чтение ключа лидера в etcd/Consul непосредственно перед транзакцией в БД. Хоть это и не заменит Fencing Tokens (упр. 836), это радикально снизит вероятность гонки.

## Теория

Проблема TOCTOU (Time-of-Check to Time-of-Use) в распределенных блокировках:
1. В момент \(T_0\) воркер проверил: `isLeader == true`.
2. В момент \(T_1\) случилась задержка: Stop-The-World пауза сборщика мусора Go (GC), своп ОС или перегрузка гипервизора на 4 секунды. За это время аренда (Lease) в etcd истекла, и другой узел стал лидером.
3. В момент \(T_2\) поток просыпается и выполняет критическую мутацию в БД (`UPDATE balance`), ошибочно полагая, что он все еще лидер!
Паттерн Double Check:
Перед выполнением необратимой мутации лидер выполняет быструю атомарную проверку свежести аренды (Remaining TTL > Safety Margin) или выполняет запись через CAS-транзакцию с проверкой ревизии (`Compare-And-Swap`). Если аренда просрочена, операция немедленно отклоняется с ошибкой `ErrLeaseExpired`.

## Решение по шагам

1. Создаем структуру ProtectedResourceManager с проверкой актуальности аренды.
2. Реализуем метод ExecuteProtectedAction() с валидацией остаточного времени Lease.
3. Проверяем успешное выполнение при свежей аренде.
4. Симулируем задержку, превышающую время аренды.
5. Подтверждаем, что повторная проверка (Double Check) блокирует мутацию.

## Код решения

**`double_check_guard.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
	"time"
)

var (
	ErrLeaseExpiredPreOperation = errors.New("aborted: lease expired immediately before critical operation execution (TOCTOU guard)")
)

type LeaseHandle struct {
	ID        int64
	ExpiresAt time.Time
}

type CriticalActionRunner struct {
	mu            sync.Mutex
	nodeID        string
	currentLease  LeaseHandle
	safetyMargin  time.Duration
}

func NewCriticalActionRunner(nodeID string, safetyMargin time.Duration) *CriticalActionRunner {
	return &CriticalActionRunner{
		nodeID:       nodeID,
		safetyMargin: safetyMargin,
	}
}

func (r *CriticalActionRunner) SetLease(id int64, ttl time.Duration) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.currentLease = LeaseHandle{
		ID:        id,
		ExpiresAt: time.Now().Add(ttl),
	}
}

func (r *CriticalActionRunner) ExecuteWithDoubleCheck(actionName string, operation func() error) error {
	// Первая проверка (Check 1)
	r.mu.Lock()
	if time.Now().After(r.currentLease.ExpiresAt) {
		r.mu.Unlock()
		return ErrLeaseExpiredPreOperation
	}
	r.mu.Unlock()

	// Имитация подготовки данных / сериализации (время идет)
	time.Sleep(50 * time.Millisecond)

	// Вторая проверка (Check 2: Double Check с запасом безопасности safetyMargin)
	r.mu.Lock()
	remaining := time.Until(r.currentLease.ExpiresAt)
	if remaining < r.safetyMargin {
		r.mu.Unlock()
		fmt.Printf("[%s] DOUBLE CHECK REJECTED '%s': Lease remaining %v is below safety threshold %v!\n",
			r.nodeID, actionName, remaining, r.safetyMargin)
		return ErrLeaseExpiredPreOperation
	}
	r.mu.Unlock()

	// Выполнение под защитой Double Check
	fmt.Printf("[%s] DOUBLE CHECK PASSED: Executing '%s' (Lease remaining: %v)\n",
		r.nodeID, actionName, remaining)
	return operation()
}

func main() {
	// Безопасный запас: 100 мс
	runner := NewCriticalActionRunner("payment-node-01", 100*time.Millisecond)

	// 1. Свежая аренда на 500 мс: операция проходит
	runner.SetLease(1001, 500*time.Millisecond)
	err := runner.ExecuteWithDoubleCheck("ChargeCard_1", func() error {
		return nil
	})
	fmt.Printf("Charge 1 result: %v\n\n", err)

	// 2. Аренда почти истекла (осталось 80 мс, а порог 100 мс): операция блокируется
	runner.SetLease(1002, 120*time.Millisecond)
	time.Sleep(50 * time.Millisecond) // Осталось ~70 мс

	err2 := runner.ExecuteWithDoubleCheck("ChargeCard_2", func() error {
		return nil
	})
	fmt.Printf("Charge 2 result: %v\n", err2)
}
```

## Под капотом

На уровне ядра БД Double Check реализуется включением Fencing Token в SQL запрос:
`UPDATE accounts SET balance = balance - 100, lock_version = $token WHERE id = $acc AND lock_version < $token`.
Если токен старого лидера меньше, чем токен, уже зафиксированный новым лидером, условие `WHERE` не совпадет, и `RowsAffected == 0`. Это делает невозможной порчу данных даже при полном отказе таймеров на прикладном уровне.

## Подводные камни

Полагаться только на Double Check в памяти без координатора: если процесс уснул прямо между строкой `r.mu.Unlock()` и выполнением `operation()`, проверка в памяти не спасет. Double Check в памяти отсекает 99% задержек, но для 100% гарантии в хранилище обязателен Fencing Token (версионный CAS).

## На собеседовании

В: Что такое TOCTOU (Time of Check to Time of Use) в распределенных системах?
О: Уязвимость состояния гонки, когда условие валидности ресурса (например, владение блокировкой или квота), проверенное в момент Check, успевает измениться к моменту фактического Use из-за сетевой задержки, переключения контекста ОС или пауз сборщика мусора.
