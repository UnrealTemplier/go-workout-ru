# Защита от Split-Brain через проверку большинства (Majority / Quorum Check)

## Условие

43. **Split-brain защита через Majority Check.**: Лидер перед обработкой write должен убедиться, что видит большинство узлов кластера. Реализуйте: лидер читает `/members` и проверяет `len(members) >= quorum`. Объясните, почему etcd lease alone не защищает от partition (старый лидер может быть в изоляции).

### Исходная формулировка

**Split-brain защита через Majority Check.**: Лидер перед обработкой write должен убедиться, что видит большинство узлов кластера. Реализуйте: лидер читает `/members` и проверяет `len(members) >= quorum`. Объясните, почему etcd lease alone не защищает от partition (старый лидер может быть в изолированной partition и продлевать lease локально).

## Теория

Фундаментальная теорема CAP и проблема изоляции:
Представьте кластер из 5 узлов: \(\{N_1, N_2, N_3, N_4, N_5\}\).
\(N_1\) — действующий лидер.
Происходит сетевой сплит: \(\{N_1, N_2\}\) изолированы от \(\{N_3, N_4, N_5\}\).

### Почему Lease не защищает в первые секунды:
- Пока TTL аренды \(N_1\) (например, 5 секунд) не истек локально, \(N_1\) считает себя лидером.
- В то же время меньшинство \(\{N_1, N_2\}\) **не может** обновить кворум, а большинство \(\{N_3, N_4, N_5\}\) уже выбирает нового лидера \(N_3\)!
- В течение этих 5 секунд \(N_1\) может продолжать принимать запросы на запись.

### Защита через Majority Check (Pre-Flight Quorum Verification):
Перед фиксацией любой мутации лидер обязан проверить, что он имеет прямую связь с большинством серверов кластера:
$$\text{ActiveMembers} \ge \left\lfloor \frac{N}{2} \right\rfloor + 1$$
Если лидер изолирован в меньшинстве, он **немедленно отклоняет запись**, предотвращая Split-Brain.

## Решение по шагам

1. Создадим калькулятор кворума `QuorumValidator`.
2. Реализуем метод `CanExecuteWrite(reachableMembers)`.
3. Смоделируем изоляцию 2 узлов из 5.
4. Продемонстрируем блокировку записи изолированным лидером.

## Код решения

**`majority_check.go`**

```go
package main

import (
	"errors"
	"fmt"
)

var ErrLostQuorum = errors.New("write rejected: leader cannot reach quorum majority (split-brain risk)")

type ClusterTopology struct {
	TotalMembers int
}

func (t ClusterTopology) RequiredQuorum() int {
	return (t.TotalMembers / 2) + 1
}

func (t ClusterTopology) ValidateWritePrecondition(reachableNodes []string) error {
	quorum := t.RequiredQuorum()
	if len(reachableNodes) < quorum {
		return fmt.Errorf("%w (Reachable: %d, Required: %d)",
			ErrLostQuorum, len(reachableNodes), quorum)
	}
	return nil
}

func main() {
	topology := ClusterTopology{TotalMembers: 5} // Кластер из 5 нод, кворум = 3

	fmt.Printf("Параметры кластера: Всего нод = %d, Необходимый кворум большинства = %d\n\n",
		topology.TotalMembers, topology.RequiredQuorum())

	// Сценарий 1: Лидер видит 4 узла из 5
	healthyCluster := []string{"node-1", "node-2", "node-3", "node-4"}
	err1 := topology.ValidateWritePrecondition(healthyCluster)
	fmt.Printf("1. Нормальная сеть (видимо 4 ноды): Ошибка = %v (Запись разрешена!)\n", err1)

	// Сценарий 2: Сетевой сплит! Лидер остался в меньшинстве (видит только себя и node-2)
	partitioned := []string{"node-1", "node-2"}
	err2 := topology.ValidateWritePrecondition(partitioned)
	fmt.Printf("2. Сетевая изоляция (видимо 2 ноды из 5): Ошибка = %v (Запись заблокирована!)\n", err2)
}
```

ℹ️ Majority Check: обязательная проверка кворума большинства перед фиксацией мутаций

## Под капотом

В протоколе Raft механизм `CheckQuorum`:
Лидер каждые `HeartbeatInterval` отправляет `AppendEntries` последователям. Если за время `ElectionTimeout` лидер не получил подтверждений от большинства, он добровольно складывает полномочия и переходит в статус `Follower`. Это исключает Split-Brain на математическом уровне.

## Подводные камни

1. **Чтение только локального кэша:** Локальное состояние не отражает реальной доступности сети.
2. **Игнорирование асимметричных сплитов:** Ситуация, когда A слышит B, но B не слышит A.
3. **Неверный расчет кворума для четного числа нод:** Для 4 нод кворум равен 3 (не 2!).

## На собеседовании

**Вопрос:** Что произойдет с кластером etcd из 3 нод, если две ноды изолируются от одной?
**Ответ:** 
- Группа из 2 нод составляет большинство (\(2 \ge 2\)) и продолжит работу: изберет лидера и будет обслуживать чтения и записи.
- Одинокая нода (\(1 < 2\)) потеряет кворум. Она перейдет в режим Read-Only (или заблокирует чтения, если включена линеаризуемость) и будет отвергать все попытки записи, исключая разделение состояния.
