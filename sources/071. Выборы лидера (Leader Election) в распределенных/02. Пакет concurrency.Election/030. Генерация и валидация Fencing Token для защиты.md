# Генерация и валидация Fencing Token для защиты от Stale Leaders

## Условие

30. **Fencing token в leader election**: При получении leadership генерируйте монотонно возрастающий fencing token. Используйте его для защиты от stale leaders.

### Исходная формулировка

**Fencing token в leader election**: При получении leadership генерируйте монотонно возрастающий fencing token. Используйте его для защиты от stale leaders.

## Теория

Даже идеальный алгоритм выбора лидера не спасает от проблемы «Зомби-лидера» (Stale Leader):
1. Лидер 1 завис в паузе сборщика мусора (GC pause) на 10 секунд.
2. Кластер переизбрал Лидера 2 (эпоха 2).
3. Лидер 2 успешно работает.
4. Внезапно Лидер 1 просыпается и отправляет сформированный 10 секунд назад сетевой пакет на запись в хранилище (например, базу данных или файловое хранилище).

### Решение Мартина Клеппмана: Fencing Tokens:
При каждом избрании сервер консенсуса возвращает строго монотонно возрастающее число:
- В etcd: `CreateRevision` или `ModRevision`.
- В Consul: `LockIndex`.
- В Raft: номер срока полномочий `Term`.

Каждая операция записи в целевое хранилище **обязана содержать Fencing Token**.
Целевое хранилище запоминает максимальный полученный токен. Запросы со старыми токенами (\(T_{\text{incoming}} < T_{\text{max}}\)) **категорически отклоняются**!

## Решение по шагам

1. Создадим хранилище данных `FencedStorage` с защитой по токену.
2. Реализуем проверку условия `token >= currentMaxToken`.
3. Смоделируем запрос от Лидера 2 с токеном 42.
4. Продемонстрируем, как запоздавший запрос от Лидера 1 с токеном 41 отвергается СУБД.

## Код решения

**`fencing_token.go`**

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

var ErrStaleToken = errors.New("fencing error: transaction rejected, token is older than current epoch")

type StorageItem struct {
	Data        string
	HighestToken int64
}

type FencedDatabase struct {
	mu    sync.Mutex
	items map[string]*StorageItem
}

func NewFencedDatabase() *FencedDatabase {
	return &FencedDatabase{items: make(map[string]*StorageItem)}
}

// WriteWithFence применяет операцию, только если переданный токен монотонно больше или равен текущему
func (db *FencedDatabase) WriteWithFence(key, value string, token int64) error {
	db.mu.Lock()
	defer db.mu.Unlock()

	item, exists := db.items[key]
	if !exists {
		db.items[key] = &StorageItem{Data: value, HighestToken: token}
		fmt.Printf("✅ Запись успешна! Ключ: '%s', Токен: %d\n", key, token)
		return nil
	}

	if token < item.HighestToken {
		return fmt.Errorf("%w (incoming: %d, current: %d)", ErrStaleToken, token, item.HighestToken)
	}

	item.Data = value
	item.HighestToken = token
	fmt.Printf("✅ Запись обновлена! Ключ: '%s', Новый Токен: %d\n", key, token)
	return nil
}

func main() {
	db := NewFencedDatabase()

	// 1. Лидер поколения 42 выполняет запись
	err1 := db.WriteWithFence("account/balance", "$500", 42)
	if err1 != nil {
		panic(err1)
	}

	// 2. Зомби-лидер поколения 41 просыпается от GC паузы и пытается записать устаревшие данные
	fmt.Println("\n💥 Зомби-лидер поколения 41 пытается совершить запись...")
	err2 := db.WriteWithFence("account/balance", "$100", 41)
	if err2 != nil {
		fmt.Printf("🛡️ ОТКЛОНЕНО: %v\n", err2)
	}

	// 3. Лидер поколения 43 успешно обновляет данные
	err3 := db.WriteWithFence("account/balance", "$600", 43)
	if err3 != nil {
		panic(err3)
	}
}
```

ℹ️ Fencing Tokens: математическая защита базы данных от запоздавших записей зомби-лидеров

## Под капотом

Классическая статья Мартина Клеппмана «How to do distributed locking»:
Распределенная блокировка без Fencing Token не способна гарантировать взаимное исключение в реальных системах с асинхронными сетями и GC-паузами. Только принимающая сторона (БД, диск, хранилище), проверяющая монотонный токен, способна окончательно предотвратить разрушение данных.

## Подводные камни

1. **Использование случайных UUID в качестве токена:** Токен обязан быть строго монотонно возрастающим (\(T_{n+1} > T_n\)).
2. **Использование системного времени (timestamp):** Смещение системных часов (NTP step) может сделать токен нового лидера меньше токена старого лидера.
3. **Отсутствие поддержки токенов на стороне БД:** Если база данных не проверяет токен в условии `WHERE token > ...`, защита не работает.

## На собеседовании

**Вопрос:** Что может выступать в качестве надежного Fencing Token при выборе лидера через etcd и Consul?
**Ответ:**
- В etcd: поле **`CreateRevision`** лидерского ключа или глобальная ревизия транзакции. Ревизия в etcd — это строго возрастающий 64-битный счетчик всех мутаций кластера.
- В Consul: счетчик **`LockIndex`** структуры `KVPair`, который атомарно увеличивается серверами Raft при каждой передаче блокировки новому владельцу.
