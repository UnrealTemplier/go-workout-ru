# Ранжирование лидеров по приоритетам оборудования и сети

## Условие

39. **Leader priority**: Назначьте priority для каждого инстанса. При равных условиях leader'ом становится инстанс с высшим priority.

### Исходная формулировка

**Leader priority**: Назначьте priority для каждого инстанса. При равных условиях leader'ом становится инстанс с высшим priority.

## Теория

При объединении облачных зон (Availability Zones) и локальных ЦОД приоритет лидера позволяет гарантировать оптимальную производительность.

### Приоритетная шкала:
- `Priority = 300`: On-Premises Bare Metal сервер рядом с хранилищем данных (RTT < 0.2ms).
- `Priority = 200`: Облачная VM в основной зоне (AZ-a).
- `Priority = 100`: Резервная VM в резервной зоне (AZ-b).

При старте кластера все кандидаты регистрируют свои веса. Алгоритм отдает приоритет серверу с наибольшим баллом.

## Решение по шагам

1. Создадим структуру узла с атрибутом `PriorityScore`.
2. Реализуем выборы на основе сортировки по приоритету.
3. Продемонстрируем выбор наиболее приоритетного сервера.
4. Покажем передачу роли второму по приоритету при отказе лидера.

## Код решения

**`priority_ranks.go`**

```go
package main

import (
	"fmt"
	"sort"
)

type ServerNode struct {
	Name          string
	PriorityScore int
	Active        bool
}

type PriorityCluster struct {
	nodes []*ServerNode
}

func (c *PriorityCluster) ElectLeader() *ServerNode {
	var candidates []*ServerNode
	for _, n := range c.nodes {
		if n.Active {
			candidates = append(candidates, n)
		}
	}

	if len(candidates) == 0 {
		return nil
	}

	sort.Slice(candidates, func(i, j int) bool {
		return candidates[i].PriorityScore > candidates[j].PriorityScore
	})

	return candidates[0]
}

func main() {
	cluster := &PriorityCluster{
		nodes: []*ServerNode{
			{Name: "cloud-backup-node", PriorityScore: 100, Active: true},
			{Name: "cloud-primary-az", PriorityScore: 200, Active: true},
			{Name: "bare-metal-direct", PriorityScore: 300, Active: true},
		},
	}

	leader1 := cluster.ElectLeader()
	fmt.Printf("1. Активный лидер: %s (Приоритет: %d)\n", leader1.Name, leader1.PriorityScore)

	// Имитируем падение самого приоритетного сервера
	fmt.Println("\n[Авария] Сервер bare-metal-direct отключен от сети!")
	cluster.nodes[2].Active = false

	leader2 := cluster.ElectLeader()
	fmt.Printf("2. Новый избранный лидер: %s (Приоритет: %d)\n", leader2.Name, leader2.PriorityScore)
}
```

ℹ️ Ранжирование лидеров по приоритетам: детерминированный выбор наиболее производительного узла

## Под капотом

В распределенных алгоритмах (Bully Algorithm):
Классический алгоритм задиры (Bully) использует именно числовые ID/приоритеты: узел с наивысшим ID всегда вытесняет узлы с меньшим ID. Однако в современных системах вытеснение делают мягким (non-preemptive), чтобы исключить лишние переключения.

## Подводные камни

1. **Одинаковые приоритеты у всех нод:** Всегда предусмотрите tie-breaker по уникальному имени/UUID.
2. **Завышение приоритета проблемной нодой:** Нестабильная нода с высоким приоритетом будет постоянно отбирать лидерство и падать.
3. **Статические веса:** Рекомендуется динамически снижать приоритет ноды при росте CPU/Memory throttling.

## На собеседовании

**Вопрос:** Как избежать постоянного перехвата лидерства нодой с высоким приоритетом, если на ней периодически мигает сеть (Flapping Priority Node)?
**Ответ:** Используется **Пенализация приоритета (Flapping Penalty / Backoff)**:
При каждом непредвиденном падении узел штрафуется (например, его приоритет снижается на 50 баллов на 30 минут). Только после стабильной работы в течение часа приоритет восстанавливается до максимального значения.
