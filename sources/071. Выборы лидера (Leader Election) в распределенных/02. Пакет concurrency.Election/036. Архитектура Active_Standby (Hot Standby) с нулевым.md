# Архитектура Active/Standby (Hot Standby) с нулевым временем переключения

## Условие

36. **Standby leader**: Один primary leader, один standby. При failover standby становится leader мгновенно (не ждет election).

### Исходная формулировка

**Standby leader**: Один primary leader, один standby. При failover standby становится leader мгновенно (не ждет election).

## Теория

Классическая процедура выборов лидера (голосование Raft, опрос кандидатов) занимает от 100 миллисекунд до нескольких секунд. В телекоме и HFT (High-Frequency Trading) такой простой недопустим.

### Паттерн Hot Standby (Active/Passive Mirroring):
1. **Primary (Active):** Принимает сетевой трафик, пишет состояние в локальную память и непрерывно реплицирует журнал операций на Standby узел (например, через сетевой сокет ring buffer).
2. **Standby (Passive):** 
   - Находится в прогретом состоянии: все пулы соединений открыты, кэши актуализированы.
   - Поддерживает постоянный высокочастотный Heartbeat пинг с Primary (RTT < 1 мс).
3. **Мгновенный Promote:** При пропадании 3 подряд аппаратных пингов Standby узел объявляет себя Active за \(\le 2\) миллисекунды, не запуская долгую процедуру выборов.

## Решение по шагам

1. Создадим модель пары `ActiveStandbyPair`.
2. Настроим репликацию состояния от Active к Standby.
3. Симулируем отказ узла Active.
4. Продемонстрируем мгновенную активацию Standby с уже прогретым состоянием.

## Код решения

**`hot_standby.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type ReplicatedState struct {
	LastSequence int64
	CachedValue  string
}

type HotStandbyNode struct {
	NodeID   string
	IsActive bool
	State    ReplicatedState
	mu       sync.Mutex
}

func (n *HotStandbyNode) ApplyReplication(seq int64, val string) {
	n.mu.Lock()
	defer n.mu.Unlock()
	n.State.LastSequence = seq
	n.State.CachedValue = val
}

func (n *HotStandbyNode) PromoteToActive() {
	n.mu.Lock()
	defer n.mu.Unlock()
	n.IsActive = true
	fmt.Printf("⚡ [%s] МГНОВЕННЫЙ PROMOTE: Узел стал Active! Состояние уже в памяти (Seq: %d, Data: '%s')!\n",
		n.NodeID, n.State.LastSequence, n.State.CachedValue)
}

func main() {
	active := &HotStandbyNode{NodeID: "Primary-Active", IsActive: true}
	standby := &HotStandbyNode{NodeID: "Secondary-HotStandby", IsActive: false}

	// 1. Постоянная потоковая синхронизация состояния
	standby.ApplyReplication(101, "balance=$1000")
	standby.ApplyReplication(102, "balance=$1500")

	fmt.Println("Кластер работает в режиме Active/Hot-Standby. Репликация актуальна.")

	// 2. Сбой Active узла
	fmt.Println("\n💥 Primary-Active упал (Hardware Watchdog Timeout)!")
	active.IsActive = false

	// 3. Мгновенная активация Standby без ожидания консенсуса
	startPromote := time.Now()
	standby.PromoteToActive()
	fmt.Printf("Время переключения: %v (субмиллисекунды)\n", time.Since(startPromote))
}
```

ℹ️ Паттерн Hot Standby: мгновенный Promote с уже синхронизированным состоянием

## Под капотом

Сравнение Cold Standby vs Hot Standby:
- **Cold Standby:** Узел не запущен или запущен без кэша. При падении мастера он должен стартовать, вычитать БД, прогреть JIT и кэш (задержка 10–60 секунд).
- **Hot Standby:** Память процесса идентична памяти мастера за счет синхронной репликации лога (Zero Initialization Overhead).

## Подводные камни

1. **Split-Brain при ложном срабатывании пинга:** Если упал только сетевой кабель между Active и Standby, оба узла станут Active! Требуется третий арбитр (Witness Node / Quorum Storage).
2. **Отставание репликации (Replication Lag):** Если Standby активируется с отставшим стейтом, произойдет откат данных (Data Loss).
3. **Нагрузка на репликацию:** Синхронная репликация каждого чиха на Standby увеличивает latency пишущих запросов.

## На собеседовании

**Вопрос:** Как избежать Split-Brain в двухнодовой схеме Active/Standby без третьего сервера консенсуса?
**Ответ:** Используется **STONITH (Shoot The Other Node In The Head)** или аппаратный Fencing (IPMI / iLO / Network PDU). Перед тем как Standby переведет себя в статус Active, он отправляет команду на аппаратное отключение питания физического сервера старого Primary через интерфейс управления питанием.
