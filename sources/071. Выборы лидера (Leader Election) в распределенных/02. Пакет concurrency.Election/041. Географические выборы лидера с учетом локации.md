# Географические выборы лидера с учетом локации клиентов (Geo-Affinity)

## Условие

41. **Geographic leader election**: В multi-region setup избирайте leader в том регионе, где большинство клиентов для снижения latency.

### Исходная формулировка

**Geographic leader election**: В multi-region setup избирайте leader в том регионе, где большинство клиентов для снижения latency.

## Теория

В глобально распределенных сервисах (Multi-Region / Cross-Continent) сетевая задержка между континентами определяет качество сервиса:
- RTT внутри одного региона: \(\approx 1\) мс.
- RTT между Европой и США: \(\approx 75\) мс.
- RTT между Европой и Азией: \(\approx 150\) мс.

### Алгоритм Geo-Aware Leader Election:
1. Система собирает телеметрию: распределение активных клиентских сессий по регионам (например: 80% запросов приходят из региона `eu-central`, 20% из `us-east`).
2. При выборах лидера узлам из доминирующего региона динамически присваивается повышенный весовой коэффициент:
   $$\text{Score}_i = \text{HardwareScore}_i + \alpha \times \text{ClientTrafficRatio}_{\text{region}}$$
3. Лидером избирается нода из `eu-central`, что снижает среднюю задержку для 80% пользователей до субмиллисекунд!

## Решение по шагам

1. Создадим модель узла с атрибутом `Region`.
2. Реализуем калькулятор географического веса на основе клиентского распределения.
3. Продемонстрируем автоматическое перемещение лидерства в регион с максимальным трафиком.

## Код решения

**`geo_affinity_election.go`**

```go
package main

import (
	"fmt"
	"sort"
)

type GeoNode struct {
	Name   string
	Region string
}

type TrafficMetrics struct {
	RegionRPS map[string]int
}

func ElectGeoOptimalLeader(nodes []GeoNode, traffic TrafficMetrics) GeoNode {
	sort.Slice(nodes, func(i, j int) bool {
		rpsI := traffic.RegionRPS[nodes[i].Region]
		rpsJ := traffic.RegionRPS[nodes[j].Region]
		// Побеждает нода из региона с максимальным RPS
		return rpsI > rpsJ
	})

	return nodes[0]
}

func main() {
	nodes := []GeoNode{
		{Name: "srv-us-east-1", Region: "us-east"},
		{Name: "srv-eu-central-1", Region: "eu-central"},
		{Name: "srv-ap-southeast-1", Region: "ap-southeast"},
	}

	// 1. Дневной пик в Европе
	trafficMorning := TrafficMetrics{
		RegionRPS: map[string]int{
			"eu-central":   50000,
			"us-east":      5000,
			"ap-southeast": 12000,
		},
	}
	leader1 := ElectGeoOptimalLeader(nodes, trafficMorning)
	fmt.Printf("1. Утренний пик (Европа): Лидер -> %s (%s) для снижения Latency 50k RPS\n",
		leader1.Name, leader1.Region)

	// 2. Вечерний пик в США
	trafficEvening := TrafficMetrics{
		RegionRPS: map[string]int{
			"eu-central":   8000,
			"us-east":      65000,
			"ap-southeast": 4000,
		},
	}
	leader2 := ElectGeoOptimalLeader(nodes, trafficEvening)
	fmt.Printf("2. Вечерний пик (США): Лидер -> %s (%s) для минимизации задержки 65k RPS\n",
		leader2.Name, leader2.Region)
}
```

ℹ️ Geo-Affinity: динамическое размещение лидера в регионе с максимальным клиентским трафиком

## Под капотом

В глобальных базах данных (Google Spanner, CockroachDB):
Используется концепция **Leader Leaseholder Migration**: диапазоны ключей (Ranges) динамически передают лидерство реплике, расположенной ближе всего к клиенту, который выполняет 90% чтений и записей данного диапазона, экономя сотни миллисекунд WAN RTT.

## Подводные камни

1. **Слишком частые миграции между регионами:** Передача лидерства через океан сбрасывает кэши. Устанавливайте минимальное время удержания (Hysteresis window: не чаще раза в 2 часа).
2. **Авария WAN-канала:** При обрыве трансатлантического кабеля кластер должен сохранять кворум в основном регионе.
3. **Нарушение консенсуса:** Кворум Raft обязан оставаться нечетным и гео-распределенным.

## На собеседовании

**Вопрос:** Как избежать лавины переключений (Leader Ping-Pong) между Европой и США, если трафик распределен примерно поровну (51% против 49%)?
**Ответ:** Применяется **Гистерезис (Hysteresis Threshold)**:
Смена региона допускается только в случае, если превышение трафика составляет не менее \(\Delta \ge 20\%\) и удерживается непрерывно в течение скользящего окна 15 минут. Это предотвращает бесполезную миграцию лидерства при незначительных колебаниях RPS.
