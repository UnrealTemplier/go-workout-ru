# Реактивный перехват власти через etcd.Watcher (Event-Driven Failover)

## Условие

28. **[Watch и Failover]**: Останови инстанс-лидер (убей процесс). Оставшиеся 2 инстанса должны слушать изменения ключа `/leader` через `etcd.Watcher`. Когда ключ исчезнет (TTL истек), они должны мгновенно начать новую борьбу за лидерство.

### Исходная формулировка

**[Watch и Failover]**: Останови инстанс-лидер (убей процесс). Оставшиеся 2 инстанса должны слушать изменения ключа `/leader` через `etcd.Watcher`. Когда ключ исчезнет (TTL истек), они должны мгновенно начать новую борьбу за лидерство.

## Теория

Отказ от поллинга в пользу событийной модели (Event-Driven Watch) — стандарт реактивных распределенных систем на Go.

### Механика etcd Watcher:
1. Ведомые инстансы открывают долгоживущий gRPC-поток:
   `watchChan := cli.Watch(ctx, "/services/leader")`
2. Горутина блокируется в ожидании событий из `watchChan`.
3. При истечении TTL аренды etcd генерирует событие:
   `event.Type == mvccpb.DELETE`.
4. Ведомые узлы мгновенно пробуждаются и запускают фазу выборов (Campaign / Txn), сводя задержку реакции к нулю.

## Решение по шагам

1. Создадим структуру `EtcdEventBroker` для трансляции событий изменения ключа.
2. Подключим двух ведомых слушателей через канал `Watch`.
3. Симулируем удаление лидерского ключа.
4. Продемонстрируем немедленное пробуждение и конкурентную борьбу за освободившийся ключ.

## Код решения

**`etcd_watch_failover.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type WatchEvent struct {
	Type string // "PUT", "DELETE"
	Key  string
}

type EtcdWatchHub struct {
	mu          sync.Mutex
	subscribers []chan WatchEvent
}

func (h *EtcdWatchHub) Watch() <-chan WatchEvent {
	h.mu.Lock()
	defer h.mu.Unlock()
	ch := make(chan WatchEvent, 5)
	h.subscribers = append(h.subscribers, ch)
	return ch
}

func (h *EtcdWatchHub) Broadcast(ev WatchEvent) {
	h.mu.Lock()
	defer h.mu.Unlock()
	for _, ch := range h.subscribers {
		select {
		case ch <- ev:
		default:
		}
	}
}

func FollowerWatcher(ctx context.Context, nodeID string, hub *EtcdWatchHub) {
	ch := hub.Watch()
	fmt.Printf("[%s] Подписался на Watch ключа /leader...\n", nodeID)

	for {
		select {
		case <-ctx.Done():
			return
		case ev := <-ch:
			if ev.Type == "DELETE" {
				fmt.Printf("⚡ [%s] Получено событие DELETE! Лидер упал! Начинаем немедленную кампанию выборов!\n", nodeID)
				// В реальном коде: election.Campaign(ctx, nodeID)
				return
			}
		}
	}
}

func main() {
	hub := &EtcdWatchHub{}
	ctx, cancel := context.WithTimeout(context.Background(), 200*time.Millisecond)
	defer cancel()

	// Запускаем 2 ведомых узла
	go FollowerWatcher(ctx, "Follower-Node-1", hub)
	go FollowerWatcher(ctx, "Follower-Node-2", hub)

	time.Sleep(50 * time.Millisecond)

	fmt.Println("\n💥 [Кластер] Лидер погиб. etcd удалил ключ по истечении Lease TTL!")
	hub.Broadcast(WatchEvent{Type: "DELETE", Key: "/leader"})

	time.Sleep(50 * time.Millisecond)
}
```

ℹ️ Реактивный перехват власти: пробуждение по событию DELETE из etcd.Watcher

## Под капотом

Внутри etcd WatchableStore:
События Watch вычитываются напрямую из кольцевого буфера памяти (Event Ring Buffer) без чтения диска bbolt. Это обеспечивает задержку доставки события от ядра etcd до клиента в пределах субмиллисекунды.

## Подводные камни

1. **Переполнение канала событий:** Небуферизированный канал может привести к замедлению всего рантайма Watcher.
2. **Игнорирование флага `Canceled`:** Если стрим Watch отменен сервером, клиент обязан пересоздать подписку с последней известной ревизии (`WithRev`).
3. **Одновременный старт всех узлов без джиттера:** Добавляйте рандомную задержку в несколько миллисекунд перед `Campaign()`.

## На собеседовании

**Вопрос:** Что делать, если во время наблюдения за ключом через `etcd.Watcher` связь с сервером прервалась на 10 секунд, а затем восстановилась?
**Ответ:** Клиент обязан передать в вызов `clientv3.Watch()` опцию `clientv3.WithRev(lastSeenRevision + 1)`. etcd автоматически дошлет все пропущенные события из журнала истории (History Compact Window). Если ревизия уже была сжата сборщиком мусора (`ErrCompacted`), клиент обязан заново вычитать текущее состояние через `Get()` и перезапустить Watch.
