# Множественные лидеры для независимых доменов задач (Multi-Topic Leadership)

## Условие

32. **Multiple leaders для разных задач**: Используйте разные leader keys для разных задач: `leader/cron`, `leader/reconciliation`, `leader/metrics_aggregation`.

### Исходная формулировка

**Multiple leaders для разных задач**: Используйте разные leader keys для разных задач: `leader/cron`, `leader/reconciliation`, `leader/metrics_aggregation`.

## Теория

Один глобальный лидер на весь микросервис — антипаттерн масштабирования:
- Если один узел выполняет генерацию отчетов, выгрузку биллинга и агрегацию метрик, его CPU и сетевой интерфейс быстро станут бутылочным горлышком.

### Шардирование обязанностей (Functional Leader Sharding):
Создаются независимые лидерские замки под каждый изолированный процесс:
1. `/leaders/billing/cron` — отвечает за списания раз в сутки.
2. `/leaders/billing/reconciliation` — непрерывно сверяет транзакции с внешними банками.
3. `/leaders/billing/metrics` — собирает и экспортирует аналитические спайны.

Разные поды кластера могут становиться лидерами в **разных функциональных областях одновременно**, обеспечивая равномерное распределение нагрузки.

## Решение по шагам

1. Создадим менеджер многодоменного лидерства `MultiTopicLeaderManager`.
2. Реализуем независимые ключи для задач `cron`, `reconciliation`, `metrics`.
3. Смоделируем распределение ролей между тремя подами.
4. Продемонстрируем независимый failover по каждой задаче.

## Код решения

**`multi_domain_leaders.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type DomainLock struct {
	Domain string
	Leader string
}

type MultiTopicCluster struct {
	mu    sync.Mutex
	locks map[string]string // domain -> nodeID
}

func NewMultiTopicCluster() *MultiTopicCluster {
	return &MultiTopicCluster{locks: make(map[string]string)}
}

func (c *MultiTopicCluster) ClaimDomain(domain, nodeID string) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	if current, exists := c.locks[domain]; exists && current != "" {
		return false
	}
	c.locks[domain] = nodeID
	return true
}

func main() {
	cluster := NewMultiTopicCluster()

	domains := []string{"cron_scheduler", "bank_reconciliation", "metrics_aggregator"}

	// Pod 1 захватывает cron
	cluster.ClaimDomain("cron_scheduler", "Pod-1")
	// Pod 2 захватывает reconciliation
	cluster.ClaimDomain("bank_reconciliation", "Pod-2")
	// Pod 3 захватывает metrics
	cluster.ClaimDomain("metrics_aggregator", "Pod-3")

	fmt.Println("Распределение функционального лидерства по подам:")
	for _, d := range domains {
		fmt.Printf("• Домен '%s' -> Активный лидер: %s\n", d, cluster.locks[d])
	}
}
```

ℹ️ Шардирование лидерства: независимые лидерские замки под разные типы задач

## Под капотом

В Kubernetes Operator SDK:
Операторы часто разделяют лидерство вебхуков (`webhook-server`) и контроллеров ресурсов (`crd-controller`). Это позволяет масштабировать прием валидационных вебхуков на 10 подов, сохраняя строгий single-writer инвариант контроллера.

## Подводные камни

1. **Слишком мелкое дробление замков:** Создание 10 000 замков на каждый мелкий заказ перегрузит Consul/etcd. Шардируйте по крупным доменам или диапазонам партиций (Consistent Hashing).
2. **Взаимная блокировка задач (Deadlock):** Если задача A ждет лидера задачи B, а задача B лидера задачи A, возникнет распределенный тупик.
3. **Сложность мониторинга:** Требуется сбор метрик по каждому лидерскому домену отдельно.

## На собеседовании

**Вопрос:** Как распределить обработку 1 000 очередей между 10 подами с гарантией отсутствия дублей и высокой доступностью?
**Ответ:** Вместо 1 000 отдельных выборов лидера применяется **Консистентное хеширование (Consistent Hashing Ring)** или шардирование через брокер сообщений (Kafka Consumer Groups / Partition Assignment). Выборы лидера используются только для выбора **Координатора распределения шардов (Shard Allocator Master)**, который назначает партиции рабочим воркерам.
