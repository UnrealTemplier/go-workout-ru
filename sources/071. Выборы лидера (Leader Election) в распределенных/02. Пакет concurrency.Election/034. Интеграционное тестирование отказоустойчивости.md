# Интеграционное тестирование отказоустойчивости и таймингов Failover

## Условие

    * Запускают 3 инстанса
    * Проверяют, что только один leader
    * Убивают leader

### Исходная формулировка

**Leader election testing**: Напишите интеграционные тесты, которые:
* Запускают 3 инстанса
* Проверяют, что только один leader
* Убивают leader
* Проверяют, что новый leader избран в течение TTL

## Теория

Тестирование распределенного консенсуса требует строгой верификации двух свойств безопасности (Safety & Liveness):
1. **Safety (Безопасность):** В любой момент времени \(t\) существует **не более одного** активного лидера:
   $$\sum \text{IsLeader}_i \le 1$$
2. **Liveness (Живучесть):** При падении действующего лидера новый лидер гарантированно избирается за время:
   $$T_{\text{election}} \le \text{TTL} + \text{ElectionTimeout}$$

В Go интеграционные тесты используют симуляцию параллельных горутин, каналы отмены контекста и assertions инвариантов.

## Решение по шагам

1. Создадим интеграционный тест `TestLeaderElection_FailoverTimings`.
2. Запустим 3 конкурентных инстанса.
3. Проверим инвариант ровно 1 победителя.
4. Имитируем падение лидера и замерим время переизбрания преемника.

## Код решения

**`election_integration_test.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"testing"
	"time"
)

type TestNode struct {
	ID       string
	IsLeader int32
}

func TestLeaderElection_FailoverTimings(t *testing.T) {
	cluster := &FailoverCluster{}
	ttl := 100 * time.Millisecond

	nodes := []*TestNode{
		{ID: "node-1"},
		{ID: "node-2"},
		{ID: "node-3"},
	}

	// 1. Захват лидерства нодой 1
	if !cluster.TryClaimLeader(nodes[0].ID, ttl) {
		t.Fatalf("node-1 failed to claim initial leadership")
	}
	atomic.StoreInt32(&nodes[0].IsLeader, 1)

	// 2. Проверка Safety инварианта: остальные ноды НЕ могут стать лидером
	for i := 1; i < len(nodes); i++ {
		if cluster.TryClaimLeader(nodes[i].ID, ttl) {
			t.Fatalf("SAFETY VIOLATION: node %s claimed leadership while node-1 was active!", nodes[i].ID)
		}
	}

	// 3. Убиваем лидера (прекращаем Heartbeat)
	atomic.StoreInt32(&nodes[0].IsLeader, 0)
	failoverStart := time.Now()

	// 4. Ожидаем перехвата лидерства нодой 2
	var newLeaderElected bool
	for time.Since(failoverStart) < 250*time.Millisecond {
		time.Sleep(15 * time.Millisecond)
		if cluster.TryClaimLeader(nodes[1].ID, ttl) {
			newLeaderElected = true
			atomic.StoreInt32(&nodes[1].IsLeader, 1)
			break
		}
	}

	elapsed := time.Since(failoverStart)
	if !newLeaderElected {
		t.Fatalf("LIVENESS VIOLATION: New leader was not elected within timeout! Elapsed: %v", elapsed)
	}

	fmt.Printf("Тест пройден! Новый лидер избран за %v (в пределах нормы TTL %v)\n", elapsed, ttl)
}

func main() {
	t := &testing.T{}
	TestLeaderElection_FailoverTimings(t)
	if !t.Failed() {
		fmt.Println("Интеграционный тест выбора лидера и фейловера завершился со 100% успехом!")
	}
}
```

ℹ️ Интеграционный тест: проверка Safety (строго 1 лидер) и Liveness (фейловер в пределах TTL)

## Под капотом

Использование Testcontainers в Go:
В реальных production-тестах запускают настоящий кластер etcd через библиотеку `testcontainers-go`:
```go
etcdContainer, _ := etcd.RunContainer(ctx, testcontainers.WithImage("gcr.io/etcd-development/etcd:v3.5.9"))
```
Это позволяет проверять поведение клиентов при реальных сетевых сбоях, проверке fsync и реальных сетевых сокетах Linux.

## Подводные камни

1. **Слишком короткие таймауты в CI/CD:** На перегруженном раннере GitHub Actions виртуальные ядра CPU могут испытывать задержки. Задавайте достаточные границы таймаутов (`ttl * 2.5`).
2. **Флаки-тесты (Flaky Tests) из-за гонок:** Запускайте тесты с флагом `go test -race -count=50`.
3. **Неочищенные контейнеры:** Всегда вызывайте `defer container.Terminate(ctx)`.

## На собеседовании

**Вопрос:** Как протестировать поведение выборов лидера при сетевой изоляции (Network Partition / Split-Brain) в автоматизированных тестах?
**Ответ:** Используется **Chaos Engineering (Toxiproxy / Chaos Mesh)**:
1. Тест поднимает 3 ноды сервиса и 3 ноды etcd.
2. Через Toxiproxy вносятся правила разрыва TCP-соединения между Лидером 1 и etcd (`toxic: timeout`).
3. Тест верифицирует, что изолированный Лидер 1 сбросил полномочия за время TTL, а Лидер 2 в оставшемся большинстве кворума успешно принял управление.
