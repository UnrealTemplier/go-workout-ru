### Исходная формулировка

**Leader Election с приоритетом.**: Узлы имеют `priority` (например, availability zone, hardware class). Реализуйте алгоритм: при попытке захвата лидерства узел записывает `/election/<node_id>` с value=priority. Лидер — узел с наименьшим приоритетом (или наибольшим). ## Теория

В гетерогенных дата-центрах не все ноды одинаковы:
- Сервер в центральном ЦОД имеет лучшую связность, чем периферийный сервер.
- Сервер с 128 GB RAM и NVMe предпочтительнее слабой VM на 4 GB RAM.

### Алгоритм Priority Leader Election:
1. Каждый кандидат регистрирует ключ со своим идентификатором и числовым весом:
   `/elections/candidates/{node_id} = { "priority": 100, "zone": "eu-west-1a" }`.
2. Координатор или кандидаты через `Txn` вычисляют победителя:
   - Считывается список всех активных кандидатов с префиксом.
   - Победителем признается узел с наивысшим приоритетом (Highest Weight).
   - Если приоритеты равны — тай-брейк по минимальной ревизии `CreateRevision`.

## Решение по шагам

1. Создадим структуру `PriorityCandidate` с весом узла.
2. Реализуем функцию выбора победителя на основе компаратора `(Priority DESC, CreateRevision ASC)`.
3. Запустим 3 разнородных узла.
4. Продемонстрируем победу наиболее мощного узла независимо от порядка старта.

## Код решения

**`priority_election.go`**

```go
package main

import (
	"fmt"
	"sort"
)

type PriorityNode struct {
	ID             string
	HardwareWeight int   // 100 = 64 CPU NVMe, 10 = 2 CPU VM
	CreateRevision int64 // Порядковый номер в очереди
}

func ElectHighestPriorityLeader(candidates []PriorityNode) PriorityNode {
	sort.Slice(candidates, func(i, j int) bool {
		// 1. Сначала сравниваем приоритет (чем выше вес, тем лучше)
		if candidates[i].HardwareWeight != candidates[j].HardwareWeight {
			return candidates[i].HardwareWeight > candidates[j].HardwareWeight
		}
		// 2. При равном весе — побеждает старший по времени (меньше ревизия)
		return candidates[i].CreateRevision < candidates[j].CreateRevision
	})

	return candidates[0]
}

func main() {
	candidates := []PriorityNode{
		{ID: "edge-vm-arm64", HardwareWeight: 20, CreateRevision: 101},
		{ID: "datacenter-heavy-xeon", HardwareWeight: 100, CreateRevision: 103}, // Запустился позже всех!
		{ID: "office-backup-node", HardwareWeight: 10, CreateRevision: 102},
	}

	winner := ElectHighestPriorityLeader(candidates)

	fmt.Println("Результаты выборов лидера с учетом аппаратного приоритета:")
	fmt.Printf("🏆 Избран лидер: %s (Вес оборудования: %d, Ревизия: %d)\n",
		winner.ID, winner.HardwareWeight, winner.CreateRevision)
}
```

ℹ️ Выборы лидера с приоритетом: победа наиболее мощного узла независимо от порядка запуска

## Под капотом

В реальном etcd v3:
Выборы с приоритетом оформляются в транзакцию:
```go
cli.Txn(ctx).
    If(clientv3.Compare(clientv3.Version("/election/active_leader"), "=", currentVer)).
    Then(clientv3.OpPut("/election/active_leader", highestPriorityNodeID))
```
Это предотвращает гонки, если состав кандидатов изменился прямо во время вычисления весов.

## Подводные камни

1. **Постоянные перевыборы при появлении мощной ноды (Preemption Storm):** Если новый сервер сразу отбирает власть, частые рестарты лидера парализуют систему. Используйте политику «не сменять действующего лидера, если он здоров» (Non-preemptive leadership).
2. **Игнорирование тай-брейка:** При равных весах двух нод алгоритм обязан детерминированно опираться на ревизию.
3. **Хранение весов в незащищенном виде:** Подделка веса скомпрометированным узлом может отдать ему лидерство.

## На собеседовании

**Вопрос:** Что такое «Non-preemptive Leader Election» и почему его чаще всего применяют в production?
**Ответ:** 
В невытесняющей модели (Non-preemptive), даже если в кластер добавился сервер с более высоким приоритетом, действующий лидер **не смещается** принудительно, пока он жив и здоров. Смена лидера — дорогая операция (сброс кэшей, закрытие очередей). Приоритет учитывается **только в момент аварии старого лидера** при выборе нового преемника из числа ожидающих кандидатов.
