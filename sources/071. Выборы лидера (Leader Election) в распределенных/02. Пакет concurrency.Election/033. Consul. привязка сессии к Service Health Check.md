# Consul: привязка сессии к Service Health Check (Failover по здоровью)

## Условие

33. **Consul: Service Check + Session.**: Привяжите session к health check сервиса (`CheckTTL` или `CheckHTTP`). Если сервис становится `critical` — session invalidated, lock released автоматически. Покажите, что это даёт «failover по health», а не только по процессу.

### Исходная формулировка

**Consul: Service Check + Session.**: Привяжите session к health check сервиса (`CheckTTL` или `CheckHTTP`). Если сервис становится `critical` — session invalidated, lock released автоматически. Покажите, что это даёт «failover по health», а не только по процессу.

## Теория

Обычный KeepAlive отслеживает только «жив ли процесс ОС». Однако процесс может быть жив, но абсолютно непригоден для работы:
- Завис пул соединений с базой данных (DB Connection Leak).
- Забился диск (`No space left on device`).
- Внутренний HTTP-эндпоинт возвращает `500 Internal Server Error`.

### Преимущество Consul Service Check Binding:
При создании сессии Consul позволяет связать ее с массивом проверок здоровья:
```go
sessionEntry := &api.SessionEntry{
    Name:   "leader-lock",
    Checks: []string{"service:payment-service", "check:db-ping"},
}
```
Как только локальный Health Check `db-ping` возвращает статус `critical`, серверы Consul **мгновенно и автоматически аннулируют сессию**! Замок освобождается, и лидерство передается узлу со здоровой базой данных.

## Решение по шагам

1. Создадим модель сессии с привязкой к списку `Checks`.
2. Реализуем автоматическую инвалидацию при падении любого чека.
3. Продемонстрируем сценарий: процесс жив, но сломался коннект к БД.
4. Зафиксируем автоматический перехват лидерства здоровым узлом.

## Код решения

**`consul_health_binding.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type HealthState string

const (
	HealthPassing  HealthState = "passing"
	HealthCritical HealthState = "critical"
)

type BoundSession struct {
	ID        string
	NodeID    string
	Checks    map[string]HealthState
	IsValid   bool
}

type HealthCoordinator struct {
	mu       sync.Mutex
	sessions map[string]*BoundSession
	activeLeader string
}

func NewHealthCoordinator() *HealthCoordinator {
	return &HealthCoordinator{sessions: make(map[string]*BoundSession)}
}

func (c *HealthCoordinator) RegisterSession(id, nodeID string, checks map[string]HealthState) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.sessions[id] = &BoundSession{
		ID:      id,
		NodeID:  nodeID,
		Checks:  checks,
		IsValid: true,
	}
}

func (c *HealthCoordinator) UpdateHealthCheck(sessionID, checkName string, state HealthState) {
	c.mu.Lock()
	defer c.mu.Unlock()

	sess, ok := c.sessions[sessionID]
	if !ok || !sess.IsValid {
		return
	}

	sess.Checks[checkName] = state
	fmt.Printf("[HealthMonitor] Сессия %s: проверка '%s' перешла в статус '%s'\n",
		sessionID, checkName, state)

	// Если хотя бы один чек стал critical — инвалидируем сессию!
	if state == HealthCritical {
		sess.IsValid = false
		if c.activeLeader == sess.NodeID {
			fmt.Printf("🚨 [Consul] Сессия лидера %s аннулирована из-за сбоя здоровья! Замок освобожден!\n", sess.NodeID)
			c.activeLeader = ""
		}
	}
}

func main() {
	coord := NewHealthCoordinator()

	checks := map[string]HealthState{
		"http_healthz": HealthPassing,
		"database_ping": HealthPassing,
	}
	coord.RegisterSession("sess-1", "node-alpha", checks)
	coord.activeLeader = "node-alpha"

	fmt.Println("Узел node-alpha является лидером, все проверки здоровья passing.")

	// Имитируем сбой соединения с базой данных на узле-лидере
	fmt.Println("\n💥 Сбой: Пул соединений PostgreSQL на node-alpha исчерпан!")
	coord.UpdateHealthCheck("sess-1", "database_ping", HealthCritical)

	fmt.Printf("Текущий активный лидер кластера: '%s' (свободен для здоровых кандидатов)\n",
		coord.activeLeader)
}
```

ℹ️ Failover по здоровью: автоматическая инвалидация сессии при сбое Health Check

## Под капотом

В Consul Core:
Агенты на хостах выполняют health checks локально (без нагрузки на Raft-мастера). Когда статус чека меняется на `critical`, локальный агент отправляет gRPC-сообщение серверу Consul: `Session.Invalidate`. Это обеспечивает изоляцию упавших сервисов за секунды.

## Подводные камни

1. **Ложноположительные проверки здоровья (Flapping Checks):** Нестабильный эндпоинт вызовет хаотическую смену лидеров каждые 3 секунды. Используйте порог падения (`consecutive_failures: 3`).
2. **Таймаут проверки здоровья больше TTL сессии:** Если чек висит 15 секунд, а TTL 10 секунд, сессия умрет раньше, чем чек вернет результат.
3. **Отсутствие проверки локального статуса перед взятием задач:** Лидер обязан сам опрашивать свои чеки.

## На собеседовании

**Вопрос:** В чем фундаментальное преимущество «Failover по Health Check» перед классическим «Failover по сетевому таймауту процесса»?
**Ответ:** При многих тяжелых инцидентах процесс ОС остается запущенным (CPU не загружен, память не течет, процесс слушает сокет), но функционально не способен работать (отвалилась БД, упал локальный диск, дедлок бизнес-горутины). Failover по Health Check выявляет функциональную недееспособность сервиса и превентивно передает лидерство здоровому дублеру.
