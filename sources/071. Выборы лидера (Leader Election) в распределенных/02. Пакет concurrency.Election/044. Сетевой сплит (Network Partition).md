# Сетевой сплит (Network Partition): детекция изоляции и отмена контекста

## Условие

44. **[Каверзный кейс — Split Brain (Network Partition)]**: Раздели сеть между лидером и etcd. Лидер потерял связь, но продолжает работать (он думает, что он все еще лидер). etcd истекает TTL ключа и выбирает нового лидера. Теперь у тебя два лидера! Реализуй паттерн: лидер должен *периодически* проверять, что его lease еще валиден, и если нет — отменять свой context.

### Исходная формулировка

**[Каверзный кейс — Split Brain (Network Partition)]**: Раздели сеть между лидером и etcd. Лидер потерял связь, но продолжает работать (он думает, что он все еще лидер). etcd истекает TTL ключа и выбирает нового лидера. Теперь у тебя два лидера! Реализуй паттерн: лидер должен *периодически* проверять свое лидерство (делать `etcd.Txn` с проверкой, что его ключ все еще существует перед выполнением работы).

## Теория

Классический сценарий катастрофы Split-Brain:
1. Нода A была лидером с Lease TTL 5 секунд.
2. Сетевой кабель ноды A отключился (или iptables заблокировал порт 2379).
3. Нода A не может связаться с etcd, но внутренние циклы продолжают работать.
4. В кластере etcd TTL истекает \(\implies\) Нода B избирается новым лидером!
5. В системе действуют **два лидера одновременно**.

### Паттерн самоконтроля лидера (Self-Auditing Leader Context):
Лидер не имеет права выполнять действия без предварительной верификации своего статуса.
Перед каждым важным шагом (или каждые 500 мс) горутина проверяет валидность аренды:
- Если `TimeToLive() <= 0` или запрос проверки вернул ошибку связи:
  - Вызывается `cancel()` контекста лидерства.
  - Все запущенные горутины получают сигнал `<-ctx.Done()` и немедленно завершают работу.

## Решение по шагам

1. Создадим структуру `PartitionAwareLeader` с управляемым `context.CancelFunc`.
2. Реализуем фоновый сторожевой таймер (Watchdog), проверяющий связь с etcd.
3. Симулируем обрыв сети.
4. Продемонстрируем своевременную отмену контекста до момента выбора нового лидера.

## Код решения

**`partition_watchdog.go`**

```go
package main

import (
	"context"
	"fmt"
	"time"
)

type NetworkStatus int32

type PartitionAwareLeader struct {
	nodeID      string
	networkUp   bool
	cancelWork  context.CancelFunc
}

func (l *PartitionAwareLeader) Run(ctx context.Context) {
	workCtx, cancel := context.WithCancel(ctx)
	l.cancelWork = cancel

	// 1. Рабочий бизнес-цикл
	go func() {
		for {
			select {
			case <-workCtx.Done():
				fmt.Printf("🛑 [%s] Бизнес-процесс остановлен по сигналу отмены контекста!\n", l.nodeID)
				return
			default:
				fmt.Printf("💼 [%s] Лидер выполняет полезную работу...\n", l.nodeID)
				time.Sleep(30 * time.Millisecond)
			}
		}
	}()

	// 2. Сторожевой таймер проверки аренды в etcd
	go func() {
		ticker := time.NewTicker(40 * time.Millisecond)
		defer ticker.Stop()

		for {
			select {
			case <-workCtx.Done():
				return
			case <-ticker.C:
				if !l.networkUp {
					fmt.Printf("🚨 [%s] ТРЕВОГА: Потеряна связь с etcd! Немедленно отменяем рабочий контекст!\n", l.nodeID)
					l.cancelWork()
					return
				}
			}
		}
	}()
}

func main() {
	leader := &PartitionAwareLeader{
		nodeID:    "Node-A-OriginalLeader",
		networkUp: true,
	}

	ctx := context.Background()
	leader.Run(ctx)

	// Лидер работает 70 мс в нормальной сети
	time.Sleep(70 * time.Millisecond)

	// Имитируем сетевой сплит (iptables DROP к etcd)
	fmt.Println("\n✂️ [Сетевой сплит] Связь с etcd оборвана!")
	leader.networkUp = false

	// Даем время сторожевому таймеру отработать
	time.Sleep(60 * time.Millisecond)
}
```

ℹ️ Защита от Split-Brain: сторожевой таймер отменяет context при потере связи с etcd

## Под капотом

В ядре Raft etcd:
Если лидер не может получить подтверждение от кворума узлов за `electionTimeout`, он сбрасывает статус до `Follower`. Клиентские библиотеки etcd фиксируют ошибку gRPC `codes.Unavailable` и закрывают каналы `session.Done()`, что дает приложению детерминированный сигнал об отмене прав.

## Подводные камни

1. **Проверка аренды реже, чем TTL:** Если проверять раз в 10 секунд при TTL 5 секунд, лидер успеет наломать дров до проверки.
2. **Игнорирование `ctx.Done()` в сетевых вызовах:** Сетевой I/O без передачи контекста зависнет и проигнорирует отмену.
3. **Отсутствие Fencing Token на целевом хранилище:** Двойная страховка обязательна.

## На собеседовании

**Вопрос:** Как гарантировать безопасность данных, если сеть упала так внезапно, что сторожевой таймер не успел среагировать?
**Ответ:** Никакой сторожевой таймер не дает 100% гарантии в асинхронной сети из-за пауз GC. Единственное абсолютно надежное математическое решение — **Fencing Tokens**: принимающая сторона (БД) обязана отклонять запросы с устаревшей эпохой, делая любые запоздавшие действия изолированного лидера полностью безвредными.
