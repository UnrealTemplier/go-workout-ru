# Распределённый планировщик (Leader-Only Scheduler) на time.Ticker

## Условие

26. **Распределённый cron (Leader-Only Scheduler).**: Реализуйте сервис, где только лидер запускает `time.Ticker` и выполняет задачи (например, агрегация статистики). При `OnLeadershipChange` — остановить ticker, при захвате — запустить. Покажите, что при failover задача не дублируется (единственный исполнитель).

### Исходная формулировка

**Распределённый cron (Leader-Only Scheduler).**: Реализуйте сервис, где только лидер запускает `time.Ticker` и выполняет задачи (например, агрегация статистики). При `OnLeadershipChange` — остановить ticker, при захвате — запустить. Покажите, что при failover задача не дублируется (единственный лидер).

## Теория

Паттерн **Leader-Only Scheduler** гарантирует, что периодические фоновые вычисления исполняются в единственном экземпляре в кластере.

### Модель переключения:
- **`OnElected`:**
  Создается `time.NewTicker(interval)` и запускается рабочий цикл генерации задач.
- **`OnResigned` / `OnRevoked`:**
  Вызывается `ticker.Stop()`, закрывается контекст горутины, текущая итерация завершается, и узел переходит в тихий режим наблюдения.
- **Инвариант Single-Worker:**
  В любой квант времени тикер тикает строго на одном инстансе.

## Решение по шагам

1. Создадим структуру `LeaderScheduler` с управлением жизненным циклом тикера.
2. Реализуем методы `StartLeading(ctx)` и `StopLeading()`.
3. Запустим симуляцию двух узлов.
4. Продемонстрируем передачу тикера при смене лидера без дублирования вызовов.

## Код решения

**`leader_scheduler.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type LeaderScheduler struct {
	nodeID     string
	mu         sync.Mutex
	running    bool
	stopChan   chan struct{}
	tasksDone  int64
}

func NewLeaderScheduler(nodeID string) *LeaderScheduler {
	return &LeaderScheduler{nodeID: nodeID}
}

func (s *LeaderScheduler) OnElected(ctx context.Context) {
	s.mu.Lock()
	defer s.mu.Unlock()

	if s.running {
		return
	}
	s.running = true
	s.stopChan = make(chan struct{})

	fmt.Printf("🚀 [%s] Запуск периодического планировщика (стал лидером)!\n", s.nodeID)

	go func() {
		ticker := time.NewTicker(40 * time.Millisecond)
		defer ticker.Stop()

		for {
			select {
			case <-s.stopChan:
				fmt.Printf("🛑 [%s] Планировщик остановлен (потеря лидерства).\n", s.nodeID)
				return
			case <-ctx.Done():
				return
			case <-ticker.C:
				atomic.AddInt64(&s.tasksDone, 1)
				fmt.Printf("⏰ [%s] Выполнение периодической задачи агрегации статистики (Итерация #%d)\n",
					s.nodeID, atomic.LoadInt64(&s.tasksDone))
			}
		}
	}()
}

func (s *LeaderScheduler) OnResigned() {
	s.mu.Lock()
	defer s.mu.Unlock()

	if !s.running {
		return
	}
	s.running = false
	close(s.stopChan)
}

func main() {
	ctx := context.Background()

	nodeA := NewLeaderScheduler("Scheduler-Node-A")
	nodeB := NewLeaderScheduler("Scheduler-Node-B")

	// 1. Узел A становится лидером
	nodeA.OnElected(ctx)
	time.Sleep(100 * time.Millisecond)

	// 2. Узел A теряет лидерство (Failover)
	fmt.Println("\n--- СМЕНА ЛИДЕРА: A -> B ---")
	nodeA.OnResigned()

	// 3. Узел B подхватывает работу
	nodeB.OnElected(ctx)
	time.Sleep(100 * time.Millisecond)
	nodeB.OnResigned()

	fmt.Println("\nИтог: Задачи выполнялись строго одним активным тикером без наложения!")
}
```

ℹ️ Паттерн Leader-Only Scheduler: запуск тикера при победе и остановка при отставке

## Под капотом

Защита от долгой итерации (Overrun Protection):
Если выполнение джобы занимает 500 мс при интервале тикера 100 мс, стандартный `time.Ticker` вызовет накопление тиков в канале. В Leader Scheduler используют конструкцию с флагом `inProgress` или заменяют тикер на `time.Sleep` после завершения предыдущей итерации, гарантируя отсутствие параллельных вычислений одного шага.

## Подводные камни

1. **Утечка тикера (`ticker.Stop()` забыт):** Горутина тикера останется жить в памяти, продолжая слать события.
2. **Неостановленная долгая итерация при потере лидерства:** Если джоба уже начала транзакцию в БД, потеря лидерства должна прерывать операцию через `context.Done()`.
3. **Отсутствие Fencing Token при обращении к БД:** Старый лидер может завершить начатую запись уже после того, как новый начал свою.

## На собеседовании

**Вопрос:** Как гарантировать, что если задача агрегации выполняется 10 секунд, а лидер потерял статус на 5-й секунде, результат вычислений старого лидера не перезапишет базу данных?
**Ответ:** Перед началом расчета лидер получает монотонный **Fencing Token** (номер ревизии etcd). Все записи в БД проверяют условие:
`UPDATE report SET data = $1, leader_epoch = $2 WHERE leader_epoch < $2;`
Если новый лидер уже успел избраться и обновил `leader_epoch`, коммит старого лидера будет отклонен СУБД с ошибкой 0 updated rows.
