# Оповещение о смене лидерства через типизированный канал событий

## Условие

29. **Оповещение о смене лидера.**: Реализуйте канал, который получает сообщения, когда узел становится лидером или теряет лидерство. Используйте long polling на ключ сессии или watch.

### Исходная формулировка

**Оповещение о смене лидера.**: Реализуйте канал, который получает сообщения, когда узел становится лидером или теряет лидерство. Используйте long polling на ключ сессии или watch.

## Теория

Архитектурный паттерн **Leadership Event Channel** развязывает низкоуровневую логику работы с etcd/Consul от бизнес-компонентов приложения.

### Типизированные события лидерства:
```go
type LeadershipEventType int

const (
    LeadershipAcquired LeadershipEventType = iota // Узел стал лидером
    LeadershipLost                                // Узел потерял лидерство
)
```
Бизнес-сервисы (HTTP серверы, очереди, планировщики) подписываются на единый канал `<-chan LeadershipEvent`, адаптируя свое поведение без знания о том, какая технология консенсуса используется под капотом.

## Решение по шагам

1. Определим типы событий `LeadershipEvent`.
2. Создадим менеджер `LeadershipNotifier`.
3. Реализуем публикацию событий при смене состояния.
4. Продемонстрируем реакцию бизнес-сервиса на события канала.

## Код решения

**`leadership_channel.go`**

```go
package main

import (
	"fmt"
	"time"
)

type LeadershipEventType string

const (
	EventAcquired LeadershipEventType = "ACQUIRED"
	EventLost     LeadershipEventType = "LOST"
)

type LeadershipEvent struct {
	Type      LeadershipEventType
	Timestamp time.Time
}

type LeadershipCoordinator struct {
	eventsChan chan LeadershipEvent
}

func NewLeadershipCoordinator() *LeadershipCoordinator {
	return &LeadershipCoordinator{
		eventsChan: make(chan LeadershipEvent, 10),
	}
}

func (c *LeadershipCoordinator) Events() <-chan LeadershipEvent {
	return c.eventsChan
}

func (c *LeadershipCoordinator) Emit(t LeadershipEventType) {
	c.eventsChan <- LeadershipEvent{
		Type:      t,
		Timestamp: time.Now(),
	}
}

func main() {
	coord := NewLeadershipCoordinator()

	// Фоновый бизнес-воркер слушает события
	go func() {
		for ev := range coord.Events() {
			switch ev.Type {
			case EventAcquired:
				fmt.Printf("[%v] 🟢 Бизнес-логика: Запускаем воркеры списания очередей.\n", ev.Timestamp.Format("15:04:05.000"))
			case EventLost:
				fmt.Printf("[%v] 🔴 Бизнес-логика: Приостанавливаем воркеры списания очередей.\n", ev.Timestamp.Format("15:04:05.000"))
			}
		}
	}()

	time.Sleep(30 * time.Millisecond)
	coord.Emit(EventAcquired)

	time.Sleep(80 * time.Millisecond)
	coord.Emit(EventLost)

	time.Sleep(30 * time.Millisecond)
}
```

ℹ️ Паттерн Leadership Event Channel: изолированная шина событий для бизнес-слоя

## Под капотом

Использование буферизованного канала:
Канал событий обязан иметь буфер (например, 10–50 элементов). Если канал не буферизирован, медленный подписчик в бизнес-логике заблокирует системную горутину KeepAlive, что приведет к задержке продления аренды и реальной потере лидерства!

## Подводные камни

1. **Блокировка отправителя событий:** Никогда не делайте синхронную отправку в небуферизированный канал без `select default`.
2. **Пропуск событий при рестарте:** При старте подписчик должен получить текущий актуальный статус.
3. **Утечка подписчиков:** Предусматривайте метод отписки `Unsubscribe()`.

## На собеседовании

**Вопрос:** Как избежать утечки горутины подписчика при завершении работы приложения?
**Ответ:** Передавать в функцию подписчика `ctx context.Context`. При `ctx.Done()` горутина завершает цикл `select` и выходит. Закрытие канала `close(eventsChan)` со стороны координатора также корректно завершает цикл `for ev := range eventsChan`.
