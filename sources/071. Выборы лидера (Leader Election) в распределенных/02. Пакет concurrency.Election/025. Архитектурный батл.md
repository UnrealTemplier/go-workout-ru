### Исходная формулировка

**Consul vs etcd для leader election:**
* Consul: встроенный DNS, health checks, multi-datacenter
* etcd: быстрее, проще, часть Kubernetes
Используйте etcd если уже в K8s, Consul для standalone distributed systems.

## Теория

Выбор между Consul и etcd в Enterprise-архитектуре зависит от целевого окружения, требований к сетевой топологии и используемого стека.

### Детальное сравнение:
1. **Когда выбирать etcd:**
   - Сервис уже развернут в **Kubernetes** (etcd уже развернут и поддерживается платформенной командой).
   - Требуется сверхнизкая задержка (микросекунды) и высокая производительность gRPC.
   - Нужна строгая математическая модель ревизий (MVCC / Linearizable Read).
2. **Когда выбирать HashiCorp Consul:**
   - **Standalone / Hybrid Cloud:** Система работает на виртуальных машинах (Bare Metal, OpenStack, AWS EC2) без Kubernetes.
   - **Multi-Datacenter Federation:** Требуется репликация каталога между ЦОД (Москва, Санкт-Петербург, Новосибирск) из коробки через WAN Gossip.
   - **Встроенные Health Checks и DNS:** Клиентам не нужно внедрять SDK etcd — достаточно резолвить DNS `leader.service.consul`.

## Код решения

**`tech_selection.go`**

```go
package main

import "fmt"

type InfrastructureProfile struct {
	InKubernetes        bool
	MultiDatacenterWAN  bool
	NeedsIntegratedDNS  bool
	HighThroughputReq   bool
}

type Decision string

const (
	ChooseEtcd   Decision = "ETCD (Fast, Lightweight, Native K8s / gRPC)"
	ChooseConsul Decision = "CONSUL (Multi-DC, Built-in DNS, Agent Health-Checks)"
)

func EvaluateTechnology(profile InfrastructureProfile) Decision {
	if profile.InKubernetes && !profile.MultiDatacenterWAN {
		return ChooseEtcd
	}
	if profile.MultiDatacenterWAN || profile.NeedsIntegratedDNS {
		return ChooseConsul
	}
	if profile.HighThroughputReq {
		return ChooseEtcd
	}
	return ChooseConsul
}

func main() {
	projectA := InfrastructureProfile{
		InKubernetes:       true,
		MultiDatacenterWAN: false,
		HighThroughputReq:  true,
	}

	projectB := InfrastructureProfile{
		InKubernetes:       false,
		MultiDatacenterWAN: true,
		NeedsIntegratedDNS: true,
	}

	fmt.Printf("Проект 1 (Cloud-Native Финтех Микросервис):\n  -> Рекомендация: %s\n\n",
		EvaluateTechnology(projectA))
	fmt.Printf("Проект 2 (Legacy Гео-распределенный Биллинг на VM):\n  -> Рекомендация: %s\n",
		EvaluateTechnology(projectB))
}
```

## Под капотом

Сетевой оверхед WAN:
Consul имеет двухуровневую архитектуру Gossip: локальный LAN (быстрый UDP пинг между узлами стойки) и глобальный WAN (только между серверами дата-центров). etcd рассчитан строго на низколатентные сети внутри одного дата-центра или региона (RTT < 10ms); растягивание etcd кластера между удаленными городами приводит к деградации Raft Heartbeats.

## Подводные камни

1. **Растягивание etcd через континент:** Пинг 80 мс между Москвой и Владивостоком приведет к постоянным таймаутам Raft в etcd.
2. **Использование Consul без выделенных серверов:** Запуск агентов Consul в режиме `-server` на каждой ноде убьет производительность Raft.
3. **Разворачивание второго etcd рядом с K8s:** Если приложение уже в K8s, часто используют Custom Resources (CRD) или координационные Leases Kubernetes (`coordination.k8s.io`).

## На собеседовании

**Вопрос:** Можно ли использовать один и тот же кластер etcd, на котором работает сам Kubernetes, для нужд пользовательских микросервисов компании?
**Ответ:** Категорически запрещено! Нагрузка от пользовательских приложений (миллионы ключей, интенсивный трафик) может забить диск и CPU etcd, вызвав потерю кворума Control Plane Kubernetes, падение Kube-API Server и каскадный отказ всего кластера. Для бизнес-приложений всегда поднимается отдельный независимый кластер etcd или Consul.
