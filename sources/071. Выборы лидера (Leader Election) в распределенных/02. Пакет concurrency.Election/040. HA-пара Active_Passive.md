# HA-пара Active/Passive: детекция потери пульса и Fencing Token

## Условие

40. **HA-пair Active/Passive.**: Два узла: active пишет heartbeat в etcd каждые 5 сек (`/heartbeat`), passive мониторит. При пропаже heartbeat > `TTL * 2` passive пытается стать active. ### Исходная формулировка

**HA-пair Active/Passive.**: Два узла: active пишет heartbeat в etcd каждые 5 сек (`/heartbeat`), passive мониторит. При пропаже heartbeat > `TTL * 2` passive пытается стать active. Покажите race condition при одновременном promote (оба видят пропажу heartbeat). Реализуйте защиту через fencing token (см. Блок 27).

## Теория

Классическая архитектура высокой доступности (High Availability Pair):
- Узел `Active` пишет метку времени в ключ `/heartbeat` каждые 5 секунд.
- Узел `Passive` опрашивает ключ.
- Если \(\Delta t > \text{TTL} \times 2 = 10\text{с}\), Passive предполагает гибель Active и инициирует процедуру **Promote**.

### Состояние гонки при одновременном Promote:
Если сеть между узлами кратковременно разорвалась, оба узла могут решить, что напарник мертв, и одновременно объявить себя Active.

### Защита через Fencing Token (Epoch/Term):
Промоут оформляется через атомарное увеличение эпохи в центральной базе:
`UPDATE cluster_state SET active_node = $1, epoch = epoch + 1 WHERE epoch = $current_epoch;`
Только один узел успешно увеличит `epoch`, получив монопольное право на запись.

## Решение по шагам

1. Создадим модель `HAPairCluster`.
2. Смоделируем сетевой сплит, провоцирующий одновременный Promote.
3. Покажем, как CAS-операция обновления эпохи отсекает дубликат.
4. Продемонстрируем сохранение строго одного лидера.

## Код решения

**`ha_pair_fencing.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type PromotionResult struct {
	Success bool
	Epoch   int64
}

type HACoordinationCenter struct {
	mu         sync.Mutex
	activeNode string
	epoch      int64
}

func NewHACenter() *HACoordinationCenter {
	return &HACoordinationCenter{activeNode: "Node-A", epoch: 1}
}

// PromoteAttempt выполняет атомарный CAS: сменяет лидера и инкрементирует Fencing Token (Epoch)
func (c *HACoordinationCenter) PromoteAttempt(candidate string, expectedEpoch int64) PromotionResult {
	c.mu.Lock()
	defer c.mu.Unlock()

	if c.epoch == expectedEpoch {
		c.epoch++
		c.activeNode = candidate
		fmt.Printf("👑 [%s] PROMOTE УСПЕШЕН! Новая эпоха: %d\n", candidate, c.epoch)
		return PromotionResult{Success: true, Epoch: c.epoch}
	}

	fmt.Printf("❌ [%s] PROMOTE ОТКЛОНЕН: Ожидалась эпоха %d, но в системе уже эпоха %d!\n",
		candidate, expectedEpoch, c.epoch)
	return PromotionResult{Success: false, Epoch: c.epoch}
}

func main() {
	ha := NewHACenter()

	fmt.Printf("Исходное состояние кластера: Active=%s, Epoch=%d\n\n", ha.activeNode, ha.epoch)

	// Оба узла заметили пропажу пинга на эпохе 1 и одновременно пытаются стать Active
	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		ha.PromoteAttempt("Node-A-Recovery", 1)
	}()

	go func() {
		defer wg.Done()
		ha.PromoteAttempt("Node-B-Passive", 1)
	}()

	wg.Wait()

	fmt.Printf("\nФинальное состояние: Active=%s, Итоговая эпоха Fencing Token: %d\n",
		ha.activeNode, ha.epoch)
}
```

ℹ️ Защита HA-пары от одновременного Promote через атомарный инкремент Fencing Token (Epoch)

## Под капотом

В распределенных СУБД (например, Patroni для PostgreSQL):
Patroni использует etcd/Consul для хранения ключа лидера кластера БД. При сбое мастера Standby реплика выполняет `PUT leader` с проверкой `resourceVersion`. Тот, кто выиграл транзакцию, выпускает SQL-команду `pg_promote()`, переводя базу из Read-Only реплики в пишущий Master.

## Подводные камни

1. **Промоут без проверки эпохи:** Приведет к ситуации Split-Brain, когда обе реплики начнут писать в независимые базы данных, вызывая дивергенцию данных (Data Divergence).
2. **Таймаут меньше RTT сети:** Приведет к ложным переключениям при малейшем лаге.
3. **Отсутствие изоляции старого мастера:** Старый мастер обязан быть принудительно переведен в `read-only`.

## На собеседовании

**Вопрос:** Что делать, если при аварийном Promote резервной ноды старый Primary сервер внезапно ожил и продолжает принимать локальные клиентские запросы?
**Ответ:** Применяется **Fencing на уровне клиента и прокси**:
1. Балансировщики нагрузки (Envoy / HAProxy) опрашивают эндпоинт `/primary` на нодах каждые 500 мс.
2. Старый Primary при потере аренды etcd обязан немедленно закрыть порт 5432 или перевести себя в режим `read_only = on`.
3. Все пишущие запросы клиентов отклоняются кодом ошибки `read-only transaction`.
