# Создание сессии и конкурентный захват лидерского ключа с Backoff

## Условие

11. **Создание сессии и захват ключа.**: Реализуйте простой лидерский лок: создайте сессию с TTL и привяжите её к ключу в KV, используя `Acquire`. Если ключ уже занят, сессия не создается – ожидайте освобождения с backoff.

### Исходная формулировка

**Создание сессии и захват ключа.**: Реализуйте простой лидерский лок: создайте сессию с TTL и привяжите её к ключу в KV, используя `Acquire`. Если ключ уже занят, сессия не создается – ожидайте освобождения с backoff.

## Теория

При проектировании распределенных воркеров претенденты, потерпевшие неудачу при вызове `Acquire`, не должны спамить запросами сервер координации.

### Стратегия захвата с экспоненциальным бэкоффом (Backoff Strategy):
1. **Попытка создания сессии и захвата:**
   Узел пытается захватить ключ `services/crawler/leader`.
2. **Если ключ свободен (`Acquire == true`):**
   Узел становится лидером, запускает цикл продления сессии и полезную работу.
3. **Если ключ занят (`Acquire == false`):**
   Узел не держит активную сессию (чтобы не расходовать память Consul), переходит в режим ожидания и засыпает на:
   $$T_{\text{wait}} = \min(T_{\text{max}}, T_{\text{base}} \times 2^{\text{attempt}}) \pm \text{jitter}$$
   Либо подписывается на событие освобождения ключа через Blocking Query.

## Решение по шагам

1. Создадим структуру `LeaderElectionCandidate`.
2. Реализуем цикл попыток с расчетом задержки экспоненциального бэкоффа.
3. При неудаче освобождаем временные ресурсы.
4. Продемонстрируем, как второй узел терпеливо дожидается освобождения ключа и занимает его.

## Код решения

**`acquire_with_backoff.go`**

```go
package main

import (
	"context"
	"fmt"
	"math/rand"
	"sync"
	"time"
)

type SharedKVLock struct {
	mu      sync.Mutex
	owner   string
	keyHeld bool
}

func (l *SharedKVLock) TryAcquire(candidateID string) bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	if !l.keyHeld {
		l.keyHeld = true
		l.owner = candidateID
		return true
	}
	return false
}

func (l *SharedKVLock) Release(candidateID string) {
	l.mu.Lock()
	defer l.mu.Unlock()
	if l.owner == candidateID {
		l.keyHeld = false
		l.owner = ""
	}
}

type CandidateNode struct {
	ID        string
	lock      *SharedKVLock
	baseDelay time.Duration
	maxDelay  time.Duration
}

func (c *CandidateNode) RunForLeader(ctx context.Context) {
	attempt := 0

	for {
		select {
		case <-ctx.Done():
			fmt.Printf("[%s] Остановка участия в выборах.\n", c.ID)
			return
		default:
		}

		if c.lock.TryAcquire(c.ID) {
			fmt.Printf("🎉 [%s] УСПЕХ: Захватил лидерский замок!\n", c.ID)
			// Имитация работы лидера
			time.Sleep(100 * time.Millisecond)
			c.lock.Release(c.ID)
			fmt.Printf("[%s] Лидер завершил работу и освободил замок.\n", c.ID)
			return
		}

		attempt++
		backoff := c.baseDelay * (1 << attempt)
		if backoff > c.maxDelay {
			backoff = c.maxDelay
		}
		// Jitter
		jitter := time.Duration(rand.Int63n(int64(c.baseDelay)))
		sleepTime := backoff + jitter

		fmt.Printf("[%s] Ключ занят. Попытка #%d не удалась, ожидание %v...\n", c.ID, attempt, sleepTime)

		select {
		case <-time.After(sleepTime):
		case <-ctx.Done():
			return
		}
	}
}

func main() {
	lock := &SharedKVLock{}

	// Инициализируем 2 узла
	node1 := &CandidateNode{ID: "node-1", lock: lock, baseDelay: 15 * time.Millisecond, maxDelay: 100 * time.Millisecond}
	node2 := &CandidateNode{ID: "node-2", lock: lock, baseDelay: 15 * time.Millisecond, maxDelay: 100 * time.Millisecond}

	ctx, cancel := context.WithTimeout(context.Background(), 500*time.Millisecond)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(2)

	go func() {
		defer wg.Done()
		node1.RunForLeader(ctx)
	}()

	go func() {
		defer wg.Done()
		node2.RunForLeader(ctx)
	}()

	wg.Wait()
}
```

ℹ️ Экспоненциальный бэкофф с джиттером при ожидании освобождения лидерского ключа

## Под капотом

Почему создание сессии откладывается до успешного захвата:
В Consul создание сессии требует записи в Raft-лог лидеров кластера. Если 1000 микросервисов создадут сессии и будут каждые 5 секунд слать Heartbeat, не являясь лидерами, Consul потратит гигабайты памяти и тысячи IOPS на пустой опрос. Создавать сессию следует только в момент непосредственного участия в выборах.

## Подводные камни

1. **Поллинг в цикле без пауз (`for !Acquire() {}`):** Загрузит CPU ядра контейнера на 100% и вызовет троттлинг cgroups в Kubernetes.
2. **Фиксированный интервал без джиттера:** Все ведомые узлы проснутся в одну миллисекунду и синхронно ударят в Consul API.
3. **Несброшенный счетчик попыток:** После успешного захвата и последующей потери замка счетчик `attempt` должен сбрасываться в 0.

## На собеседовании

**Вопрос:** Почему при конкуренции за лидерство в Consul рекомендуется использовать Blocking Query вместо постоянного цикла `Acquire()` с бэкоффом?
**Ответ:** 
При бэкоффе задержка обнаружения освобождения ключа может составлять от сотен миллисекунд до секунд (пока поток спит). 
При использовании **Blocking Query (`WaitIndex`)** соединение висит в ожидании на стороне сервера Consul. Как только ключ освобождается (прежний лидер упал), Consul мгновенно отправляет ответ клиенту, позволяя новому лидеру занять место за считанные миллисекунды без лишних опросов.
