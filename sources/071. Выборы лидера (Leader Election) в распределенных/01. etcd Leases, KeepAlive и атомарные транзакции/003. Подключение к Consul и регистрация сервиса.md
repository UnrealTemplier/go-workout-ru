# Подключение к Consul и регистрация сервиса с проверкой здоровья (Health Check)

## Условие

### Исходная формулировка

**Подключение к Consul и регистрация сервиса.**: Запустите Consul (dev-режим). Используя `consul/api`, зарегистрируйте экземпляр сервиса с health-check (ttl или http). Получите список здоровых экземпляров через DNS или HTTP API.

## Теория

HashiCorp Consul — распределенный Service Mesh и Key-Value реестр на базе протокола консенсуса Raft и протокола сплетен (Gossip Protocol Serf).

### Механика регистрации сервиса в Consul:
1. **Регистрация агента (`Agent.ServiceRegister`):**
   Каждый узел объявляет свое имя, теги, сетевой адрес и порт.
2. **Health Check (Проверка жизнеспособности):**
   - **HTTP Check:** Consul периодически опрашивает эндпоинт сервиса (например, `GET /healthz`). При статусе `200 OK` сервис считается `passing`.
   - **TTL Check:** Сервис обязан сам периодически слать подтверждение пульса (`agent.UpdateTTL`). Если сервис не обновил TTL за указанное время, статус меняется на `critical`.
3. **Обнаружение сервисов (Service Discovery):**
   Другие микросервисы опрашивают Consul через HTTP API (`/v1/health/service/{name}?passing=true`) или встроенный DNS-сервер (`{name}.service.consul`), получая только здоровые реплики.

## Решение по шагам

1. Подготовим структуру конфигурации агента Consul `AgentServiceRegistration`.
2. Настроим проверку здоровья типа `AgentServiceCheck` с интервалом опроса.
3. Смоделируем работу каталога Consul с фильтрацией `passing: true`.
4. Продемонстрируем исключение упавшего сервиса из списка обнаружения.

## Код решения

**`consul_registration.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type CheckStatus string

const (
	StatusPassing  CheckStatus = "passing"
	StatusCritical CheckStatus = "critical"
)

type ServiceRegistration struct {
	ID      string
	Name    string
	Address string
	Port    int
	Status  CheckStatus
}

type ConsulCatalogEmulator struct {
	mu       sync.RWMutex
	services map[string]*ServiceRegistration
}

func NewConsulCatalog() *ConsulCatalogEmulator {
	return &ConsulCatalogEmulator{
		services: make(map[string]*ServiceRegistration),
	}
}

func (c *ConsulCatalogEmulator) Register(reg ServiceRegistration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.services[reg.ID] = &reg
	fmt.Printf("[Consul] Зарегистрирован сервис %s (ID: %s) на %s:%d\n",
		reg.Name, reg.ID, reg.Address, reg.Port)
}

func (c *ConsulCatalogEmulator) SetStatus(serviceID string, status CheckStatus) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if s, ok := c.services[serviceID]; ok {
		s.Status = status
		fmt.Printf("[Consul HealthCheck] Статус сервиса %s изменен на '%s'\n", serviceID, status)
	}
}

func (c *ConsulCatalogEmulator) GetHealthyServices(name string) []ServiceRegistration {
	c.mu.RLock()
	defer c.mu.RUnlock()

	var healthy []ServiceRegistration
	for _, s := range c.services {
		if s.Name == name && s.Status == StatusPassing {
			healthy = append(healthy, *s)
		}
	}
	return healthy
}

func main() {
	catalog := NewConsulCatalog()

	// 1. Регистрируем 2 реплики PaymentService
	catalog.Register(ServiceRegistration{
		ID:      "payment-node-1",
		Name:    "payment-service",
		Address: "10.0.1.10",
		Port:    8080,
		Status:  StatusPassing,
	})
	catalog.Register(ServiceRegistration{
		ID:      "payment-node-2",
		Name:    "payment-service",
		Address: "10.0.1.11",
		Port:    8080,
		Status:  StatusPassing,
	})

	// 2. Поиск здоровых инстансов
	healthy := catalog.GetHealthyServices("payment-service")
	fmt.Printf("Здоровых инстансов найдено: %d\n", len(healthy))

	// 3. Симуляция сбоя Node 1
	catalog.SetStatus("payment-node-1", StatusCritical)

	// 4. Повторный запрос: Node 1 исключена из балансировки
	healthyAfter := catalog.GetHealthyServices("payment-service")
	fmt.Printf("Здоровых инстансов после сбоя Node 1: %d (Активен: %s)\n",
		len(healthyAfter), healthyAfter[0].ID)
}
```

## Под капотом

В Consul кластер делится на две плоскости:
1. **Control Plane (Consul Servers, Raft):** 3 или 5 серверов поддерживают согласованный лог состояния каталога, сессий и KV.
2. **Gossip Protocol (Serf):** Агенты на хостах обмениваются UDP-пакетами через SWIM-протокол обнаружения сбоев (Failure Detector). Это позволяет обнаруживать падения нод за сотни миллисекунд без нагрузки на центральные серверы Raft.

## Подводные камни

1. **Регистрация сервиса без `DeregisterCriticalServiceAfter`:** Если не указать этот параметр, упавший сервис навсегда останется в статусе `critical`, загрязняя каталог Consul.
2. **Слишком частые HTTP Health Checks:** Если 100 сервисов пингуют друг друга каждую секунду, сетевой стек хоста захлебнется в SYN/ACK пакетах.
3. **Flapping Health Checks:** Нестабильные сервисы (мигающие между passing и critical) вызывают шторм обновлений в Consul DNS.

## На собеседовании

**Вопрос:** В чем фундаментальное архитектурное отличие обнаружения сервисов через Consul DNS от HTTP Catalog API?
**Ответ:**
- **Consul DNS (порт 8600):** Прост в интеграции (работает с любым языком без SDK), кэшируется DNS-резолвером ОС, но имеет проблемы с задержкой инвалидации TTL записей (stale IPs).
- **HTTP API (`/v1/health/service`):** Поддерживает **Blocking Queries / Long Polling**: клиент открывает соединение и мгновенно получает push-уведомление при изменении состава здоровых нод, исключая задержки DNS-кэша.
