# Захват распределенной блокировки в Consul через KV.Acquire

## Условие

7. **Consul lock acquisition**: Попытайтесь захватить lock через `consul.KV().Acquire()` с session ID. Первый успешный — leader.

### Исходная формулировка

**Consul lock acquisition**: Попытайтесь захватить lock через `consul.KV().Acquire()` с session ID. Первый успешный — leader.

## Теория

Захват блокировки в Consul Key-Value осуществляется с помощью специального флага операции `Acquire`:
```go
pair := &api.KVPair{
    Key:     "service/leader",
    Value:   []byte("node-1"),
    Session: sessionID,
}
success, meta, err := client.KV().Acquire(pair, nil)
```

### Принцип работы KV.Acquire:
1. Запрос проверяет, связано ли поле `Session` ключа с какой-либо активной сессией.
2. Если `Session == ""`: Consul атомарно записывает переданный `sessionID`, инкрементирует `LockIndex` и возвращает `true`. Узел победил и признается лидером.
3. Если `Session != ""`: ключ уже заблокирован другой сессией. Метод возвращает `false` без ошибки. Узел признается ведомым (follower).
4. Атомарность гарантируется лидером кластера серверов Consul через Raft.

## Решение по шагам

1. Создадим структуру `ConsulLockManager`.
2. Реализуем атомарный метод `Acquire(key, value, sessionID)`.
3. Запустим двух претендентов на одну блокировку.
4. Продемонстрируем, что ровно один узел получает `success == true`.

## Код решения

**`consul_acquire_lock.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type LockRecord struct {
	Key       string
	Value     string
	Session   string
	LockIndex uint64
}

type MemoryConsulKV struct {
	mu    sync.Mutex
	store map[string]*LockRecord
}

func NewMemoryConsulKV() *MemoryConsulKV {
	return &MemoryConsulKV{store: make(map[string]*LockRecord)}
}

// Acquire эмулирует consul.KV().Acquire(pair, nil)
func (c *MemoryConsulKV) Acquire(key, val, sessionID string) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	rec, exists := c.store[key]
	if !exists {
		// Ключ свободен, захватываем
		c.store[key] = &LockRecord{
			Key:       key,
			Value:     val,
			Session:   sessionID,
			LockIndex: 1,
		}
		return true
	}

	// Если уже удерживается какой-то сессией
	if rec.Session != "" {
		if rec.Session == sessionID {
			return true // Уже удерживается нами
		}
		return false // Занят чужой сессией!
	}

	// Ключ существовал, но сессия была сброшена
	rec.Session = sessionID
	rec.Value = val
	rec.LockIndex++
	return true
}

func main() {
	kv := NewMemoryConsulKV()
	lockKey := "service/payment-gateway/leader"

	// Инстанс 1 захватывает лидерство
	ok1 := kv.Acquire(lockKey, "192.168.1.10:8080", "session-node-1-xyz")
	fmt.Printf("[Node-1] Попытка Acquire: %v (Лидер избран!)\n", ok1)

	// Инстанс 2 пытается захватить тот же ключ
	ok2 := kv.Acquire(lockKey, "192.168.1.11:8080", "session-node-2-abc")
	fmt.Printf("[Node-2] Попытка Acquire: %v (Замок занят!)\n", ok2)
}
```

ℹ️ Атомарный захват блокировки в KV Consul через привязку SessionID

## Под капотом

Счетчик `LockIndex`:
Каждый успешный вызов `Acquire` на ключе увеличивает монотонный 64-битный счетчик `LockIndex`. Этот счетчик выступает естественным **Fencing Token** в распределенной системе: внешние сервисы могут проверять `LockIndex`, гарантируя, что старый лидер с меньшим индексом не повредит данные.

## Подводные камни

1. **Игнорирование `Release` при graceful shutdown:** Если лидер завершает работу и не вызывает `KV().Release(pair)`, ключ останется заблокированным на все время действия TTL сессии.
2. **Перезапись ключа через `Put` вместо `Acquire`:** Вызов обычного `KV().Put()` сбросит привязку сессии и сломает всю систему координации!
3. **Отсутствие проверки `Session` при чтении:** Чтение ключа возвращает данные, но если `pair.Session == ""`, лидера в данный момент нет.

## На собеседовании

**Вопрос:** Что произойдет при попытке вызвать `consul.KV().Acquire` с несуществующим или просроченным `sessionID`?
**Ответ:** Consul вернет ошибку `Invalid session: <id>`. Захват замка немедленно провалится, предотвращая создание зомби-лидеров с недействительными сессиями.
