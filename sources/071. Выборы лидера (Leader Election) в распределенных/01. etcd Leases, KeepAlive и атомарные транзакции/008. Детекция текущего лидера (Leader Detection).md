# Детекция текущего лидера (Leader Detection) и сверка активной сессии

## Условие

8. **Leader detection**: Каждый инстанс проверяет, является ли он leader'ом через проверку session ID в KV. Если `key.Session == mySession` — я leader.

### Исходная формулировка

**Leader detection**: Каждый инстанс проверяет, является ли он leader'ом через проверку session ID в KV. Если `key.Session == mySession` — я leader.

## Теория

Удержание лидерства в распределенной системе — непрерывный процесс. Недостаточно однажды получить `success = true` при старте приложения: узел обязан непрерывно валидировать свой статус.

### Алгоритм Leader Detection:
1. Узел опрашивает KV-хранилище Consul по пути `/service/leader`.
2. Анализируется поле `KVPair.Session`:
   - Если `pair.Session == mySessionID`: узел **подтверждает** статус активного лидера и продолжает выполнение критических задач.
   - Если `pair.Session != mySessionID` или `pair.Session == ""`: узел **немедленно прекращает** выполнение лидерских функций (снимает регистрацию cron, закрывает воркеры) и переходит в статус ведомого.
3. Для минимизации сетевого оверхеда опрос выполняется через **Consul Blocking Queries** (`WaitIndex`), получая мгновенный ответ только при смене состояния ключа.

## Решение по шагам

1. Создадим структуру `NodeAgent` с уникальным `SessionID`.
2. Реализуем метод проверки лидерства `CheckIsLeader()`.
3. Смоделируем смену лидера и покажем реакцию инстансов.
4. Продемонстрируем немедленную остановку фоновых задач ведомого.

## Код решения

**`leader_detection.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type ConsulKVPair struct {
	Key     string
	Value   string
	Session string
}

type NodeAgent struct {
	NodeID    string
	SessionID string
	IsLeader  bool
}

type ClusterStore struct {
	mu sync.RWMutex
	kv map[string]*ConsulKVPair
}

func (s *ClusterStore) Get(key string) *ConsulKVPair {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return s.kv[key]
}

func (a *NodeAgent) EvaluateRole(store *ClusterStore, key string) {
	pair := store.Get(key)
	if pair != nil && pair.Session == a.SessionID {
		if !a.IsLeader {
			a.IsLeader = true
			fmt.Printf("[%s] СТАТУС: Я избран ЛИДЕРОМ (Session: %s)!\n", a.NodeID, a.SessionID)
		}
	} else {
		if a.IsLeader {
			a.IsLeader = false
			fmt.Printf("[%s] ТРЕВОГА: Я потерял статус лидера! Переход в standby.\n", a.NodeID)
		} else {
			fmt.Printf("[%s] Статус: ведомый (Follower). Текущий лидер: %s\n",
				a.NodeID, func() string {
					if pair != nil {
						return pair.Value
					}
					return "отсутствует"
				}())
		}
	}
}

func main() {
	store := &ClusterStore{
		kv: map[string]*ConsulKVPair{
			"services/order/leader": {
				Key:     "services/order/leader",
				Value:   "node-alpha:8080",
				Session: "session-alpha-111",
			},
		},
	}

	nodeA := &NodeAgent{NodeID: "node-alpha", SessionID: "session-alpha-111"}
	nodeB := &NodeAgent{NodeID: "node-beta", SessionID: "session-beta-222"}

	fmt.Println("=== Раунд 1: Оценка статуса узлов ===")
	nodeA.EvaluateRole(store, "services/order/leader")
	nodeB.EvaluateRole(store, "services/order/leader")

	fmt.Println("\n=== Раунд 2: Лидерство передано Node Beta ===")
	store.mu.Lock()
	store.kv["services/order/leader"] = &ConsulKVPair{
		Key:     "services/order/leader",
		Value:   "node-beta:8080",
		Session: "session-beta-222",
	}
	store.mu.Unlock()

	nodeA.EvaluateRole(store, "services/order/leader")
	nodeB.EvaluateRole(store, "services/order/leader")
}
```

ℹ️ Детекция роли лидера через сверку session ID в ключе KV Consul

## Под капотом

Механика Consul Blocking Queries:
Клиент передает в заголовке `?index=12345` последний известный `ModifyIndex`. Сервер Consul не отвечает сразу, а удерживает HTTP-соединение до тех пор, пока индекс ключа не изменится, либо до истечения таймаута (по умолчанию 5 минут). Это превращает опрос в сверхэффективный Push-механизм.

## Подводные камни

1. **Проверка только адреса, а не `SessionID`:** Если упавший узел перезапустился на том же IP и порту, старый замок может удерживаться его погибшей сессией. Сверять нужно строго криптографический `SessionID`.
2. **Кэширование роли без перепроверки:** Лидер не имеет права выполнять операции, опираясь на проверку 5-секундной давности.
3. **Отсутствие обработки сетевой ошибки Consul:** Если Consul недоступен, узел обязан пессимистично сбросить с себя роль лидера.

## На собеседовании

**Вопрос:** Почему при потере связи с кластером координации (Consul/etcd) лидер обязан немедленно сложить полномочия, даже если локально процесс полностью исправен?
**Ответ:** Потому что в распределенной сети потеря связи с кворумом чаще всего означает сетевую изоляцию (Network Partition). Кластер на другой стороне уже избрал нового лидера. Продолжение работы изолированного лидера гарантированно приведет к катастрофическому Split-Brain и повреждению данных.
