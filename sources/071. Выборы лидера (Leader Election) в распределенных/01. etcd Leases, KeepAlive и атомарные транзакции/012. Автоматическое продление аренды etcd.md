# Автоматическое продление аренды etcd (KeepAlive Loop)

## Условие

12. **[KeepAlive]**: Если процесс умрет, etcd должен удалить ключ через 10 секунд. Напиши горутину, которая постоянно отправляет `KeepAlive` запросы, чтобы продлить аренду, пока процесс жив.

### Исходная формулировка

**[KeepAlive]**: Если процесс умрет, etcd должен удалить ключ через 10 секунд. Напиши горутину, которая постоянно отправляет `KeepAlive` запросы, чтобы продлить аренду, пока процесс жив.

## Теория

В etcd v3 вызов `client.KeepAlive(ctx, leaseID)` открывает двунаправленный gRPC-стрим к лидеру кластера. Внутри официального Go SDK фоновая горутина самостоятельно отправляет пакеты продления аренды с оптимальной частотой.

Однако в коде приложения разработчик обязан обрабатывать возвращаемый канал:
```go
keepAliveCh, err := cli.KeepAlive(ctx, leaseID)
```
Канал `keepAliveCh` транслирует входящие структуры `*clientv3.LeaseKeepAliveResponse`.
Если связь с кластером etcd разорвана или TTL аренды истек на стороне сервера, etcd закрывает стрим, и канал `keepAliveCh` закрывается (`resp == nil`).
В эту же миллисекунду горутина приложения обязана зафиксировать потерю лидерства и отменить `context.Context` всех активных бизнес-воркеров.

## Решение по шагам

1. Создадим структуру `EtcdKeepAliveChannel` для имитации gRPC стрима ответов.
2. Реализуем горутину мониторинга канала KeepAlive.
3. Добавим атомарный флаг `isLeader` (`sync/atomic`).
4. Смоделируем сетевой обрыв стрима и покажем мгновенный сброс статуса лидера.

## Код решения

**`keepalive_stream.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"
)

type KeepAliveResponse struct {
	ID  int64
	TTL int64
}

func RunLeaderKeepAliveMonitor(ctx context.Context, keepAliveCh <-chan *KeepAliveResponse, isLeader *int32) {
	fmt.Println("[KeepAliveMonitor] Мониторинг пульса аренды etcd запущен.")

	for {
		select {
		case <-ctx.Done():
			atomic.StoreInt32(isLeader, 0)
			fmt.Println("[KeepAliveMonitor] Контекст приложения завершен.")
			return
		case resp, ok := <-keepAliveCh:
			if !ok {
				// КРИТИЧЕСКИЙ СБОЙ: Канал закрыт etcd!
				atomic.StoreInt32(isLeader, 0)
				fmt.Println("🚨 [KeepAliveMonitor] Канал KeepAlive закрыт! Аренда аннулирована! Складываем полномочия лидера!")
				return
			}
			fmt.Printf("[KeepAliveMonitor] Аренда #%d подтверждена сервером (TTL: %d с)\n", resp.ID, resp.TTL)
		}
	}
}

func main() {
	var isLeader int32 = 1 // Узел является лидером
	ch := make(chan *KeepAliveResponse, 5)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	go RunLeaderKeepAliveMonitor(ctx, ch, &isLeader)

	// Имитация успешных ответов от etcd
	ch <- &KeepAliveResponse{ID: 1001, TTL: 10}
	time.Sleep(30 * time.Millisecond)
	ch <- &KeepAliveResponse{ID: 1001, TTL: 10}
	time.Sleep(30 * time.Millisecond)

	// Имитируем сетевой сбой: etcd разрывает стрим
	close(ch)
	time.Sleep(50 * time.Millisecond)

	fmt.Printf("Итоговый статус ноды: IsLeader=%d (0 означает безопасный переход в standby)\n",
		atomic.LoadInt32(&isLeader))
}
```

ℹ️ Обработка закрытия канала KeepAlive: мгновенный сброс статуса лидера

## Под капотом

В gRPC транспорте etcd v3:
Метод `LeaseKeepAlive` использует один мультиплексированный HTTP/2 стрим. Клиент раз в $TTL/3$ шлет сообщение `LeaseKeepAliveRequest`. Сервер отвечает `LeaseKeepAliveResponse`. Если сервер не ответил за время `keepAliveTimeout` (по умолчанию 3 секунды), клиент разрывает TCP-сокет и переподключается к следующему endpoint из списка кластера.

## Подводные камни

1. **Игнорирование закрытия канала:** Если просто запустить `cli.KeepAlive(ctx, id)` и не читать канал, буфер переполнится, а при сетевом обрыве приложение не узнает, что ключ удален.
2. **Блокирующие операции при потере аренды:** Лидер обязан мгновенно завершить все операции записи в БД при закрытии канала.
3. **Отсутствие буфера в канале:** Несвоевременное чтение из канала может затормозить внутренний рантайм клиента etcd.

## На собеседовании

**Вопрос:** Что делать, если при вызове `client.KeepAlive` кластер etcd возвращает ошибку `etcdserver: requested lease not found`?
**Ответ:** Это означает, что из-за сетевой задержки или GC-паузы аренда уже истекла на стороне etcd, и кластер удалил ее вместе со всеми ключами. Приложение обязано немедленно прекратить выполнение лидерских обязанностей, сбросить локальное состояние, закрыть открытые транзакции и заново начать процесс выборов с создания новой аренды (`client.Grant`).
