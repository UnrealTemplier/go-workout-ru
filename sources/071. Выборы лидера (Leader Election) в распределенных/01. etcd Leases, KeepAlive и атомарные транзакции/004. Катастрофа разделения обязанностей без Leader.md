# Катастрофа разделения обязанностей без Leader Election (Split Execution Hazard)

## Условие

4. **Проблема без leader election**: Покажите проблему: 3 инстанса сервиса запускают cron job одновременно. Результат: duplicate processing, data corruption.

### Исходная формулировка

**Проблема без leader election**: Покажите проблему: 3 инстанса сервиса запускают cron job одновременно. Результат: duplicate processing, data corruption.

## Теория

При горизонтальном масштабировании stateless-сервисов (например, 3 пода в Kubernetes) разработчики часто забывают, что периодические фоновые задачи (Cron, генерация счетов, начисление кэшбэка, списание подписок) не должны выполняться параллельно.

### Сценарий аварии (Double Billing Disaster):
1. Три пода `Billing-Pod-A`, `Billing-Pod-B` и `Billing-Pod-C` просыпаются по системному таймеру в 00:00:00.
2. Каждый под выполняет: `SELECT * FROM subscriptions WHERE status = 'ACTIVE'`.
3. Все три пода одновременно находят пользователя с ID 42 и списывают ежемесячную абонентскую плату $15.
4. **Итог:** Пользователь получает 3 SMS-уведомления о списании $45 вместо $15, репутация сервиса уничтожена, база данных заполнена дубликатами.

### Решение через выбор лидера:
В каждый момент времени только **один активный лидер (Active Leader)** имеет право исполнять фоновые фоновые джобы. Остальные ноды работают в режиме ожидания (Hot Standby).

## Решение по шагам

1. Создадим структуру `BillingCron` без координации.
2. Запустим 3 параллельных горутины (3 пода), имитирующих срабатывание расписания.
3. Зафиксируем тройное списание средств одного пользователя.
4. Покажем, как внедрение флага лидера исключает катастрофу.

## Код решения

**`uncoordinated_cron.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
	"time"
)

type Account struct {
	mu      sync.Mutex
	Balance int
}

func main() {
	account := &Account{Balance: 100}
	var totalCharges int64

	fmt.Println("=== СЦЕНАРИЙ 1: Запуск фонового Cron БЕЗ Leader Election ===")

	var wg sync.WaitGroup
	// 3 независимых инстанса сервиса
	instances := []string{"Billing-Pod-A", "Billing-Pod-B", "Billing-Pod-C"}

	for _, name := range instances {
		wg.Add(1)
		go func(podName string) {
			defer wg.Done()
			// Каждый под считает, что он обязан списать абонплату
			account.mu.Lock()
			fee := 30
			account.Balance -= fee
			atomic.AddInt64(&totalCharges, 1)
			fmt.Printf("[%s] Списана абонплата $%d! Текущий баланс: $%d\n", podName, fee, account.Balance)
			account.mu.Unlock()
		}(name)
	}

	wg.Wait()
	fmt.Printf("\nИтог катастрофы: Баланс счета $%d (вместо $70). Списаний: %d!\n",
		account.Balance, atomic.LoadInt64(&totalCharges))

	fmt.Println("\n=== СЦЕНАРИЙ 2: Запуск фонового Cron С Leader Election ===")
	accountSafe := &Account{Balance: 100}
	leaderNode := "Billing-Pod-B" // Только Pod-B избран лидером

	for _, name := range instances {
		if name == leaderNode {
			accountSafe.Balance -= 30
			fmt.Printf("[%s (LEADER)] Единовременное списание выполнено! Баланс: $%d\n", name, accountSafe.Balance)
		} else {
			fmt.Printf("[%s (FOLLOWER)] Пропуск джобы: узел не является лидером.\n", name)
		}
	}
	fmt.Printf("Итог безопасного выполнения: Баланс счета ровно $%d.\n", accountSafe.Balance)
}
```

ℹ️ Наглядная демонстрация проблемы дублирования операций без координации лидера

## Под капотом

В распределенных системах данная проблема классифицируется как **Concurrency Hazard / Split-Brain Execution**.
Если две ноды считают себя лидерами одновременно (например, при сетевой задержке проверки кворума), они обе отправляют транзакции. В реляционных БД это лечится строчной блокировкой `FOR UPDATE`, но если операция включает внешний вызов (банк, SMS), защита на уровне БД бессильна без лидера.

## Подводные камни

1. **Использование локального таймера без координации:** `time.Ticker` внутри каждого пода гарантированно приведет к дублированию cron-задач.
2. **Отсутствие проверки роли лидера перед каждым шагом:** Если под стал лидером 5 минут назад, он не имеет права слепо выполнять джобу: за это время лидерство могло перейти другому узлу.
3. **Хранение состояния лидерства в глобальной статической переменной:** Роль лидера динамична и может быть утрачена в любую миллисекунду.

## На собеседовании

**Вопрос:** Как организовать запуск периодических задач в распределенном кластере Kubernetes: через Kubernetes CronJob или Leader Election внутри подов?
**Ответ:**
- **Kubernetes CronJob:** Подходит для редких (раз в день/час) тяжелых задач, порождая отдельный под на каждое выполнение. Минус: накладные расходы на старт контейнера (секунды), невозможность частых запусков (каждые 5 секунд).
- **Leader Election внутри постоянно работающих подов:** Идеален для непрерывных фоновых процессов, очередей и высокочастотных задач. Микросервисы держат прогретые пулы соединений к БД и кэшам, мгновенно подхватывая работу лидера при сбое.
