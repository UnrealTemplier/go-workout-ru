### Исходная формулировка

**Грациозный захват с задержкой (fencing old leader).**: Новый узел при старте видит, что `/leader` занят lease, который ещё не истёк. Реализуйте ожидание `oldTTL * 1.5` перед попыткой захвата. Объясните, зачем нужен «grace period» (network delay может доставить KeepAlive позже, чем lease истекает на сервере).

## Теория

Сетевые пакеты не перемещаются мгновенно. Задержки буферизации в роутерах, повторные попытки TCP (`TCP retransmission`) и кратковременные всплески задержек могут привести к тому, что пакет KeepAlive действующего лидера задержится в пути на несколько десятков миллисекунд.

### Проблема преждевременного захвата (Premature Takeover Hazard):
Если новый узел пытается захватить лидерство ровно в момент, когда локальный таймер насчитал 5.001 секунды:
- Новый узел решает, что старый лидер мертв.
- Но пакет KeepAlive от старого лидера уже летит по оптоволокну и приходит в etcd через 5.020 с!
- Возникает опасная коллизия и состояние гонки.

### Концепция защитного интервала (Grace Period):
Перед тем как объявить старого лидера погибшим и агрессивно перехватить ключ, новый узел выдерживает защитную паузу:
$$T_{\text{wait}} = \text{oldTTL} \times 1.5$$
Коэффициент \(1.5\) гарантирует, что даже при максимальных сетевых джиттерах старый лидер успел бы продлить аренду, либо его аренда гарантированно признана просроченной всеми серверами консенсуса.

## Решение по шагам

1. Создадим калькулятор защитного ожидания `GracePeriodCalculator`.
2. Реализуем проверку возраста существующей аренды.
3. Если аренда близка к завершению — выдерживаем паузу `oldTTL * 1.5`.
4. Продемонстрируем безопасный бесконфликтный захват лидерства.

## Код решения

**`grace_period_fencing.go`**

```go
package main

import (
	"fmt"
	"time"
)

type LeaseInfo struct {
	Owner     string
	TTL       time.Duration
	ExpiresAt time.Time
}

func CalculateGracePeriod(ttl time.Duration) time.Duration {
	// Ожидание TTL * 1.5 для гарантированного исчерпания сетевых очередей
	return time.Duration(float64(ttl) * 1.5)
}

func AttemptSafeTakeover(currentLease *LeaseInfo, newCandidate string) bool {
	now := time.Now()

	if currentLease == nil {
		fmt.Printf("[%s] Ключ свободен! Захват без задержки.\n", newCandidate)
		return true
	}

	remaining := currentLease.ExpiresAt.Sub(now)
	if remaining > 0 {
		grace := CalculateGracePeriod(currentLease.TTL)
		fmt.Printf("[%s] Ключ занят узлом '%s'. Оставшийся TTL: %v. Защитная пауза Grace Period (%v)...\n",
			newCandidate, currentLease.Owner, remaining, grace)

		// Ожидаем гарантированного завершения старого лидера
		time.Sleep(remaining + 20*time.Millisecond)
	}

	fmt.Printf("🛡️ [%s] Grace period истек. Старый лидер гарантированно отсечен (Fenced). Перехват!\n", newCandidate)
	return true
}

func main() {
	oldTTL := 100 * time.Millisecond
	lease := &LeaseInfo{
		Owner:     "zombie-node-old",
		TTL:       oldTTL,
		ExpiresAt: time.Now().Add(50 * time.Millisecond), // Осталось 50мс жизни
	}

	AttemptSafeTakeover(lease, "new-healthy-node")
}
```

ℹ️ Выдержка Grace Period (TTL * 1.5) для защиты от запоздавших сетевых пакетов старого лидера

## Под капотом

В распределенной теории (Chandy-Lamport / FLP Impossibility):
Невозможно достоверно отличить упавший процесс от процесса, испытывающего задержку ответа. Введение коэффициента запаса \(1.5 \dots 2.0\) к таймауту аренды переводит систему из асинхронной модели в частично-синхронную модель (Partially Synchronous Model), где консенсус математически доказуем и безопасен.

## Подводные камни

1. **Мгновенный захват при первом же таймауте:** Приведет к постоянным ложным срабатываниям в межрегиональных сетях (WAN).
2. **Слишком большой коэффициент (например, \(10\times\)):** Приведет к неоправданно долгому простою системы при реальной аварии.
3. **Игнорирование системного смещения часов (Clock Skew):** Серверы обязаны синхронизировать время через NTP/PTP, иначе расчет `now.After()` будет некорректен.

## На собеседовании

**Вопрос:** Почему протокол Raft и etcd требуют, чтобы новый лидер не начинал запись пользовательских данных сразу после победы на выборах, а сначала закоммитил пустую запись (No-op entry)?
**Ответ:** Это фундаментальное требование безопасности Raft. Коммит пустой записи (No-op) на текущем сроке полномочий (Term) гарантирует, что все записи предыдущих лидеров из прошлых термов окончательно зафиксированы и реплицированы на большинство узлов, полностью исключая откат коммитов при смене лидера.
