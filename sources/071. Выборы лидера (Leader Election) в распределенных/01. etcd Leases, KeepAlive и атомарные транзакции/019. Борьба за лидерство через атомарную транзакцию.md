# Борьба за лидерство через атомарную транзакцию etcd.Txn

## Условие

19. **[Борьба за лидерство]**: Запусти 3 инстанса твоего Go-приложения. Каждый пытается выполнить `etcd.Txn` (Transaction): `If(key /leader does not exist) Then(Put /leader with lease) Else(Get /leader)`. Убедись, что только один становится лидером, а остальные видят чужой ключ.

### Исходная формулировка

**[Борьба за лидерство]**: Запусти 3 инстанса твоего Go-приложения. Каждый пытается выполнить `etcd.Txn` (Transaction): `If(key /leader does not exist) Then(Put /leader with lease) Else(Get /leader)`. Убедись, что только один становится лидером, а остальные видят чужой ключ.

## Теория

Транзакция `etcd.Txn` (Compare-And-Swap / CAS) — фундаментальный строительный блок всей распределенной синхронизации.

### Структура транзакции:
- **`If (Предикаты)`:**
  `clientv3.Compare(clientv3.CreateRevision("/leader"), "=", 0)`
- **`Then (Ветвь успеха)`:**
  `clientv3.OpPut("/leader", "my-node-address", clientv3.WithLease(myLeaseID))`
- **`Else (Ветвь неудачи)`:**
  `clientv3.OpGet("/leader")`

### Гарантия математической строгости:
Когда три процесса параллельно отправляют эту транзакцию в etcd:
1. Raft-лидер etcd сериализует их в строгий последовательный порядок коммитов.
2. Первая транзакция видит `CreateRevision == 0` \(\implies\) выполняет `Then`, создавая ключ.
3. Вторая и третья транзакции видят `CreateRevision > 0` \(\implies\) условие ложно, они выполняют ветку `Else` и считывают адрес первой ноды.

## Решение по шагам

1. Реализуем точный эмулятор транзакции `etcd.Txn` с предикатом `CreateRevision == 0`.
2. Запустим 3 конкурирующих воркера через `sync.WaitGroup`.
3. Зафиксируем, что ровно один выполняет ветвь `Then` (победитель).
4. Проверим, что остальные два получают данные победителя через ветвь `Else`.

## Код решения

**`etcd_txn_battle.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type TxnResponse struct {
	Succeeded bool
	LeaderVal string
}

type EtcdEngine struct {
	mu             sync.Mutex
	keyValue       string
	createRevision int64
}

func (e *EtcdEngine) ExecuteElectionTxn(candidateAddress string) TxnResponse {
	e.mu.Lock()
	defer e.mu.Unlock()

	// IF CreateRevision("/leader") == 0
	if e.createRevision == 0 {
		// THEN Put("/leader", candidateAddress)
		e.keyValue = candidateAddress
		e.createRevision = 100 // Назначаем ненулевую ревизию создания
		return TxnResponse{Succeeded: true, LeaderVal: candidateAddress}
	}

	// ELSE Get("/leader")
	return TxnResponse{Succeeded: false, LeaderVal: e.keyValue}
}

func main() {
	engine := &EtcdEngine{}
	candidates := []string{
		"node-alpha.dc1.prod:8080",
		"node-beta.dc1.prod:8080",
		"node-gamma.dc1.prod:8080",
	}

	var wg sync.WaitGroup
	results := make([]TxnResponse, len(candidates))

	// Запускаем 3 одновременных вызова транзакции
	for i, addr := range candidates {
		wg.Add(1)
		go func(idx int, candidate string) {
			defer wg.Done()
			results[idx] = engine.ExecuteElectionTxn(candidate)
		}(i, addr)
	}

	wg.Wait()

	fmt.Println("Результаты параллельной битвы за лидерство в etcd.Txn:")
	var winners int
	for i, res := range results {
		if res.Succeeded {
			winners++
			fmt.Printf("  🏆 Кандидат #%d (%s): ПОБЕДА! Ветка THEN выполнена. Я лидер!\n",
				i+1, candidates[i])
		} else {
			fmt.Printf("  ❌ Кандидат #%d (%s): ОТКАЗ. Ветка ELSE. Действующий лидер: %s\n",
				i+1, candidates[i], res.LeaderVal)
		}
	}

	fmt.Printf("\nИтого победителей: %d (должен быть строго 1)\n", winners)
}
```

ℹ️ Борьба за лидерство через etcd.Txn: строго один победитель ветви THEN

## Под капотом

В etcd транзакции не используют классические двухфазные блокировки (2PL), как в PostgreSQL.
Они построены на **Multi-Version Concurrency Control (MVCC)** и предикатах ревизий. Если предикат истинен на текущей ревизии базы, набор операций `Then` коммитится в bbolt за один атомарный шаг с инкрементом глобальной ревизии хранилища.

## Подводные камни

1. **Забытая опция `WithLease` в `OpPut`:** Если победившая транзакция не привяжет ключ к аренде, при падении победителя ключ останется в базе навсегда.
2. **Разные ключи у кандидатов:** Опечатка в префиксе ключа (`/leader` vs `/leaders`) приведет к выбору двух параллельных лидеров.
3. **Чтение без кворума:** Чтение лидерского ключа всегда должно быть строго линеаризуемым (`WithSerializable(false)`).

## На собеседовании

**Вопрос:** Может ли в etcd возникнуть Deadlock при выполнении параллельных `Txn` между несколькими кандидатами?
**Ответ:** Нет, дедлоки в etcd невозможны. Все транзакции упорядочиваются монопольным лидером Raft в линейный лог. Каждая транзакция выполняется детерминированно от начала до конца за одно монопольное обращение к памяти стейт-машины без удержания распределенных взаимных замков.
