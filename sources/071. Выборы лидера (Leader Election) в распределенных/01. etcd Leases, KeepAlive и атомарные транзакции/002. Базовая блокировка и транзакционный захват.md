### Исходная формулировка

**Базовая блокировка в etcd.**: Реализуйте захват «блокировки» через `clientv3.Put` с `clientv3.WithLease(leaseID)` и `clientv3.WithPrevKV()`. Покажите, что второй процесс не может записать ключ, пока lease активен. Объясните, почему `TTL` + `KeepAlive` — сердце etcd-координации, а не просто `SET`/`GET`.

## Теория

Обычный вызов `Put` без условий подвержен состоянию гонки: второй узел может банально перезаписать значение лидера своим адресом, лишив первый узел контроля.

### Почему обычный Redis `SET key val` недостаточен:
В простейших базах без консенсуса команда `SET` не проверяет ревизию создания и не обеспечивает строгого порядка. В etcd любое изменение имеет глобальный монотонный номер ревизии (`revision`).

### Атомарная транзакция etcd (`Txn`):
Захват лидерства оформляется через проверку ревизии создания (`CreateRevision`):
```go
cli.Txn(ctx).
    If(clientv3.Compare(clientv3.CreateRevision(key), "=", 0)).
    Then(clientv3.OpPut(key, nodeID, clientv3.WithLease(leaseID))).
    Else(clientv3.OpGet(key))
```
- **`CreateRevision(key) == 0`:** Ключ физически не существует.
- **`Then`:** Ключ атомарно создается с привязкой к аренде. Узел становится лидером.
- **`Else`:** Ключ уже занят другим узлом. Узел получает данные текущего лидера и встает в режим ожидания (Watch).

## Решение по шагам

1. Создадим транзакционный интерфейс `TxnExecutor` для атомарных операций сравнения и вставки.
2. Проверим условие `CreateRevision == 0`.
3. Убедимся, что первый узел успешно захватывает лидерский ключ.
4. Продемонстрируем, что второй узел при попытке вставки получает отказ и читает адрес первого узла.

## Код решения

**`etcd_atomic_lock.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
)

type TxnResult struct {
	Succeeded bool
	Leader    string
}

type EtcdTxnEmulator struct {
	mu       sync.Mutex
	leaderKV map[string]string
}

func NewEtcdTxnEmulator() *EtcdTxnEmulator {
	return &EtcdTxnEmulator{leaderKV: make(map[string]string)}
}

// TryAcquireLeader выполняет Txn: IF CreateRevision == 0 THEN Put ELSE Get
func (e *EtcdTxnEmulator) TryAcquireLeader(key, candidateID string) TxnResult {
	e.mu.Lock()
	defer e.mu.Unlock()

	currentLeader, exists := e.leaderKV[key]
	if !exists {
		// Условие выполнено: ключа нет, создаем и захватываем лидерство
		e.leaderKV[key] = candidateID
		return TxnResult{Succeeded: true, Leader: candidateID}
	}

	// Условие ложно: ключ уже занят действующим лидером
	return TxnResult{Succeeded: false, Leader: currentLeader}
}

func (e *EtcdTxnEmulator) ReleaseLeader(key, candidateID string) bool {
	e.mu.Lock()
	defer e.mu.Unlock()

	if e.leaderKV[key] == candidateID {
		delete(e.leaderKV, key)
		return true
	}
	return false
}

func main() {
	etcd := NewEtcdTxnEmulator()
	leaderKey := "/elections/scheduler/leader"

	// Узел 1 пытается стать лидером
	res1 := etcd.TryAcquireLeader(leaderKey, "srv-alpha:8080")
	fmt.Printf("[Node-1] Попытка захвата: Успех=%v, Текущий лидер: %s\n", res1.Succeeded, res1.Leader)

	// Узел 2 пытается захватить тот же ключ одновременно
	res2 := etcd.TryAcquireLeader(leaderKey, "srv-beta:8080")
	fmt.Printf("[Node-2] Попытка захвата: Успех=%v, Текущий лидер: %s\n", res2.Succeeded, res2.Leader)

	// Узел 1 освобождает ключ при плановой остановке
	etcd.ReleaseLeader(leaderKey, "srv-alpha:8080")
	fmt.Println("[Node-1] Узел 1 снял с себя лидерские полномочия.")

	// Узел 2 повторяет попытку и становится лидером
	res3 := etcd.TryAcquireLeader(leaderKey, "srv-beta:8080")
	fmt.Printf("[Node-2] Повторная попытка: Успех=%v, Новый лидер: %s\n", res3.Succeeded, res3.Leader)
}
```

ℹ️ Транзакционный захват лидерства через сравнение CreateRevision: атомарный выбор без гонок

## Под капотом

В etcd транзакция `Txn` коммитится как единая запись в Raft log.
Пока транзакция выполняется на стейт-машине etcd, никакой другой запрос не может вклиниться между проверкой `CreateRevision(key) == 0` и записью `Put`. Это обеспечивает сериализуемую изоляцию (Strict Serializability) выбора лидера.

## Подводные камни

1. **Запись без проверки `CreateRevision`:** Если использовать обычный `Put`, узел-дублер затрет адрес действующего лидера.
2. **Отсутствие привязки к Lease:** Если транзакция запишет ключ без аренды (`WithLease`), при падении узла ключ останется в etcd навечно, и кластер никогда не сможет выбрать нового лидера.
3. **Игнорирование контекста:** Запросы к etcd обязаны иметь `context.WithTimeout` во избежание зависания горутин при сетевой изоляции.

## На собеседовании

**Вопрос:** Почему в etcd используется `CreateRevision == 0`, а не проверка `Value == ""` для определения отсутствия ключа?
**Ответ:** Ключ в etcd может существовать, но содержать пустое значение (`Value: ""`). Свойство `CreateRevision` равно 0 тогда и только тогда, когда ключ физически отсутствует в дереве B-Tree / bbolt хранилища. Это самый надежный предикат отсутствия записи в распределенном консенсусе.
