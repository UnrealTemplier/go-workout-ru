### Исходная формулировка

Используйте `clientv3.Concurrency.Election` (или ручной `Campaign` через `Txn` с `CreateRevision` compare). Покажите, что только один получает `leaderCh`, остальные ждут. Объясните роль `CreateRevision` в определении порядка.

## Теория

Официальный пакет `go.etcd.io/etcd/client/v3/concurrency` предоставляет высокоуровневую и математически выверенную абстракцию для выборов лидера: `concurrency.Election`.

### Архитектура `concurrency.Election`:
1. **Сессия (`concurrency.Session`):**
   Оборачивает Lease и автоматически продлевает его пульсом в фоне.
2. **Метод `Campaign(ctx, val)`:**
   Нода выдвигает свою кандидатуру на лидерство. Под капотом etcd создает ключ вида `/leader/{lease_id}` с использованием механизма монотонных ревизий (FIFO Queue Lock).
3. **Роль `CreateRevision`:**
   Победителем выборов объявляется узел, чей ключ имеет **наименьшую ревизию создания (`CreateRevision`)** среди всех текущих кандидатов!
4. **Ожидание остальных кандидатов:**
   Узлы, чья `CreateRevision` больше минимальной, не опрашивают etcd в цикле (без busy waiting). Они подписываются через `Watch` на удаление ключа **непосредственно предшествующего кандидата**, формируя идеальную распределенную очередь ожидания без эффекта Thundering Herd.

## Решение по шагам

1. Создадим эмулятор `ConcurrencyElectionQueue`.
2. Смоделируем 3 параллельных кандидата, вызывающих `Campaign`.
3. Назначим победителем узел с минимальной ревизией создания `CreateRevision`.
4. Покажем передачу лидерства второму кандидату при уходе первого.

## Код решения

**`etcd_concurrency_election.go`**

```go
package main

import (
	"context"
	"fmt"
	"sort"
	"sync"
	"time"
)

type Candidate struct {
	ID             string
	CreateRevision int64
	LeaderCh       chan struct{}
}

type ConcurrencyElection struct {
	mu           sync.Mutex
	prefix       string
	revisionSeq  int64
	candidates   map[string]*Candidate
	activeLeader string
}

func NewConcurrencyElection(prefix string) *ConcurrencyElection {
	return &ConcurrencyElection{
		prefix:     prefix,
		candidates: make(map[string]*Candidate),
	}
}

func (e *ConcurrencyElection) Campaign(ctx context.Context, nodeID string) <-chan struct{} {
	e.mu.Lock()
	defer e.mu.Unlock()

	e.revisionSeq++
	cand := &Candidate{
		ID:             nodeID,
		CreateRevision: e.revisionSeq,
		LeaderCh:       make(chan struct{}, 1),
	}
	e.candidates[nodeID] = cand

	fmt.Printf("[etcd-concurrency] Нода %s встала в очередь выборов (CreateRevision: %d)\n",
		nodeID, cand.CreateRevision)

	e.electLocked()
	return cand.LeaderCh
}

func (e *ConcurrencyElection) Resign(nodeID string) {
	e.mu.Lock()
	defer e.mu.Unlock()

	if _, exists := e.candidates[nodeID]; exists {
		delete(e.candidates, nodeID)
		fmt.Printf("[etcd-concurrency] Лидер %s отказался от полномочий (Resign)\n", nodeID)
		e.electLocked()
	}
}

func (e *ConcurrencyElection) electLocked() {
	if len(e.candidates) == 0 {
		e.activeLeader = ""
		return
	}

	// Сортируем кандидатов по возрастанию CreateRevision
	var list []*Candidate
	for _, c := range e.candidates {
		list = append(list, c)
	}
	sort.Slice(list, func(i, j int) bool {
		return list[i].CreateRevision < list[j].CreateRevision
	})

	winner := list[0]
	if e.activeLeader != winner.ID {
		e.activeLeader = winner.ID
		// Оповещаем победителя
		select {
		case winner.LeaderCh <- struct{}{}:
		default:
		}
		fmt.Printf(">>> ИЗБРАН НОВЫЙ ЛИДЕР: %s (CreateRevision: %d) <<<\n",
			winner.ID, winner.CreateRevision)
	}
}

func main() {
	election := NewConcurrencyElection("/services/scheduler/leader")
	ctx := context.Background()

	// Запускаем 3 ноды на выборы
	ch1 := election.Campaign(ctx, "worker-node-1")
	ch2 := election.Campaign(ctx, "worker-node-2")
	ch3 := election.Campaign(ctx, "worker-node-3")

	// Проверяем, кто стал лидером
	select {
	case <-ch1:
		fmt.Println("[worker-node-1] Я получил сигнал лидерства! Запускаю задачи.")
	default:
		fmt.Println("[worker-node-1] В ожидании...")
	}

	select {
	case <-ch2:
		fmt.Println("[worker-node-2] Я получил сигнал лидерства!")
	default:
		fmt.Println("[worker-node-2] Я в режиме ожидания (Standby).")
	}

	// Имитируем падение первого лидера
	time.Sleep(50 * time.Millisecond)
	election.Resign("worker-node-1")

	// Теперь Node-2 мгновенно становится лидером!
	select {
	case <-ch2:
		fmt.Println("[worker-node-2] Перехватил лидерство после падения Node-1!")
	case <-time.After(50 * time.Millisecond):
		fmt.Println("Таймаут ожидания")
	}
}
```

## Под капотом

В реальном `go.etcd.io/etcd/client/v3/concurrency`:
Метод `Campaign` выполняет транзакцию создания ключа `${prefix}/${lease_id}`. После этого клиент делает `Get(prefix, WithPrefix(), WithSort(SortByCreateRevision))` и находит свой порядковый номер в очереди. Если узел не первый, он запускает `clientv3.Watch(ctx, previous_candidate_key)`, засыпая до момента гибели предшественника. Это дает алгоритмическую сложность \(O(1)\) сообщений на смену лидера.

## Подводные камни

1. **Использование одного `concurrency.Session` на все сервисы:** Если сессия отменится из-за ошибки сети в одном компоненте, все выборы лидера приложения синхронно упадут.
2. **Неосвобожденный контекст `Campaign`:** Если отменить контекст до завершения кампании, узел может зависнуть в неопределенном состоянии.
3. **Отсутствие обработки канала `session.Done()`:** Лидер обязан следить за `<-session.Done()`. Если соединение с etcd потеряно, узел перестает быть лидером мгновенно.

## На собеседовании

**Вопрос:** Почему алгоритм очереди кандидатов в `concurrency.Election` etcd превосходит обычную конкуренцию за один общий ключ?
**Ответ:** 
При борьбе 100 узлов за один ключ `/leader` в момент падения лидера все 100 узлов одновременно бросаются делать `Put` (эффект **Thundering Herd**), вызывая пиковую нагрузку на CPU etcd.
В очереди по `CreateRevision` каждый кандидат наблюдает только за *одним* ключом своего прямого предшественника. При сбое лидера просыпается строго **один следующий узел**, не создавая никакой паразитной нагрузки на кластер.
