# Автоматическое переключение при отказе лидера (Failover Simulation)

## Условие

14. **Leader failover**: Убейте leader процесс. Через TTL (15s) session expires, lock освобождается, другой инстанс захватывает lock.

### Исходная формулировка

**Leader failover**: Убейте leader процесс. Через TTL (15s) session expires, lock освобождается, другой инстанс захватывает lock.

## Теория

Сценарий автоматического восстановления (Failover) — главная проверка жизнеспособности распределенного консенсуса.

### Фазы переключения при аварии (Failover Timeline):
1. **\(T_0\) (Авария):** Лидер внезапно погибает (`kill -9`, отключение питания ноды).
2. **\(T_0 \dots T_0 + \text{TTL}\) (Окно обнаружения сбоя):**
   Сервер координации (Consul/etcd) больше не получает подтверждений пульса. Новые запросы ждут. Статус замка все еще формально занят.
3. **\(T_0 + \text{TTL}\) (Экспирация сессии):**
   Таймер истекает. Сервер консенсуса аннулирует сессию/аренду и освобождает ключ.
4. **\(T_0 + \text{TTL} + \Delta t\) (Захват новым лидером):**
   Ведомый узел (Standby), ожидающий освобождения через Watch или таймер, немедленно делает `Acquire()` и принимает на себя обязанности активного лидера.

## Решение по шагам

1. Создадим симулятор двух узлов `NodePrimary` и `NodeStandby`.
2. Назначим `NodePrimary` действующим лидером.
3. Симулируем внезапную гибель `NodePrimary`.
4. Покажем автоматическое истечение TTL и мгновенный перехват власти узлом `NodeStandby`.

## Код решения

**`leader_failover.go`**

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

type FailoverCluster struct {
	mu           sync.Mutex
	activeLeader string
	leaseExpire  time.Time
}

func (c *FailoverCluster) Heartbeat(nodeID string, ttl time.Duration) {
	c.mu.Lock()
	defer c.mu.Unlock()
	if c.activeLeader == nodeID {
		c.leaseExpire = time.Now().Add(ttl)
	}
}

func (c *FailoverCluster) TryClaimLeader(nodeID string, ttl time.Duration) bool {
	c.mu.Lock()
	defer c.mu.Unlock()

	now := time.Now()
	// Если лидера нет или его аренда просрочена
	if c.activeLeader == "" || now.After(c.leaseExpire) {
		old := c.activeLeader
		c.activeLeader = nodeID
		c.leaseExpire = now.Add(ttl)
		if old != "" && old != nodeID {
			fmt.Printf("⚡ [Cluster] Аренда лидера %s истекла! Лидерство перехвачено узлом %s!\n", old, nodeID)
		} else {
			fmt.Printf("👑 [Cluster] Узел %s успешно захватил лидерство!\n", nodeID)
		}
		return true
	}

	return false
}

func main() {
	cluster := &FailoverCluster{}
	ttl := 100 * time.Millisecond

	// 1. Первичный узел захватывает лидерство
	cluster.TryClaimLeader("Primary-Worker", ttl)

	// Имитируем отправку KeepAlive в течение 150 мс
	cluster.Heartbeat("Primary-Worker", ttl)
	time.Sleep(50 * time.Millisecond)
	cluster.Heartbeat("Primary-Worker", ttl)

	// 2. Внезапная смерть первичного узла (SIGKILL)
	fmt.Println("\n💥 [Авария] Primary-Worker аварийно завершился (kill -9)!")

	// 3. Standby узел периодически пытается перехватить замок
	for i := 1; i <= 5; i++ {
		time.Sleep(40 * time.Millisecond)
		acquired := cluster.TryClaimLeader("Standby-Worker", ttl)
		if acquired {
			fmt.Println("🚀 [Standby-Worker] Я стал новым лидером системы и запустил обработку очереди!")
			break
		}
		fmt.Printf("[Standby-Worker] Попытка %d: Замок еще удерживается старой арендой...\n", i)
	}
}
```

ℹ️ Симуляция Failover: автоматический перехват лидерства узлом Standby при отказе Primary

## Под капотом

Почему окно failover не может быть нулевым:
Время переключения при отказе фундаментально ограничено временем обнаружения сбоя:
$$T_{\text{failover}} = \text{TTL} + T_{\text{election}}$$
Если сделать TTL слишком маленьким (например, 50 мс), малейший всплеск задержки сети или сборки мусора (GC pause) приведет к ложному переключению (False Failover) и постоянным миганиям лидерства (Flapping).

## Подводные камни

1. **Слишком агрессивный перехват:** Попытка занять ключ до истечения TTL приведет к отказу.
2. **Неготовность Standby узла к моментальному старту:** Если Standby узел не прогрел соединения к БД или кэшам, при переключении возникнет спайк задержки (Cold Start Spike).
3. **Отсутствие алертинга на факт переключения:** Смена лидера всегда должна регистрироваться метрикой `leader_election_failovers_total` в Prometheus.

## На собеседовании

**Вопрос:** Как минимизировать время простоя (Downtime) при плановой перезагрузке лидера (например, Rolling Update подов)?
**Ответ:** При плановом завершении (Graceful Shutdown) лидер не должен дожидаться истечения TTL сессии. По сигналу SIGTERM он обязан вызвать **`Election.Resign()`** или **`Session.Destroy()`**. Это мгновенно освобождает ключ за 1–2 миллисекунды, позволяя Standby-узлу перехватить работу с практически нулевым даунтаймом.
