# Архитектура кластера Consul из 3 серверов и кворум Raft

## Условие

9. **Consul setup**: Поднимите Consul cluster из 3 серверов через Docker Compose. Изучите Consul UI на порту 8500.

### Исходная формулировка

**Consul setup**: Поднимите Consul cluster из 3 серверов через Docker Compose. Изучите Consul UI на порту 8500.

## Теория

Для обеспечения высокой доступности (High Availability) Consul требует нечетного числа серверов (минимум 3, в крупных дата-центрах — 5).

### Расчет кворума Raft:
Формула необходимого большинства:
$$Q = \left\lfloor \frac{N}{2} \right\rfloor + 1$$
- Кластер из 3 серверов выдерживает падение **1 сервера** (\(Q = 2\)).
- Кластер из 5 серверов выдерживает падение **2 серверов** (\(Q = 3\)).
- Кластер из 2 серверов требует кворум 2 и **не выдерживает падения ни одного узла** (при сбое 1 сервера \(1 < 2\), кластер полностью блокирует запись)!

### Сетевые порты Consul:
- `8500`: HTTP API и Web UI.
- `8600`: Встроенный DNS-сервер.
- `8300`: RPC серверного консенсуса Raft.
- `8301`: Serf LAN Gossip (связь между агентами в одном дата-центре).
- `8302`: Serf WAN Gossip (связь между дата-центрами).

## Решение по шагам

1. Опишем конфигурацию `docker-compose.yml` для 3 серверов Consul (`consul-server-1`, `consul-server-2`, `consul-server-3`).
2. Настроим параметры `bootstrap_expect: 3` и автоприсоединение через `retry_join`.
3. Создадим тестовую утилиту проверки кворума и статуса лидеров на Go.
4. Продемонстрируем сохранение доступности при отказе одной ноды.

## Код решения

**`consul_cluster_topology.go`**

```go
package main

import (
	"fmt"
)

type ConsulNodeRole string

const (
	RoleServer ConsulNodeRole = "SERVER"
	RoleClient ConsulNodeRole = "CLIENT"
)

type ClusterNode struct {
	Name    string
	Role    ConsulNodeRole
	IP      string
	IsAlive bool
}

type RaftQuorumCalculator struct {
	TotalServers int
}

func (r RaftQuorumCalculator) QuorumSize() int {
	return (r.TotalServers / 2) + 1
}

func (r RaftQuorumCalculator) MaxFaultTolerance() int {
	return (r.TotalServers - 1) / 2
}

func (r RaftQuorumCalculator) CanFormQuorum(activeServers int) bool {
	return activeServers >= r.QuorumSize()
}

func main() {
	// Демонстрация топологии кластера Consul
	calc3 := RaftQuorumCalculator{TotalServers: 3}
	calc5 := RaftQuorumCalculator{TotalServers: 5}

	fmt.Println("Математика консенсуса Raft в кластерах Consul/etcd:")
	fmt.Printf("• Кластер из 3 серверов: Кворум = %d, Допустимо сбоев = %d\n",
		calc3.QuorumSize(), calc3.MaxFaultTolerance())
	fmt.Printf("• Кластер из 5 серверов: Кворум = %d, Допустимо сбоев = %d\n\n",
		calc5.QuorumSize(), calc5.MaxFaultTolerance())

	nodes := []*ClusterNode{
		{Name: "consul-server-1", Role: RoleServer, IP: "172.20.0.2", IsAlive: true},
		{Name: "consul-server-2", Role: RoleServer, IP: "172.20.0.3", IsAlive: true},
		{Name: "consul-server-3", Role: RoleServer, IP: "172.20.0.4", IsAlive: true},
	}

	fmt.Println("Состояние серверов кластера:")
	for _, n := range nodes {
		fmt.Printf("  Нода %s (%s): статус alive=%v\n", n.Name, n.IP, n.IsAlive)
	}

	// Имитируем падение одного сервера
	nodes[2].IsAlive = false
	fmt.Printf("\n[Авария] Сервер %s потерпел крах!\n", nodes[2].Name)

	active := 0
	for _, n := range nodes {
		if n.IsAlive {
			active++
		}
	}

	fmt.Printf("Активных серверов: %d из 3. Кворум достижим? %v (Кластер полностью работоспособен!)\n",
		active, calc3.CanFormQuorum(active))
}
```

ℹ️ Математика кворума Raft и топология отказоустойчивого кластера из 3 нод

## Под капотом

Фрагмент конфигурации Docker Compose для 3 нод Consul:
```yaml
services:
  consul-server-1:
    image: hashicorp/consul:latest
    command: "agent -server -bootstrap-expect=3 -node=s1 -client=0.0.0.0 -ui"
  consul-server-2:
    image: hashicorp/consul:latest
    command: "agent -server -retry-join=consul-server-1 -node=s2"
  consul-server-3:
    image: hashicorp/consul:latest
    command: "agent -server -retry-join=consul-server-1 -node=s3"
```
При запуске серверы через Gossip обнаруживают друг друга и формируют Raft-группу с общим кворумом.

## Подводные камни

1. **Четное количество серверов (например, 4 или 2):** Кластер из 4 серверов требует кворум 3. Он выдерживает падение только 1 ноды — ровно столько же, сколько кластер из 3 серверов, но потребляет больше ресурсов и повышает вероятность split-brain.
2. **Размещение всех серверов в одной стойке/AZ:** При падении стойки или зоны доступности падает весь кластер. Серверы обязаны быть распределены по разным Availability Zones.
3. **Использование медленных дисков (HDD) для Raft WAL:** Протокол Raft требует синхронного fsync журнала на диск. Медленный диск вызовет таймауты сердечных сокращений Raft и постоянные перевыборы лидера.

## На собеседовании

**Вопрос:** Почему в кластерах etcd и Consul не рекомендуется использовать более 7 серверов консенсуса?
**Ответ:** Протокол Raft требует подтверждения записи от большинства узлов. С ростом числа серверов (например, 9 или 11) накладные расходы на сетевой обмен и репликацию логов по схеме \(O(N)\) резко увеличивают задержку (Write Latency). Для масштабирования чтения используют Consul Client Agents или etcd Read Replicas (Learners).
