### Исходная формулировка

**Consul Session + KV Lock.**: Создайте Consul Session с `TTL=10s` и `Behavior=release`. Захватите KV-пару через `session` в `Acquire`. Покажите, что при `DestroySession` или истечении TTL блокировка снимается автоматически. Сравните с etcd: Consul использует health checks + session, etcd — lease.

## Теория

Consul и etcd решают одну фундаментальную задачу распределенного консенсуса, но используют принципиально разные архитектурные абстракции.

### Сравнительная таблица механизмов:

| Критерий | HashiCorp Consul | CoreOS etcd v3 |
| :--- | :--- | :--- |
| **Единица времени жизни** | **Session** (привязана к ноде и health check) | **Lease** (64-битный токен времени) |
| **Связка с проверкой здоровья** | **Встроенная:** сессия инвалидируется при падении Health Check агента | **Прикладная:** клиент сам обязан слать `KeepAlive` или отменять Lease |
| **Политика истечения** | `release` (сброс замка) или `delete` (удаление ключа) | Всегда каскадное удаление всех привязанных ключей |
| **Протокол консенсуса** | HashiCorp Raft | etcd Raft (используется в Kubernetes) |
| **Модель наблюдения** | Blocking Queries (HTTP Long Polling / WaitIndex) | gRPC Streams (двунаправленный HTTP/2 Watch) |
| **Fencing Token** | Монотонный `LockIndex` в метаданных ключа | Глобальная `ModRevision` / `CreateRevision` |

## Решение по шагам

1. Создадим модуль сравнения жизненного цикла замка.
2. Продемонстрируем автоматическое освобождение (`release`) в Consul при уничтожении сессии (`DestroySession`).
3. Сравним со снятием блокировки по истечении `Lease.Revoke()` в etcd.
4. Выделим сценарии применения для каждого инструмента.

## Код решения

**`consul_vs_etcd_lock.go`**

```go
package main

import (
	"fmt"
	"sync"
)

type CoordinationSystem string

const (
	SystemConsul CoordinationSystem = "CONSUL_SESSION_BASED"
	SystemEtcd   CoordinationSystem = "ETCD_LEASE_BASED"
)

type UnifiedLockManager struct {
	mu           sync.Mutex
	consulLock   map[string]string // key -> sessionID
	etcdKeysWithLease map[string]int64 // key -> leaseID
}

func NewUnifiedLockManager() *UnifiedLockManager {
	return &UnifiedLockManager{
		consulLock:        make(map[string]string),
		etcdKeysWithLease: make(map[string]int64),
	}
}

// Consul: DestroySession освобождает ключ (Behavior: release)
func (m *UnifiedLockManager) ConsulDestroySession(sessionID string) {
	m.mu.Lock()
	defer m.mu.Unlock()
	for k, v := range m.consulLock {
		if v == sessionID {
			m.consulLock[k] = "" // Сброс сессии, ключ сохраняется
			fmt.Printf("[Consul] Сессия %s уничтожена. Ключ '%s' освобожден (LockIndex сброшен)!\n", sessionID, k)
		}
	}
}

// etcd: RevokeLease физически удаляет ключ
func (m *UnifiedLockManager) EtcdRevokeLease(leaseID int64) {
	m.mu.Lock()
	defer m.mu.Unlock()
	for k, v := range m.etcdKeysWithLease {
		if v == leaseID {
			delete(m.etcdKeysWithLease, k)
			fmt.Printf("[etcd] Аренда #%d отозвана. Ключ '%s' полностью удален из KV!\n", leaseID, k)
		}
	}
}

func main() {
	mgr := NewUnifiedLockManager()

	// 1. Захват в Consul
	mgr.consulLock["service/leader"] = "sess_node1"
	fmt.Println("1. [Consul] Замок удерживается сессией sess_node1")
	mgr.ConsulDestroySession("sess_node1")
	fmt.Printf("   Состояние ключа в Consul: существует, но свободен (Session='%s')\n\n",
		mgr.consulLock["service/leader"])

	// 2. Захват в etcd
	mgr.etcdKeysWithLease["service/leader"] = 999
	fmt.Println("2. [etcd] Ключ привязан к Lease #999")
	mgr.EtcdRevokeLease(999)
	_, exists := mgr.etcdKeysWithLease["service/leader"]
	fmt.Printf("   Существует ли ключ в etcd: %v (удален каскадно)\n", exists)
}
```

ℹ️ Сравнение моделей: сброс сессии (Consul release) vs каскадное удаление ключа (etcd lease)

## Под капотом

В Consul привязка к Health Checks позволяет обнаруживать сбои без участия самого приложения:
Если процесс завис или упал веб-сервер, локальный Consul Agent хоста обнаруживает это по локальному TCP/HTTP сокету и отправляет RPC на аннулирование сессии на серверы Consul.
В etcd клиентское приложение само является актором: оно обязано поддерживать gRPC-стрим KeepAlive непосредственно с кластером etcd.

## Подводные камни

1. **Ожидание удаления ключа в Consul при политике release:** Если клиент ожидает исчезновения ключа, а стоит `Behavior: release`, он зависнет в ожидании.
2. **Перегрузка etcd созданием миллионов Lease:** Каждая аренда создает накладные расходы на таймеры в etcd. Привязывайте тысячи ключей к одному LeaseID.
3. **Разные ожидания от консистентности:** etcd по умолчанию гарантирует линеаризуемость чтения (`Linearizable Read`), Consul по умолчанию использует `stale: false` (согласованное чтение через Raft-лидера).

## На собеседовании

**Вопрос:** Почему для координации компонентов Kubernetes (API Server, Controller Manager, Scheduler) был выбран etcd, а не Consul?
**Ответ:** 
1. **Чистая специализированная модель:** etcd спроектирован строго как распределенное иерархическое key-value хранилище с нативной поддержкой ревизий и потоковых событий Watch.
2. **Минимализм:** etcd не содержит встроенного DNS, Service Mesh, Connect proxies и Consul Web UI, представляя собой сверхнадежное минималистичное ядро с открытым API, идеально интегрирующееся с контроллерами Kubernetes.
