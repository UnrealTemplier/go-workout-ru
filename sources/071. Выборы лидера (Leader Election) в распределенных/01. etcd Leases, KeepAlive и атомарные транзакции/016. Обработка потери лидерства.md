# Обработка потери лидерства: немедленный сброс полномочий (Atomic Resignation)

## Условие

16. **Обработка потери лидерства.**: В leader-процессе запустите горутину, которая слушает `KeepAlive` ответы (или `Session.RenewPeriodic`). При ошибке (lease expired) — немедленно остановить обработку запросов (`atomic.StoreUint32(&isLeader, 0)`). Объясните, почему продолжение работы после lease expiry — это баг.

### Исходная формулировка

**Обработка потери лидерства.**: В leader-процессе запустите горутину, которая слушает `KeepAlive` ответы (или `Session.RenewPeriodic`). При ошибке (lease expired) — немедленно остановить обработку запросов (`atomic.StoreUint32(&isLeader, 0)`). Объясните, почему продолжение работы после lease expiration — это split-brain.

## Теория

Опаснейшая иллюзия распределенного разработчика: «Раз я стал лидером, я лидер до тех пор, пока явно не решу уйти».

### Почему работа после потери Lease — это критический баг:
1. Сеть между лидером и etcd моргнула на 6 секунд при TTL 5 секунд.
2. etcd посчитал лидера мертвым, удалил ключ и передал лидерство Узлу B.
3. Узел B стал лидером и начал выполнять операции (например, модифицировать состояние партиции).
4. Узел A **все еще считает себя лидером**, потому что не проверил статус ошибки `KeepAlive`!
5. **Катастрофа Split-Brain:** В системе работают **два параллельных лидера**, перезаписывая данные друг друга и разрушая инварианты консистентности.

### Правило немедленной остановки (Fail-Fast Shutdown):
При первой же ошибке продления аренды лидер обязан:
1. Атомарно выставить `isLeader = 0`.
2. Вызвать функцию отмены контекста `cancel()`, немедленно прервав все горутины записи.
3. Отклонять все входящие запросы клиентов ошибкой `503 Service Unavailable / 409 Conflict`.

## Решение по шагам

1. Создадим рабочий сервис `LeaderWorkerTask` с атомарным флагом лидерства.
2. Свяжем выполнение полезной работы с проверкой `atomic.LoadUint32(&isLeader) == 1`.
3. Смоделируем сбой пульса аренды.
4. Продемонстрируем немедленное прерывание текущей фоновой задачи.

## Код решения

**`atomic_resignation.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync/atomic"
	"time"
)

type CriticalLeaderService struct {
	isLeader uint32 // 1 = лидер, 0 = ведомый
	cancelFn context.CancelFunc
}

func (s *CriticalLeaderService) StartWork(ctx context.Context) {
	workCtx, cancel := context.WithCancel(ctx)
	s.cancelFn = cancel
	atomic.StoreUint32(&s.isLeader, 1)

	go func() {
		for {
			select {
			case <-workCtx.Done():
				fmt.Println("🛑 [Worker] Выполнение бизнес-задач немедленно остановлено!")
				return
			default:
				// Двойная проверка атомарного флага
				if atomic.LoadUint32(&s.isLeader) == 0 {
					fmt.Println("🛑 [Worker] Обнаружена потеря лидерства! Прекращаем работу.")
					cancel()
					return
				}

				fmt.Println("⚙️ [Leader-Worker] Обработка критической финансовой транзакции...")
				time.Sleep(40 * time.Millisecond)
			}
		}
	}()
}

func (s *CriticalLeaderService) OnLeaseExpired() {
	fmt.Println("\n🚨 [ALARM] Кластер etcd сообщил об истечении аренды!")
	// 1. Атомарно сбрасываем флаг
	atomic.StoreUint32(&s.isLeader, 0)
	// 2. Отменяем контекст фоновых воркеров
	if s.cancelFn != nil {
		s.cancelFn()
	}
}

func main() {
	svc := &CriticalLeaderService{}
	ctx := context.Background()

	svc.StartWork(ctx)

	// Лидер работает 100 мс
	time.Sleep(100 * time.Millisecond)

	// Сеть упала, аренда протухла
	svc.OnLeaseExpired()

	// Даем время на остановку
	time.Sleep(50 * time.Millisecond)

	fmt.Printf("Финальное состояние флага: isLeader = %d\n", atomic.LoadUint32(&svc.isLeader))
}
```

ℹ️ Fail-Fast семантика: атомарный сброс лидерства и отмена context при потере аренды

## Под капотом

В ядре Kubernetes Controller Manager:
Каждый контроллер (DeploymentController, NodeLifecycleController) слушает канал `leaderelection.LeaderCallbacks.OnStoppedLeading`:
```go
OnStoppedLeading: func() {
    klog.Fatalf("leaderelection lost, exiting process to prevent split-brain")
}
```
Kubernetes выбирает самую радикальную и безопасную стратегию: при потере лидерства процесс контроллера вызывает `os.Exit(1)` или `log.Fatalf()`, немедленно убивая свой собственный под. Затем Kubelet поднимает чистый под с нуля, гарантируя отсутствие остаточных зависших горутин.

## Подводные камни

1. **Продолжение выполнения работы в фоновых горутинах после сброса флага:** Если горутины не проверяют `ctx.Done()`, они продолжат писать в базу данных, повреждая данные.
2. **Использование неатомарных булевых переменных (`var isLeader bool`):** Чтение и запись без мьютекса или `sync/atomic` вызывает гонку данных (`Data Race`) и UB компилятора.
3. **Попытка пересоздать сессию на ходу без остановки воркеров:** Сначала обязана произойти полная остановка старых процессов, и только потом — новая кампания.

## На собеседовании

**Вопрос:** Почему при потере лидерства в критических системах часто предпочитают вызвать `os.Exit(1)` (self-termination), а не пытаться переизбраться «на лету» внутри того же процесса?
**Ответ:** Потому что внутри сложного процесса могут быть запущены десятки сторонних библиотек, фоновых очередей и незавершенных транзакций в БД. Полная перезагрузка процесса (`os.Exit(1)`) гарантирует 100% очистку памяти рантайма Go, сброс всех TCP-пулов и освобождение файловых дескрипторов, предотвращая скрытые утечки состояния и гарантируя абсолютную чистоту следующего запуска.
