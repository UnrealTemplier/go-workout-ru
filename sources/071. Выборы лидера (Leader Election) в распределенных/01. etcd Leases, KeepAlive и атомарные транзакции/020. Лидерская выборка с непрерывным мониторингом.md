# Лидерская выборка с непрерывным мониторингом и автоматическим фейловером

## Условие

20. **Лидерская выборка с мониторингом и фейловером.**: Запустите несколько горутин (эмулирующих узлы). Каждая пытается стать лидером через сессию. Лидер периодически продлевает сессию. При остановке лидера другой узел должен захватить лидерство. Используйте `Session.Renew` или TTL-чек.

### Исходная формулировка

**Лидерская выборка с мониторингом и фейловером.**: Запустите несколько горутин (эмулирующих узлы). Каждая пытается стать лидером через сессию. Лидер периодически продлевает сессию. При остановке лидера другой узел должен захватить лидерство. Используйте `Session.Renew` или TTL-чек.

## Теория

Полноценный жизненный цикл узла в кластере высокой доступности состоит из бесконечного цикла состояний:
$$\text{Standby} \xrightarrow{\text{Acquire()}} \text{Leader} \xrightarrow{\text{Heartbeat/Renew}} \text{Leader} \xrightarrow{\text{Fail/Resign}} \text{Standby}$$

### Архитектура бесконечного цикла:
1. Нода запускается и пытается захватить лидерский замок.
2. Если замок занят: нода подписывается на событие освобождения или спит короткий интервал.
3. Если замок захвачен: нода запускает фоновую горутину продления (Heartbeat) и бизнес-воркеры.
4. При аварии лидера (сбой продления) замок освобождается сервером консенсуса, и ведомые ноды немедленно начинают новую фазу выборов.

## Решение по шагам

1. Создадим модель распределенного кластера с поддержкой сессий и аренды.
2. Реализуем бесконечный цикл жизненного цикла узла `RunLifecycle(ctx)`.
3. Запустим 3 конкурирующих узла.
4. Имитируем падение первого лидера и продемонстрируем, как второй узел автоматически перехватывает управление.

## Код решения

**`cluster_lifecycle.go`**

```go
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

type CentralLockStore struct {
	mu           sync.Mutex
	leaderNode   string
	leaseExpires time.Time
}

func (s *CentralLockStore) TryAcquireOrRenew(nodeID string, ttl time.Duration) bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	now := time.Now()
	// Если ключ свободен или аренда старого лидера протухла
	if s.leaderNode == "" || now.After(s.leaseExpires) {
		s.leaderNode = nodeID
		s.leaseExpires = now.Add(ttl)
		return true
	}

	// Если ключ уже удерживается нами — продлеваем
	if s.leaderNode == nodeID {
		s.leaseExpires = now.Add(ttl)
		return true
	}

	return false
}

func NodeLifecycleWorker(ctx context.Context, nodeID string, store *CentralLockStore, isDead *int32) {
	ttl := 80 * time.Millisecond
	isLeader := false

	for {
		select {
		case <-ctx.Done():
			return
		default:
		}

		if isDead != nil && *isDead == 1 {
			// Узел убит
			return
		}

		acquired := store.TryAcquireOrRenew(nodeID, ttl)
		if acquired {
			if !isLeader {
				isLeader = true
				fmt.Printf("👑 [%s] СТАЛ ЛИДЕРОМ КЛАСТЕРА!\n", nodeID)
			}
		} else {
			if isLeader {
				isLeader = false
				fmt.Printf("⚠️ [%s] Утратил статус лидера. Переход в режим Standby.\n", nodeID)
			}
		}

		time.Sleep(30 * time.Millisecond)
	}
}

func main() {
	store := &CentralLockStore{}
	ctx, cancel := context.WithTimeout(context.Background(), 350*time.Millisecond)
	defer cancel()

	var node1Dead int32 = 0

	// Запускаем 3 ноды
	go NodeLifecycleWorker(ctx, "Node-1", store, &node1Dead)
	go NodeLifecycleWorker(ctx, "Node-2", store, nil)
	go NodeLifecycleWorker(ctx, "Node-3", store, nil)

	// Node-1 работает лидером 100 мс
	time.Sleep(100 * time.Millisecond)

	fmt.Println("\n💥 Убиваем Node-1...")
	node1Dead = 1 // Имитация краха Node-1

	// Ждем автоматического фейловера
	time.Sleep(200 * time.Millisecond)
}
```

## Под капотом

В распределенных координаторах:
Узел переходит в режим Standby без расхода ресурсов CPU. Он регистрирует Watcher на ключ `/services/leader`. Когда сервер консенсуса высылает событие `DELETE`, поток немедленно пробуждается из селектора событий, минимизируя задержку перехвата лидерства до единиц миллисекунд.

## Подводные камни

1. **Борьба нескольких Standby-узлов без задержки:** При падении лидера все Standby узлы одновременно попытаются захватить ключ. Всегда добавляйте небольшой рандомизированный джиттер перед повторной попыткой.
2. **Забытый статус при рестарте:** После сбоя сервис должен начинать с предположения «я не лидер».
3. **Утечка ресурсов старого лидера:** При переходе в Standby все открытые сокеты и блокировки в БД обязаны быть закрыты.

## На собеседовании

**Вопрос:** Как избежать ситуации, когда два узла попеременно отбирают друг у друга статус лидера каждые несколько секунд (Flapping Leader)?
**Ответ:** 
1. Добавить защитный интервал **`LockDelay`** (как в Consul) или задержку после ухода в отставку (`ResignWaitPeriod`).
2. Использовать экспоненциальный бэкофф при частых переключениях.
3. Проверять здоровье локального узла: если узел испытывает проблемы с памятью или связью, он обязан временно дисквалифицировать себя из участия в выборах.
