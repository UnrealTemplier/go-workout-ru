# Базовый C10K Bench: Измерение потребления стека горутин в pprof

## Условие

Напиши TCP-эхо-сервер на стандартном `net.Listen`. В цикле вызывай `Accept` и запускай `go handleConn(c)`. Запусти 10 000 пустых TCP соединений с клиента. Посмотри в `pprof` на количество потребляемой памяти (минимум 2-4 КБ стека на горутину = мегабайты памяти на пустое ожидание данных).

### Исходная формулировка

**Базовый C10K Bench**: Напиши TCP-эхо-сервер на стандартном `net.Listen`. В цикле вызывай `Accept` и запускай `go handleConn(c)`. Запусти 10 000 пустых TCP соединений с клиента. Посмотри в `pprof` на количество потребляемой памяти (минимум 2-4 КБ стека на горутину = мегабайты памяти на пустое ожидание данных).

## Теория

Для того чтобы лично убедиться в оверхеде классической модели `net.Listen`, мы напишем стандартный TCP-эхо сервер на чистом Go, подключим профилировщик **`net/http/pprof`** и сгенерируем **10 000 неактивных TCP-соединений**.

В неактивном состоянии клиенты просто открывают соединение (завершают TCP handshake) и не отправляют ни одного байта.
Серверные горутины застревают внутри блокирующего вызова:
```go
n, err := conn.Read(buf)
```
Под капотом рантайм Go переводит эти 10 000 горутин в статус `_Gwaiting` с причиной `waitReasonIOWait`.

### Что покажет профилировщик памяти (pprof heap & goroutine):
1. **Goroutine Count:** Ровно 10 000 активных горутин в состоянии `runtime.gopark` -> `netpollblock`.
2. **Stack Memory:** Команда `go tool pprof http://localhost:6060/debug/pprof/heap` в секции `inuse_space` покажет существенный объем памяти, удерживаемый стеками (`runtime.stacks_sys`), составляющий от 25 до 45 МБ исключительно на пустое ожидание сетевых пакетов!

## Решение по шагам

1. Напишите классический сервер на `net.Listen("tcp", ":9011")` с циклом `Accept()` и запуском `go handleConn(conn)`.
2. Подключите профилировщик `net/http/pprof` на отдельном порту `:6060`.
3. Напишите тестовый генератор 10 000 пустых TCP-подключений.
4. Исследуйте распределение памяти через эндпоинт `/debug/pprof/goroutine?debug=1` и `runtime.ReadMemStats`.

## Код решения

**`classic_server.go`**

```go
package main

import (
	"fmt"
	"io"
	"log"
	"net"
	"net/http"
	_ "net/http/pprof"
	"runtime"
	"sync/atomic"
	"time"
)

var activeConnections int64

func handleConn(c net.Conn) {
	defer func() {
		_ = c.Close()
		atomic.AddInt64(&activeConnections, -1)
	}()

	atomic.AddInt64(&activeConnections, 1)

	// Аллоцируем буфер для чтения
	buf := make([]byte, 1024)
	for {
		// Блокирующий вызов: горутина засыпает в runtime.gopark
		n, err := c.Read(buf)
		if err != nil {
			if err != io.EOF {
				// Ошибка сокета
			}
			return
		}
		// Эхо-ответ
		if _, err := c.Write(buf[:n]); err != nil {
			return
		}
	}
}

func main() {
	// 1. Запуск pprof профилировщика на порту 6060
	go func() {
		log.Println("[pprof] Доступен по адресу: http://localhost:6060/debug/pprof/")
		_ = http.ListenAndServe("127.0.0.1:6060", nil)
	}()

	// 2. Фоновый мониторинг использования памяти
	go func() {
		var m runtime.MemStats
		ticker := time.NewTicker(3 * time.Second)
		defer ticker.Stop()

		for range ticker.C {
			runtime.ReadMemStats(&m)
			fmt.Printf("[METRICS] Соединений: %5d | Горутин: %5d | Память стеков: %6.2f MB | Heap InUse: %6.2f MB\n",
				atomic.LoadInt64(&activeConnections),
				runtime.NumGoroutine(),
				float64(m.StackInuse)/(1024*1024),
				float64(m.HeapInuse)/(1024*1024),
			)
		}
	}()

	// 3. Запуск классического TCP-слушателя
	ln, err := net.Listen("tcp", "127.0.0.1:9011")
	if err != nil {
		log.Fatalf("Listen error: %v", err)
	}
	defer ln.Close()

	log.Println("Классический сервер Go запущен на 127.0.0.1:9011...")
	for {
		conn, err := ln.Accept()
		if err != nil {
			log.Printf("Accept error: %v", err)
			continue
		}
		// Запуск новой горутины на КАЖДОЕ соединение!
		go handleConn(conn)
	}
}
```

**`idle_clients.go`**

```go
package main

import (
	"fmt"
	"net"
	"time"
)

func main() {
	const targetConnections = 10000
	conns := make([]net.Conn, 0, targetConnections)

	fmt.Printf("Создание %d неактивных TCP-подключений...\n", targetConnections)

	for i := 1; i <= targetConnections; i++ {
		c, err := net.Dial("tcp", "127.0.0.1:9011")
		if err != nil {
			fmt.Printf("Ошибка подключения на шаге %d: %v\n", i, err)
			break
		}
		conns = append(conns, c)

		if i%1000 == 0 {
			fmt.Printf("Установлено %d подключений...\n", i)
		}
	}

	fmt.Printf("\nУспешно удерживается %d соединений в режиме Idle!\n", len(conns))
	fmt.Println("Откройте в браузере: http://localhost:6060/debug/pprof/goroutine?debug=1")
	fmt.Println("Для завершения нажмите Ctrl+C...")

	time.Sleep(10 * time.Minute)
	for _, c := range conns {
		_ = c.Close()
	}
}
```

## Под капотом

Когда горутина вызывает `net.Conn.Read()`, стандартный рантайм Go обращается к внутреннему вызову `poll.FD.Read()`. Дескриптор сокета уже переведен рантаймом в неблокирующий режим (`O_NONBLOCK`).
Если системный вызов `unix.Read()` возвращает `EAGAIN`, рантайм вызывает `runtime.poll_runtime_pollWait(pd, 'r')`. 
Горутина отвязывается от процессора `P` и системного потока `M` и засыпает. Однако ее стек (`runtime.g.stack.lo` - `runtime.g.stack.hi`) **остается физически выделенным в памяти** до тех пор, пока сокет не будет закрыт. При 10 000 соединений это минимум 20 МБ чистой физической памяти ядра и рантайма.

## Подводные камни

Если при создании 10 000 подключений вы получаете ошибку `dial tcp 127.0.0.1:9011: socket: too many open files`, это означает, что вы уперлись в стандартный лимит дескрипторов операционной системы (по умолчанию в Linux обычно `1024`). Перед запуском теста обязательно выполните команду в терминале: `ulimit -n 65535`.

## На собеседовании

**Вопрос на собеседовании (Senior Go Developer / Infrastructure):**
«В чем разница между HeapInuse и StackInuse в структуре runtime.MemStats, и почему рост количества горутин не виден в стандартном heap-профайле pprof по умолчанию?»

**Эталонный ответ:**
- `HeapInuse`: Объем памяти в пролетах аллокатора Go (`mspan`), занятых объектами, созданными в куче через `new()`, `make()` или в результате escape analysis. Стандартный профиль `debug/pprof/heap` показывает исключительно кучу.
- `StackInuse`: Объем памяти, выделенный аллокатором под стеки горутин (`runtime.mcache` -> `mcentral` для стеков фиксированных классов 2KB, 4KB, 8KB...). 
Поскольку стеки горутин не являются объектами кучи, они **не отображаются** в графе аллокаций heap. Их точный объем можно увидеть только в общем профиле памяти через поле `runtime.MemStats.StackInuse` или через эндпоинт `/debug/pprof/goroutine`.
