# Graceful Shutdown в gnet: Остановка сокетов, дренаж соединений и sync.WaitGroup

## Условие

Реализуйте обработку `SIGTERM`: `Stop()` останавливает accept, дожидается завершения `OnTraffic` для текущих соединений (через `sync.WaitGroup`), затем закрывает все fd. Объясните, почему `gnet` требует ручного управления lifecycle, в отличие от `http.Server.Shutdown`.

### Исходная формулировка

**Graceful Shutdown в `gnet`.**: Реализуйте обработку `SIGTERM`: `Stop()` останавливает accept, дожидается завершения `OnTraffic` для текущих соединений (через `sync.WaitGroup`), затем закрывает все fd. ## Теория

В микросервисной архитектуре под управлением Kubernetes поды непрерывно перезапускаются в ходе деплоев, Rolling Updates и автомасштабирования (HPA).
Когда pod получает сигнал `SIGTERM`, приложение обязано корректно завершить работу (**Graceful Shutdown**):
1. Перестать принимать новые входящие TCP-соединения (`close(listen_fd)`).
2. Дать активным сетевым запросам время на завершение (дренаж соединений).
3. Дождаться окончания фоновых задач в Worker Pool.
4. Закрыть открытые сокеты с отправкой клиентам корректного FIN-пакета (без аварийного сброса `TCP RST`).

### Разница с `http.Server.Shutdown`:
В стандартном `net/http` метод `srv.Shutdown(ctx)` инкапсулирует всю механику: закрывает слушатель, переводит сокеты в статус idle и ждет завершения горутин.
В `gnet` жизненным циклом управляет сам разработчик:
- Функция `gnet.Stop(ctx, addr)` останавливает слушающие сокеты и прерывает циклы `epoll_wait`.
- Задачи, переданные в Worker Pool, должны отслеживаться через `sync.WaitGroup`.
- При вызове shutdown необходимо установить флаг состояния сервера (Atomic Flag), отклоняя новые входящие запросы.

## Решение по шагам

1. Инициализируйте перехват системных сигналов `os.Interrupt`, `syscall.SIGTERM` через `signal.Notify`.
2. Используйте `sync.WaitGroup` для учета всех in-flight сетевых задач.
3. При получении сигнала вызовите `gnet.Stop(context.Background(), addr)`.
4. Дождитесь завершения всех активных воркеров через `wg.Wait()` с заданным таймаутом.
5. Завершите процесс с кодом возврата 0.

## Код решения

**`graceful_server.go`**

```go
package main

import (
	"context"
	"log"
	"os"
	"os/signal"
	"sync"
	"sync/atomic"
	"syscall"
	"time"

	"github.com/panjf2000/gnet/v2"
)

type GracefulServer struct {
	gnet.BuiltinEventEngine
	addr       string
	inShutdown int32
	inflightWg sync.WaitGroup
}

func (s *GracefulServer) OnTraffic(c gnet.Conn) gnet.Action {
	// Проверяем, не находится ли сервер в фазе остановки
	if atomic.LoadInt32(&s.inShutdown) == 1 {
		_ = c.AsyncWrite([]byte("ERR: SERVER_SHUTTING_DOWN\n"), func(c gnet.Conn, err error) error {
			return c.Close()
		})
		return gnet.None
	}

	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Увеличиваем счетчик активных задач
	s.inflightWg.Add(1)
	taskData := append([]byte(nil), buf...)

	// Передаем задачу в фоновую обработку
	go func(conn gnet.Conn, data []byte) {
		defer s.inflightWg.Done()

		// Имитация полезной работы
		time.Sleep(100 * time.Millisecond)

		_ = conn.AsyncWrite(append([]byte("ACK: "), data...), nil)
	}(c, taskData)

	return gnet.None
}

func main() {
	serverAddr := "tcp://127.0.0.1:9019"
	server := &GracefulServer{addr: serverAddr}

	// Канал системных сигналов ОС
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)

	go func() {
		sig := <-sigChan
		log.Printf("[SHUTDOWN] Получен сигнал %v. Инициализация Graceful Shutdown...\n", sig)

		// 1. Устанавливаем флаг отключения
		atomic.StoreInt32(&server.inShutdown, 1)

		// 2. Останавливаем движок gnet (перестает принимать новые подключения)
		shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
		defer cancel()

		if err := gnet.Stop(shutdownCtx, serverAddr); err != nil {
			log.Printf("[SHUTDOWN] Ошибка gnet.Stop: %v\n", err)
		}

		// 3. Ждем завершения всех in-flight задач воркеров
		log.Println("[SHUTDOWN] Ожидание завершения текущих задач...")
		done := make(chan struct{})
		go func() {
			server.inflightWg.Wait()
			close(done)
		}()

		select {
		case <-done:
			log.Println("[SHUTDOWN] Все задачи успешно завершены. Выход.")
		case <-time.After(4 * time.Second):
			log.Println("[SHUTDOWN] Истек таймаут дренажа задач. Принудительный выход.")
		}

		os.Exit(0)
	}()

	log.Printf("Сервер запущен на %s. Для остановки нажмите Ctrl+C.\n", serverAddr)
	if err := gnet.Run(server, serverAddr, gnet.WithMulticore(true)); err != nil {
		log.Printf("Работа сервера завершена: %v\n", err)
	}
}
```

## Под капотом

Когда вызывается `gnet.Stop(ctx, addr)`:
1. Движок `gnet` закрывает слушающие файловые дескрипторы сокетов (`listen_fd`), поэтому ядро Linux немедленно прекращает отвечать `SYN-ACK` на новые запросы клиентов.
2. `gnet` отправляет внутреннее прерывание во все Sub-Reactors через `eventfd`.
3. Потоки реакторов завершают последний цикл обработки активных событий `epoll_wait`, закрывают клиентские файловые дескрипторы и выходят из системного вызова.

## Подводные камни

Использование `os.Exit(0)` сразу при получении сигнала `SIGTERM`. Это грубая ошибка, которая приводит к моментальному закрытию TCP-сокетов с флагом `RST`. Клиенты получают ошибку `Connection reset by peer`, их сетевые запросы падают с кодом 502/504, а в микросервисной сети возникают ложные алерты.

## На собеседовании

**Вопрос на собеседовании (DevSecOps / Cloud Platform Lead):**
«Как в Kubernetes устроен жизненный цикл завершения Pod (Terminating Phase) и почему правильный Graceful Shutdown требует паузы (preStop hook) перед закрытием сокетов?»

**Эталонный ответ:**
При удалении Pod в Kubernetes происходят два параллельных процесса:
1. Kubelet посылает контейнеру сигнал `SIGTERM`.
2. Kube-proxy / CNI исключает IP-адрес пода из таблицы маршрутизации EndpointSlice / iptables / IPVS.
Если сервер на Go закроет слушающий сокет мгновенно по получению `SIGTERM`, то из-за распределенной задержки распространения EndpointSlice (которая может занимать 1–3 секунды) вышестоящие балансировщики (Ingress Nginx / Envoy) продолжат отправлять новые запросы на старый IP-адрес, приводя к ошибкам `502 Bad Gateway`.
Для исключения дропов в продакшене настраивают `lifecycle.preStop: exec: command: ["sleep", "3"]`, давая балансировщику время убрать под из ротации до того, как Go-приложение получит `SIGTERM`.
