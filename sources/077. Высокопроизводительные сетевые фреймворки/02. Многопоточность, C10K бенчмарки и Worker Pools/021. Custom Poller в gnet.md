## Теория

Любой кроссплатформенный сетевой движок (включая рантайм Go, libuv в Node.js и gnet) обязан изолировать низкоуровневые системные механизмы ввода-вывода под единым интерфейсом абстракции (**Poller Abstraction**).

### Матрица механизмов мультиплексирования ОС:
- **Linux:** `epoll` (`epoll_create1`, `epoll_ctl`, `epoll_wait`). Наиболее производительный механизм, поддерживающий миллионы сокетов.
- **macOS, FreeBSD, OpenBSD:** `kqueue` (`kqueue()`, `kevent()`). Работает на уровне фильтров событий (`EVFILT_READ`, `EVFILT_WRITE`).
- **Windows:** `IOCP` (I/O Completion Ports) или `WSAEventSelect`.

### Условная компиляция (Build Tags) в Go:
Для сборки специфичного для платформы кода в Go применяются директивы компилятора:
```go
//go:build linux
```
или
```go
//go:build darwin || freebsd || openbsd
```

В этом упражнении мы напишем минимальный собственный кроссплатформенный `Poller`, демонстрирующий, как устроена внутренняя архитектура мультиплексирования в `gnet`.

## Решение по шагам

1. Создайте интерфейс `Poller` с методами `Add(fd int)`, `Delete(fd int)` и `Polling(callback)`.
2. Реализуйте версию для Linux (`poller_linux.go`) с директивой `//go:build linux` на базе пакета `unix`.
3. Реализуйте заглушку или версию для других ОС (`poller_other.go`) с директивой `//go:build !linux`.
4. Объясните, почему `gnet` разделяет код на файлы `poller_epoll.go` и `poller_kqueue.go`.

## Код решения

**`poller.go`**

```go
package main

// Poller определяет унифицированный контракт мультиплексора событий ввода-вывода
type Poller interface {
	AddRead(fd int) error
	Delete(fd int) error
	Polling(onEvent func(fd int) error) error
	Close() error
}
```

ℹ️ Унифицированный интерфейс абстракции сетевого поллера

**`poller_linux.go`**

```go
//go:build linux

package main

import (
	"fmt"
	"syscall"

	"golang.org/x/sys/unix"
)

// LinuxEpollPoller реализует мультиплексирование на базе системных вызовов Linux epoll
type LinuxEpollPoller struct {
	epfd   int
	events []unix.EpollEvent
}

func NewPoller() (Poller, error) {
	epfd, err := unix.EpollCreate1(unix.EPOLL_CLOEXEC)
	if err != nil {
		return nil, fmt.Errorf("epoll_create1: %w", err)
	}
	return &LinuxEpollPoller{
		epfd:   epfd,
		events: make([]unix.EpollEvent, 128),
	}, nil
}

func (p *LinuxEpollPoller) AddRead(fd int) error {
	ev := &unix.EpollEvent{
		Events: unix.EPOLLIN,
		Fd:     int32(fd),
	}
	return unix.EpollCtl(p.epfd, unix.EPOLL_CTL_ADD, fd, ev)
}

func (p *LinuxEpollPoller) Delete(fd int) error {
	return unix.EpollCtl(p.epfd, unix.EPOLL_CTL_DEL, fd, nil)
}

func (p *LinuxEpollPoller) Polling(onEvent func(fd int) error) error {
	for {
		n, err := unix.EpollWait(p.epfd, p.events, -1)
		if err != nil {
			if err == syscall.EINTR {
				continue
			}
			return err
		}

		for i := 0; i < n; i++ {
			fd := int(p.events[i].Fd)
			if err := onEvent(fd); err != nil {
				// Ошибка обработки
			}
		}
	}
}

func (p *LinuxEpollPoller) Close() error {
	return unix.Close(p.epfd)
}
```

## Под капотом

Почему `epoll` на Linux быстрее `kqueue` на macOS при больших объемах:
`epoll` спроектирован так, что регистрация дескрипторов сохраняется в структуре ядра `struct eventpoll` на все время жизни соединения. При вызове `epoll_wait` приложение не передает список сокетов в ядро, а получает готовый массив.
В `kqueue` список изменений (`changelist`) передается системным вызовом `kevent()`, что требует копирования массива структур `struct kevent` из пространства пользователя в ядро при каждом обновлении фильтров.

## Подводные камни

При использовании `epoll_create1` всегда передавайте флаг `EPOLL_CLOEXEC` (`FD_CLOEXEC`). Если ваше приложение в дальнейшем выполнит запуск внешнего дочернего процесса через `os/exec`, без этого флага дескриптор epoll утечет в дочерний процесс, блокируя корректное закрытие сокетов в родительском приложении!

## На собеседовании

**Вопрос на собеседовании (Senior Linux Systems / Network Engineer):**
«Что такое io_uring в современном ядре Linux, и сможет ли он в будущем заменить epoll в таких фреймворках, как gnet?»

**Эталонный ответ:**
- **Ограничение epoll:** epoll лишь сообщает о *готовности* сокета. После пробуждения из `epoll_wait` поток обязан сделать реальный системный вызов `read()` или `write()`, переключая контекст из User Space в Kernel Space.
- **Революция io_uring (Jens Axboe):** Позволяет осуществлять полностью **асинхронный ввод-вывод без системных вызовов**. Приложение и ядро разделяют две кольцевые очереди в общей памяти: Submission Queue (SQ) и Completion Queue (CQ). Приложение помещает операцию `read` в SQ, а ядро само вычитывает данные. Потенциально `io_uring` способен обогнать `epoll` по пропускной способности еще на 20-30%, и в gnet уже ведутся эксперименты по его поддержке.
