# [Правильный дизайн] Worker Pool: Неблокирующий OnTraffic и AsyncWrite

## Условие

Перепиши `gnet` сервер: `OnTraffic` не должен ничего вычислять. Он должен читать `[]byte` из сокета и кидать их в неблокирующий `go channel`. Пул горутин (воркеры) читают канал, обрабатывают запрос и отправляют ответ обратно через `conn.AsyncWrite(data)`.

### Исходная формулировка

**[Правильный дизайн (Worker Pool)]**: Перепиши `gnet` сервер: `OnTraffic` не должен ничего вычислять. Он должен читать `[]byte` из сокета и кидать их в неблокирующий `go channel`. Пул горутин (воркеры) читают канал, обрабатывают запрос и отправляют ответ обратно через `conn.AsyncWrite(data)`.

## Теория

В производственных HighLoad-системах паттерн **«Неблокирующий OnTraffic + Worker Pool»** является ключевым архитектурным решением, позволяющим совместить ультравысокую пропускную способность сетевого ввода-вывода (I/O Bound) и стабильную обработку ресурсоемких вычислений (CPU/DB Bound).

### Механика конвейера:
1. **Фаза I/O (Сетевой поток Sub-Reactor):**
   При срабатывании `EPOLLIN` реактор мгновенно забирает байты из внутреннего кольцевого буфера `c.Next(-1)`. Это занимает доли микросекунды.
2. **Фаза передачи (Offload):**
   Реактор копирует байты в структуру задачи и отправляет ее в ограниченную очередь задач (Bounded Channel или Ring Buffer). Если очередь полна, реактор применяет политику Backpressure (сброс пакета или ответ с ошибкой 429/503), но **никогда не блокируется в вызове send**.
3. **Фаза выполнения (Worker Goroutines):**
   Пул фоновых воркеров вычитывает задачи из канала, десериализует полезную нагрузку, делает запросы к СУБД/кэшу или проводит вычисления.
4. **Фаза ответа (AsyncWrite):**
   Воркер вызывает метод `conn.AsyncWrite(responseData, callback)`. 
   Этот метод является **строго потокобезопасным**: он регистрирует исходящий буфер во внутренней очереди сокета и пробуждает локальный Sub-Reactor через системный вызов `eventfd` или `pipe`, гарантируя, что запись в сокет произойдет в правильном потоке без Data Race.

## Решение по шагам

1. Спроектируйте структуру задачи `Job`, содержащую ссылку `c gnet.Conn` и срез байт `Payload []byte`.
2. Создайте пул горутин с буферизованным каналом задач емкостью 10 000 элементов.
3. В обработчике `OnTraffic` выполните неблокирующий опрос канала через `select-default`.
4. Внутри цикла воркера выполните обработку и вызовите `c.AsyncWrite(...)`.
5. Убедитесь в потокобезопасности передачи данных и корректности освобождения памяти.

## Код решения

**`async_worker_server.go`**

```go
package main

import (
	"log"
	"runtime"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// Job инкапсулирует входящий сетевой пакет и дескриптор соединения
type Job struct {
	Conn    gnet.Conn
	Payload []byte
}

type ProductionWorkerServer struct {
	gnet.BuiltinEventEngine
	jobChan    chan Job
	droppedJobs int64
}

func NewProductionWorkerServer(numWorkers int, queueCap int) *ProductionWorkerServer {
	s := &ProductionWorkerServer{
		jobChan: make(chan Job, queueCap),
	}

	// Запуск пула независимых воркеров
	for i := 0; i < numWorkers; i++ {
		go s.worker(i)
	}

	return s
}

func (s *ProductionWorkerServer) worker(workerID int) {
	for job := range s.jobChan {
		// 1. Имитация полезной вычислительной нагрузки
		time.Sleep(5 * time.Millisecond)

		// 2. Формирование ответа
		resp := append([]byte("PROCESSED_OK: "), job.Payload...)

		// 3. Потокобезопасная асинхронная запись в сокет
		err := job.Conn.AsyncWrite(resp, func(c gnet.Conn, err error) error {
			if err != nil {
				log.Printf("[Worker %d] Ошибка AsyncWrite: %v", workerID, err)
			}
			return nil
		})
		if err != nil {
			log.Printf("[Worker %d] Сбой постановки в очередь записи: %v", workerID, err)
		}
	}
}

// OnTraffic исполняется исключительно в потоке Sub-Reactor
func (s *ProductionWorkerServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Обязательное копирование: буфер gnet будет перезаписан следующим сетевым пакетом!
	packetData := make([]byte, len(buf))
	copy(packetData, buf)

	// Неблокирующая передача в очередь воркеров
	select {
	case s.jobChan <- Job{Conn: c, Payload: packetData}:
		return gnet.None
	default:
		// Очередь заполнена — защита от OOM (Backpressure)
		atomic.AddInt64(&s.droppedJobs, 1)
		_ = c.AsyncWrite([]byte("ERR: SERVER_OVERLOADED_BACKPRESSURE\n"), nil)
		return gnet.None
	}
}

func main() {
	workers := runtime.NumCPU() * 4
	server := NewProductionWorkerServer(workers, 20000)
	addr := "tcp://127.0.0.1:9017"

	log.Printf("Запуск сервера с Worker Pool (%d воркеров) на %s...\n", workers, addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка запуска: %v", err)
	}
}
```

ℹ️ Эталонная архитектура неблокирующего реактора с пулом воркеров и AsyncWrite

## Под капотом

Что происходит внутри `conn.AsyncWrite()`:
1. `AsyncWrite` упаковывает байты в буферную очередь структуры `conn`.
2. Если вызов совершен из потока, отличного от владельца данного Sub-Reactor (например, из горутины-воркера), `gnet` не может напрямую писать в сокет, так как это нарушило бы потокобезопасность epoll.
3. `gnet` вызывает системный вызов `unix.Write(reactor.eventfd, ...)` (Linux `eventfd`).
4. Поток реактора, спящий в `epoll_wait`, мгновенно пробуждается по событию `eventfd`, считывает накопившиеся в очереди задачи и безопасно отправляет их клиенту через `write()` или `writev()`.

## Подводные камни

Использование небуферизованного или неограниченного канала для передачи задач:
- Если канал небуферизован (`make(chan Job)`), сетевой реактор мгновенно зависнет при попытке записи `ch <- job`, превращаясь в блокирующий сервер!
- Если канал бесконечен (или вы запускаете `go worker(job)` на каждый запрос), при всплеске нагрузки сервер создаст сотни тысяч горутин и упадет по OOM (Out Of Memory). Очередь обязана иметь строгий лимит емкости (Bounded Queue) и логику Backpressure.

## На собеседовании

**Вопрос на собеседовании (Principal Engineer / HighLoad Lead):**
«Как в Linux устроен механизм eventfd и почему высокопроизводительные сетевые библиотеки используют его вместо каналов Go или мьютексов для межпоточного пробуждения?»

**Эталонный ответ:**
Системный вызов `eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC)` создает 64-битный счетчик в ядре Linux, представленный обычным файловым дескриптором. 
Главное преимущество `eventfd` — его можно зарегистрировать в системном вызове `epoll_wait` наряду с тысячами сетевых TCP-сокетов!
Когда фоновому воркеру нужно разбудить спящий сетевой поток, он делает запись 8 байт `write(eventfd, &val, 8)`. Ядро Linux атомарно увеличивает счетчик и немедленно пробуждает `epoll_wait`. Это избавляет от необходимости использовать мьютексы, условные переменные (`pthread_cond_t`) или периодический поллинг таймерами.
