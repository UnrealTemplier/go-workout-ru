# Многопоточность в gnet: Настройка NumEventLoop и горизонтальное масштабирование

## Условие

Установите `NumEventLoop` равным `runtime.NumCPU()`. Сравните производительность (RPS, задержку) с однопоточным режимом и с обычным TCP-сервером на `net`.

### Исходная формулировка

**Многопоточность в gnet: настройка количества event-loop.**: Установите `NumEventLoop` равным `runtime.NumCPU()`. Сравните производительность (RPS, задержку) с однопоточным режимом и с обычным TCP-сервером на `net`.

## Теория

В многоядерных серверных архитектурах (от 16 до 128 ядер) производительность однопоточного реактора упирается в предел пропускной способности одного процессорного ядра (около 150 000 – 300 000 RPS).

Для полного раскрытия потенциала современного серверного оборудования `gnet` позволяет сконфигурировать параметр **`NumEventLoop`**:
- Если `NumEventLoop = 1`: запускается классический однопоточный реактор.
- Если `NumEventLoop = runtime.NumCPU()` и `Multicore = true`: запускается многопоточный Multi-Reactor, где каждое ядро CPU обрабатывает свой независимый набор сокетов.

### Привязка потоков к ядрам (CPU Affinity / Thread Pinning):
Для предотвращения миграции потоков между ядрами ОС (что приводит к сбросу кэшей процессора L1i/L1d и задержкам на межпроцессорной шине NUMA), `gnet` предоставляет опцию:
```go
gnet.WithLockOSThread(true)
```
Каждый Event Loop жестко связывается со своим системным потоком `OS Thread` вызовом `runtime.LockOSThread()`, обеспечивая максимальную локальность кэша (Cache Locality).

## Решение по шагам

1. Сконфигурируйте сервер с `gnet.WithNumEventLoop(runtime.NumCPU())`.
2. Включите привязку потоков операционной системы через `gnet.WithLockOSThread(true)`.
3. Реализуйте мониторинг распределения соединений между реакторами через метод `OnOpen`.
4. Сравните масштабируемость RPS при увеличении числа ядер от 1 до `NumCPU`.

## Код решения

**`multithread_server.go`**

```go
package main

import (
	"fmt"
	"log"
	"runtime"
	"sync/atomic"

	"github.com/panjf2000/gnet/v2"
)

type MultiLoopServer struct {
	gnet.BuiltinEventEngine
	activeLoops int64
}

func (s *MultiLoopServer) OnBoot(eng gnet.Engine) gnet.Action {
	log.Printf("[MultiLoopEngine] Успешно инициализировано %d Event Loops\n", runtime.NumCPU())
	return gnet.None
}

func (s *MultiLoopServer) OnOpen(c gnet.Conn) ([]byte, gnet.Action) {
	// Идентификатор локального реактора (sub-reactor index)
	return nil, gnet.None
}

func (s *MultiLoopServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Эхо-ответ
	_, _ = c.Write(buf)
	return gnet.None
}

func main() {
	numCPU := runtime.NumCPU()
	server := &MultiLoopServer{}
	addr := "tcp://127.0.0.1:9010"

	fmt.Printf("Конфигурация gnet сервера: Cores = %d, LockOSThread = true\n", numCPU)

	err := gnet.Run(
		server,
		addr,
		gnet.WithMulticore(true),
		gnet.WithNumEventLoop(numCPU),
		gnet.WithLockOSThread(true),
		gnet.WithReusePort(true),
	)
	if err != nil {
		log.Fatalf("Сбой gnet: %v", err)
	}
}
```

ℹ️ Масштабирование сетевого сервера на все доступные аппаратные ядра CPU

## Под капотом

Под капотом `gnet.WithLockOSThread(true)` вызывает `runtime.LockOSThread()`, сообщая планировщику Go, что данная горутина привязана исключительно к текущему потоку `M`. Этот поток никогда не отдастся другой горутине и не будет перемещен ядром Linux на другое процессорное ядро, что исключает TLB shootdowns и инвалидацию L1/L2 кэш-линий.

## Подводные камни

Не устанавливайте `NumEventLoop` больше, чем физическое количество ядер CPU (`runtime.NumCPU()`). В отличие от горутин, создание избыточного количества системных потоков приводит к конкуренции за процессорное время в планировщике ядра Linux (CFS scheduler), росту context switches и падению общей пропускной способности!

## На собеседовании

**Вопрос на собеседовании (Systems Architect / HighLoad Engineer):**
«Что такое NUMA (Non-Uniform Memory Access) и почему привязка потоков к ядрам (Thread Affinity) критична на двухсокетных серверах?»

**Эталонный ответ:**
На двухсокетных материнских платах каждый процессор имеет собственный контроллер памяти и локальные планки RAM. Доступ к памяти соседнего сокета (Remote Memory Access) идет через шину Ultra Path Interconnect (UPI / QPI) с задержкой в 2–3 раза выше, чем к локальной памяти. 
Если поток сетевого Event Loop мигрирует между ядрами разных физических процессоров, он вынужден постоянно обращаться к удаленным узлам NUMA, вызывая резкие просадки производительности. Привязка потоков (`pthread_setaffinity_np` / `LockOSThread`) гарантирует исполнение кода строго на локальном NUMA-узле.
