# Знакомство с gnet/v2: Внутреннее устройство сетевого движка нового поколения

### Исходная формулировка

## Теория

Библиотека **`github.com/panjf2000/gnet/v2`** — это высокопроизводительный, легковесный, событийно-ориентированный сетевой фреймворк для Go, разработанный как прямая замена стандартному сетевому стеку в задачах с экстремальной нагрузкой.

### Ключевые архитектурные новшества `gnet/v2`:
1. **Прямое взаимодействие с ядром ОС:** `gnet` не оборачивает сокеты в структуры `net.TCPConn` и интерфейс `net.Conn`. Он работает с «сырыми» целочисленными файловыми дескрипторами `fd int` через системные пакеты `golang.org/x/sys/unix`.
2. **Адаптивный кольцевой буфер (RingBuffer):**
   Внутренний кольцевой буфер динамически расширяется и сжимается, предотвращая частые аллокации памяти. При чтении сокета данные ложатся в непрерывный сегмент памяти.
3. **Кроссплатформенные абстракции Poller:**
   - Linux: `epoll` с режимами Edge-Triggered / Level-Triggered.
   - macOS / FreeBSD / OpenBSD: `kqueue`.
   - Windows: Реактор на базе механизма `poll`/`WSAEventSelect` (для локальной разработки).
4. **Встроенный балансировщик нагрузки сокетов (Load Balancer):**
   Main Reactor распределяет новые подключения между Sub-Reactors по одной из стратегий:
   - `RoundRobin`: Циклическое распределение.
   - `LeastConnections`: Отправка сокета наименее загруженному реактору.
   - `SourceAddrHash`: Хеширование IP-адреса клиента для поддержания аффинности сессий.

## Решение по шагам

1. Установите актуальную мажорную версию библиотеки: `go get -u github.com/panjf2000/gnet/v2`.
2. Изучите базовые структуры конфигурации: `gnet.Options`.
3. Напишите сервер, реализующий базовые коллбэки `OnBoot`, `OnOpen`, `OnTraffic`.
4. Запустите сервер с опцией `gnet.WithLoadBalancing(gnet.RoundRobin)`.

## Код решения

**`gnet_v2_intro.go`**

```go
package main

import (
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

type GnetV2DemoServer struct {
	gnet.BuiltinEventEngine
}

func (s *GnetV2DemoServer) OnBoot(eng gnet.Engine) gnet.Action {
	log.Println("[gnet/v2] Сетевой движок успешно запущен!")
	return gnet.None
}

func (s *GnetV2DemoServer) OnOpen(c gnet.Conn) ([]byte, gnet.Action) {
	log.Printf("[gnet/v2] Новое соединение от %s (fd=%d)\n", c.RemoteAddr(), c.Fd())
	return []byte("CONNECTED_TO_GNET_V2\n"), gnet.None
}

func (s *GnetV2DemoServer) OnTraffic(c gnet.Conn) gnet.Action {
	// Считываем все байты из кольцевого буфера
	data, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Эхо-ответ
	_, _ = c.Write(append([]byte("ECHO: "), data...))
	return gnet.None
}

func main() {
	server := &GnetV2DemoServer{}
	addr := "tcp://127.0.0.1:9020"

	fmt.Printf("Запуск сервера gnet/v2 на %s...\n", addr)

	// Тонкая настройка параметров gnet/v2
	options := []gnet.Option{
		gnet.WithMulticore(true),
		gnet.WithLoadBalancing(gnet.RoundRobin),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
		gnet.WithSocketRecvBuffer(64 * 1024), // Буфер приема сокета 64 KB
		gnet.WithSocketSendBuffer(64 * 1024), // Буфер передачи сокета 64 KB
	}

	if err := gnet.Run(server, addr, options...); err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

## Под капотом

В `gnet/v2` ключевым изменением по сравнению с первой версией стал полный отказ от устаревших срезов байтов в пользу структуры `ringbuffer.RingBuffer`. 
Когда сокет готов к чтению, `gnet` выполняет вызов `readv()`, используя два указателя: от текущего индекса чтения до физического конца слайса буфера, и от начала буфера до индекса записи (wrap-around). Это позволяет эффективно утилизировать память без необходимости выравнивания и сдвига элементов массива (`memmove`).

## Подводные камни

Метод `c.Fd()` возвращает числовой дескриптор файла сокета ОС. Категорически запрещено вызывать стандартные функции закрытия (`unix.Close(c.Fd())`) или менять флаги сокета напрямую без уведомления `gnet`. Если дескриптор будет закрыт в обход `gnet`, в `epoll` останется «висячая» ссылка (Dangling FD), что приведет к ошибкам `EBADF` при следующем системном вызове!

## На собеседовании

**Вопрос на собеседовании (HighLoad Go Developer):**
«Зачем в сетевых приложениях отключать алгоритм Нагла опцией TCP_NODELAY, и когда его отключение может навредить?»

**Эталонный ответ:**
- **Что делает алгоритм Нагла (Nagle's Algorithm):** Он объединяет несколько мелких исходящих сообщений в один крупный TCP-пакет, задерживая отправку до тех пор, пока от клиента не придет подтверждение (TCP ACK) на предыдущий сегмент.
- **Почему его отключают (`TCP_NODELAY = 1`):** В интерактивных протоколах (RPC, Echo, игры, торги) задержка отправки даже на 40 мс (Delayed ACK таймаут) катастрофична для SLA. Отключение Нагла заставляет ядро отправлять пакет в сеть немедленно.
- **Когда отключение может навредить:** Если приложение делает тысячи вызовов `write()` размером по 2–5 байт, отключение Нагла приведет к генерации огромного количества микропакетов (40 байт TCP/IP заголовков на 2 байта данных), перегружая коммутаторы и сетевые каналы.
