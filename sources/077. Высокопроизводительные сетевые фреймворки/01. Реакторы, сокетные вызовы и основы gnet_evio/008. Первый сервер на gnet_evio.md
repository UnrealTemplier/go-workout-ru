# Первый сервер на gnet/evio: Нагрузочное тестирование и метрики производительности

## Условие

Напишите эхо-сервер, использующий событийно-ориентированный движок `gnet`. Реализуйте обработчики `OnInitComplete`, `OnTraffic`, `OnClose`. Запустите и проверьте нагрузочным тестом.

### Исходная формулировка

**Первый сервер на gnet (или evio).**: Напишите эхо-сервер, использующий событийно-ориентированный движок `gnet`. Реализуйте обработчики `OnInitComplete`, `OnTraffic`, `OnClose`. Запустите и проверьте нагрузочным тестом.

## Теория

Разработка сверхбыстрого сетевого сервера теряет смысл без строгой инженерной методологии его валидации под нагрузкой.

Когда сервер на стандартной библиотеке `net/http` или `net.Listen` начинает деградировать при нагрузке, узкие места обычно видны сразу: рост задержки p99, исчерпание дескрипторов файлов или лавинообразное потребление памяти.
В событийно-ориентированных движках типа `gnet` и `evio` профиль поведения принципиально иной:
- **CPU Bound:** Сервер утилизирует процессор почти на 100% в пользовательском пространстве и ядре (softirq, сетевой стек Linux), не расходуя память.
- **Стабильный RSS:** Потребление памяти остается плоским (flat memory curve) независимо от роста подключений с 100 до 50 000.

### Методология нагрузочного тестирования:
Для тестирования серверов используются:
1. **`hey` / `wrk`:** Высокопроизводительные генераторы HTTP/TCP нагрузки на C/Go с поддержкой асинхронных сокетов.
2. **`tcpkali`:** Специализированный инструмент для нагрузочного тестирования сырых TCP-сокетов с гибкой настройкой размера окон и конвейерной обработки (pipelining).
3. **Метрики ядра Linux:** Очереди сокетов через команду `ss -s`, прерывания через `/proc/interrupts` и мониторинг переключений контекста через `pidstat -w`.

## Решение по шагам

1. Реализуйте чистый минималистичный эхо-сервер на `gnet`.
2. Добавьте счетчик успешно обработанных пакетов и переданных байт с использованием `sync/atomic`.
3. Напишите скрипт нагрузочного тестирования с помощью утилиты `hey` или `wrk`.
4. Проанализируйте распределение времени отклика: p50, p90, p99 и максимальную задержку (Max Latency).

## Код решения

**`bench_echo_server.go`**

```go
package main

import (
	"fmt"
	"log"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"

	"github.com/panjf2000/gnet/v2"
)

type BenchEchoServer struct {
	gnet.BuiltinEventEngine
	addr       string
	totalReqs  int64
	totalBytes int64
}

func (b *BenchEchoServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	atomic.AddInt64(&b.totalReqs, 1)
	atomic.AddInt64(&b.totalBytes, int64(len(buf)))

	// Пишем эхо-ответ обратно
	_, _ = c.Write(buf)
	return gnet.None
}

func main() {
	server := &BenchEchoServer{addr: "tcp://127.0.0.1:9007"}

	// Фоновый сборщик метрик в консоль
	go func() {
		ticker := time.NewTicker(2 * time.Second)
		defer ticker.Stop()
		var lastReqs int64

		for range ticker.C {
			current := atomic.LoadInt64(&server.totalReqs)
			bytes := atomic.LoadInt64(&server.totalBytes)
			rps := (current - lastReqs) / 2
			lastReqs = current

			fmt.Printf("[METRICS] Текущий RPS: %d req/s | Всего обработано: %d пакетов (%d MB)\n",
				rps, current, bytes/(1024*1024))
		}
	}()

	// Graceful shutdown по сигналам SIGINT/SIGTERM
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)
	go func() {
		<-sigChan
		log.Println("Остановка сервера по сигналу...")
		_ = gnet.Stop(nil, server.addr)
	}()

	log.Printf("Запуск Bench Echo сервера на %s...\n", server.addr)
	err := gnet.Run(
		server,
		server.addr,
		gnet.WithMulticore(true),
		gnet.WithReusePort(true),
	)
	if err != nil {
		log.Fatalf("Ошибка gnet: %v", err)
	}
}
```

**`load_test.sh`**

```bash
#!/usr/bin/env bash
# Скрипт запуска стресс-тестирования TCP эхо-сервера

TARGET_HOST="127.0.0.1"
TARGET_PORT="9007"
CONCURRENCY=500
DURATION="20s"

echo "=== Запуск стресс-теста на ${TARGET_HOST}:${TARGET_PORT} ==="
echo "Параллельных соединений: ${CONCURRENCY}, Длительность: ${DURATION}"

# Проверка наличия tcpkali или hey/wrk
if command -v tcpkali &> /dev/null; then
    tcpkali --connections ${CONCURRENCY} \
            --duration ${DURATION} \
            --message "PING_BENCHMARK_PAYLOAD" \
            ${TARGET_HOST}:${TARGET_PORT}
else
    echo "Утилита tcpkali не найдена. Установите tcpkali: sudo apt install tcpkali"
    echo "Или используйте Go-бенчмарк: go test -bench=BenchmarkTCPEcho -benchtime=10s"
fi
```

## Под капотом

Во время проведения высокоинтенсивного нагрузочного тестирования узким местом часто становится не серверный код на Go, а сетевые буферы операционной системы и системные лимиты дескрипторов. 
Для того чтобы сервер на `gnet` смог выдержать 50 000+ одновременных соединений:
1. Системный лимит открытых файлов должен быть увеличен: `ulimit -n 1000000`.
2. Параметры ядра Linux для сокетов должны быть скорректированы:
   - `net.core.somaxconn = 65535` (максимальный размер очереди backlog для `listen()`).
   - `net.ipv4.tcp_max_syn_backlog = 65535` (размер очереди незавершенных полуоткрытых соединений).
   - `net.ipv4.ip_local_port_range = 1024 65535` (диапазон динамических портов для генератора нагрузки).

## Подводные камни

При тестировании сервера с локальной машины (`localhost` -> `127.0.0.1`) трафик идет через виртуальный loopback-интерфейс ядра Linux (`lo`). Сетевой стек loopback не выполняет аппаратную фрагментацию пакетов сетевой картой (TSO/GSO) и имеет гигантский MTU (обычно 65536 байт вместо стандартных 1500 байт Ethernet). Результаты тестов на `localhost` показывают идеальную картину, но при выходе в реальную сеть 10G/40G с реальными сетевыми задержками и размером MTU 1500 поведение буферов может существенно измениться!

## На собеседовании

**Вопрос на собеседовании (Lead Performance Engineer / SRE):**
«Что такое Coordinated Omission (скоординированный пропуск) в бенчмарках сетевых серверов, и почему стандартные замеры latency могут быть обманчиво оптимистичными?»

**Эталонный ответ:**
Coordinated Omission — фундаментальная ошибка многих генераторов нагрузки (например, старых версий JMeter или наивных скриптов на Go), работающих по принципу синхронных циклов `for { send(); recv() }`.
Если сервер зависает на 500 мс (например, из-за блокировки Event Loop или паузы GC), клиентский генератор тоже блокируется в ожидании ответа и **не отправляет новые запросы** во время этого сбоя. В результате в статистику попадает всего один «медленный» запрос, а тысячи запросов, которые должны были прийти в этот интервал и получить чудовищную задержку, просто не были отправлены! Реальная задержка p99 при этом искажается в десятки раз в лучшую сторону. Профессиональные генераторы (wrk2, tcpkali) используют генерацию запросов по расписанию независимо от времени отклика сервера.
