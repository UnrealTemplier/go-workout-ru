# Echo на gnet: Событийно-ориентированная модель и обход goroutine-per-connection

## Теория

Сетевая архитектура стандартной библиотеки Go (`net.Listen`, `net.Conn`) базируется на элегантной парадигме **«одна горутина на одно сетевое соединение»** (`goroutine-per-connection`). В этой модели каждая горутина выполняет блокирующий вызов `conn.Read()`. Под капотом среда выполнения Go переводит этот вызов в регистрацию дескриптора сокета в системном `netpoller` (использующем `epoll` на Linux, `kqueue` на macOS/FreeBSD). Когда в сокете нет данных, горутина переводится планировщиком GMP в статус `_Gwaiting`, освобождая поток `M` (`OS Thread`) для исполнения других задач.

Несмотря на потрясающую простоту и удобство разработки, классическая модель Go сталкивается с фундаментальными барьерами на экстремальных нагрузках (**C100K** и **C1M**):
1. **Потребление оперативной памяти под стек:** Начальный стек горутины составляет 2 КБ (с метаданными runtime — порядка 2.5–4 КБ). При 100 000 неактивных (idle keep-alive) соединениях только на пустые стеки горутин расходуется от 250 до 400 МБ RAM. При миллионе соединений оверхед достигает 2.5–4 ГБ.
2. **Накладные расходы планировщика (GMP Context Switching):** При высокой частоте коротких сетевых транзакций планировщик Go вынужден непрерывно переключать сотни тысяч горутин между очередями `runq`, что приводит к вымыванию процессорных кэшей L1d/L2 и высокой задержке хвостовых запросов (p99/p999 latency spikes).
3. **Аллокации в куче:** Передача данных через интерфейс `net.Conn` влечет за собой экранирование буферов в кучу (`heap escape analysis`), нагружая трехцветный сборщик мусора (GC).

Фреймворк **`gnet`** (`github.com/panjf2000/gnet/v2`) кардинально меняет сетевую архитектуру приложения, реализуя реакторный паттерн (**Reactor Pattern**) в пространстве пользователя (Userspace). Вместо модели «горутина на соединение» `gnet` использует строго фиксированное число потоков/горутин — **Event Loops** (обычно равное числу ядер процессора `runtime.NumCPU()`). 
Входящие сетевые события мультиплексируются системными вызовами `epoll_wait` пачками (batching syscalls), а данные из сокетов читаются непосредственно в циклические кольцевые буферы (ring buffers) без дополнительных копирований и аллокаций памяти.

## Решение по шагам

1. Импортируйте пакет `github.com/panjf2000/gnet/v2` и создайте структуру сервера, реализующую интерфейс `gnet.EventHandler`.
2. Реализуйте коллбэк `OnTraffic(c gnet.Conn) gnet.Action`. Внутри прочитайте поступившие байты методом `c.Next(-1)` и верните их обратно клиенту через `c.Write(buf)`.
3. Инициализируйте и запустите сервер функцией `gnet.Run(&echoServer{}, "tcp://:9000", opts...)`.
4. Настройте генератор нагрузки (`wrk` или `hey`) для проверки пропускной способности (Throughput) и сравнения с `net/http`.

## Код решения

**`server.go`**

```go
package main

import (
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

// EchoServer реализует сетевые обработчики gnet.EventHandler.
type EchoServer struct {
	gnet.BuiltinEventEngine
	addr string
}

// OnBoot вызывается при инициализации движка gnet перед открытием сокетов.
func (es *EchoServer) OnBoot(eng gnet.Engine) (action gnet.Action) {
	log.Printf("[gnet] Движок инициализирован на адресе %s\n", es.addr)
	return gnet.None
}

// OnOpen срабатывает при установке нового входящего TCP-соединения (после accept).
func (es *EchoServer) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	// Соединение успешно открыто, ресурсов под стек горутины не выделялось.
	return nil, gnet.None
}

// OnTraffic вызывается при поступлении сетевых пакетов в сокет (событие EPOLLIN).
func (es *EchoServer) OnTraffic(c gnet.Conn) (action gnet.Action) {
	// Читаем все доступные данные из кольцевого буфера сокета без аллокации
	buf, err := c.Next(-1)
	if err != nil {
		log.Printf("Ошибка чтения буфера: %v", err)
		return gnet.Close
	}

	// Отправляем эхо-ответ обратно клиенту
	if _, err := c.Write(buf); err != nil {
		log.Printf("Ошибка записи в сокет: %v", err)
		return gnet.Close
	}

	return gnet.None
}

// OnClose срабатывает при закрытии соединения со стороны клиента или сервера.
func (es *EchoServer) OnClose(c gnet.Conn, err error) (action gnet.Action) {
	return gnet.None
}

func main() {
	serverAddr := "tcp://127.0.0.1:9000"
	server := &EchoServer{addr: serverAddr}

	// Запуск gnet в режиме фиксированного числа реакторов
	err := gnet.Run(
		server,
		serverAddr,
		gnet.WithMulticore(true),
		gnet.WithReusePort(true),
	)
	if err != nil {
		log.Fatalf("Сбой запуска gnet сервера: %v", err)
	}
	fmt.Println("Сервер завершил работу")
}
```

## Под капотом

Под капотом архитектура `gnet` полностью отвязана от рантайм-планировщика Go:
1. **Userspace Event Loop:** Вместо системного `netpoller` Go, `gnet` создает системные потоки ОС (`runtime.LockOSThread()`) или ограниченный набор горутин, каждая из которых крутит цикл вызова `unix.EpollWait` с массивом структур `epoll_event`. За один сисколл извлекается пачка до сотен готовых файловых дескрипторов.
2. **Ring Buffer:** При наступлении события `EPOLLIN` данные считываются системным вызовом `readv` в циклический буфер памяти (elastic ring buffer). Метод `c.Next(-1)` возвращает срез (`slice`) прямо на этот внутренний буфер, избегая вызова аллокатора кучи `mallocgc`.
3. **Syscall Batching:** Ответы накапливаются во внутреннем буфере сокета и отправляются клиенту через пакетный `writev`, что сводит к минимуму общее количество переходов пользователя в ядро ОС (kernel context switches).

## Подводные камни

Главная ловушка реакторной модели: **категорически запрещено выполнять блокирующие операции** (I/O в базу данных, обращение к диску, тяжелые криптографические вычисления, вызовы `time.Sleep`) внутри метода `OnTraffic`. Поскольку один Event Loop обслуживает тысячи сетевых соединений одновременно, любая блокировка на 10 мс мгновенно заморозит обработку трафика для всех остальных клиентов, закрепленных за данным реактором!

## На собеседовании

**Вопрос на собеседовании (Senior Network Engineer / HighLoad Go Developer):**
«Почему gnet способен показать 1 000 000+ RPS на Echo-тестах, в то время как стандартный сервер net/http упирается в 200 000 – 300 000 RPS на той же машине?»

**Эталонный ответ:**
1. **Ликвидация оверхеда горутин:** В `net/http` на каждое соединение создаются 2 горутины (чтение и запись) плюс структуры `http.Request`/`http.response`. Это влечет вызовы `runtime.newstack`, переключения контекста GMP и существенную нагрузку на GC. В `gnet` сокеты мультиплексируются фиксированным числом потоков без создания горутин на запрос.
2. **Батчинг системных вызовов:** Стандартный стек Go выполняет `read()` и `write()` индивидуально для каждого пакета при пробуждении от `netpoller`. `gnet` считывает события пачками через `epoll_wait(..., events, maxevents, ...)`, уменьшая число переходов кольца привилегий CPU (ring 3 -> ring 0).
3. **Zero-Copy дизайн буферов:** `gnet` не копирует тело запроса в промежуточный `bytes.Buffer`, а предоставляет прямой указатель на кольцевой буфер `c.Next()`, нивелируя давление на сборщик мусора.
