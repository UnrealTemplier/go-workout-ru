# Length-prefixed protocol: Пользовательский буфер кольца и избежание лишних read()

## Условие

Реализуйте codec в `gnet`: каждое сообщение = 4 байта длина (big-endian) + payload. В `OnTraffic` читайте `c.InboundBuffered()`, парсите длину, ждёте полного сообщения. Объясните, почему `gnet` не вызывает `read()` на каждый байт, а буферизует в userspace ring buffer.

### Исходная формулировка

**Length-prefixed protocol.**: Реализуйте codec в `gnet`: каждое сообщение = 4 байта длина (big-endian) + payload. В `OnTraffic` читайте `c.InboundBuffered()`, парсите длину, ждёте полного сообщения. Объясните, почему `gnet` не вызывает `read()` на каждый байт, а буферизует в userspace ring buffer.

## Теория

Сетевой протокол TCP является **потоковым протоколом** (`stream-oriented protocol`), а не пакетным. Это означает, что TCP не сохраняет границы прикладных сообщений:
- Сообщение может быть разбито на несколько сегментов TCP (фрагментация).
- Несколько независимых сообщений могут быть склеены в один TCP-сегмент (пакетирование / склейка).

Для разделения сообщений в высокопроизводительных распределенных системах и RPC-фреймворках чаще всего применяется протокол с префиксом длины (**Length-Prefixed Framing**):
```
+-------------------+-----------------------------------+
| Length (4 байта)  | Payload (Length байт)             |
| Big-Endian uint32 | Бинарные данные / JSON / Protobuf |
+-------------------+-----------------------------------+
```

### Проблема традиционного чтения сокетов:
В наивной реализации под каждое сообщение разработчик делает:
1. `io.ReadFull(conn, headerBuf)` (чтение 4 байт длины) — системный вызов `read()`.
2. Парсинг размера \(L\).
3. `io.ReadFull(conn, payloadBuf)` (чтение \(L\) байт данных) — еще один системный вызов `read()`.

Если сервер обрабатывает 100 000 сообщений в секунду, такой подход совершит **200 000+ системных вызовов в секунду** только на чтение!

### Решение в gnet (Userspace Ring Buffer):
Движок `gnet` агрегирует поступающие данные в собственном кольцевом буфере в пространстве пользователя. 
В методе `OnTraffic(c gnet.Conn)`:
1. Метод `c.InboundBuffered()` возвращает общее число байт, доступных для чтения без единого системного вызова!
2. Если `c.InboundBuffered() < 4`, сообщение еще не доехало целиком — сервер просто возвращает `gnet.None`, дожидаясь следующего события.
3. Сервер читает 4 байта длины методом `c.Peek(4)` без их сдвига из буфера.
4. Если `c.InboundBuffered() < 4 + msgLen`, сервер также выходит без копирования.
5. Когда весь кадр в сборе, сервер извлекает полное сообщение и смещает указатель кольца вызовом `c.Discard(...)`.

## Решение по шагам

1. Определите заголовок протокола: 4 байта длины в формате `binary.BigEndian.Uint32`.
2. В обработчике `OnTraffic(c gnet.Conn)` организуйте цикл извлечения полных сообщений.
3. Используйте `c.InboundBuffered()` для проверки объема данных в кольцевом буфере.
4. Примените `c.Peek(4)` для чтения длины кадра без извлечения.
5. При накоплении полного кадра прочитайте данные и сместите указатель чтения через `c.Discard(totalLen)`.

## Код решения

**`codec_server.go`**

```go
package main

import (
	"encoding/binary"
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

const HeaderLen = 4

type LengthPrefixedServer struct {
	gnet.BuiltinEventEngine
}

func (s *LengthPrefixedServer) OnTraffic(c gnet.Conn) gnet.Action {
	// В одном сетевом событии может прийти сразу несколько склеенных сообщений,
	// поэтому обрабатываем их в цикле, пока буфер полон.
	for {
		buffered := c.InboundBuffered()
		if buffered < HeaderLen {
			// Меньше 4 байт — заголовок длины еще не получен целиком.
			// Ждем следующего OnTraffic без блокировки!
			return gnet.None
		}

		// Подглядываем первые 4 байта (Peek не сдвигает указатель чтения)
		header, err := c.Peek(HeaderLen)
		if err != nil {
			log.Printf("Ошибка Peek: %v", err)
			return gnet.Close
		}

		// Декодируем размер полезной нагрузки (Big Endian)
		payloadLen := int(binary.BigEndian.Uint32(header))
		totalMsgLen := HeaderLen + payloadLen

		if buffered < totalMsgLen {
			// Заголовок есть, но тело сообщения доехало не полностью.
			// Ждем докачки оставшихся байтов.
			return gnet.None
		}

		// Все сообщение целиком находится в кольцевом буфере gnet!
		fullMsg, err := c.Peek(totalMsgLen)
		if err != nil {
			log.Printf("Ошибка чтения сообщения: %v", err)
			return gnet.Close
		}

		payload := fullMsg[HeaderLen:totalMsgLen]
		// Обрабатываем сообщение (бизнес-логика)
		handleMessage(c, payload)

		// Сдвигаем указатель чтения в кольцевом буфере на размер обработанного кадра
		if _, err := c.Discard(totalMsgLen); err != nil {
			log.Printf("Ошибка Discard: %v", err)
			return gnet.Close
		}
	}
}

func handleMessage(c gnet.Conn, payload []byte) {
	// Формируем эхо-ответ с префиксом длины
	respPayload := append([]byte("ACK: "), payload...)
	resp := make([]byte, HeaderLen+len(respPayload))
	binary.BigEndian.PutUint32(resp[:HeaderLen], uint32(len(respPayload)))
	copy(resp[HeaderLen:], respPayload)

	_ = c.AsyncWrite(resp, nil)
}

func main() {
	server := &LengthPrefixedServer{}
	addr := "tcp://127.0.0.1:9003"
	log.Printf("Запуск Length-Prefixed Codec сервера на %s...\n", addr)
	if err := gnet.Run(server, addr, gnet.WithMulticore(true)); err != nil {
		log.Fatalf("Ошибка gnet: %v", err)
	}
}
```

**`client_test.go`**

```go
package main

import (
	"encoding/binary"
	"io"
	"net"
	"testing"
)

func TestLengthPrefixedCodec(t *testing.T) {
	conn, err := net.Dial("tcp", "127.0.0.1:9003")
	if err != nil {
		t.Skip("Сервер не запущен")
	}
	defer conn.Close()

	msg := []byte("HELLO_GNET_HIGHLOAD")
	frame := make([]byte, 4+len(msg))
	binary.BigEndian.PutUint32(frame[:4], uint32(len(msg)))
	copy(frame[4:], msg)

	// Отправляем пакет
	if _, err := conn.Write(frame); err != nil {
		t.Fatalf("Write: %v", err)
	}

	// Читаем заголовок ответа
	var respLen uint32
	if err := binary.Read(conn, binary.BigEndian, &respLen); err != nil {
		t.Fatalf("Read header: %v", err)
	}

	respBody := make([]byte, respLen)
	if _, err := io.ReadFull(conn, respBody); err != nil {
		t.Fatalf("Read body: %v", err)
	}

	expected := "ACK: HELLO_GNET_HIGHLOAD"
	if string(respBody) != expected {
		t.Errorf("Получено %q, ожидалось %q", string(respBody), expected)
	}
}
```

## Под капотом

Встроенный `RingBuffer` в `gnet` представляет собой структуру с виртуальными индексами чтения и записи (`read_ptr`, `write_ptr`), работающими по модулю размера буфера (обычно степень двойки, что позволяет вычислять остаток побитовым `& (size - 1)`).
Когда сетевая карта наполняет буфер сокета, `epoll_wait` оповещает реактор, который за **один вызов** `read()` заполняет кольцевой буфер до конца доступного окна. 
Методы `c.Peek()` и `c.Discard()` не производят системных вызовов в ядро: они манипулируют обычными указателями в памяти приложения, благодаря чему оверхед на разбор протокола становится почти нулевым.

## Подводные камни

Распространенная уязвимость протоколов с префиксом длины — атака **Memory Exhaustion (DoS)**. Если злоумышленник отправит фальшивый заголовок с `payloadLen = 4294967295` (максимальный `uint32` = 4 ГБ), наивный сервер начнет бесконечно ждать накопления 4 ГБ в буфере или аллоцирует огромный массив. Всегда ограничивайте максимальный допустимый размер кадра (например, `const MaxFrameSize = 16 * 1024 * 1024` — 16 МБ) и немедленно закрывайте сокет при его превышении!

## На собеседовании

**Вопрос на собеседовании (Senior Backend / Fintech Architect):**
«Каковы преимущества бинарного Length-Prefixed протокола перед протоколами с разделителями (Delimiter-Based, например \r\n в HTTP/1.1 или Redis RESP)?»

**Эталонный ответ:**
1. **Эффективность парсинга \(O(1)\):** В протоколе с префиксом длины размер кадра известен сразу после чтения первых 4 байт. Сервер выполняет прямую проверку `buffered >= 4 + L` и сдвигает указатель. В протоколах с разделителем парсер вынужден сканировать каждый отдельный байт потока в поиске символа `\n` (\(O(N)\)), что приводит к промахам кэша процессора и лишним ветвлениям (Branch Mispredictions).
2. **Произвольный бинарный Payload:** Length-Prefixed протокол прозрачен для любых бинарных данных (включая символы `0x00` и `\n`), не требуя экранирования байтов (escaping) или кодирования в Base64.
