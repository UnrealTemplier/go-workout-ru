# gnet Echo Server: Реализация полного жизненного цикла gnet.EventHandler

## Условие

Установи `github.com/panjf2000/gnet`. Напиши Echo-сервер, реализующий интерфейс `gnet.EventHandler` (`OnInit`, `OnTraffic`, `OnClose`). Запусти его в одном потоке (`WithNumEventLoop(1)`).

### Исходная формулировка

**[gnet Echo Server]**: Установи `github.com/panjf2000/gnet`. Напиши Echo-сервер, реализующий интерфейс `gnet.EventHandler` (`OnInit`, `OnTraffic`, `OnClose`). Запусти его в одном потоке (`WithNumEventLoop(1)`).

## Теория

Для полного контроля над жизненным циклом сетевых соединений `gnet` предоставляет контракт интерфейса **`gnet.EventHandler`**.

В отличие от стандартного интерфейса Go `net.Conn`, где чтение и закрытие вызываются императивно, архитектура `gnet` является строго декларативной и управляемой событиями (**Event-Driven Framework**).

### Методы интерфейса `gnet.EventHandler`:
- **`OnBoot(eng gnet.Engine) (action gnet.Action)`:** Вызывается один раз при инициализации движка. Здесь инициализируются глобальные ресурсы, пулы памяти и метрики.
- **`OnOpen(c gnet.Conn) (out []byte, action gnet.Action)`:** Срабатывает сразу после завершения TCP 3-way handshake. Если сервер хочет немедленно отправить приветственное сообщение (например, баннер SSH или приветствие SMTP), он может вернуть срез байт в `out`.
- **`OnTraffic(c gnet.Conn) (action gnet.Action)`:** Главный обработчик входящего трафика. Вызывается при готовности данных в сокете.
- **`OnClose(c gnet.Conn, err error) (action gnet.Action)`:** Вызывается при закрытии сокета со стороны удаленного узла (FIN/RST) либо по инициативе сервера. Гарантирует очистку контекста соединения.
- **`OnTick() (delay time.Duration, action gnet.Action)`:** Опциональный таймер, вызываемый циклически внутри Event Loop (для heartbeat, сбора метрик или очистки протухших сессий без создания фоновых горутин).

## Решение по шагам

1. Создайте структуру сервера, реализующую все методы интерфейса `gnet.EventHandler`.
2. Реализуйте инициализацию контекста сессии в `OnOpen` с помощью метода `c.SetContext(...)`.
3. В `OnTraffic` извлеките контекст сессии через `c.Context()`, обработайте данные и отправьте эхо.
4. В `OnClose` гарантированно освободите ресурсы соединения.
5. Запустите сервер в строго однопоточном режиме с помощью опции `gnet.WithNumEventLoop(1)`.

## Код решения

**`lifecycle_server.go`**

```go
package main

import (
	"fmt"
	"log"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// SessionState хранит контекст отдельного клиентского подключения
type SessionState struct {
	ID        int64
	OpenedAt  time.Time
	BytesRead int64
}

type SingleLoopEchoServer struct {
	gnet.BuiltinEventEngine
	connCounter int64
}

// OnBoot инициализирует сервер
func (s *SingleLoopEchoServer) OnBoot(eng gnet.Engine) (action gnet.Action) {
	log.Println("[SingleLoop] Сервер успешно загружен и готов принимать соединения")
	return gnet.None
}

// OnOpen инициализирует состояние сессии
func (s *SingleLoopEchoServer) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	id := atomic.AddInt64(&s.connCounter, 1)
	state := &SessionState{
		ID:       id,
		OpenedAt: time.Now(),
	}
	// Сохраняем состояние сессии в метаданных соединения
	c.SetContext(state)

	// Отправляем приветственный баннер без heap-аллокаций
	welcome := []byte(fmt.Sprintf("WELCOME_CONN_%d\n", id))
	return welcome, gnet.None
}

// OnTraffic обрабатывает входящие данные
func (s *SingleLoopEchoServer) OnTraffic(c gnet.Conn) (action gnet.Action) {
	state, ok := c.Context().(*SessionState)
	if !ok {
		return gnet.Close
	}

	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	state.BytesRead += int64(len(buf))

	// Эхо-ответ
	if _, err := c.Write(buf); err != nil {
		return gnet.Close
	}

	return gnet.None
}

// OnClose очищает контекст соединения
func (s *SingleLoopEchoServer) OnClose(c gnet.Conn, err error) (action gnet.Action) {
	if state, ok := c.Context().(*SessionState); ok {
		duration := time.Since(state.OpenedAt)
		log.Printf("[Conn %d] Закрыто. Время жизни: %v, Обработано байт: %d, Ошибка: %v\n",
			state.ID, duration, state.BytesRead, err)
	}
	return gnet.None
}

func main() {
	server := &SingleLoopEchoServer{}
	addr := "tcp://127.0.0.1:9006"

	log.Printf("Запуск однопоточного gnet сервера (1 EventLoop) на %s...\n", addr)

	// Запуск в строго одном потоке (NumEventLoop = 1)
	err := gnet.Run(
		server,
		addr,
		gnet.WithNumEventLoop(1),
		gnet.WithMulticore(false),
	)
	if err != nil {
		log.Fatalf("Ошибка gnet: %v", err)
	}
}
```

ℹ️ Полная реализация жизненного цикла gnet.EventHandler в однопоточном режиме

## Под капотом

Внутри `gnet` объект `c gnet.Conn` не является интерфейсной оберткой вокруг файлового дескриптора на каждую операцию. Это долгоживущая структура, которая переиспользуется из внутреннего пула объектов ядра `gnet`. 
Поле `c.SetContext(val)` позволяет ассоциировать любые пользовательские данные с соединением. Это исключает необходимость заводить внешнюю потокобезопасную карту `sync.Map` для хранения сессий: пока соединение живо, контекст доступен по прямому указателю без синхронизации мьютексами, поскольку вызовы `OnTraffic` для данного сокета гарантированно последовательны в рамках одного Event Loop!

## Подводные камни

Хотя `c.Context()` доступен без синхронизации внутри методов `OnTraffic` и `OnClose`, если вы передаете указатель на этот контекст в сторонние горутины (Worker Pool), возникает состояние гонки данных (**Data Race**). Либо копируйте состояние, либо используйте атомики внутри полей `SessionState`.

## На собеседовании

**Вопрос на собеседовании (Senior Go Developer / Infrastructure):**
«Зачем в gnet предусмотрен метод OnTick(), если в Go можно в любой момент запустить горутину с time.NewTicker()? В чем преимущество OnTick с точки зрения профилирования CPU?»

**Эталонный ответ:**
Каждая отдельная горутина с `time.Ticker` требует отдельного стека памяти, а срабатывание таймера в рантайме Go приводит к пробуждению планировщика GMP (`sysmon` или runtime timer heap) и переключению контекста на поток `M`.
Метод `OnTick()` исполняется прямо внутри самого цикла `epoll_wait` (за счет таймаута системного вызова epoll). Это гарантирует, что периодическая работа (heartbeat сокетов, сброс метрик) выполняется в контексте уже активного сетевого потока без создания горутин, без захвата блокировок планировщика и с минимальным CPU cache miss.
