## Теория

Создание собственного высокопроизводительного сервера баз данных класса Redis в оперативной памяти — вершина мастерства бэкенд-инженера.

### Архитектурные требования:
1. **100 000 одновременных подключений:** Соединения удерживаются событийно-ориентированным движком `gnet` без создания 100K горутин.
2. **Память процесса не более 20–30 МБ:** Отсутствие персональных стеков горутин на сокет.
3. **Сотни тысяч RPS:** Zero-Copy парсинг протокола RESP (`*`, `$`, `\r\n`).
4. **Шардированное хранилище данных (Partitioned In-Memory Store):**
   Чтобы избежать конкуренции за глобальный мьютекс `sync.RWMutex` между всеми ядрами CPU, хранилище делится на \(K\) независимых шардов (обычно 64 или 256):
   ```
   ShardIndex = FNV64(key) % 64
   ```
   Каждый шард защищен собственным локальным мьютексом, снижая конкуренцию (Contention) практически до нуля.

## Решение по шагам

1. Спроектируйте шардированную структуру `ShardedMap` с 64 сегментами.
2. Реализуйте функцию хеширования FNV-1a для быстрого вычисления индекса шарда.
3. Интегрируйте Zero-Copy парсер протокола RESP.
4. Реализуйте базовые команды Redis: `PING`, `SET key val`, `GET key`, `DEL key`.
5. Проверьте работу сервера стандартной консольной утилитой `redis-cli` и бенчмарком `redis-benchmark`.

## Код решения

**`mini_redis.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"log"
	"runtime"
	"sync"
	"unsafe"

	"github.com/panjf2000/gnet/v2"
)

const NumShards = 64

// Shard представляет собой изолированный сегмент хранилища со своим мьютексом
type Shard struct {
	sync.RWMutex
	data map[string][]byte
}

type ShardedStore struct {
	shards [NumShards]*Shard
}

func NewShardedStore() *ShardedStore {
	store := &ShardedStore{}
	for i := 0; i < NumShards; i++ {
		store.shards[i] = &Shard{
			data: make(map[string][]byte),
		}
	}
	return store
}

func fnvHash(key string) uint32 {
	var h uint32 = 2166136261
	for i := 0; i < len(key); i++ {
		h ^= uint32(key[i])
		h *= 16777619
	}
	return h
}

func (s *ShardedStore) Get(key string) ([]byte, bool) {
	shard := s.shards[fnvHash(key)%NumShards]
	shard.RLock()
	val, ok := shard.data[key]
	shard.RUnlock()
	return val, ok
}

func (s *ShardedStore) Set(key string, val []byte) {
	shard := s.shards[fnvHash(key)%NumShards]
	shard.Lock()
	shard.data[key] = val
	shard.Unlock()
}

type MiniRedisEngine struct {
	gnet.BuiltinEventEngine
	store *ShardedStore
}

func (e *MiniRedisEngine) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Разбор команд (RESP или Inline)
	if bytes.Equal(bytes.TrimSpace(buf), []byte("PING")) {
		_, _ = c.Write([]byte("+PONG\r\n"))
		return gnet.None
	}

	// Упрощенный парсинг бинарного протокола RESP
	if len(buf) > 0 && buf[0] == '*' {
		e.handleRESP(c, buf)
	}

	return gnet.None
}

func (e *MiniRedisEngine) handleRESP(c gnet.Conn, buf []byte) {
	// Декодирование аргументов
	lines := bytes.Split(buf, []byte("\r\n"))
	var args [][]byte
	for i := 1; i < len(lines); i++ {
		if len(lines[i]) > 0 && lines[i][0] != '$' {
			args = append(args, lines[i])
		}
	}

	if len(args) == 0 {
		return
	}

	cmd := bytes.ToUpper(args[0])
	switch string(cmd) {
	case "PING":
		_, _ = c.Write([]byte("+PONG\r\n"))
	case "SET":
		if len(args) >= 3 {
			key := unsafeString(args[1])
			val := make([]byte, len(args[2]))
			copy(val, args[2])
			e.store.Set(key, val)
			_, _ = c.Write([]byte("+OK\r\n"))
		}
	case "GET":
		if len(args) >= 2 {
			key := unsafeString(args[1])
			if val, ok := e.store.Get(key); ok {
				_, _ = c.Write([]byte(fmt.Sprintf("$%d\r\n%s\r\n", len(val), val)))
			} else {
				_, _ = c.Write([]byte("$-1\r\n"))
			}
		}
	default:
		_, _ = c.Write([]byte("-ERR unknown command\r\n"))
	}
}

func unsafeString(b []byte) string {
	if len(b) == 0 {
		return ""
	}
	return unsafe.String(&b[0], len(b))
}

func main() {
	redis := &MiniRedisEngine{
		store: NewShardedStore(),
	}
	addr := "tcp://127.0.0.1:6380"

	log.Printf("Запуск мини-клона Redis на %s (Ядер: %d, Шардов: %d)...\n",
		addr, runtime.NumCPU(), NumShards)
	fmt.Println("Тестируйте через: redis-benchmark -p 6380 -t set,get -q -c 1000 -n 100000")

	err := gnet.Run(
		redis,
		addr,
		gnet.WithMulticore(true),
		gnet.WithReusePort(true),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
	)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

## Под капотом

В оригинальном сервере Redis используется один поток (Single-Threaded Reactor). Это избавляет Redis от любых мьютексов.
В нашей Go-реализации на базе `gnet` задействованы **все ядра процессора** (Multi-Reactor). Чтобы потоки реакторов не конфликтовали за общую память, мы применили шардирование по хешу ключа `FNV-1a % 64`. 
Поскольку вероятность попадания двух потоков в один и тот же шард невелика, время удержания блокировки составляет доли наносекунды, обеспечивая линейное масштабирование RPS по мере добавления процессорных ядер.

## Подводные камни

В оригинальном Redis протокол RESP2/RESP3 поддерживает конвейеризацию (Pipelining). Если клиент отправляет 50 команд в одном пакете, парсер обязан разобрать и выполнить все 50 команд, собрав ответы в один буфер перед вызовом `Write()`. Если отправлять ответ на каждую команду отдельным системным вызовом `Write()`, пропускная способность упадет в разы из-за оверхеда TCP ACK и системных вызовов.

## На собеседовании

**Вопрос на собеседовании (Principal Architect / Database Engine Developer):**
«Почему Redis 6.0 внедрил многопоточность исключительно для операций сокетного I/O, оставив исполнение команд строго однопоточным?»

**Эталонный ответ:**
Сальваторе Санфилиппо (antirez) пришел к выводу, что узким местом современного сервера баз данных в памяти является не исполнение команд (поиск в хеш-таблице занимает наносекунды), а **сетевой ввод-вывод**: чтение байтов из сокета, системные вызовы `read()`/`write()` и парсинг протокола RESP.
В Redis 6.0 сеть была вынесена в параллельные потоки (I/O Threads), а манипуляции со структурами данных остались в одном главном потоке. Это позволило увеличить RPS более чем в 2 раза без внедрения сложных блокировок, мьютексов и риска состояния гонки при операциях со словарем данных.
