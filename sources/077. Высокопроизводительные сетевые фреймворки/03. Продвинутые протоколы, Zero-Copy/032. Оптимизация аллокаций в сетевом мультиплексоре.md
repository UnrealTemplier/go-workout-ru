# Оптимизация аллокаций в сетевом мультиплексоре: Внутренний gnet.RingBuffer и минимизация GC

## Условие

Напишите `gnet`-сервер, который распределяет поступающие тяжелые задачи по неблокирующему пулу воркеров (Worker Pool). Для того чтобы избежать выделения памяти (garbage) при чтении входящих пакетов, используйте встроенный в `gnet` кольцевой буфер `gnet.RingBuffer` для переиспользования байтовых массивов и минимизации нагрузки на сборщик мусора Go.

## Теория

Завершающее упражнение главы посвящено глубокому анатомическому анализу внутреннего механизма **`RingBuffer`** (кольцевого буфера памяти) во фреймворке `gnet` и ликвидации аллокаций мусора при обработке тяжелых потоков данных.

### Анатомия циклического кольцевого буфера:
В стандартных слайсах Go при удалении обработанных элементов в начале массива разработчик вынужден либо сдвигать оставшиеся байты влево вызовом `copy(buf, buf[n:])` (\(O(N)\), трата тактов CPU), либо создавать новый слайс в куче.

В кольцевом буфере память организована по кругу фиксированного размера \(S\) (степень двойки, \(S = 2^k\)):
```
        [0]  [1]  [2]  [3]  [4]  [5]  [6]  [7]
         ▲                   ▲
         │                   │
      ReadPtr             WritePtr
```
- **Запись:** Новые байты из сокета пишутся по индексу `WritePtr`. Указатель увеличивается: `WritePtr = (WritePtr + n) & (S - 1)`.
- **Чтение:** Приложение читает байты по индексу `ReadPtr`. Указатель увеличивается: `ReadPtr = (ReadPtr + n) & (S - 1)`.
- **Нулевые аллокации:** Память выделяется один раз при создании сокета. Никаких перемещений элементов (`memcpy`) не происходит! Если буфер переполняется, его емкость удваивается (Elastic Expansion).

Использование встроенных методов `c.InboundBuffered()`, `c.Peek()` и `c.Discard()` позволяет проводить сложнейший сетевой анализ без создания ни одного временного объекта в куче Go.

## Решение по шагам

1. Изучите принципы кольцевой адресации через побитовое умножение `index & (capacity - 1)`.
2. Реализуйте оптимизированный сетевой обработчик, проводящий разбор потока исключительно через методы `c.Peek` и `c.Discard`.
3. Запустите бенчмарк памяти с профилированием аллокаций: `go test -bench . -benchmem`.
4. Подтвердите нулевое потребление памяти (0 B/op, 0 allocs/op) на всем цикле обработки пакетов.

## Код решения

**`ring_buffer_tuning.go`**

```go
package main

import (
	"encoding/binary"
	"fmt"
	"log"
	"runtime"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// ZeroAllocMetricServer демонстрирует работу с кольцевым буфером с нулевыми аллокациями
type ZeroAllocMetricServer struct {
	gnet.BuiltinEventEngine
	totalPackets int64
}

func (s *ZeroAllocMetricServer) OnTraffic(c gnet.Conn) gnet.Action {
	for {
		// 1. Проверяем доступный объем данных в кольцевом буфере
		buffered := c.InboundBuffered()
		if buffered < 8 { // Минимальный телеметрический пакет: 4 байта ID + 4 байта Value
			return gnet.None
		}

		// 2. Заглядываем в кольцевой буфер без аллокаций
		data, err := c.Peek(8)
		if err != nil {
			return gnet.Close
		}

		// 3. Декодируем поля пакета через ассемблерные инструкции BSWAP
		metricID := binary.BigEndian.Uint32(data[:4])
		metricVal := binary.BigEndian.Uint32(data[4:8])

		// Исполняем вычисления над метрикой на месте (in-place)
		_ = metricID
		_ = metricVal

		// 4. Сдвигаем указатель чтения в кольцевом буфере на 8 байт
		if _, err := c.Discard(8); err != nil {
			return gnet.Close
		}

		s.totalPackets++
	}
}

func main() {
	server := &ZeroAllocMetricServer{}
	addr := "tcp://127.0.0.1:9032"

	// Мониторинг GC пауз и аллокаций
	go func() {
		var m runtime.MemStats
		ticker := time.NewTicker(3 * time.Second)
		for range ticker.C {
			runtime.ReadMemStats(&m)
			fmt.Printf("[RING-BUFFER TUNING] Обработано пакетов: %d | TotalAlloc: %d KB | NumGC: %d\n",
				server.totalPackets, m.TotalAlloc/1024, m.NumGC)
		}
	}()

	log.Printf("Запуск Zero-Allocation сетевого мультиплексора на %s...\n", addr)

	err := gnet.Run(
		server,
		addr,
		gnet.WithMulticore(true),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
		gnet.WithReadBufferCap(64*1024), // Начальная емкость кольцевого буфера 64 KB
	)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

ℹ️ Предельно оптимизированный обработчик с нулевыми аллокациями памяти поверх RingBuffer

## Под капотом

Когда сетевая карта принимает трафик, `gnet` выполняет вызов системного вызова `readv(fd, iov, 2)`. В структуре `iovec` передаются два сегмента:
1. `iov[0]` указывает от текущего индекса записи до конца кольцевого массива памяти.
2. `iov[1]` указывает от начала массива до индекса чтения.
Ядро Linux за один системный вызов заполняет оба непрерывных сегмента. Это исключает необходимость кольцевого выравнивания или сдвига байт в пользовательском пространстве, обеспечивая максимальную скорость обмена данными между ядром ОС и приложением на Go.

## Подводные камни

Если приложение сохраняет ссылку на срез байт `data`, возвращенный методом `c.Peek()`, за пределами вызова `c.Discard()`, эти данные будут перезаписаны ядром в момент следующего сетевого события. Если данные необходимо сохранить для долговременного использования, всегда выполняйте явное копирование в собственный буфер.

## На собеседовании

**Вопрос на собеседовании (Principal Performance Architect / Staff Engineer):**
«Каковы ключевые инженерные компромиссы (Trade-offs) между использованием системного кольцевого буфера (Userspace Ring Buffer) и аллокацией свежих срезов памяти под каждый запрос?»

**Эталонный ответ:**
- **Userspace Ring Buffer (gnet, Netty):**
  - *Плюсы:* Нулевая нагрузка на сборщик мусора Go, отсутствие пауз GC Stop-The-World, стабильная хвостовая задержка p999, низкий расход оперативной памяти.
  - *Минусы:* Опасность повреждения данных при преждевременном сдвиге буфера, необходимость ручного управления временем жизни срезов байтов, сложность отладки гонок данных.
- **Свежие срезы в куче (Standard net/http):**
  - *Плюсы:* 100% безопасность памяти (Memory Safety), данные изолированы и принадлежат конкретной горутине, тривиальная читаемость кода.
  - *Минусы:* Высокое давление на GC при сотнях тысяч RPS, фрагментация памяти, деградация латентности при пиковых нагрузках.
