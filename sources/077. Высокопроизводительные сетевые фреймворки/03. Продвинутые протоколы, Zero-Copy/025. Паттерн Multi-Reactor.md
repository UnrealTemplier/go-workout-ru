# Паттерн Multi-Reactor: Архитектура Main Reactor и Sub-Reactors в gnet

## Условие

В отличие от горутин, `gnet` запускает ровно столько потоков, сколько ядер у твоего CPU (Event Loops). Главный реактор (Main Reactor) принимает соединения (`Accept`), а Sub-реакторы слушают события `Read/Write` и вызывают твои коллбеки (`OnTraffic`). Запусти свой сервер с флагом `Multicore: true`.

### Исходная формулировка

**Паттерн Multi-Reactor**: В отличие от горутин, `gnet` запускает ровно столько потоков, сколько ядер у твоего CPU (Event Loops). Главный реактор (Main Reactor) принимает соединения (`Accept`), а Sub-реакторы слушают события `Read/Write` и вызывают твои коллбеки (`OnTraffic`). Запусти свой сервер с флагом `Multicore: true`.

## Теория

Архитектурный паттерн **Multi-Reactor** (также известный как Master-Worker Reactor) является стандартом де-факто в мировой индустрии высокопроизводительных серверов (Nginx, Netty, Envoy, Node.js cluster, gnet).

### Внутреннее разделение ролей:

```
                      [ Сетевые клиенты (TCP Connect) ]
                                      │
                                      ▼
                      ┌───────────────────────────────┐
                      │  Main Reactor (Acceptor Loop) │
                      │       - epoll_wait            │
                      │       - accept4(listen_fd)    │
                      └───────────────┬───────────────┘
                                      │ (Round-Robin / Least-Conns)
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
    ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
    │  Sub-Reactor 0   │    │  Sub-Reactor 1   │    │  Sub-Reactor 2   │
    │  - epoll 0       │    │  - epoll 1       │    │  - epoll 2       │
    │  - Sockets: 0..K │    │  - Sockets: 0..K │    │  - Sockets: 0..K │
    │  - OnTraffic()   │    │  - OnTraffic()   │    │  - OnTraffic()   │
    └──────────────────┘    └──────────────────┘    └──────────────────┘
```

1. **Главный реактор (Main Reactor / Acceptor):**
   - Выполняет ровно одну задачу: непрерывно ожидает события готовности слушающего сокета (`EPOLLIN` на `listen_fd`) и вызывает системный вызов `accept4()`.
   - Получив новый дескриптор `client_fd`, Main Reactor не читает из него данные! Он выбирает один из дочерних Sub-реакторов по заданному алгоритму балансировки (Load Balancer) и регистрирует дескриптор в `epoll` выбранного Sub-реактора.
2. **Дочерние реакторы (Sub-Reactors / Worker Loops):**
   - Число дочерних реакторов строго равно числу процессорных ядер (`NumCPU`).
   - Каждый Sub-Reactor имеет собственный независимый инстанс `epoll`.
   - При появлении данных в сокете Sub-Reactor считывает байты и вызывает пользовательский обработчик `OnTraffic()`.

Преимущество: полное отсутствие взаимных блокировок между процессами `accept()` и передачей данных, а также равномерная утилизация всех ядер CPU.

## Решение по шагам

1. Инициализируйте `gnet` с опцией `gnet.WithMulticore(true)`.
2. Задайте алгоритм балансировки между Sub-реакторами `gnet.WithLoadBalancing(gnet.RoundRobin)`.
3. В обработчике `OnOpen` выведите идентификатор соединения и адрес клиента.
4. Запустите сервер и убедитесь через `pidstat -t -p <PID>`, что создано ровно \(N\) потоков, равномерно нагружающих процессор.

## Код решения

**`multi_reactor_demo.go`**

```go
package main

import (
	"fmt"
	"log"
	"runtime"
	"sync/atomic"

	"github.com/panjf2000/gnet/v2"
)

type MultiReactorEngine struct {
	gnet.BuiltinEventEngine
	totalConns int64
}

func (e *MultiReactorEngine) OnBoot(eng gnet.Engine) gnet.Action {
	log.Printf("[Multi-Reactor] Инициализирован Главный Реактор (Main Reactor) и %d Sub-Реакторов\n",
		runtime.NumCPU())
	return gnet.None
}

func (e *MultiReactorEngine) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	connID := atomic.AddInt64(&e.totalConns, 1)
	if connID%1000 == 0 {
		log.Printf("[Main Reactor] Принято %d соединений. Клиент %s привязан к Sub-Reactor\n",
			connID, c.RemoteAddr())
	}
	return nil, gnet.None
}

func (e *MultiReactorEngine) OnTraffic(c gnet.Conn) gnet.Action {
	// Исполняется локальным Sub-Reactor
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Отправляем эхо-ответ
	_, _ = c.Write(buf)
	return gnet.None
}

func main() {
	engine := &MultiReactorEngine{}
	addr := "tcp://127.0.0.1:9025"

	fmt.Printf("Запуск сервера Multi-Reactor на %s (Ядер CPU: %d)...\n", addr, runtime.NumCPU())

	err := gnet.Run(
		engine,
		addr,
		gnet.WithMulticore(true),
		gnet.WithLoadBalancing(gnet.RoundRobin),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
	)
	if err != nil {
		log.Fatalf("Ошибка запуска: %v", err)
	}
}
```

ℹ️ Паттерн Multi-Reactor с распределением соединений по алгоритму Round-Robin

## Под капотом

В исходном коде `gnet` при `WithMulticore(true)` создается структура `engine`:
1. Создается массив структур `subEventLoop` размером `NumEventLoop`.
2. Каждый `subEventLoop` в конструкторе вызывает `unix.EpollCreate1(0)` и запускает отдельную горутину, привязанную к потоку ОС (`runtime.LockOSThread()`).
3. Слушающий сокет `listener` регистрируется в отдельном `mainLoop`. Когда `mainLoop` принимает клиентский сокет `fd` через `accept4`, он вызывает `lb.register(c)`, который добавляет `fd` в `epoll` соответствующего `subEventLoop` с помощью системного вызова `epoll_ctl(sub_epfd, EPOLL_CTL_ADD, fd, &ev)`.

## Подводные камни

Если один из клиентов отправляет непрерывный поток данных гигантского объема (например, заливает файл 10 ГБ по TCP со скоростью 10 Gbps), соответствующий Sub-Reactor будет непрерывно загружен обработкой его пакетов, что приведет к задержке обработки других клиентов, оказавшихся на этом же Sub-Reactor. В промышленных системах для защиты применяют квоты на объем вычитывания байт за одну итерацию (Rate Limiting per Connection / Fair Dispatch).

## На собеседовании

**Вопрос на собеседовании (Staff Engineer / Distributed Systems):**
«В чем разница между архитектурой Nginx (Process-per-Core + SO_REUSEPORT) и Netty/gnet (Multi-Reactor с потоками в одном адресном пространстве)?»

**Эталонный ответ:**
- **Nginx (Multi-Process):** Архитектура с независимыми процессами (Master + N Workers). Процессы изолированы на уровне виртуальной памяти: если один воркер упадет с Segfault, остальные продолжат работу. Однако межпроцессный обмен (IPC / Shared Memory) сложен и требует мьютексов в разделяемой памяти (`shm`).
- **Netty / gnet (Multi-Threaded):** Все реакторы работают в едином адресном пространстве одного процесса. Это дает мгновенный обмен данными через указатели без копирования (`Zero-Copy IPC`), общие пулы памяти (`sync.Pool`) и простоту управления состоянием, но требует строгой потокобезопасности.
