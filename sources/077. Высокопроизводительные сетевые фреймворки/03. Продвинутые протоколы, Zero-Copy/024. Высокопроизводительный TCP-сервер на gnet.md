# Высокопроизводительный TCP-сервер на gnet: Сравнение памяти под 50 000 соединений

## Условие

Установите популярный асинхронный сетевой фреймворк `github.com/panjf2000/gnet/v2` (работающий по событийно-ориентированной модели epoll/kqueue в пользовательском пространстве). Реализуйте на нем Echo-сервер, обрабатывающий события жизненного цикла соединений: `OnBoot`, `OnOpen`, `OnTraffic`. Сравните потребление памяти этим сервером и вашим стандартным TCP-сервером из раздела №23 под нагрузкой в 50 000 неактивных (keep-alive) соединений.

## Теория

Кульминацией первого блока изучения сетевых реакторов является практическое сравнение потребления системных ресурсов между стандартным сервером Go (`net.Listen`) и фреймворком `gnet/v2` под реальной нагрузкой в **50 000 одновременных соединений (C50K)**.

### Профиль потребления ресурсов при 50 000 соединений:

1. **Стандартный `net.Listen` (модель goroutine-per-connection):**
   - Количество горутин: 50 000+ горутин.
   - Физический стек горутин: \(50\,000 \times 2048 \text{ байт} = 102.4 \text{ МБ}\).
   - С учетом служебных структур `runtime.g`, буферов `bufio` и дескрипторов сокетов реальный Resident Set Size (RSS) процесса составляет **от 150 до 250 МБ** оперативной памяти.
   - Время одного прохода сборщика мусора (GC Mark): 3–8 мс на сканирование 50 000 стеков.

2. **Событийно-ориентированный `gnet/v2` (Multi-Reactor):**
   - Количество горутин: ровно \(N\) (по числу ядер CPU, например 8 или 16).
   - Физический стек горутин: 8 горутин \(\times\) 4 КБ = 32 КБ.
   - Сокеты мультиплексируются в системных вызовах `epoll_wait`.
   - Реальный Resident Set Size (RSS) процесса составляет **всего 12–20 МБ**!
   - Время одного прохода сборщика мусора (GC Mark): менее 0.05 мс.

## Решение по шагам

1. Разверните полноценный сервер на `gnet/v2` с обработчиками `OnBoot`, `OnOpen`, `OnTraffic`.
2. Подключите мониторинг системной памяти через `runtime.ReadMemStats`.
3. Настройте системные лимиты дескрипторов `ulimit -n 100000`.
4. С помощью отдельного нагрузочного скрипта откройте 50 000 keep-alive соединений.
5. Зафиксируйте показатели `RSS` в `htop`/`ps` и сравните со стандартным Go-сервером.

## Код решения

**`c50k_server.go`**

```go
package main

import (
	"fmt"
	"log"
	"runtime"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

type C50KServer struct {
	gnet.BuiltinEventEngine
	activeConns int64
}

func (s *C50KServer) OnBoot(eng gnet.Engine) gnet.Action {
	log.Printf("[C50K Engine] Запущен на %d реакторах. Готов к 50 000 соединений!\n", runtime.NumCPU())
	return gnet.None
}

func (s *C50KServer) OnOpen(c gnet.Conn) ([]byte, gnet.Action) {
	atomic.AddInt64(&s.activeConns, 1)
	return nil, gnet.None
}

func (s *C50KServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}
	// Мгновенное эхо
	_, _ = c.Write(buf)
	return gnet.None
}

func (s *C50KServer) OnClose(c gnet.Conn, err error) gnet.Action {
	atomic.AddInt64(&s.activeConns, -1)
	return gnet.None
}

func main() {
	server := &C50KServer{}
	addr := "tcp://127.0.0.1:9024"

	// Мониторинг памяти каждые 3 секунды
	go func() {
		var m runtime.MemStats
		ticker := time.NewTicker(3 * time.Second)
		defer ticker.Stop()

		for range ticker.C {
			runtime.ReadMemStats(&m)
			fmt.Printf("[C50K MONITOR] Активных сокетов: %6d | Горутин: %3d | Память стека: %6.2f MB | Sys RSS: %6.2f MB\n",
				atomic.LoadInt64(&server.activeConns),
				runtime.NumGoroutine(),
				float64(m.StackInuse)/(1024*1024),
				float64(m.Sys)/(1024*1024),
			)
		}
	}()

	log.Printf("Запуск C50K сервера на %s...\n", addr)
	err := gnet.Run(
		server,
		addr,
		gnet.WithMulticore(true),
		gnet.WithReusePort(true),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
	)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

## Под капотом

Почему разница в потреблении памяти столь радикальна:
В операционной системе Linux файловый дескриптор сокета (`struct file` / `struct socket`) весит в ядре около 1–2 КБ. 
Однако в стандартной модели Go поверх этого дескриптора создаются:
1. `runtime.g` (структура горутины).
2. Выделенный непрерывный стек памяти размером минимум 2048 байт.
3. Структуры `pollDesc` и дескриптор `net.netFD`.
В `gnet` все эти 50 000 сокетов просто регистрируются в массиве структур `epoll_event` ядра Linux. В адресном пространстве Go создается только компактная структура `conn` без выделения персонального стека горутины, что снижает оверхед до абсолютного теоретического минимума.

## Подводные камни

При тестировании 50 000 соединений на Linux система может начать аварийно разрывать соединения с ошибкой `connection refused`. Это происходит из-за исчерпания диапазона локальных исходящих портов (Ephemeral Ports). Для генератора нагрузки необходимо расширить диапазон:
`sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"` и включить повторное использование сокетов: `sudo sysctl -w net.ipv4.tcp_tw_reuse=1`.

## На собеседовании

**Вопрос на собеседовании (Principal Infrastructure Architect):**
«Если gnet потребляет в 11 раз меньше памяти и работает быстрее, почему сама команда разработки Go (Go Team) не сделает Event Loop стандартной моделью в пакете net?»

**Эталонный ответ:**
Философия языка Go ставит во главу угла **простоту разработки, читаемость кода и надежность (Developer Experience)**.
Модель «горутина на соединение» позволяет любому разработчику писать простой синхронный линейный код:
`data := read(); process(data); write(response)`.
Переход на реакторную модель (`Event Loop`) вынуждает разработчика:
1. Вручную управлять машинами состояний (State Machines) при фрагментации кадров.
2. Никогда не делать блокирующих вызовов в Event Loop (любой случайный вызов СУБД ложит весь сервер).
3. Вручную жонглировать пулами воркеров, очередями задач и контролировать время жизни срезов байтов.
Для 99% стандартных бизнес-приложений оверхед в 50-100 МБ памяти полностью оправдан удобством разработки. Специализированные реакторы применяются точечно там, где цена железа или жесткие требования к задержке становятся критическими.
