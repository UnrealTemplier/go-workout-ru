# HTTP-подобный сервер на gnet: sync.Pool и форматирование ответов с нулевыми аллокациями

## Условие

Постройте минимальный HTTP/1.x сервер, который парсит запросы, отдаёт статический ответ и измеряет заголовки. Используйте пулы байтовых буферов (sync.Pool) для снижения аллокаций.

### Исходная формулировка

**HTTP-подобный сервер на gnet.**: Постройте минимальный HTTP/1.x сервер, который парсит запросы, отдаёт статический ответ и измеряет заголовки. Используйте пулы байтовых буферов (sync.Pool) для снижения аллокаций.

## Теория

При проектировании высокоскоростных API-шлюзов (Edge Proxies) основной задачей является парсинг входящих заголовков и мгновенная отдача ответа без порождения мусора в куче Go.

### Где стандартный Go генерирует мусор при формировании ответов:
1. `fmt.Sprintf("HTTP/1.1 200 OK\r\nContent-Length: %d\r\n...", len(body))` — аллоцирует строку в куче, преобразует интерфейсы `any` в `fmt` и тратит до сотни наносекунд на парсинг формата `%d`.
2. Преобразование `[]byte(str)` создает дублирующую копию массива байт.
3. Добавление заголовков в `w.Header().Set(...)` аллоцирует мапу и срезы строк.

### Решение: Zero-Allocation ответ через предварительно подготовленный sync.Pool
1. Мы используем `sync.Pool` для пула байтовых буферов `[]byte` фиксированного размера (например, 4 КБ).
2. Заголовки добавляются через быстрый `append()` байтовых литералов.
3. Целые числа (размер `Content-Length`) форматируются с помощью `strconv.AppendInt(buf, int64(len(body)), 10)` прямо в существующий слайс без создания строк!
4. Готовый буфер отдается через `c.Write(buf)`, после чего буфер возвращается в пул.

## Решение по шагам

1. Создайте `sync.Pool` для хранения буферов `*[]byte`.
2. В обработчике `OnTraffic` извлеките буфер из пула через `getBuffer()`.
3. Сформируйте заголовки HTTP/1.1 с помощью `strconv.AppendInt` без промежуточных строк.
4. Запишите ответ в сокет и гарантированно верните буфер в `sync.Pool`.
5. Проверьте профилировщиком аллокаций `go test -bench . -benchmem`, что число аллокаций равно 0 B/op.

## Код решения

**`fast_http_pool_server.go`**

```go
package main

import (
	"bytes"
	"log"
	"strconv"
	"sync"
	"time"

	"github.com/panjf2000/gnet/v2"
)

var (
	crlfHeaderEnd = []byte("\r\n\r\n")

	// Статические литералы заголовков
	httpHeaderStatus  = []byte("HTTP/1.1 200 OK\r\nServer: gnet-pool-srv\r\nContent-Type: text/plain\r\nContent-Length: ")
	httpHeaderDate    = []byte("\r\nDate: ")
	httpHeaderBodySep = []byte("\r\n\r\n")
	responseBody      = []byte("PONG_SUPER_FAST_ZERO_ALLOC")
)

// Пул байтовых буферов емкостью 4 КБ
var httpBufPool = sync.Pool{
	New: func() any {
		b := make([]byte, 0, 4096)
		return &b
	},
}

type FastHTTPPoolServer struct {
	gnet.BuiltinEventEngine
}

func (s *FastHTTPPoolServer) OnTraffic(c gnet.Conn) gnet.Action {
	buffered := c.InboundBuffered()
	if buffered < 14 {
		return gnet.None
	}

	data, err := c.Peek(buffered)
	if err != nil {
		return gnet.Close
	}

	// Проверяем окончание заголовков HTTP-запроса
	idx := bytes.Index(data, crlfHeaderEnd)
	if idx == -1 {
		return gnet.None
	}

	// Сдвигаем входящий буфер
	_, _ = c.Discard(idx + len(crlfHeaderEnd))

	// Берем буфер из пула
	bufPtr := httpBufPool.Get().(*[]byte)
	buf := (*bufPtr)[:0]

	// 1. Статус и Content-Length без аллокаций
	buf = append(buf, httpHeaderStatus...)
	buf = strconv.AppendInt(buf, int64(len(responseBody)), 10)

	// 2. Заголовок Date (RFC1123) прямо в буфер
	buf = append(buf, httpHeaderDate...)
	buf = time.Now().AppendFormat(buf, time.RFC1123)

	// 3. Тело ответа
	buf = append(buf, httpHeaderBodySep...)
	buf = append(buf, responseBody...)

	// Отправка в сокет
	_, _ = c.Write(buf)

	// Возврат буфера в пул
	*bufPtr = buf
	httpBufPool.Put(bufPtr)

	return gnet.None
}

func main() {
	server := &FastHTTPPoolServer{}
	addr := "tcp://127.0.0.1:8082"

	log.Printf("Запуск Zero-Allocation HTTP сервера на %s...\n", addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}
```

ℹ️ Сборка HTTP-ответа без единой аллокации в куче с помощью sync.Pool и strconv.AppendInt

## Под капотом

В функции `FastHTTPPoolServer.OnTraffic` не происходит ни одного вызова `runtime.newobject` или `runtime.makeslice`:
1. `sync.Pool` возвращает указатель `*[]byte`, ссылающийся на уже существующий непрерывный массив в памяти.
2. `strconv.AppendInt(buf, n, 10)` работает прямо со срезом байтов, деля число на 10 и заполняя символы цифр с конца без создания временной строки `string`.
3. `time.Now().AppendFormat(buf, ...)` форматирует дату прямо в переданный срез.
В результате нагрузка на Garbage Collector сводится к абсолютному нулю, позволяя обрабатывать миллионы HTTP-запросов с минимальной дисперсией задержки.

## Подводные камни

Если размер сформированного HTTP-ответа превысит исходную емкость буфера из пула (`cap(buf) = 4096`), вызов `append()` аллоцирует новый массив большего размера. Помещение такого разросшегося буфера обратно в пул может привести к постепенному раздуванию пула памяти (Pool Memory Bloat). Рекомендуется сбрасывать буфер, если его емкость превысила лимит: `if cap(buf) > MaxPoolBufCap { /* не возвращаем в пул */ }`.

## На собеседовании

**Вопрос на собеседовании (HighLoad Go Specialist):**
«Как sync.Pool взаимодействует со сборщиком мусора Go, и почему данные из sync.Pool могут неожиданно исчезнуть?»

**Эталонный ответ:**
В рантайме Go структуры `sync.Pool` очищаются сборщиком мусора. До версии Go 1.13 пул полностью очищался при каждом цикле GC. 
Начиная с Go 1.13, механизм оптимизирован через двухфазную модель (`victim cache`):
- При наступлении GC объекты из первичного пула переносятся в резервный пул (Victim Cache), а старый Victim Cache очищается.
- Если объект не был востребован в течение двух полных циклов GC, он освобождается.
Это сглаживает просадки производительности (Cold Cache Spikes), но разработчик обязан помнить: `sync.Pool` — это не постоянный кэш, любой объект из него может быть удален в любой момент.
