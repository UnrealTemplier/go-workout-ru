# Оптимизация TLB и Huge Pages (2MB / 1GB) для интенсивных нагрузок на память

## Условие

Изучите влияние таблицы трансляции адресов Translation Lookaside Buffer (TLB) на производительность Go-сервисов. Напишите практическое руководство по выделению Huge Pages (2 МБ / 1 ГБ) через системный вызов `unix.Madvise` с флагом `MADV_HUGEPAGE` для снижения количества TLB Misses в 512 раз.

### Исходная формулировка

**Huge pages для memory-intensive workloads.**: TLB misses expensive. Huge pages (2MB/1GB) снижают TLB misses в 512x/262144x. Используйте для больших data structures.

## Теория

При обращении к оперативной памяти процессор оперирует виртуальными адресами, которые блок управления памятью (MMU) транслирует в физические адреса DRAM с помощью 4-уровневой таблицы страниц (Page Tables).

**Проблема стандартных страниц 4 КБ и TLB:**
- Чтобы не обращаться к оперативной памяти 4 раза при каждом чтении, процессор кэширует трансляции в **Translation Lookaside Buffer (TLB)**.
- Размер L1 D-TLB ограничен (обычно 64 записи).
- 64 записи по 4 КБ покрывают всего **256 КБ оперативной памяти**!
- Если рабочий набор данных сервиса составляет 10 ГБ (база данных в памяти, кэш Redis, граф в оперативной памяти), процессор постоянно промахивается мимо TLB (**TLB Miss**), тратя до 30–40% тактов на проход по таблицам страниц (Page Table Walk)!

**Решение: Huge Pages (Большие страницы):**
- **Стандартная страница**: 4 КБ (\(4096\) байт).
- **Huge Page (2 МБ)**: 2 097 152 байт. 64 записи TLB теперь покрывают **128 МБ памяти** (в 512 раз больше!).
- **Giant Page (1 ГБ)**: 64 записи покрывают **64 ГБ памяти**!

**Использование в Go:**
Рантайм Go выделяет память блоками через `mmap`. С помощью системного вызова `madvise(addr, size, MADV_HUGEPAGE)` ядру Linux дается указание объединить стандартные страницы в Huge Pages (Transparent Huge Pages — THP).

## Решение по шагам

1. Создайте структуру демонстрации механики трансляции адресов и TLB.
2. Выделите блок памяти размером 64 МБ через `syscall.Mmap`.
3. Примените системный вызов `madvise` с константой `MADV_HUGEPAGE`.
4. Реализуйте бенчмарк случайного доступа по памяти (Pointer Chasing), провоцирующий TLB misses.
5. Замерьте время доступа и сформулируйте системные настройки Linux (`/sys/kernel/mm/transparent_hugepage`).

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"syscall"
	"time"
	"unsafe"
)

const MADV_HUGEPAGE = 14 // Системная константа Linux madvise

type MemoryArena struct {
	data     []byte
	pageSize int
}

func NewHugePageArena(sizeBytes int) (*MemoryArena, error) {
	// Выделение анонимной памяти
	mem, err := syscall.Mmap(
		-1, 0, sizeBytes,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		return nil, err
	}

	// Намек ядру Linux использовать Transparent Huge Pages (2 MB)
	// В Linux: madvise(ptr, size, MADV_HUGEPAGE)
	_, _, errno := syscall.Syscall(
		syscall.SYS_MADVISE,
		uintptr(unsafe.Pointer(&mem[0])),
		uintptr(sizeBytes),
		uintptr(MADV_HUGEPAGE),
	)
	if errno != 0 {
		fmt.Printf("Notice: madvise(MADV_HUGEPAGE) returned errno %d (handled)\n", errno)
	}

	return &MemoryArena{
		data:     mem,
		pageSize: 2 * 1024 * 1024, // 2 MB Huge Page
	}, nil
}

func (a *MemoryArena) Close() {
	if len(a.data) > 0 {
		_ = syscall.Munmap(a.data)
	}
}

func main() {
	const arenaSize = 64 * 1024 * 1024 // 64 MB
	arena, err := NewHugePageArena(arenaSize)
	if err != nil {
		fmt.Printf("Arena allocation fallback: %v\n", err)
		return
	}
	defer arena.Close()

	fmt.Println("=== TLB & Huge Pages (2MB / 1GB) Optimization ===")
	fmt.Printf("Allocated Arena: %d MB\n", arenaSize/(1024*1024))
	fmt.Println("Memory Architecture Metrics:")
	fmt.Println("  Standard Page:   4 KB (64 TLB entries cover 256 KB)")
	fmt.Println("  Huge Page (2MB): 2048 KB (64 TLB entries cover 128 MB -> 512x TLB reach!)")
	fmt.Println("  Giant Page (1GB): 64 TLB entries cover 64 GB")

	// Тест случайного доступа по 64 МБ памяти (симуляция нагрузки на TLB)
	const iters = 5000000
	indices := make([]int, iters)
	r := rand.New(rand.NewSource(12345))
	for i := range indices {
		indices[i] = r.Intn(arenaSize - 8)
	}

	start := time.Now()
	var checksum uint64
	for i := 0; i < iters; i++ {
		idx := indices[i]
		checksum += *(*uint64)(unsafe.Pointer(&arena.data[idx]))
	}
	dur := time.Since(start)

	fmt.Printf("\nRandom Access Benchmark (5M reads over 64 MB):\n")
	fmt.Printf("Time taken: %v (%.2f ns/op) | Checksum: %d\n", dur, float64(dur.Nanoseconds())/iters, checksum)
	fmt.Println("\nLinux OS Configuration for HighLoad:")
	fmt.Println("  echo madvise > /sys/kernel/mm/transparent_hugepage/enabled")
	fmt.Println("  perf stat -e dTLB-loads,dTLB-load-misses ./mybinary")
}
```

ℹ️ Выделение памяти под Transparent Huge Pages через syscall madvise.

## Под капотом

При стандартных страницах 4 КБ таблица страниц для 64 ГБ памяти занимает более 128 МБ в DRAM, создавая колоссальную нагрузку на кэш процессора. При переходе на Huge Pages 2 МБ размер всей таблицы страниц сжимается всего до 256 КБ, что позволяет таблице страниц целиком уместиться в быстрый кэш L2/L3 процессора.

## Подводные камни

1. Фрагментация памяти ядра: если в операционной системе мало непрерывной физической памяти, выделение Huge Pages может приводить к временным задержкам из-за дефрагментации памяти ядром (`kcompactd`).
2. Чрезмерный оверхед на малых объектах: выделение 2 МБ страницы для хранения объекта размером 10 КБ приведет к расточительной трате оперативной памяти (Internal Fragmentation).

## На собеседовании

«Как измерить количество TLB-промахов сервиса в Linux?». Ответ: запустить утилиту `perf stat -e dTLB-loads,dTLB-load-misses ./service`. Если метрика `dTLB-load-misses` превышает 2–3% от общего числа обращений к данным, включение Huge Pages даст сервису прирост производительности от 15% до 40% без изменения единой строчки алгоритмов.
