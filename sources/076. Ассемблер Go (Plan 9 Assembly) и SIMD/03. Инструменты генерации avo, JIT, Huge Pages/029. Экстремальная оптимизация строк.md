# Экстремальная оптимизация строк: бенчмаркинг IndexByte на 10 МБ буфере

## Условие

Проведите масштабный сравнительный бенчмарк поиска символа в 10-мегабайтном срезе байт между скалярным циклом `for` и стандартной функцией `bytes.IndexByte`. Изучите исходный код `src/internal/bytealg/indexbyte_amd64.s` и объясните 30-кратную разницу в скорости.

### Исходная формулировка

**Оптимизация строк (IndexByte)**: Напиши бенчмарк, который ищет символ в строке на 10 МБ с помощью цикла `for` и с помощью `strings.IndexByte`. Посмотри исходники `IndexByte` — ты увидишь, что "под капотом" она реализована на чистом Assembly с использованием SIMD, поэтому работает в десятки раз быстрее.

## Теория

Операция `bytes.IndexByte(b, c)` — эталонный пример того, как низкоуровневый ассемблер и SIMD трансформируют производительность рантайма Go.

**Сравнение двух миров на 10 МБ данных (\(10^7\) байт):**
1. **Скалярный цикл Go**:
   - Выполняет 10 000 000 итераций.
   - 10 000 000 проверок условий перехода `CMPB + JNE`.
   - Время выполнения: **~6–8 миллисекунд**.
   - Скорость: **~1.2–1.5 ГБ/с**.
2. **Ассемблерный `bytes.IndexByte` (AVX2)**:
   - Проверяет по **32 байта за один такт** с помощью инструкции `VPCMPEQB`.
   - Число итераций цикла снижается с 10 000 000 до всего **312 500**!
   - Время выполнения: **~0.25 миллисекунды**!
   - Скорость: **~40 ГБ/с** (физический предел пропускной способности оперативной памяти DDR4/DDR5)!

**Анатомия реализации в рантайме Go:**
- Первые несколько байт выравниваются до границы 32 байт.
- Основной цикл развернут на обработку двух 256-битных блоков (64 байта за итерацию — размер целой кэш-линии!).
- Используется инструкция `VPTEST` для быстрой проверки обоих блоков на наличие совпадений.

## Решение по шагам

1. Выделите срез байт размером 10 МБ (`10 * 1024 * 1024` байт).
2. Поместите искомый символ в самый конец буфера (Worst-Case Scenario).
3. Напишите скалярную функцию поиска в цикле `for`.
4. Запустите замер времени выполнения скалярного поиска и стандартного `bytes.IndexByte`.
5. Рассчитайте пропускную способность в гигабайтах в секунду (GB/s) и выведите сравнительный анализ.

## Код решения

**`main.go`**

```go
package main

import (
	"bytes"
	"fmt"
	"time"
)

// NaiveLoopIndexByte выполняет стандартный скалярный перебор
//
//go:noinline
func NaiveLoopIndexByte(b []byte, c byte) int {
	for i := 0; i < len(b); i++ {
		if b[i] == c {
			return i
		}
	}
	return -1
}

func main() {
	const size = 10 * 1024 * 1024 // 10 MB
	buffer := make([]byte, size)
	for i := range buffer {
		buffer[i] = 'a'
	}

	target := byte('Z')
	// Худший случай: искомый байт в предпоследней позиции
	buffer[size-2] = target

	const iters = 50

	// 1. Scalar Loop
	start1 := time.Now()
	var idx1 int
	for i := 0; i < iters; i++ {
		idx1 = NaiveLoopIndexByte(buffer, target)
	}
	dur1 := time.Since(start1)

	// 2. Optimized bytes.IndexByte (Assembly AVX2/SSE)
	start2 := time.Now()
	var idx2 int
	for i := 0; i < iters; i++ {
		idx2 = bytes.IndexByte(buffer, target)
	}
	dur2 := time.Since(start2)

	totalGB := (float64(size*iters) / (1024 * 1024 * 1024))
	fmt.Println("=== 10 MB Buffer String Search Benchmark ===")
	fmt.Printf("Buffer Size: %d bytes (10 MB)\n", size)
	fmt.Printf("Scalar Loop:      %v | Throughput: %.2f GB/s\n", dur1, totalGB/dur1.Seconds())
	fmt.Printf("bytes.IndexByte:  %v | Throughput: %.2f GB/s\n", dur2, totalGB/dur2.Seconds())

	ratio := float64(dur1) / float64(dur2)
	fmt.Printf("\nAssembly SIMD Speedup: %.2fx faster!\n", ratio)

	if idx1 != idx2 || idx1 != size-2 {
		panic("index mismatch")
	}
	fmt.Println("Verification: Both search implementations returned exact target index.")
}
```

ℹ️ Сравнение производительности скалярного поиска и векторного bytes.IndexByte на 10 МБ данных.

## Под капотом

В функции `bytes.IndexByte` скорость 40+ ГБ/с означает, что алгоритм полностью утилизирует пропускную способность контроллера памяти (Memory Bus Saturation). Процессор успевает обработать данные быстрее, чем контроллер памяти DDR5 способен их поставлять из DRAM в L3/L2 кэш (Memory-Bound limit). Дальнейшая оптимизация алгоритма физически невозможна без изменения типа оперативной памяти.

## Подводные камни

1. Написание кастомных циклов вместо стандартных функций: многие разработчики пишут свои циклы поиска или фильтрации, не зная, что в стандартных пакетах `bytes` и `strings` большинство операций (`Index`, `Count`, `Equal`, `HasPrefix`) уже оптимизированы на ассемблере с использованием AVX2/AVX-512.
2. Промахи кэша при повторных поисках: если искать в срезе, превышающем размер кэша L3, каждый поиск сбрасывает кэш процессора.
