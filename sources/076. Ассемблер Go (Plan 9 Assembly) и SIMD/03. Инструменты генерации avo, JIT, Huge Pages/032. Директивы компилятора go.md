# Директивы компилятора go:noescape и go:nosplit: безопасность стека и сборщика мусора

## Условие

Проведите углубленный анализ системных директив компилятора `//go:noescape` и `//go:nosplit`. Напишите демонстрационную программу и разберите сценарии, когда неправильное использование этих прагм приводит к повреждению стека (Stack Corruption) или взаимным блокировкам с Garbage Collector.

### Исходная формулировка

**Директива `go:noescape` и `go:nosplit`**: При объявлении ассемблерных функций добавь над ними эти прагмы. Узнай, что `go:noescape` говорит компилятору не делать Escape Analysis для аргументов функции (ускоряет работу памяти), а `go:nosplit` запрещает рантайму проверять размер стека горутины (экономит такты, но может вызвать панику, если стек переполнится).

---

## Теория

Прагмы компилятора Go начинаются со специального префикса `//go:` без пробела. При работе с низкоуровневым кодом и ассемблером критически важны две из них:

**1. Директива `//go:noescape`:**
- Разрешена **только** для функций без тела (ассемблерных или внешних).
- Отключает алгоритм Escape Analysis: гарантирует компилятору, что переданные указатели не сохранятся в глобальных переменных или других объектах кучи.
- *Польза*: сохраняет аргументы на стеке, исключая аллокации в куче (`0 B/op`).
- *Опасность*: если ассемблерная функция все же сохранит указатель, после возврата стек будет перезаписан, породив висячий указатель (Dangling Pointer) и разрушение памяти.

**2. Директива `//go:nosplit`:**
- Запрещает компилятору вставлять проверку переполнения стека (`runtime.morestack`).
- *Где обязательна*: в критических путях самого рантайма Go — обработчиках сигналов ОС, функциях расширения стека `morestack`, низкоуровневом планировщике, так как вызов `morestack` внутри самого `morestack` привел бы к бесконечной рекурсии и падению процесса.
- *Ограничение*: тело функции с `//go:nosplit` гарантированно не должно использовать больше `_StackLimit` (~792 байт стека), иначе она физически затрет стек соседней структуры рантайма!

## Решение по шагам

1. Создайте структуру демонстрации влияния директив на escape-анализ.
2. Реализуйте тест на предотвращение аллокаций через симуляцию `//go:noescape`.
3. Опишите механизм работы проверки стека `nosplit`.
4. Продемонстрируйте замер аллокаций памяти с помощью `testing.AllocsPerRun`.
5. Сформулируйте правила безопасности для Senior-разработчиков.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"testing"
)

type HeavyRecord struct {
	ID    int64
	Score float64
	Tags  [8]int64
}

// EmulatedNoEscapeFunction симулирует поведение функции с //go:noescape
//
// В реальном проекте:
// //go:noescape
// func ProcessRecordAsm(r *HeavyRecord)
func EmulatedNoEscapeFunction(r *HeavyRecord) {
	// Функция работает только с полями по месту и никуда не сохраняет указатель r
	r.Score += 10.5
}

func main() {
	fmt.Println("=== Compiler Directives: //go:noescape & //go:nosplit ===")
	fmt.Println("1. //go:noescape Rules:")
	fmt.Println("   - Applies only to declarations without bodies (assembly primitives)")
	fmt.Println("   - Disables escape analysis for pointer parameters")
	fmt.Println("   - Keeps structures on the caller's stack frame (zero heap pressure)")
	fmt.Println("-------------------------------------------------------------------------")
	fmt.Println("2. //go:nosplit Rules:")
	fmt.Println("   - Disables stack overflow check (preamble CMPQ SP, (R14))")
	fmt.Println("   - Mandatory for runtime routines (signals, morestack, malloc)")
	fmt.Println("   - Strictly limited stack depth (< 792 bytes)")
	fmt.Println("-------------------------------------------------------------------------")

	// Проверка аллокаций
	allocs := testing.AllocsPerRun(10000, func() {
		var rec HeavyRecord
		rec.ID = 100
		EmulatedNoEscapeFunction(&rec)
	})

	fmt.Printf("Memory Allocation Verification: %.0f allocs/op (Stack resident)\n", allocs)
	fmt.Println("Verdict: With //go:noescape parameters safely reside on stack without GC overhead.")
}
```

ℹ️ Исследование директив //go:noescape и //go:nosplit и предотвращение аллокаций в куче.

## Под капотом

В исходниках рантайма Go (`src/runtime`) директива `//go:nosplit` встречается более чем в 500 функциях. Компилятор Go на этапе компиляции строит граф вызовов всех `nosplit` функций и статически вычисляет максимальную суммарную глубину стека этой цепочки. Если цепочка превышает лимит безопасности, компилятор прерывает сборку с ошибкой `nosplit stack overflow`.

## Подводные камни

1. Пробел после слэшей: если написать `// go:noescape` (с пробелом), компилятор расценит это как обычный комментарий и проигнорирует директиву, вернув стандартный escape в кучу!
2. Вызов обычной Go-функции из `nosplit`: вызов функции без `nosplit` из `nosplit`-функции сводит на нет все гарантии безопасности стека.

## На собеседовании

«Что произойдет, если в функции с //go:nosplit произойдет глубокая рекурсия?». Ответ: компилятор Go запрещает рекурсию в `nosplit`-функциях на этапе статического анализа. Если же обойти проверку через ассемблер, стек горутины переполнится, затрет служебные структуры рантайма и операционная система аварийно завершит процесс сигналом `SIGSEGV` без генерации читаемого стек-трейса.
