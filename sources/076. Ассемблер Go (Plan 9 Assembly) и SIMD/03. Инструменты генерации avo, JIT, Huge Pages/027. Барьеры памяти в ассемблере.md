# Барьеры памяти в ассемблере: MFENCE, LFENCE, SFENCE и слабые модели памяти

## Условие

Изучите использование инструкций аппаратных барьеров памяти (`MFENCE`, `LFENCE`, `SFENCE` на x86_64 и `DMB ISH` на ARM64). Объясните, почему на архитектурах со слабой моделью памяти (ARM64, POWER) отсутствие барьеров приводит к повреждению разделяемых данных, и как рантайм Go использует барьеры памяти.

### Исходная формулировка

**[Memory Fences]**: Используй `runtime.StoreLoadFence()` или `MFENCE` в ассемблере. Объясни, почему на слабых архитектурах памяти (ARM) переупорядочивание инструкций процессором может сломать Lock-Free алгоритмы, написанные для x86 (где модель памяти строгая — Total Store Order).

## Теория

Модель памяти определяет правила видимости операций записи и чтения между разными ядрами процессора.

**1. Сильная модель памяти x86_64 (Total Store Order — TSO):**
- Процессоры x86 аппаратно гарантируют порядок:
  - `LoadLoad`: чтения не переставляются с чтениями.
  - `StoreStore`: записи не переставляются с записями.
  - `LoadStore`: чтения не переставляются со следующими записями.
- **Единственное разрешенное аппаратное переупорядочивание на x86** — `StoreLoad`: процессор помещает запись в локальный Store Buffer и может спекулятивно прочитать следующее значение из памяти до того, как буфер сбросится в кэш!

**2. Слабая модель памяти ARM64 / POWER (Weakly-Ordered Memory Model):**
- Процессор ARM64 имеет право переставить практически **любые** независимые инструкции памяти: `LoadLoad`, `StoreStore`, `LoadStore`, `StoreLoad`!
- Если поток 1 инициализирует структуру `data = 42` и ставит флаг `ready = 1`, поток 2 на ARM64 может увидеть `ready == 1` РДО того, как значение `data == 42` дойдет до его кэша! В результате поток 2 прочитает мусор!

**Аппаратные инструкции барьеров памяти:**
- `MFENCE` (Memory Fence): полный двухсторонний барьер на x86. Задерживает выполнение, пока все предыдущие чтения и записи не станут глобально видимы.
- `LFENCE` (Load Fence): барьер чтения (сериализует конвейер инструкций, используется для защиты от уязвимостей Spectre).
- `SFENCE` (Store Fence): барьер записи (сбрасывает буферы нетемпоральной записи `MOVNTQ`).
- `DMB ISH` (Data Memory Barrier Inner Shareable): универсальный аппаратный барьер памяти на ARM64.

## Решение по шагам

1. Создайте структуру моделирования поведения шины памяти на TSO (x86) и Weak (ARM64).
2. Опишите сценарий нарушения публикации флага готовности данных (Publication Safety).
3. Продемонстрируйте ассемблерный вызов `MFENCE` в файле `fence_amd64.s`.
4. Реализуйте верификатор видимости разделяемого состояния.
5. Зафиксируйте правила расстановки барьеров в Lock-free коде.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

// Демонстрация файла fence_amd64.s:
//
// #include "textflag.h"
//
// // func MemoryFence()
// TEXT ·MemoryFence(SB), NOSPLIT, $0-0
//     MFENCE    // Полный барьер памяти на x86 (сброс Store Buffer)
//     RET
//
// В файле fence_arm64.s:
// TEXT ·MemoryFence(SB), NOSPLIT, $0-0
//     DMB ISH   // Data Memory Barrier Inner Shareable
//     RET

type SharedPayload struct {
	data  int64
	ready int32
}

func main() {
	fmt.Println("=== Hardware Memory Barriers (MFENCE vs DMB ISH) ===")
	fmt.Println("Memory Model Architectures:")
	fmt.Println("  x86-64 (TSO): Strong ordering. Stores are buffered, but StoreStore/LoadLoad preserved.")
	fmt.Println("  ARM64 (Weak): Aggressive reordering. Both Stores and Loads can be reordered by hardware!")
	fmt.Println("-----------------------------------------------------------------------------------------")
	fmt.Println("Instructions:")
	fmt.Println("  x86_64: MFENCE (Full Barrier), LFENCE (Load/Speculation Barrier), SFENCE (Store Barrier)")
	fmt.Println("  ARM64:  DMB ISH (Full Barrier), LDAR (Load-Acquire), STLR (Store-Release)")

	// В Go рантайме барьеры встроены в sync/atomic:
	var payload SharedPayload
	var wg sync.WaitGroup
	wg.Add(2)

	// Producer (Горутина 1)
	go func() {
		defer wg.Done()
		payload.data = 1337 // 1. Запись данных
		// atomic.Store обеспечивает семантику Store-Release (барьер)
		atomic.StoreInt32(&payload.ready, 1)
	}()

	// Consumer (Горутина 2)
	go func() {
		defer wg.Done()
		// atomic.Load обеспечивает семантику Load-Acquire
		for atomic.LoadInt32(&payload.ready) == 0 {
			// Ожидание готовности
		}
		// Гарантированно видим payload.data == 1337 на ЛЮБОЙ архитектуре (x86, ARM64, RISC-V)
		fmt.Printf("\nConsumer observed safe publication: data = %d (ready = %d)\n",
			payload.data, payload.ready)
	}()

	wg.Wait()
	fmt.Println("Verification: Memory barrier safely enforced synchronization across CPU cores.")
}
```

ℹ️ Аппаратные барьеры памяти MFENCE / DMB ISH и безопасная публикация данных.

## Под капотом

На архитектуре ARM64 инструкции `LDAR` (Load-Acquire) и `STLR` (Store-Release) встроены прямо в систему команд процессора (в отличие от x86, где `MOV` по умолчанию имеет Acquire/Release семантику). При вызове `atomic.StoreInt32` компилятор Go на ARM64 генерирует ровно инструкцию `STLR`, которая гарантирует, что все предшествующие записи памяти станут видимы другим ядрам до сохранения флага.

## Подводные камни

1. Злоупотребление инструкцией `MFENCE`: инструкция `MFENCE` на x86 останавливает конвейер ядра до полного подтверждения от шины кэшей, занимая 30–50 тактов. Ее следует использовать только там, где действительно требуется предотвратить Store-Load переупорядочивание.
2. Использование неатомарных переменных для синхронизации: если флаг `ready` читать и писать без `sync/atomic`, оптимизатор компилятора Go имеет право вынести чтение флага из цикла (`hoisting`), превратив `for !ready {}` в бесконечный зависший цикл.

## На собеседовании

«Чем отличается инструкция LFENCE от MFENCE на процессорах Intel?». Ответ: `LFENCE` исторически гарантировал порядок только между чтениями (`LoadLoad`). Однако после обнаружения уязвимости Spectre V2 компания Intel обновила микрокод: теперь `LFENCE` является инструкцией сериализации конвейера (Dispatch Serializing), предотвращая спекулятивное выполнение любых последующих инструкций до завершения всех предшествующих.
