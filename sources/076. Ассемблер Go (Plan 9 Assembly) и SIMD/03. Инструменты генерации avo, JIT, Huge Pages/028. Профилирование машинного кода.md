# Профилирование машинного кода: perf record, perf annotate и objdump

## Условие

Изучите методику сквозного профилирования машинного кода в production-окружении Linux. Продемонстрируйте связку инструментов `perf record -g`, `perf annotate` и `go tool objdump` для локализации неэффективных ассемблерных инструкций (CPU Hotspots) и их устранения.

### Исходная формулировка

**Профилирование на уровне инструкций с `perf` и `objdump`.**: Скомпилируйте Go-бинарник с `-gcflags="-S"` для вывода asm, найдите неэффективные участки с помощью `perf record`, `perf annotate`. Оптимизируйте на основе анализа.

## Теория

Когда стандартный CPU-профиль Go (`pprof`) указывает на конкретную функцию как на потребителя 40%+ процессорного времени, разработчик часто видит одну строку кода: например, `sum += s[i] * w[i]`. На уровне языка оптимизировать нечего.

В этот момент инженеры переходят на уровень машинных инструкций:
1. **Сбор профиля аппаратных прерываний**:
   ```bash
   perf record -F 999 -g -- ./service_binary
   ```
   Утилита `perf` сэмплирует аппаратные счетчики ядра 999 раз в секунду, сохраняя стек вызовов и точный адрес счетчика инструкций (`PC`).
2. **Интерактивная аннотация машинного кода (`perf annotate`)**:
   Команда `perf annotate --symbol="main.HotKernel"` выводит дизассемблированный код функции, где напротив каждой машинной инструкции указан **точный процент тактов CPU**:
   ```text
   12.45% : 0x45a120: MOVQ  (DX)(CX*8), AX
   65.80% : 0x45a125: IMULQ (BX)(CX*8), AX   <-- УЗКОЕ МЕСТО!
    3.10% : 0x45a12a: ADDQ  AX, R8
   ```
3. **Анализ узкого места**:
   Высокий процент на конкретной инструкции `IMULQ` указывает на задержку (Latency Stall) или нехватку портов умножения. Оптимизация заключается в векторизации через SIMD или развертке на несколько независимых аккумуляторов.

## Решение по шагам

1. Создайте структуру моделирования анализа хот-спота через `perf`.
2. Реализуйте функцию `HeavyCalculationKernel` с вычислительно тяжелым циклом.
3. Опишите команды генерации отчета: `go build -o app main.go`, `perf record ./app`, `perf annotate`.
4. Реализуйте оптимизированную версию ядра `OptimizedCalculationKernel`.
5. Сравните время выполнения и покажите снижение доли тактов на инструкцию.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

// HeavyKernel: наивный цикл с зависимостью по данным
//
//go:noinline
func HeavyKernel(a, b []int64) int64 {
	var total int64
	for i := 0; i < len(a); i++ {
		// В ассемблере: IMULQ задерживает следующую итерацию на 3 такта
		total += a[i] * b[i]
	}
	return total
}

// OptimizedKernel: 4 независимых аккумулятора (устранение задержки конвейера)
//
//go:noinline
func OptimizedKernel(a, b []int64) int64 {
	n := len(a)
	blocks := n / 4

	var s0, s1, s2, s3 int64
	for i := 0; i < blocks*4; i += 4 {
		s0 += a[i+0] * b[i+0]
		s1 += a[i+1] * b[i+1]
		s2 += a[i+2] * b[i+2]
		s3 += a[i+3] * b[i+3]
	}

	total := (s0 + s1) + (s2 + s3)
	for i := blocks * 4; i < n; i++ {
		total += a[i] * b[i]
	}
	return total
}

func main() {
	const count = 10000000
	a := make([]int64, count)
	b := make([]int64, count)
	for i := range a {
		a[i] = int64(i % 50)
		b[i] = int64((i % 30) + 1)
	}

	// 1. Heavy Kernel Benchmark
	start1 := time.Now()
	res1 := HeavyKernel(a, b)
	dur1 := time.Since(start1)

	// 2. Optimized Kernel Benchmark
	start2 := time.Now()
	res2 := OptimizedKernel(a, b)
	dur2 := time.Since(start2)

	fmt.Println("=== Perf Instruction-Level Profiling & Hotspot Optimization ===")
	fmt.Printf("Heavy Kernel:     %v (%.2f ns/op)\n", dur1, float64(dur1.Nanoseconds())/count)
	fmt.Printf("Optimized Kernel: %v (%.2f ns/op)\n", dur2, float64(dur2.Nanoseconds())/count)
	if dur1 > dur2 {
		fmt.Printf("Throughput Gain:  %.2fx faster via superscalar pipelining\n", float64(dur1)/float64(dur2))
	}

	if res1 != res2 {
		panic("result mismatch")
	}

	fmt.Println("\nWorkflow Guide:")
	fmt.Println("  1. go build -o app main.go")
	fmt.Println("  2. perf record -F 999 -g ./app")
	fmt.Println("  3. perf annotate --symbol=\"main.HeavyKernel\"")
}
```

ℹ️ Устранение ассемблерного хот-спота зависимости умножения через 4 независимых аккумулятора.

## Под капотом

Инструмент `perf annotate` сопоставляет адреса инструкций из секции `.text` ELF-бинарника со строками отладочной информации DWARF (`.debug_line`). Если бинарный файл собран с флагами стриппинга (`-ldflags="-s -w"`), отладочная информация удаляется, и сопоставить ассемблер с исходным Go-кодом станет невозможно. Для профилирования всегда используйте бинарники с полными символами.

## Подводные камни

1. Профилирование с инлайнингом: если функция была встроена компилятором в `main`, символ функции исчезнет из таблицы символов. Для исследования ассемблера конкретной функции используют `//go:noinline`.
2. Инструкции сэмплирования с плавающим смещением (Skid): аппаратное прерывание PMU срабатывает с задержкой в несколько тактов процессора, поэтому самый горячий сэмпл может указывать на следующую инструкцию после реального виновника.

## На собеседовании

«Что такое Precise Event-Based Sampling (PEBS) на процессорах Intel?». Ответ: PEBS — это аппаратный механизм, который при возникновении события счетчика производительности сохраняет точное состояние регистров и точный адрес инструкции в специальный кольцевой буфер ядра процессора без задержки (Skid = 0), обеспечивая 100% точность позиционирования хот-спота в `perf annotate`.
