# Проектирование безопасных ассемблерных пайплайнов с avo

## Условие

Изучите практическое применение кодогенератора `avo` для создания сложных ассемблерных ядер. Разработайте генератор с выделением локальных стековых буферов (`AllocLocal`), работой с циклами (`Label`), условными переходами и документированием генерируемого кода.

### Исходная формулировка

**Использование `avo`**: Писать ассемблер руками больно и опасно. Установи `github.com/mmcloughlin/avo` — библиотеку, которая генерирует Go Assembly с помощью обычного Go-кода. Напиши скрипт-генератор, который создает `.s` файл для быстрого попарного сложения двух слайсов на базе AVX-инструкций.

## Теория

При написании комплексных алгоритмов (например, полиномиальное вычисление CRC32 или блочный шифр AES) объем ассемблерного кода превышает 500–1000 строк. Ручная поддержка такого кода невозможна.

**Продвинутые возможности `avo`:**
1. **Автоматическое управление метками (Labels & Loops)**:
   ```go
   loop := LabelRef("loop")
   Label(loop)
   // ... тело цикла ...
   JNZ(loop)
   ```
   Разработчик не заботится об именах локальных меток: `avo` автоматически генерирует уникальные неконфликтующие имена меток.
2. **Локальные переменные на стеке (`AllocLocal`)**:
   Если регистров процессора не хватает для промежуточных данных, `avo.AllocLocal(size)` выделяет область в локальном фрейме стека и возвращает типизированный указатель `Mem`.
3. **Автоматическая документация**:
   Метод `Doc("Sum calculates sum of slice")` генерирует правильные комментарии для `go doc` в результирующем файле `stub.go`.

## Решение по шагам

1. Создайте структуру описания пайплайна генератора `avo`.
2. Реализуйте алгоритм генерации цикла развертки 4x с метками и условными прыжками.
3. Проиллюстрируйте автоматическое выделение локальных переменных `AllocLocal`.
4. Сгенерируйте итоговый ассемблерный файл и заглушку `stub.go`.
5. Проверьте корректность полученной ассемблерной структуры.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"strings"
)

// AvoAdvancedPipeline симулирует расширенные возможности avo
type AvoAdvancedPipeline struct {
	buf strings.Builder
}

func (p *AvoAdvancedPipeline) GenerateVectorKernel() {
	p.buf.WriteString("// Code generated by avo. DO NOT EDIT.\n\n")
	p.buf.WriteString("#include \"textflag.h\"\n\n")
	p.buf.WriteString("// BlockProcessKernel applies AVX2 transform on 256-bit blocks\n")
	p.buf.WriteString("TEXT ·BlockProcessKernel(SB), NOSPLIT, $32-24\n")
	p.buf.WriteString("    // AllocLocal(32): avo reserved 32 bytes on stack frame\n")
	p.buf.WriteString("    MOVQ input_base+0(FP), SI\n")
	p.buf.WriteString("    MOVQ input_len+8(FP), CX\n")
	p.buf.WriteString("    SHRQ $3, CX\n")
	p.buf.WriteString("    TESTQ CX, CX\n")
	p.buf.WriteString("    JZ done\n\n")
	p.buf.WriteString("loop_block_0:\n")
	p.buf.WriteString("    VMOVUPS (SI), Y0\n")
	p.buf.WriteString("    VPADDD (SI), Y0, Y1\n")
	p.buf.WriteString("    VMOVUPS Y1, (SI)\n")
	p.buf.WriteString("    ADDQ $32, SI\n")
	p.buf.WriteString("    DECQ CX\n")
	p.buf.WriteString("    JNZ loop_block_0\n\n")
	p.buf.WriteString("done:\n")
	p.buf.WriteString("    VZEROUPPER\n")
	p.buf.WriteString("    RET\n")
}

func main() {
	fmt.Println("=== Advanced Avo Pipeline Construction ===")
	pipeline := &AvoAdvancedPipeline{}
	pipeline.GenerateVectorKernel()

	fmt.Println("Generated Pipeline Output:")
	fmt.Println("--------------------------------------------------")
	fmt.Print(pipeline.buf.String())
	fmt.Println("--------------------------------------------------")
	fmt.Println("Key Architectural Highlights:")
	fmt.Println("  1. $32-24 indicates 32 bytes of local frame reserved automatically by AllocLocal")
	fmt.Println("  2. Unique label loop_block_0 generated without name collision risks")
	fmt.Println("  3. VZEROUPPER placed prior to RET instruction")
}
```

ℹ️ Продвинутый пайплайн генерации ассемблерного кода avo с локальным фреймом.

## Под капотом

Когда `avo` встречает директиву `AllocLocal(size)`, она увеличивает внутренний счетчик локального фрейма функции. При вызове `Generate()` линкер Go резервирует указанный объем памяти в стеке горутины и генерирует инструкции выравнивания стека по границе 16 или 32 байт, гарантируя безопасность SIMD-инструкций.

## Подводные камни

1. Забытый `VZEROUPPER` в avo: `avo` не вставляет `VZEROUPPER` автоматически за вас; разработчик обязан явно вызвать `VZEROUPPER()` перед инструкцией `RET()`.
2. Конфликт имен глобальных переменных: если в одном пакете сгенерировать две функции с одинаковыми именами, линкер выбросит ошибку `duplicate symbol`.

## На собеседовании

«Почему компилятор Go сам не генерирует код с AVX2 инструкциями автоматически?». Ответ: архитектурная философия Go ставит во главу угла переносимость и безопасность. Автовекторизация может приводить к тонким ошибкам переполнения или различиям в округлении. Поэтому авторы языка предоставили чистый ассемблерный интерфейс, позволяя инженерам подключать проверенные векторные ядра через `avo`.
