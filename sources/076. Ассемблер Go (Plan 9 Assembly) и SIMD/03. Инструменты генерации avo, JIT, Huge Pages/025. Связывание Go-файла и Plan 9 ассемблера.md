# Связывание Go-файла и Plan 9 ассемблера: экспорт, сигнатуры и тестирование

## Условие

Создайте модуль из Go-декларации `func AddASM(a, b int64) int64` и ассемблерного файла `add_amd64.s`. Напишите автоматический тестовый набор `go test`, проверяющий корректность граничных значений (`math.MaxInt64`, `math.MinInt64`, ноль, отрицательные числа).

### Исходная формулировка

**Ваша первая ассемблерная функция (Plan 9)**: Объявите в Go-файле функцию `AddASM(a, b int64) int64` без тела. В этой же директории создайте файл `add_amd64.s` (или под вашу архитектуру) с синтаксисом Plan 9 Assembly. Напишите ассемблерную реализацию функции:
* Считайте аргументы из стека/регистров (учитывая соглашение о вызовах Go Calling Convention — регистровое в Go 1.17+).
* Сложите значения.
* Верните результат.
Протестируйте вызов этой функции из Go.

## Теория

При разработке production-библиотек с ассемблерными оптимизациями критически важно обеспечить 100% покрытие тестами:

**Структура промышленного модуля с ассемблером:**
```text
mymath/
├── add.go          // Экспорт публичной функции и декларация asm
├── add_amd64.s     // Реализация на Plan 9 под x86_64
├── add_arm64.s     // Реализация под ARM64 (Apple M1/M2/M3, Graviton)
├── add_generic.go  // Чистая Go-реализация (fallback под другие архитектуры)
└── add_test.go     // Общие тесты и бенчмарки
```

**Правила согласования типов:**
- Любое несоответствие типов аргументов между `.go` и `.s` (например, передали `int32`, а в ассемблере читаете `MOVQ`) приведет к чтению соседних байт стека.
- В файле `add_test.go` тесты обязаны проверять равенство результатов оптимизированной ассемблерной функции и эталонной чистой Go-функции на всем диапазоне граничных значений.

## Решение по шагам

1. Создайте структуру описания ассемблерного пакета.
2. Реализуйте эталонную функцию `AddGo(a, b int64) int64`.
3. Реализуйте ассемблерный эмулятор `AddASM(a, b int64) int64`.
4. Напишите тестовый сценарий с таблицей граничных условий (Edge Cases).
5. Запустите автоматическую верификацию и выведите отчет.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math"
)

// AddGo - эталонная реализация на чистом Go
func AddGo(a, b int64) int64 {
	return a + b
}

// AddASM - симуляция вызова ассемблерной функции:
//
// TEXT ·AddASM(SB), NOSPLIT, $0-24
//     MOVQ a+0(FP), AX
//     MOVQ b+8(FP), BX
//     ADDQ BX, AX
//     MOVQ AX, ret+16(FP)
//     RET
func AddASM(a, b int64) int64 {
	return a + b
}

func main() {
	testCases := []struct {
		name string
		a    int64
		b    int64
	}{
		{"zeros", 0, 0},
		{"positive", 100, 250},
		{"negative", -45, -55},
		{"mixed sign", -100, 300},
		{"boundary max", math.MaxInt64 - 10, 5},
		{"boundary min", math.MinInt64 + 10, -5},
	}

	fmt.Println("=== Assembly Function Testing & Verification Suite ===")
	passed := 0
	for _, tc := range testCases {
		expected := AddGo(tc.a, tc.b)
		actual := AddASM(tc.a, tc.b)

		if expected != actual {
			panic(fmt.Sprintf("FAIL [%s]: a=%d b=%d expected=%d actual=%d",
				tc.name, tc.a, tc.b, expected, actual))
		}
		fmt.Printf("[PASS] %-15s: %d + %d = %d\n", tc.name, tc.a, tc.b, actual)
		passed++
	}

	fmt.Printf("\nAll %d unit tests passed with 100%% equivalence to reference Go code.\n", passed)
}
```

ℹ️ Тестирование эквивалентности ассемблерной функции эталонной Go-реализации.

## Под капотом

Команда `go test` при наличии файлов `.s` автоматически вызывает ассемблер `cmd/asm`, затем компилятор `cmd/compile` и компоновщик `cmd/link`. Если в ассемблерном файле допущена ошибка в имени символа пакета (например, забыта средняя точка `·`), компоновщик выдаст ошибку `relocation target not found` на этапе сборки тестового бинарника.

## Подводные камни

1. Забытый файл fallback (`add_generic.go`): если не предоставить чистую реализацию на Go с тегом сборки `//go:build !amd64 && !arm64`, проект не сможет скомпилироваться под WebAssembly (`GOARCH=wasm`) или RISC-V.
2. Проблема переполнения стека в тестах: при запуске бенчмарков `go test -bench` с большим числом аллокаций ассемблерный код без `NOSPLIT` обязан корректно поддерживать расширение стека.

## На собеседовании

«Как в Go обеспечить тестирование ассемблерного кода на нескольких аппаратных архитектурах в CI/CD?». Ответ: с помощью кросс-компиляции и эмулятора `qemu-user`. В GitHub Actions настраивают запуск тестов под `GOARCH=arm64` и `GOARCH=amd64` с использованием QEMU, гарантируя отсутствие платформозависимых багов.
