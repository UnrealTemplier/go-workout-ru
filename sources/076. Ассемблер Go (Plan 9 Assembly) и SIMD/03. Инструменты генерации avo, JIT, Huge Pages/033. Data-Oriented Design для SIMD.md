# Data-Oriented Design для SIMD: Struct of Arrays (SoA) против Array of Structs (AoS)

## Условие

Исследуйте влияние организации данных в памяти на возможность применения SIMD-инструкций. Напишите практический бенчмарк, доказывающий превосходство формата Struct of Arrays (SoA) над традиционным Array of Structs (AoS) при параллельной обработке координат и физических частиц.

### Исходная формулировка

**Struct of Arrays > Array of Structs для SIMD.**: Если вы обрабатываете одно поле множества объектов (например, все X координаты), SoA позволяет SIMD обрабатывать 8 значений одновременно.

## Теория

При проектировании структур данных разработчики инстинктивно используют объектно-ориентированный подход **Array of Structs (AoS)**:
```go
type Particle struct {
    X, Y, Z, Mass float32
}
var particles []Particle // AoS: [X Y Z M] [X Y Z M] [X Y Z M]
```

**Почему AoS катастрофичен для SIMD:**
Если требуется обновить только координату `X` всех частиц (например, \(X = X + V_x \cdot dt\)):
- Векторный регистр AVX2 может загрузить 8 чисел `float32` подряд.
- Но в формате AoS между соседними \(X_0\) и \(X_1\) лежат 12 байт посторонних данных (\(Y, Z, \text{Mass}\))!
- Чтобы загрузить 8 координат \(X\), процессору требуются медленные инструкции разреженного чтения (Gather / Scatter: `VGATHERDPS`), которые работают в 5–10 раз медленнее прямого линейного чтения.

**Решение: Struct of Arrays (SoA) / Data-Oriented Design:**
```go
type ParticlesSoA struct {
    X []float32 // Все X лежат непрерывно в памяти!
    Y []float32
    Z []float32
    Mass []float32
}
```
1. Координаты \(X\) образуют непрерывный блок памяти.
2. Векторный регистр AVX2 загружает ровно 8 координат \(X\) **за один такт** инструкцией `VMOVUPS`!
3. Никаких лишних данных в кэше L1, идеальная утилизация шины памяти, аппаратное ускорение в 8–10 раз!

## Решение по шагам

1. Создайте структуры `ParticleAoS` и `ParticlesSoA` на 1 000 000 элементов.
2. Реализуйте алгоритм физического сдвига координат \(X\) для модели AoS.
3. Реализуйте векторно-ориентированный сдвиг для модели SoA.
4. Проведите сравнительный замер времени выполнения.
5. Продемонстрируйте превосходство SoA по пропускной способности и объему кэш-трафика.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
)

// 1. Array of Structs (AoS) - классический ООП подход
type ParticleAoS struct {
	X, Y, Z, Mass float32
}

// 2. Struct of Arrays (SoA) - Data-Oriented Design подход
type ParticlesSoA struct {
	X []float32
	Y []float32
	Z []float32
	M []float32
}

func NewParticlesSoA(n int) *ParticlesSoA {
	return &ParticlesSoA{
		X: make([]float32, n),
		Y: make([]float32, n),
		Z: make([]float32, n),
		M: make([]float32, n),
	}
}

// UpdateAoS обновляет только X координаты в формате AoS
//
//go:noinline
func UpdateAoS(particles []ParticleAoS, dx float32) {
	for i := 0; i < len(particles); i++ {
		particles[i].X += dx // Шаг по памяти 16 байт, 12 байт читаются в кэш впустую!
	}
}

// UpdateSoA обновляет X координаты в формате SoA (идеально для SIMD)
//
//go:noinline
func UpdateSoA(x []float32, dx float32) {
	n := len(x)
	// Векторный шаг по 8 элементов
	for i := 0; i < (n/8)*8; i += 8 {
		x[i+0] += dx
		x[i+1] += dx
		x[i+2] += dx
		x[i+3] += dx
		x[i+4] += dx
		x[i+5] += dx
		x[i+6] += dx
		x[i+7] += dx
	}
	for i := (n / 8) * 8; i < n; i++ {
		x[i] += dx
	}
}

func main() {
	const count = 4000000
	const dx = 1.5

	aos := make([]ParticleAoS, count)
	soa := NewParticlesSoA(count)

	// 1. AoS Benchmark
	start1 := time.Now()
	UpdateAoS(aos, dx)
	dur1 := time.Since(start1)

	// 2. SoA Benchmark
	start2 := time.Now()
	UpdateSoA(soa.X, dx)
	dur2 := time.Since(start2)

	fmt.Println("=== Data-Oriented Design: AoS vs SoA for SIMD ===")
	fmt.Printf("Particles count: %d\n", count)
	fmt.Printf("AoS Update Time: %v (%.2f ns/op)\n", dur1, float64(dur1.Nanoseconds())/count)
	fmt.Printf("SoA Update Time: %v (%.2f ns/op)\n", dur2, float64(dur2.Nanoseconds())/count)

	if dur1 > dur2 {
		fmt.Printf("SoA Speedup:     %.2fx faster purely due to linear contiguous memory layout!\n",
			float64(dur1)/float64(dur2))
	}
	fmt.Printf("Sample result check: AoS X[0]=%.2f | SoA X[0]=%.2f\n", aos[0].X, soa.X[0])
}
```

ℹ️ Сравнение структур данных AoS и SoA и их влияние на кэш и SIMD-обработку.

## Под капотом

В формате AoS размер кэш-линии 64 байта вмещает ровно 4 структуры `ParticleAoS`. При обновлении только координаты `X` процессор вынужден прокачивать через шину памяти 64 байта, из которых полезными являются только 16 байт (эффективность кэша всего 25%). В формате SoA в 64-байтную кэш-линию помещается ровно 16 координат `X` подряд, обеспечивая 100% полезную утилизацию кэша L1/L2/L3.

## Подводные камни

1. Удаление/добавление элементов в SoA: при добавлении или удалении одного объекта в SoA приходится модифицировать сразу 4 отдельных среза, что усложняет код бизнес-логики.
2. Компромисс AoSoA (Array of Structs of Arrays): для баланса между удобством и скоростью часто используют чанки (например, массив структур из 64 элементов в SoA-виде).

## На собеседовании

«Почему современные высокопроизводительные движки (Apache Arrow, ClickHouse, DuckDB) хранят данные строго в колоночном формате (SoA), а не построчно (AoS)?». Ответ: колоночный формат позволяет применять прямое векторное сканирование SIMD по отдельным колонкам, сжимать однородные данные алгоритмами SIMD-BP (Bit Packing) и исключать чтение ненужных колонок с диска и из оперативной памяти.
