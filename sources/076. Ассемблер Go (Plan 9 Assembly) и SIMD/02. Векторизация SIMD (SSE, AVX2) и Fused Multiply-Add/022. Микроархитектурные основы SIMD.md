# Микроархитектурные основы SIMD: Векторные АЛУ, выравнивание и кэш L1

## Условие

Изучите аппаратную архитектуру векторных модулей процессора. Напишите сравнительный аналитический отчет и практический тест, объясняющие физическую разницу между скалярным конвейером и векторными execution ports (SSE, AVX, AVX-512, NEON), а также влияние 64-байтных границ кэш-линий на векторные инструкции.

### Исходная формулировка

**Векторизация (SIMD)**: Изучи, что такое SIMD (Single Instruction, Multiple Data). Обычный процессор складывает два массива в цикле по 1 элементу за раз. SIMD инструкции (например, AVX2) могут сложить по 4 или 8 чисел (`float64`) за ОДИН такт процессора!

## Теория

Чтобы осознанно применять SIMD в Go, инженер обязан понимать устройство процессорного ядра:

**1. Физические векторные регистры и Register Renaming:**
Хотя архитектура x86 декларирует шестнадцать 256-битных регистров `YMM0`–`YMM15`, внутри кристалла процессора физический файл регистров (Physical Register File — PRF) содержит 168–256 векторных регистров. Модуль переименования регистров устраняет ложные зависимости (Write-After-Read и Write-After-Write), позволяя выполнять независимые векторные операции параллельно.

**2. Порты исполнения (Execution Ports):**
Например, в микроархитектуре Intel Raptor Lake / AMD Zen 4:
- Порт 0: Векторное FMA, побитовые операции, векторный сдвиг.
- Порт 1: Векторное FMA, векторное сложение.
- Порт 5: Векторные перестановки (Shuffle), упаковка/распаковка.
Если алгоритм состоит только из векторных умножений и сложений, он идеально загружает порты 0 и 1, утилизируя 100% мощности обоих векторных блоков ядра.

**3. Проблема пересечения границ кэш-линий (Split Loads):**
Размер кэш-линии процессора составляет 64 байта.
- Если 32-байтный вектор AVX2 читается по адресу, кратному 32 (выровнен): чтение происходит мгновенно из L1-кэша.
- Если 32-байтный вектор пересекает границу 64-байтной кэш-линии (Split Load): контроллеру кэша требуется прочитать **две разные кэш-линии**, объединить их во внутреннем буфере и только потом отдать в регистр. Это снижает скорость чтения в 2–3 раза!

## Решение по шагам

1. Создайте структуру исследования микроархитектурных метрик SIMD.
2. Продемонстрируйте проверку выравнивания адреса по границе 32 байт: `uintptr(ptr) % 32 == 0`.
3. Реализуйте тест чтения выровненных и невыровненных векторов памяти.
4. Проанализируйте штраф пересечения кэш-линий (Split Load Penalty).
5. Сформулируйте правила аллокации памяти под SIMD-обработку в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"time"
	"unsafe"
)

func main() {
	fmt.Println("=== CPU SIMD Microarchitecture Deep Dive ===")
	fmt.Println("1. Vector Register Sizes:")
	fmt.Println("   SSE (128-bit):     4 x float32 or 2 x int64")
	fmt.Println("   AVX2 (256-bit):    8 x float32 or 4 x int64")
	fmt.Println("   AVX-512 (512-bit): 16 x float32 or 8 x int64")
	fmt.Println("   ARM NEON (128-bit):4 x float32 or 2 x int64")

	// Тест выравнивания и Split Load Penalty
	const size = 16 * 1024 * 1024 // 16 MB
	rawMemory := make([]byte, size+64)

	// Находим идеально выровненный по 64 байта адрес
	baseAddr := uintptr(unsafe.Pointer(&rawMemory[0]))
	alignedOffset := (64 - (baseAddr % 64)) % 64
	alignedPtr := unsafe.Pointer(baseAddr + alignedOffset)

	// Невыровненный адрес, гарантированно пересекающий границу 64-байтной кэш-линии (смещение 48)
	misalignedPtr := unsafe.Pointer(baseAddr + alignedOffset + 48)

	fmt.Println("\n2. Cache Line Crossing Analysis (64-byte line):")
	fmt.Printf("   Aligned Address:    0x%X (mod 64 = %d) -> Clean L1 Hit\n",
		uintptr(alignedPtr), uintptr(alignedPtr)%64)
	fmt.Printf("   Misaligned Address: 0x%X (mod 64 = %d) -> Crosses 64-byte boundary (Split Load)!\n",
		uintptr(misalignedPtr), uintptr(misalignedPtr)%64)

	const iters = 50000000
	// 1. Чтение выровненного 32-байтного слова
	start1 := time.Now()
	var sink1 uint64
	for i := 0; i < iters; i++ {
		sink1 += *(*uint64)(alignedPtr)
	}
	dur1 := time.Since(start1)

	// 2. Чтение невыровненного слова
	start2 := time.Now()
	var sink2 uint64
	for i := 0; i < iters; i++ {
		sink2 += *(*uint64)(misalignedPtr)
	}
	dur2 := time.Since(start2)

	fmt.Printf("\nAligned Memory Read:   %v (%.2f ns/op)\n", dur1, float64(dur1.Nanoseconds())/iters)
	fmt.Printf("Misaligned Read:       %v (%.2f ns/op)\n", dur2, float64(dur2.Nanoseconds())/iters)
	if dur2 > dur1 {
		fmt.Printf("Split Load Overhead:   %.2fx slower due to cache-line boundary crossings!\n",
			float64(dur2)/float64(dur1))
	}

	if sink1 == 0 && sink2 == 0 {
		_ = sink1
	}
}
```

ℹ️ Микроархитектурный анализ векторных регистров и штрафа Split Load.

## Под капотом

В современных процессорах аппаратный блок Load-Store Unit (LSU) способен выполнять два 256-битных чтения и одну 256-битную запись за один такт ядра. Однако при возникновении Split Load (когда 32-байтный вектор переходит через адрес, кратный 64), операция распадается на две микрооперации (uOps), блокируя порты загрузки на дополнительный такт.

## Подводные камни

1. Аллокации срезов в Go: стандартный `make([]float32, n)` не гарантирует выравнивание по границе 32 байт. Для критических структур используют слайсы с запасом в 32 байта и ручным сдвигом указателя.
2. Неверный расчет SIMD-ширины: написание кода в расчете на 512-битный AVX-512 на машинах без его поддержки приведет к аварийной остановке программы.

## На собеседовании

«Почему AVX-512 часто называют спорной технологией для бэкенд-серверов?». Ответ: первые реализации AVX-512 (Skylake-SP) требовали повышенного напряжения питания, что заставляло процессор временно снижать базовую частоту ВСЕХ ядер на сокете (AVX Frequency Throttling). Если тяжелый AVX-код выполнялся редко, замедление остальных скалярных горутин перекрывало выгоду от векторизации. В современных архитектурах (Zen 4, Sapphire Rapids) эта проблема устранена.
