# Глубокое дизассемблирование через go tool compile -S: стек, TLS и Safepoints

## Условие

Изучите машинный код, генерируемый компилятором Go (`go tool compile -S`). Разберите пролог и эпилог функции, механизм динамического расширения стека (`runtime.morestack`), размещение Thread-Local Storage (TLS) и точки безопасной остановки сборщика мусора (GC Preemption Safepoints).

### Исходная формулировка

**Дизассемблирование**: Напиши простую функцию на Go и скомпилируй её командой `go tool compile -S math.go`. Изучи сгенерированный ассемблерный код. Найди, как компилятор настраивает стек-фреймы и как передает регистры (в современном Go используется register-based calling convention).

## Теория

Когда компилятор Go компилирует функцию, он генерирует не только бизнес-логику, но и служебный код поддержки рантайма:

**1. Пролог функции и динамический стек (Stack Split Check):**
Стек горутины при создании занимает всего 2 КБ. Чтобы стек не переполнился, компилятор вставляет в начало каждой функции (если нет `NOSPLIT`):
```asm
MOVQ (TLS), CX       // Получаем указатель на структуру g (текущая горутина)
CMPQ SP, 16(CX)      // Сравниваем SP со stackguard0
JLS  call_morestack  // Если SP <= stackguard0, стек почти полон!
CALL runtime.morestack_noctxt(SB)
```
Функция `runtime.morestack` выделяет новый блок стека удвоенного размера (4 КБ, 8 КБ...), копирует данные, корректирует указатели и возвращает выполнение.

**2. Кооперативное вытеснение (Non-cooperative Preemption) и Safepoints:**
Сборщик мусора (GC) обязан периодически останавливать горутины для фазы сканирования корней стека (STW).
Компилятор внедряет метаданные `PCDATA` (Program Counter Data) и `FUNCDATA` (Function Data), которые указывают сборщику мусора, в каких регистрах и слотах стека в данный момент находятся живые указатели на объекты в куче.

**3. Эпилог функции:**
Восстановление регистра фрейма `BP` (если включен Frame Pointer) и возврат `RET`.

## Решение по шагам

1. Создайте структуру анализа служебных метаданных рантайма Go.
2. Продемонстрируйте пролог стековой проверки `CMPQ SP, (R14)`.
3. Разберите назначение метаданных `PCDATA $0, $stack_map`.
4. Объясните, почему инкремент стека работает незаметно для разработчика.
5. Запустите демонстрационный отчет с картой пролога и эпилога функции.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

// TargetFunction для исследования ассемблерного листинга
//
//go:noinline
func TargetFunction(a, b int64) int64 {
	// Компилятор сгенерирует:
	// 1. Пролог: проверка стека
	// 2. Тело: сложение
	// 3. Эпилог: очистка и возврат
	return (a * 3) + (b * 5)
}

func main() {
	fmt.Println("=== Deep Disassembly Analysis (go tool compile -S) ===")
	fmt.Printf("Go Version: %s | Compiler: gc\n\n", runtime.Version())

	fmt.Println("1. FUNCTION PROLOGUE:")
	fmt.Println("   TEXT \"\".TargetFunction(SB), ABIInternal, $0-16")
	fmt.Println("   CMPQ SP, 16(R14)                // R14 points to current goroutine *g")
	fmt.Println("   JLS  morestack                   // If stack exhausted, jump to runtime")
	fmt.Println("   // ... function body executes ...")

	fmt.Println("\n2. RUNTIME METADATA (GC Safepoints):")
	fmt.Println("   PCDATA  $0, $0                   // Stack map index at entry")
	fmt.Println("   FUNCDATA $0, gclocals...          // Pointer bitmask of live stack objects")
	fmt.Println("   FUNCDATA $1, gclocals...          // Arguments pointer bitmask")

	fmt.Println("\n3. FUNCTION EPILOGUE:")
	fmt.Println("   RET                              // Return with RAX holding result")
	fmt.Println("morestack:")
	fmt.Println("   CALL runtime.morestack_noctxt(SB)// Allocates larger contiguous stack")
	fmt.Println("   JMP  start                       // Retries function execution")

	res := TargetFunction(10, 20)
	fmt.Printf("\nTargetFunction(10, 20) = %d\n", res)
}
```

ℹ️ Анализ пролога проверки переполнения стека и метаданных сборщика мусора.

## Под капотом

В Go 1.14+ появилась асинхронная вытесняющая многозадачность (Asynchronous Preemption): операционная система посылает потоку \(M\) сигнал `SIGURG`. Обработчик сигнала приостанавливает выполнение горутины, анализирует метаданные `PCDATA` для текущего счетчика инструкций `PC` и переключает контекст на другую готовую горутину, даже если текущая горутина крутится в бесконечном цикле без вызовов функций.

## Подводные камни

1. Ассемблер без проверок точек вытеснения: рукописная ассемблерная функция с бесконечным циклом без вызовов Go-кода не может быть вытеснена планировщиком (сигнал `SIGURG` не знает, как безопасно остановить рукописный код без stack maps). Это может заблокировать сборщик мусора Go.
2. Проблема Stack Growth: если ассемблерная функция не помечена `NOSPLIT`, но не настроила фрейм аргументов `$locals-args`, вызов `morestack` завершится фатальным крахом рантайма.

## На собеседовании

«Почему размер минимального стека горутины в Go уменьшили с 4 КБ до 2 КБ в Go 1.4?». Ответ: благодаря этому миллион горутин в памяти требует всего около 2 ГБ RAM (вместо 4 ГБ). Если бы стек горутин был фиксированным (как в C/C++ потоках pthread — 2–8 МБ), создание сотен тысяч конкурентных соединений было бы физически невозможно.
