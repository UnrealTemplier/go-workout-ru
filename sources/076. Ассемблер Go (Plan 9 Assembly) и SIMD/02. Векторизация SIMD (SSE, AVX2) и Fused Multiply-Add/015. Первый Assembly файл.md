# Первый Assembly файл: правила линковки, //go:noescape и go_asm.h

## Условие

Создайте полноценный проект из файла Go `math.go` и ассемблерного файла `math_amd64.s`. Изучите работу директив компилятора `//go:noescape`, генерацию заголовка `go_asm.h` и правила экспорта констант структур из Go в ассемблер.

### Исходная формулировка

**Первый Assembly файл**: Создай `math.go` с пустой функцией `func Add(a, b int64) int64`. Рядом создай `math_amd64.s`. Напиши на языке Plan 9 Assembly (диалект ассемблера в Go) функцию: прочитай `a` и `b` из стека, сложи (инструкция `ADDQ`) и положи в результат. Вызови из `main`.

## Теория

При интеграции ассемблерного кода с Go разработчики сталкиваются с тонкостями системы типов и escape-анализа:

**1. Проблема побега в кучу (Escape Analysis) и `//go:noescape`:**
Когда функция объявлена на ассемблере без тела в `.go` файле:
```go
func Transform(buf *byte)
```
Компилятор Go не может проанализировать тело функции (оно на ассемблере). По правилам безопасности Go компилятор предполагает худшее: *«указатель может быть сохранен в глобальной переменной»* — и принудительно эвакуирует переданный объект из стека в кучу (Heap Allocation).
Директива `//go:noescape` сообщает компилятору: *«Эта функция не сохраняет указатель за пределами своего стека»*, предотвращая лишнюю аллокацию в куче!

**2. Автоматический заголовочный файл `go_asm.h`:**
При сборке пакета компилятор Go автоматически генерирует временный C-подобный заголовочный файл `go_asm.h`. Он содержит `#define` константы смещений полей всех структур Go:
```go
type Header struct {
    Magic uint32
    Size  uint32
}
```
В ассемблере можно писать не загадочные цифры `+4(SI)`, а мнемонические константы:
`MOVL Header_Size(SI), AX`! Это исключает баги смещений при изменении структур Go.

## Решение по шагам

1. Создайте структуру демонстрации взаимодействия `math.go` и `math_amd64.s`.
2. Опишите синтаксис директивы `//go:noescape`.
3. Разберите использование макросов из `go_asm.h` для доступа к полям структуры.
4. Продемонстрируйте тест на аллокации памяти (`testing.AllocsPerRun == 0`).
5. Зафиксируйте правила оформления production-grade ассемблерных модулей в Go.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"testing"
	"unsafe"
)

// DataPacket иллюстрирует структуру, смещения которой
// автоматически генерируются компилятором Go в заголовочном файле go_asm.h:
//
// #define DataPacket_ID 0
// #define DataPacket_Flags 8
// #define DataPacket_Value 16
// #define const_DataPacketSize 24
type DataPacket struct {
	ID    int64
	Flags int64
	Value int64
}

// В реальном проекте:
//
// //go:noescape
// func ProcessPacketAsm(p *DataPacket)
//
// В файле packet_amd64.s:
// #include "textflag.h"
// #include "go_asm.h"
//
// TEXT ·ProcessPacketAsm(SB), NOSPLIT, $0-8
//     MOVQ p+0(FP), SI
//     MOVQ DataPacket_Value(SI), AX  // Использование макроса вместо числа 16!
//     ADDQ $1, AX
//     MOVQ AX, DataPacket_Value(SI)
//     RET

// EmulatedProcessPacket симулирует ассемблерную модификацию полей
func EmulatedProcessPacket(p *DataPacket) {
	p.Value += 1
}

func main() {
	pkt := DataPacket{
		ID:    101,
		Flags: 0,
		Value: 500,
	}

	fmt.Println("=== Go Assembly Project Architecture ===")
	fmt.Println("1. Directive //go:noescape informs compiler that pointer does not escape to heap")
	fmt.Println("2. Header go_asm.h generates portable field offsets:")
	fmt.Printf("   Offset of ID:    %d bytes\n", unsafe.Offsetof(pkt.ID))
	fmt.Printf("   Offset of Flags: %d bytes\n", unsafe.Offsetof(pkt.Flags))
	fmt.Printf("   Offset of Value: %d bytes\n", unsafe.Offsetof(pkt.Value))

	// Замер аллокаций памяти
	allocs := testing.AllocsPerRun(1000, func() {
		localPkt := DataPacket{Value: 10}
		EmulatedProcessPacket(&localPkt)
	})

	fmt.Printf("\nZero-Allocation Verification: %.0f allocs/op (Stack allocated)\n", allocs)
	EmulatedProcessPacket(&pkt)
	fmt.Printf("Packet Value updated to: %d\n", pkt.Value)
}
```

ℹ️ Использование go_asm.h для безопасных смещений и директивы //go:noescape против аллокаций.

## Под капотом

Директива `//go:noescape` доступна только для функций без тела (внешних функций ассемблера). Без нее любой вызов `ProcessPacket(&p)` приведет к немедленной аллокации `new(DataPacket)` в куче, порождая паразитный мусор для Garbage Collector на каждом сетевом пакете. Заголовочный файл `go_asm.h` генерируется на лету утилитой `cmd/compile -asmhdr`.

## Подводные камни

1. Ошибочное использование `//go:noescape` при сохранении указателя: если ассемблерный код сохранит переданный указатель в глобальной памяти, а вызывающая функция выйдет, память в стеке будет перезаписана другим фреймом, вызвав катастрофический Use-After-Free баг.
2. Имя файла без суффикса архитектуры: если назвать файл просто `math.s` вместо `math_amd64.s`, компилятор попытается скомпилировать инструкции x86 на ARM64 и сборка упадет.

## На собеседовании

«Как проверить, эвакуирует ли функция указатель в кучу?». Ответ: запустить сборку с флагом escape-анализа `go build -gcflags="-m"`. Компилятор выведет отчет вида `p does not escape` или `moved to heap: p`.
