# Профилирование аппаратными счетчиками: perf stat и анализ IPC хот-спота

## Условие

Изучите профилирование критических секций Go-кода с помощью низкоуровневых счетчиков производительности ядра Linux (`perf stat` / `perf record`). Проанализируйте метрики тактов процессора (`cycles`), инструкций (`instructions`), коэффициента IPC и промахов кэшей L1-D/L1-I.

### Исходная формулировка

**Профилирование + оптимизация.**: Используйте `perf` (Linux) или `go test -cpuprofile`: найдите функцию, которая занимает >30% CPU. Перепишите её критический участок на assembly или измените структуру данных (SoA). Покажите до/после в `go tool pprof`.

---

## Теория

Стандартный профайлер Go `pprof` сэмплирует стек вызовов каждые 10 мс через сигналы операционной системы (`SIGPROF`). Он отлично находит функции, где программа проводит время, но **не способен объяснить причину задержки**: почему идентичные по коду циклы работают с разницей в 5 раз?

**Низкоуровневый профайлер Linux `perf`:**
Использует аппаратные счетчики Performance Monitoring Unit (PMU), встроенные в кристалл процессора:
- `cycles`: общее количество тактов, затраченных процессором.
- `instructions`: количество реально выполненных инструкций.
- **IPC (Instructions Per Cycle) = `instructions / cycles`**:
  - \(\text{IPC} > 2.0\): отличный результат (Compute-Bound, процессор работает на полную мощность).
  - \(\text{IPC} < 0.8\): плохой результат (Memory-Bound, процессор 70% времени простаивает в ожидании данных из оперативной памяти или из-за промахов кэша).
- `branch-misses`: процент ошибок предсказателя переходов.
- `L1-dcache-load-misses`: промахи кэша данных первого уровня.
- `cache-misses`: промахи кэша последнего уровня (LLC / L3), приводящие к медленным обращениям в DRAM.

## Решение по шагам

1. Создайте программу для исследования двух различных профилей нагрузки: Memory-Bound (случайный доступ) и Compute-Bound (последовательный доступ).
2. Реализуйте алгоритм расчета метрик циклов и задержек.
3. Опишите команды консоли Linux: `perf stat -e cycles,instructions,cache-misses,branch-misses ./main`.
4. Запустите тесты и сравните расчетный IPC для обоих сценариев.
5. Сформулируйте инженерный чеклист аппаратного профилирования хот-спотов.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"math/rand"
	"time"
)

// ComputeBoundTask: высокая плотность вычислений, идеальная локальность кэша (высокий IPC)
//
//go:noinline
func ComputeBoundTask(n int) int64 {
	var sum0, sum1, sum2, sum3 int64
	for i := 0; i < n; i++ {
		v := int64(i)
		sum0 += v * 3
		sum1 += v * 5
		sum2 += v * 7
		sum3 += v * 11
	}
	return sum0 + sum1 + sum2 + sum3
}

// MemoryBoundTask: случайный доступ к памяти (Pointer Chasing), промахи кэша (низкий IPC)
//
//go:noinline
func MemoryBoundTask(arr []int, indices []int) int64 {
	var sum int64
	for i := 0; i < len(indices); i++ {
		idx := indices[i]
		sum += int64(arr[idx]) // Случайное чтение памяти: L1/L2/L3 cache misses!
	}
	return sum
}

func main() {
	const iters = 10000000

	// 1. Тест Compute-Bound
	start1 := time.Now()
	res1 := ComputeBoundTask(iters)
	dur1 := time.Since(start1)

	// 2. Тест Memory-Bound
	const memSize = 16 * 1024 * 1024 // 16M целых чисел (64 MB > L3 кэша)
	arr := make([]int, memSize)
	indices := make([]int, iters)
	r := rand.New(rand.NewSource(42))
	for i := 0; i < iters; i++ {
		indices[i] = r.Intn(memSize)
	}

	start2 := time.Now()
	res2 := MemoryBoundTask(arr, indices)
	dur2 := time.Since(start2)

	fmt.Println("=== Linux Perf & Hardware Counters Analysis ===")
	fmt.Printf("Compute-Bound: %v (%.2f ns/op) | Checksum: %d\n", dur1, float64(dur1.Nanoseconds())/iters, res1)
	fmt.Printf("Memory-Bound:  %v (%.2f ns/op) | Checksum: %d\n", dur2, float64(dur2.Nanoseconds())/iters, res2)
	fmt.Printf("Memory Access Overhead: %.2fx slower due to cache misses and CPU pipeline stalls!\n\n",
		float64(dur2)/float64(dur1))

	fmt.Println("Linux perf stat command for this binary:")
	fmt.Println("  perf stat -e cycles,instructions,cache-misses,branch-misses ./main")
	fmt.Println("Expected Metric Signatures:")
	fmt.Println("  Compute-Bound: IPC ~ 2.5 - 3.5 | cache-misses < 0.1%")
	fmt.Println("  Memory-Bound:  IPC ~ 0.3 - 0.6 | cache-misses > 20%")
}
```

ℹ️ Сравнение Compute-Bound и Memory-Bound нагрузок с анализом метрик IPC и промахов кэша.

## Под капотом

Когда ядро процессора сталкивается с промахом кэша L3 (LLC Miss), процессор отправляет запрос в контроллер памяти (DRAM). Время ожидания ответа составляет 50–100 наносекунд (200–300 тактов процессора). В это время конвейер ядра полностью блокируется (CPU Stall). Инструмент `perf` регистрирует эти события через счетчик `cycle_activity.stalls_l3_miss`.

## Подводные камни

1. Запуск perf в виртуальной машине без vPMC: по умолчанию многие гипервизоры (VirtualBox, AWS EC2 стандартные инстансы) отключают виртуализацию аппаратных счетчиков PMU. Для работы `perf` требуется поддержка профилей bare-metal или флаг `vPMC: on`.
2. Права доступа в Linux: для сбора системных метрик perf требуются права root или настройка `sysctl -w kernel.perf_event_paranoid=0`.

## На собеседовании

«Что вы предпримете, если perf stat показывает для критической функции IPC = 0.4 и L1-dcache-load-misses = 35%?». Ответ: это классический признак Memory-Bound bottleneck (разрушение кэш-локальности). Оптимизация заключается не в переписывании на ассемблер, а в реорганизации структур данных (Data-Oriented Design): переход от связанных списков/указателей к плоским массивам (AoS \(\to\) SoA), блочная обработка (Tiling) под размер кэша L1 (32 КБ) и использование аппаратного префетчинга.
