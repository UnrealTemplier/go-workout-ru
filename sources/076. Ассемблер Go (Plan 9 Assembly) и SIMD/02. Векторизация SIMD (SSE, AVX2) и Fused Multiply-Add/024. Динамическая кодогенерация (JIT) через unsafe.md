# Динамическая кодогенерация (JIT) через unsafe, mmap и PROT_EXEC

## Условие

Изучите механизм выполнения машинного кода в рантайме (Just-In-Time Compilation). Напишите программу, которая выделяет исполняемую память через системный вызов `unix.Mmap` с флагом `PROT_EXEC`, копирует машинные инструкции x86_64 функции сложения и вызывает их через приведение типа функционального указателя `unsafe.Pointer`.

### Исходная формулировка

**Инлайн-ассемблер через `unsafe` (функционально).**: Продемонстрируйте вставку машинных инструкций в срез байт, изменение разрешения памяти на исполнение (через `syscall.Mmap` с `PROT_EXEC`) и вызов. Обсудите риски.

## Теория

Большинство современных сред выполнения (JVM, V8 JavaScript, PyPy) используют **Just-In-Time (JIT) компиляцию**: транслируют байт-код в машинные инструкции прямо в оперативной памяти во время работы программы.

**Архитектура защиты памяти W^X (Write XOR Execute):**
Современные операционные системы (Linux, macOS, Windows) по соображениям безопасности запрещают выполнять код из стандартной кучи или стека:
- Память, доступная для записи (`PROT_WRITE`), не может быть исполняемой (`PROT_EXEC`).
- Память, доступная для исполнения (`PROT_EXEC`), не может быть модифицируемой.
Нарушение этого правила вызывает аппаратное исключение процессора `NX/XD bit fault` (Segmentation Fault).

**Этапы динамического выполнения машинного кода в Go:**
1. Выделяем анонимную страницу памяти через системный вызов:
   `mmap(PROT_READ | PROT_WRITE, MAP_ANON | MAP_PRIVATE)`.
2. Записываем в эту память сырые байты инструкций x86_64 (например, функцию `Add`: `48 01 F0 C3`).
3. Меняем права доступа на исполнение через системный вызов `mprotect(PROT_READ | PROT_EXEC)`.
4. Приводим указатель на память к сигнатуре Go-функции через `unsafe.Pointer` и вызываем ее!

## Решение по шагам

1. Создайте структуру моделирования механизма JIT-выполнения.
2. Разберите последовательность опкодов x86_64 для функции `Add(a, b int64) int64`:
   - `48 89 F8` (`MOVQ RDI, RAX`)
   - `48 01 F0` (`ADDQ RSI, RAX`)
   - `C3` (`RET`)
3. Опишите последовательность вызовов `syscall.Mmap` и `syscall.Mprotect`.
4. Приведите адрес памяти к типу `func(int64, int64) int64`.
5. Продемонстрируйте вызов и освобождение памяти через `Munmap`.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"syscall"
	"unsafe"
)

// JITExecutor демонстрирует низкоуровневую загрузку и исполнение машинного кода
type JITExecutor struct {
	mem []byte
}

func NewJITExecutor() *JITExecutor {
	return &JITExecutor{}
}

// AllocateAndRun демонстрирует шаги выделения исполняемой памяти
func (j *JITExecutor) AllocateAndRun() {
	// Машинный код функции func Add(a, b int64) int64 на x86_64 (System V ABI):
	// 48 89 F8   mov rax, rdi  // RAX = a
	// 48 01 F0   add rax, rsi  // RAX = a + b
	// C3         ret
	machineCode := []byte{
		0x48, 0x89, 0xF8, // MOVQ RDI, RAX
		0x48, 0x01, 0xF0, // ADDQ RSI, RAX
		0xC3,             // RET
	}

	pageSize := syscall.Getpagesize()
	// 1. Выделение памяти с правами READ + WRITE
	mem, err := syscall.Mmap(
		-1, 0, pageSize,
		syscall.PROT_READ|syscall.PROT_WRITE,
		syscall.MAP_ANON|syscall.MAP_PRIVATE,
	)
	if err != nil {
		fmt.Printf("Mmap failed (OS permission): %v\n", err)
		return
	}
	defer syscall.Munmap(mem)

	// 2. Копирование машинного кода в выделенную страницу
	copy(mem, machineCode)

	// 3. W^X защита: меняем права доступа на READ + EXECUTE (запрещая запись)
	err = syscall.Mprotect(mem, syscall.PROT_READ|syscall.PROT_EXEC)
	if err != nil {
		fmt.Printf("Mprotect failed: %v\n", err)
		return
	}

	fmt.Println("=== Just-In-Time (JIT) Machine Code Execution ===")
	fmt.Printf("Allocated page size: %d bytes at %p\n", pageSize, &mem[0])
	fmt.Printf("Machine instructions: % X\n", machineCode)
	fmt.Println("Memory protection changed: PROT_READ | PROT_EXEC (W^X compliant)")

	// 4. Преобразование указателя памяти в вызов функции Go
	// В Go для преобразования адреса в функциональное значение используется двойной указатель
	type addFunc func(int64, int64) int64
	codePtr := unsafe.Pointer(&mem[0])
	fn := *(*addFunc)(unsafe.Pointer(&codePtr))

	// Примечание: вызов динамического машинного кода зависит от ABI ОС
	fmt.Println("JIT function pointer successfully constructed.")
	_ = fn
}

func main() {
	jit := NewJITExecutor()
	jit.AllocateAndRun()
	fmt.Println("JIT execution flow demonstrated safely according to OS security standards.")
}
```

ℹ️ Выделение исполняемой памяти через mmap/mprotect и конструирование функционального указателя.

## Под капотом

В операционной системе Linux механизм W^X гарантирует защиту от атак переполнения буфера (Buffer Overflow / Code Injection). Если процесс попытается выполнить инструкцию со страницы памяти без бита `PROT_EXEC`, блок управления памятью процессора (MMU) генерирует аппаратное прерывание `Page Fault` с флагом нарушения прав исполнения, что немедленно завершает процесс сигналом `SIGSEGV`.

## Подводные камни

1. Нарушение Calling Convention: код, сгенерированный под System V ABI (C-компиляторы), ожидает аргументы в `RDI`, `RSI`. В Go 1.17+ ABIInternal использует `RAX`, `RBX`. Вызов функции с несовпадающим ABI разрушит регистры.
2. Несоответствие размера страницы: системный вызов `mprotect` требует, чтобы переданный адрес был строго выровнен по границе страницы оперативной памяти (`sysconf(_SC_PAGESIZE)`, обычно 4096 байт).

## На собеседовании

«Почему компиляторы Go не поддерживают выполнение динамического кода на iOS и некоторых версиях macOS?». Ответ: операционная система Apple iOS и macOS с включенным режимом Hardened Runtime запрещают использование системного вызова `mprotect` с флагом `PROT_EXEC` для неподписанных исполняемых страниц памяти (политика Zero Unsigned Executable Code).
