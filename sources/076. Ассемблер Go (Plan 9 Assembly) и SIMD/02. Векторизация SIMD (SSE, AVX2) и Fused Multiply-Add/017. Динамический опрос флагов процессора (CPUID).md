# Динамический опрос флагов процессора (CPUID) и Runtime Dispatch

## Условие

Реализуйте механизм динамического выбора алгоритма (Runtime Dispatching) в зависимости от аппаратных возможностей процессора хоста (AVX2, SSE4.2, ARM NEON). Обеспечьте быстрый вызов оптимизированной векторной функции при наличии флагов и безопасный скалярный Fallback на устаревших серверах.

### Исходная формулировка

**Работа с флагами процессора.**: Определите поддержку AVX2/SSE4.2 через `runtime` или `golang.org/x/sys/cpu`. Используйте условный вызов asm-функции при наличии SIMD, иначе – fallback на Go.

## Теория

При дистрибуции скомпилированных бинарных файлов Go (например, через Docker-образы или пакетные менеджеры) сервис должен надежно запускаться на любом оборудовании — от старых облачных виртуальных машин 2012 года (где нет AVX2) до новейших серверов AMD EPYC / Intel Xeon.

Если скомпилировать бинарник с безусловными инструкциями AVX2, на старом процессоре программа немедленно упадет с фатальной ошибкой ядра ОС `SIGILL: illegal instruction`.

**Паттерн Runtime Feature Dispatching (CPU Detection):**
1. **Инициализация при старте (`init()`)**:
   - Программа опрашивает аппаратные регистры процессора через инструкцию `CPUID` (в Go доступно через пакет `internal/cpu` или `golang.org/x/sys/cpu`).
   - Проверяется флаг `cpu.X86.HasAVX2` или `cpu.ARM64.HasASIMD`.
2. **Указатель на функцию (Function Pointer Dispatch)**:
   - Объявляется глобальная переменная функции: `var vectorAddFn func(a, b, res []float32)`.
   - Если AVX2 поддерживается процессором, переменная инициализируется ассемблерной функцией `AddFloatsAVX2`.
   - Если AVX2 отсутствует, выставляется скалярный безопасный fallback `AddFloatsScalar`.
3. При каждом вызове в рантайме нет никаких `if`: вызов идет прямо по указателю на функцию!

## Решение по шагам

1. Создайте структуру детектора возможностей процессора (симуляция `CPUID`).
2. Объявите сигнатуру функции и глобальную переменную диспетчера.
3. Реализуйте скалярную реализацию (Fallback).
4. Реализуйте оптимизированную реализацию (AVX2).
5. Напишите функцию `initDispatcher()`, выбирающую алгоритм, и протестируйте оба сценария.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
	"runtime"
)

// CPUFeatures симулирует флаги, определяемые через инструкцию CPUID
type CPUFeatures struct {
	HasAVX2 bool
	HasSSE42 bool
	HasAVX512 bool
}

// Диспетчеризуемая функция
var processBatchFn func(dst, src []float32)

// Скалярный fallback для любых CPU
func processBatchScalar(dst, src []float32) {
	for i := range src {
		dst[i] = src[i] * 2.0
	}
}

// Оптимизированный AVX2 обработчик
func processBatchAVX2(dst, src []float32) {
	n := len(src)
	// Векторная обработка по 8 элементов
	for i := 0; i < (n/8)*8; i += 8 {
		dst[i+0] = src[i+0] * 2.0
		dst[i+1] = src[i+1] * 2.0
		dst[i+2] = src[i+2] * 2.0
		dst[i+3] = src[i+3] * 2.0
		dst[i+4] = src[i+4] * 2.0
		dst[i+5] = src[i+5] * 2.0
		dst[i+6] = src[i+6] * 2.0
		dst[i+7] = src[i+7] * 2.0
	}
	for i := (n / 8) * 8; i < n; i++ {
		dst[i] = src[i] * 2.0
	}
}

// initDispatch настраивает глобальный указатель при старте
func initDispatch(features CPUFeatures) {
	if features.HasAVX2 && runtime.GOARCH == "amd64" {
		processBatchFn = processBatchAVX2
		fmt.Println("[Dispatcher] Hardware AVX2 detected: Activated 256-bit SIMD fast path.")
	} else {
		processBatchFn = processBatchScalar
		fmt.Println("[Dispatcher] Fallback mode: Activated generic scalar path.")
	}
}

func main() {
	fmt.Println("=== Runtime CPU Feature Detection & Dispatching ===")
	fmt.Printf("OS: %s | Architecture: %s\n\n", runtime.GOOS, runtime.GOARCH)

	// Сценарий 1: Современный хост с AVX2
	initDispatch(CPUFeatures{HasAVX2: true, HasSSE42: true})
	src := []float32{1.5, 2.5, 3.5, 4.5, 5.5, 6.5, 7.5, 8.5}
	dst := make([]float32, len(src))
	processBatchFn(dst, src)
	fmt.Printf("AVX2 Result: %v\n\n", dst)

	// Сценарий 2: Устаревший хост без AVX2 (симуляция)
	initDispatch(CPUFeatures{HasAVX2: false, HasSSE42: true})
	processBatchFn(dst, src)
	fmt.Printf("Scalar Result: %v\n", dst)
}
```

ℹ️ Динамический выбор аппаратного пути (Runtime Dispatching) по флагам CPUID.

## Под капотом

В стандартной библиотеке Go (например, `crypto/aes`, `math/big`, `bytes.IndexByte`) используется точно такой же паттерн: в файле `cpu_x86.go` при инициализации вызывается ассемблерная функция `runtime.cpuid`, а глобальные функциональные указатели выставляются один раз при загрузке программы. Это исключает накладные расходы на проверку флагов `if hasAVX2` внутри каждого вызова.

## Подводные камни

1. Проверка `runtime.GOARCH`: флаг `HasAVX2` имеет смысл проверять только на `amd64`. Если забыть проверку архитектуры, компиляция под `arm64` или `riscv64` сломается.
2. Косвенный вызов функции (Indirect Call): вызов через указатель `processBatchFn()` не может быть инлайнен компилятором. Для ультра-коротких функций (менее 5 нс) накладные расходы на косвенный вызов могут нивелировать выигрыш от SIMD.

## На собеседовании

«Как в Go работает переменная окружения GODEBUG=cpu.all=off?». Ответ: флаги `GODEBUG` позволяют принудительно отключить использование расширений процессора (AVX, SSE, AES) рантаймом Go. Это используется в тестировании и CI/CD пайплайнах для проверки работоспособности Fallback-веток кода на современном оборудовании.
