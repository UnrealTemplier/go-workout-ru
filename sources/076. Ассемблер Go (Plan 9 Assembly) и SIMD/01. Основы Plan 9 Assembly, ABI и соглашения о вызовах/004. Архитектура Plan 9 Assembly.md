# Архитектура Plan 9 Assembly и первая функция на ассемблере Go

## Условие

Изучите синтаксис ассемблера Plan 9, принятого в Go. Реализуйте и разберите ассемблерную функцию сложения `Add(x, y int) int`, связываемую с декларацией в Go без тела. Объясните назначение флагов NOSPLIT, директивы TEXT и спецификации фрейма `$0-24`.

### Исходная формулировка

**Первая функция на ассемблере Go.**: Напишите ассемблерный файл `.s` с функцией `Add(x, y int) int`, использующей инструкции `ADDQ`. Свяжите с Go-функцией, объявленной как `func Add(x, y int) int` без тела.

## Теория

Ассемблер Go не использует синтаксис Intel или AT&T. Он происходит от операционной системы **Plan 9 from Bell Labs**, созданной авторами C и Unix (Кен Томпсон, Роб Пайк).

**Главные отличия Plan 9 Assembly:**
1. **Порядок операндов**: источник слева, приемник справа:
   `ADDQ AX, BX` означает `BX = BX + AX` (как в AT&T, но без префиксов `%` и `$`).
2. **Псевдорегистры (Pseudo-registers)**:
   - `SB` (Static Base): глобальные переменные и функции. Имя `foo(SB)` означает символ в глобальной таблице. Средняя точка `·` (Unicode `U+00B7`) отделяет имя пакета: `·Add(SB)`.
   - `FP` (Frame Pointer): виртуальный указатель на аргументы функции, переданные вызывающим кодом.
   - `SP` (Stack Pointer): локальный стек функции. Если перед `SP` стоит имя переменной `x-8(SP)`, это псевдорегистр. Если без имени `-8(SP)`, это физический аппаратный стек.
3. **Декларация функции (Директива `TEXT`)**:
   ```asm
   TEXT ·Add(SB), NOSPLIT, $0-24
   ```
   - `TEXT ·Add(SB)`: объявление символа функции.
   - `NOSPLIT`: запрет компилятору вставлять проверку переполнения стека горутины (Stack Split Check).
   - `$0-24`: фрейм функции. Число перед дефисом (`$0`) — размер локальных переменных на стеке. Число после дефиса (`24`) — суммарный размер входящих аргументов и возвращаемых значений (два `int` по 8 байт + один результат `int` 8 байт = 24 байта).

## Решение по шагам

1. Создайте структуру демонстрации связывания Go и Plan 9 ассемблера.
2. Подробно опишите файл `add_amd64.s` с инструкциями загрузки из `FP`, сложения и записи в возвращаемое значение.
3. Объясните разницу между 32-битными (`MOVL`, `ADDL`) и 64-битными (`MOVQ`, `ADDQ`) инструкциями.
4. Разберите механизм предотвращения сплита стека (`NOSPLIT`) и размер кванта стека горутины (2 КБ).
5. Напишите эмулятор вызова ассемблерной функции в среде Go.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

// В реальном проекте объявление связывается с файлом add_amd64.s:
//
// package main
// func AsmAdd(x, y int64) int64
//
// Файл add_amd64.s:
// #include "textflag.h"
//
// // func AsmAdd(x, y int64) int64
// TEXT ·AsmAdd(SB), NOSPLIT, $0-24
//     MOVQ x+0(FP), AX    // Загрузка первого аргумента x в регистр AX
//     MOVQ y+8(FP), BX    // Загрузка второго аргумента y в регистр BX
//     ADDQ BX, AX         // AX = AX + BX
//     MOVQ AX, ret+16(FP) // Запись суммы в слот возвращаемого значения
//     RET                 // Возврат из функции

// EmulatedAsmAdd симулирует поведение ассемблерной инструкции Plan 9 ADDQ
func EmulatedAsmAdd(x, y int64) int64 {
	// В регистрах x86_64:
	// MOVQ x, AX
	// ADDQ y, AX
	// MOVQ AX, ret
	return x + y
}

func main() {
	fmt.Println("=== Plan 9 Go Assembly Primer ===")
	fmt.Println("Directives:")
	fmt.Println("  TEXT ·Func(SB): Global function symbol entry")
	fmt.Println("  NOSPLIT:        Do not emit stack allocation preamble")
	fmt.Println("  $FrameSize-ArgSize: $0-24 indicates 0 stack locals, 24 bytes args")
	fmt.Println("Pseudo-registers:")
	fmt.Println("  FP: Frame Pointer for function arguments (virtual)")
	fmt.Println("  SB: Static Base pointing to global symbols")
	fmt.Println("  SP: Stack Pointer pointing to local frame")

	a, b := int64(100), int64(250)
	result := EmulatedAsmAdd(a, b)
	fmt.Printf("\nOperation: %d + %d = %d\n", a, b, result)
}
```

ℹ️ Структура Plan 9 ассемблерного файла и семантика псевдорегистров Go.

## Под капотом

Символ точки `·` в Plan 9 ассемблере на этапе линковки заменяется именем текущего пакета (например, `main`). Если в директиве `TEXT` не указать флаг `NOSPLIT`, компилятор Go при входе в функцию сгенерирует инструкции `CMPQ SP, (R14)` (сравнение `SP` со `stackguard` текущей горутины в регистре `R14`) и вызов `runtime.morestack` при исчерпании 2 КБ стека.

## Подводные камни

1. Превышение лимита стека с `NOSPLIT`: функции с флагом `NOSPLIT` имеют жесткое аппаратное ограничение на размер фрейма (не более `_StackLimit` ~ 792 байт). Превышение приведет к разрушению стека соседней горутины без возможности восстановления.
2. Неверный размер `$Locals-Args`: если указать неверный размер аргументов (например, `$0-16` вместо `$0-24`), сборщик мусора Go (GC) не сможет корректно построить карту живых указателей стека, что вызовет фатальный сбой памяти.

## На собеседовании

«Почему в Plan 9 ассемблере перед именами аргументов обязательно писать имена параметров, например `x+0(FP)`, а не просто `0(FP)`?». Ответ: компилятор Go строго сверяет имена аргументов в ассемблерном файле с декларацией в `.go` файле. Если сигнатура функции в Go изменится, а ассемблерный файл не обновят, линкер выбросит ошибку несоответствия сигнатуры, предотвращая передачу поврежденных данных.
