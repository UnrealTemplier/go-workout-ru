# Соглашения о вызовах в Go: Стек ABI0 против Регистров ABIInternal

## Условие

Изучите эволюцию соглашений о вызовах (Calling Conventions) в рантайме Go: переход от стекового соглашения ABI0 к регистровому ABIInternal. Объясните, как передаются аргументы и возвращаются значения, и почему рукописный ассемблер требует адаптеров или директивы pragma.

### Исходная формулировка

**Calling Convention Go.**: Изучите `src/runtime/sys_amd64.s` или документацию. Объясните: параметры передаются в `AX`, `BX`, `CX`, `DX`, `DI`, `SI`, стек; возврат в `AX` (для int/pointer). Напишите функцию `func Add(a, b int64) int64` на Plan 9 assembly (`TEXT ·Add(SB), NOSPLIT, $0-24; MOVQ a+0(FP), AX; ADDQ b+8(FP), AX; MOVQ AX, ret+16(FP); RET`). Объясните синтаксис `a+0(FP)`.

## Теория

Исторически Go использовал архитектуру компилятора Plan 9 со **стековым соглашением о вызовах (Stack-based ABI0)**:
- Все аргументы функции и возвращаемые значения помещались в оперативную память стека текущей горутины (`SP + offset`).
- Плюсы: максимальная простота кодогенерации и интроспекции рантайма (сборка мусора видит все указатели в стеке через stack maps).
- Минусы: каждая операция вызова функции требовала серий инструкций записи в память `MOVQ AX, 0(SP)` и чтения из памяти `MOVQ 8(SP), BX`, что приводило к колоссальному оверхеду даже при наличии L1-кэша.

**Революция Go 1.17+: Регистровое соглашение (ABIInternal)**
Компилятор перешел на передачу аргументов через регистры процессора общего назначения и регистры XMM:
- Целочисленные аргументы и указатели: последовательно в регистрах `RAX`, `RBX`, `RCX`, `RDI`, `RSI`, `R8`, `R9`, `R10`, `R11` (до 9 регистров).
- Числа с плавающей точкой (`float32`, `float64`): в векторных регистрах `X0`–`X14` (до 15 регистров).
- Если параметров больше, чем свободных регистров, остаток передается через стек.
- **Прирост производительности**: автоматическое ускорение всех Go-программ на 5–15% без изменения кода!

**Проблема рукописного ассемблера (.s)**:
Все рукописные функции на ассемблере Plan 9 по умолчанию линкуются как **ABI0** (ожидают аргументы на стеке). Чтобы вызвать Go-функцию (ABIInternal) из ассемблера или наоборот, линкер компилятора Go генерирует специальный переходник — **ABI Wrapper (Thunk)**, копирующий регистры в стек и обратно.

## Решение по шагам

1. Создайте структуру демонстрации смещений аргументов в стеке ABI0.
2. Проиллюстрируйте, как в ABI0 аргументы `a, b int64` располагаются по смещениям `0(FP)` и `8(FP)`, а возвращаемое значение — по `16(FP)`.
3. Проиллюстрируйте эквивалентную схему ABIInternal, где `a` передается в `AX`, `b` в `BX`, а результат возвращается в `AX`.
4. Объясните назначение линкерных символов `·MyFunc(SB)` и псевдорегистра `FP` (Frame Pointer).
5. Напишите тесты и выведите подробную карту раскладки регистров.

## Код решения

**`main.go`**

```go
package main

import (
	"fmt"
)

// ABIDemonstrator иллюстрирует разницу между ABI0 и ABIInternal
type ABIDemonstrator struct{}

// Пример сигнатуры: func Add(a, b int64) int64
//
// В стековом ABI0 (устаревший / рукописный .s по умолчанию):
//   Память стека вызывающего:
//   SP + 0x00: аргумент 'a' (8 байт)  -> в asm: a+0(FP)
//   SP + 0x08: аргумент 'b' (8 байт)  -> в asm: b+8(FP)
//   SP + 0x10: возврат 'ret' (8 байт) -> в asm: ret+16(FP)
//   Фрейм функции: $0-24 (0 байт локальных переменных, 24 байта аргументов)
//
// В регистровом ABIInternal (Go 1.17+):
//   Регистр RAX: аргумент 'a'
//   Регистр RBX: аргумент 'b'
//   Регистр RAX: возвращаемое значение (перезаписывается при выходе)
//   Стек: НЕ ИСПОЛЬЗУЕТСЯ (zero memory traffic!)

//go:noinline
func EmulatedABIInternalAdd(a, b int64) int64 {
	// В скомпилированном виде на AMD64:
	// ADDQ RBX, RAX
	// RET
	return a + b
}

func main() {
	fmt.Println("=== Go Calling Conventions: ABI0 vs ABIInternal ===")
	fmt.Println("Architecture: AMD64 (x86-64)")
	fmt.Println("-------------------------------------------------------")
	fmt.Println("Parameter Register Mapping (ABIInternal):")
	fmt.Println("  GPR Integer/Pointer: RAX, RBX, RCX, RDI, RSI, R8, R9, R10, R11")
	fmt.Println("  FPR Floating Point:  X0 - X14")
	fmt.Println("-------------------------------------------------------")

	res := EmulatedABIInternalAdd(42, 58)
	fmt.Printf("Result: %d\n", res)
	fmt.Println("ABI Wrapper: Linker automatically synthesizes ABI wrappers")
	fmt.Println("when Go code calls assembly functions defined without ABIInternal pragmas.")
}
```

ℹ️ Сравнение схемы размещения параметров в стеке ABI0 и регистрах ABIInternal.

## Под капотом

Внутренний линкер Go (`cmd/link`) при обнаружении вызова между кодом с разными ABI вставляет синтетические функции `abi0 -> abiInternal` и `abiInternal -> abi0`. В ассемблерных файлах Go 1.18+ можно явно декларировать ABI через директиву pragma `//go:registerparams` или ассемблерный тег `<ABIInternal>`, что исключает накладные расходы на адаптер.

## Подводные камни

1. Ошибочные смещения псевдорегистра `FP`: в Plan 9 `FP` (Frame Pointer) виртуален. Если не указать имя аргумента `arg+0(FP)`, компилятор выдаст ошибку `unknown variable`.
2. Повреждение callee-save регистров: в ABIInternal большинство регистров являются caller-save (уничтожаются вызовом функции), но регистр `g` (указатель на текущую горутину) фиксирован в `R14` и его модификация приведет к мгновенному краху рантайма!

## На собеседовании

«Почему регистр R14 на архитектуре amd64 зарезервирован в Go?». Ответ: в Go регистр `R14` постоянно хранит указатель на структуру текущей горутины (`*g`). Это позволяет любой функции мгновенно обращаться к полям горутины (стек, планировщик, m) без выполнения медленного системного вызова получения Thread-Local Storage (TLS) через сегментные регистры `FS`/`GS`.
